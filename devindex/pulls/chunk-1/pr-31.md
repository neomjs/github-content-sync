## Deltas from ticket
- **Why the root entry needs `<base>`.** In the build, the app entry sits at `dist/production/apps/devindex/`. A worker resolves the document-relative `basePath` against its own script (`dist/production/`), so under a sub-path the data fetch climbed out of the mount: measured `/apps/devindex/resources/data/users.jsonl` → 404. The site's root `index.html` sets `<base href="./dist/production/">`, where the workers are served from, and the site's `neo-config.json` there sets `basePath: '../../'` and `workerBasePath: './'`. That names the mount from both sides, and the engine's `Stylesheet` derivation (`basePath.substring(6)`) still lands on `dist/production/css`. A click handler keeps `#` links on the page, the same one the engine portal's root entry uses.
- **Learn path (fix step 3):** built environments read `Neo.config.basePath + 'learn/'`. Development keeps the origin-absolute `/learn/`, because there the app worker runs from the engine package and a relative climb lands inside it. The provider's comment says why in five lines instead of eighteen.
- **Check #10 (fix step 4)** turned out to be required, not optional: with `-f`, the bundle was the engine's pre-split devindex. That fix is #30, which this PR stacks on.
- **Data source:** the pull reads `publishedWorkingSet.baseUrl`, today `pages`' frozen 2026-08-31 copy. #29 moves it to the store the pipeline publishes to, and a green collection run redeploys the site.

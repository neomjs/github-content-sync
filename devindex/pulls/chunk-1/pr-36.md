The Pages site serves the store's latest publish, and every publish redeploys it.
- A new `data` job is the only one holding a store token, and it runs no npm. It fetches `users.jsonl` from the store, verifies it against the manifest's digest, and hands it to the build as an artifact.
- The data-sync pipeline dispatches the Pages workflow after each publish.
- `devindex:pull-data` reads the deployed site's copy.

Evidence: L2 (unit arms on the store fetch and on both workflows' shape, red on `dev`; a live pull from the site) → L3 required for the first publish-driven deploy. Residual: AC-1 and AC-2 need scheduled runs. Residual-Owner: neomjs/neo#19047 (#33's deferred ACs carry `[L3-deferred — operator handoff needed]`).

**Why a separate token job.** The WIF binding admits any workflow in this repository to the publish identity (`setup-gcp-publish.sh`: `attribute.repository`), and that identity holds `roles/storage.objectAdmin`. The build job runs `npm ci`, so dependency code runs there. Only a job that runs none may mint that token.

The data-sync pipeline has been red on 100 of 100 runs since 2026-08-30, and a green run would still not have carried anything forward. This makes the pipeline read the store it publishes to, once per run, from a destination outside the middleware's delete scope.

Evidence: L2 (unit arms driving the real `Storage` hydration paths and the workflow's own probe script against a stub `gcloud`; red-first at `6e7fcc7`) → L3 required for the live store. ## Deltas from ticket
- **AC-6 is new, found while implementing** (#29 Problem item 4): run 35978993043 adopts the set three times, once per stage process, so only the last stage's writes could ever reach the publish. The fix marks the run on its first hydration (`GITHUB_RUN_ID-GITHUB_RUN_ATTEMPT`). No opt-out was affected: the intake repository has none.
- **The seed is pinned.** `publishedWorkingSet.baseUrl` moves from `neomjs.com/node_modules/…`, which the next `pages` rebuild deletes, to `raw.githubusercontent.com/neomjs/pages/1847ca65…/`. All nine members answer 200 there, with no manifest, so seeding is unverified by construction and logged as such. Developers' `devindex:pull-data` reads the same pinned copy until the public-read follow-up points it at the live site.
- **The token never leaves the job:** it is the auth action's short-lived output, passed only to the four stage steps.
- **Hydration happens at the entry, not on first read** (Euclid RA-1): `Manager` hydrates before any command runs, so a stage's first write always follows its run's one adoption.
- **The collapse guard compares against the run's start** (RA-3): the run mark records the index size hydration adopted, and the publisher refuses a drop below 80% of it. A run without a mark has no baseline and does not publish. The public-seed count it used to read is gone.

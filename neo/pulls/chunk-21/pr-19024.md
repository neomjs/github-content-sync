Fixes #19010.

A CSS-3D layout is the easiest thing here to break silently. Nothing throws when a transform is composed in the wrong order or a face carries the wrong sign; the cube simply shows the wrong side, and only a human notices. The ticket asked for the component tier for that reason, and named the trap: a unit test can only assert the values the layout just wrote, which pins the implementation against itself and passes while the cube renders inside out.

So the central assertion is a hit test. `elementFromPoint` at the cube's centre must return the face the layout was asked for, for all six.

Measured against the running engine before anything was asserted:

```
front -> front     back  -> back      left -> left
right -> right     top   -> top       bottom -> bottom
```

Every other test in the file reads config values. This one is what a cube with all six faces on one plane fails.

Four tests in total: the hit test, the class and axis group each face carries, the rotation `activeFace` derives from `static faces`, and the interaction the ticket calls subtlest, where `activeFace` and a pending `rotateX` arrive in one config object and the derived rotation deletes the pending value rather than merging it.

## The fixture

`component/apps/layout-cube/` is three files, matching every sibling app: the entry `index.html` MicroLoader bootstraps from, its `neo-config.json`, and `app.mjs`.

One detail worth recording, because it cost me two debugging rounds: the cube layout module is imported for its **side effect**. `Cube.mjs` registers its ntype through `setupClass` at module scope, and a container resolves its layout by ntype, so a fixture that imports the class and never uses it throws `ntype layout-cube does not exist` with no clue as to why.

## Asserting from the rendered result needed the render to settle

The container's `--rot-x`/`--rot-y` update synchronously, but the transform that moves the cube belongs to `.neo-box` and transitions over 300ms (`resources/scss/src/layout/Cube.scss`). A hit test taken during that transition sees the cube mid-turn and returns the face it is passing through: turning to `back`, the first version of this spec measured `left`.

Waiting on the custom property therefore waits for nothing. `waitForCubeToSettle` waits for the box's own computed transform to hold across frames instead. This is the kind of mistake the ticket was pointing at, and I could only hit it by asserting from the rendered result.

## Sized against the sabotage

A component spec that cannot catch a broken cube is decoration, so each mutation below was applied to `src/layout/Cube.mjs` and required to fail this file:

```
baseline (unmodified)                4 passed / 0 failed
front/back rotations swapped         1 passed / 3 failed
top sign flipped, 270 -> 90          2 passed / 2 failed
face-name class dropped              2 passed / 2 failed
rotation derivation removed          1 passed / 3 failed
restored                             4 passed / 0 failed
```

## Scope

Test-only. `src/` is untouched, so nothing about the layout's behaviour changes here. The sibling component suites stay at 40 passed, and the repo's own checks report 0 violations.

Right, and the gap was wider than the finding says: the suite asserted none of `perspective`, `sideX`/`sideY`/`sideZ`, or the container class. Addressed in `27c4ab36e` with two tests, both reading computed style rather than the config just set.

Measured first, so the assertions state what actually renders:

```
before   perspective 600px   sides 300/300/300   cls ... neo-layout-cube ...
after    perspective 900px   sides 500/250/400   (runtime change through the shell)
face at centre after the resize: front
```

The runtime test changes perspective and all three side lengths, requires the rendered styles to follow, and then hit-tests the centre again. A resize that left the cube unable to present a face would fail on the hit test rather than pass on a style read.

On `containerCls`, which is the one worth having: it is load-bearing for every other assertion here. Without `neo-layout-cube` the children lay out as plain boxes and no face is positioned, so the sabotage that empties it fails **all six** tests:

```
baseline                                     6 passed / 0 failed
perspective never reaches --perspective      5 passed / 1 failed
sideX writes --side-q instead of --side-x    3 passed / 3 failed
containerCls dropped                         0 passed / 6 failed
```

That all-six result is the signal I wanted: it confirms the class is what the rest of the file stands on, and it is now pinned explicitly rather than assumed.

Source untouched. The hit test, the face classes, the rotation derivation, and the `activeFace`/`rotateX` interaction are unchanged.

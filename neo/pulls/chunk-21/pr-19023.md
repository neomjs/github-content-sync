Fixes #19007.

Adds `test/playwright/unit/collection/SorterPrecedence.spec.mjs`. Every expectation was read off the running engine rather than derived from the source, because the two composition paths in `collection/Base.mjs` (`hasSortByMethod` and the mapped-value path) are different code doing the same job.

What the engine does, measured:

```
two sorters        [['a',20],['a',50],['b',10],['b',30]]   second only breaks ties
DESC second        [['a',50],['a',20],['b',30],['b',10]]   first sorter stays ASC
three sorters      the third reaches items the first two tie on
raw vs sortBy      identical ordering through both paths
useTransformValue  false gives code-unit order, caps before lowercase
```

Mixed-direction composition and the three-sorter case are the ones that would break loudly if precedence inverted, so the fixtures are built around them rather than around easy cases.

## Two cases recorded rather than blessed

The ticket asks for the gap between intended and actual behaviour, and these are it.

**Mixed number and non-numeric strings do not form a total order.** `5 > 'abc'` and `5 < 'abc'` are both false, so the comparator returns 0 for any number against any non-numeric string, while `5` and `1` still compare to each other. The relation is intransitive and the result depends on the engine's sort algorithm rather than on the data. Measured output is `[5, 'abc', 1]`, which is not in order, and no edit to this spec would make it so. I asserted it as-is and said why in the test body: it looks like a decision for its own ticket, not something to fix inside a test-only PR.

**`null` and `undefined` go last through an early return, but other falsy values do not.** `''`, `0` and `1` all reach the comparison and keep input order among the values that compare equal. The doc comment on `Sorter` says null and undefined are pushed to the bottom, so the narrow claim holds; what is worth knowing is that `''` and `0` are not treated as absent.

## Why the assertions are known to bite

A test-only PR earns its place by failing when the behaviour changes, so I checked that rather than assuming it:

```
last sorter wins instead of first non-zero   3 failed / 5 passed
first sorter's direction applied to all keys 1 failed / 7 passed
source untouched                             8 passed
sibling collection suite                     49 passed
```

The three failures are the three precedence cases by name. The source is unchanged in this PR.

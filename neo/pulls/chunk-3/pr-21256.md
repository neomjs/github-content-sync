Resolves #21254

The spec-retirement guard now asks a commit for a `spec-retired:` account only when its range lands the deletion: the unit spec is in the tree of the range's merge base and not in the tree of its tip. A spec the branch added and deletes again, or one a later commit restores at its path, no longer reads as retired, while a real deletion is still reported. `landedDeletions(range, git)` reads the two trees once per range, only after a commit of the range deletes a spec, and fails closed like the commit-tree read.

Evidence: L2 (unit arms, one against a real git repository, red on `dev`; the old and the new guard run against #21154's merge ref) → L2 required (every AC is unit-level).

## Deltas from ticket
- The merge base comes from the range itself rather than from `origin/dev` (recorded in the ticket's The Fix). CI's `origin/dev..HEAD` gets the same answer, and the guard's fixture repositories, which have no `origin/dev`, keep working.
- The spec's port fake gains `mergeBase` and a base tree that holds the deleted spec, so the existing arms keep their meaning. The ENOBUFS arm now fails the commit's own tree read; the new AC-5 arm covers the base and tip reads.

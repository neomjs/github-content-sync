Resolves #22571

🌿 Two step-6 rows bound a variable to a mix of two roles and passed every guard; now `theme-base` can no longer hold a colour that no role names.

`colourSources` in `themeCss.mjs` reads the colours a value derives instead of reading: each `color-mix()` whose two colours are both something other than `transparent`, and each raw colour, one inside a `var()` fallback too. A raw colour is a hex colour, a colour function or one of the 148 named colours of CSS Color 4 (`rawColours`), read in any case, and nothing inside `url()` data or a quoted string counts. `check-theme-surfaces` now reads raw colour through the same function. `check-theme-palette` fails either in a `theme-base` component variable, as `[mix]` or `[raw]`, naming the sheet, the variable and the value. `BASE_COLOURS_ALLOWED` keeps a listed value with its reason, and an entry that matches nothing fails, so the list can only shrink. `theme-census` counts a two-colour mix in section 2 and reports `theme-base`'s own values beside each theme's.

Intake (self-authored, same session). Prescription checked: `buildScripts/util/check-theme-palette.mjs` owns the concern. `inspectThemePalettes` already walks every component sheet's declarations with their values for `[scope]`, and the shape that decision 4 limits serves the same measurability. `themeCss.mjs` holds the reading the census shares, as it does `radiusLiterals`.

Evidence: L2 (specs red without the source and green with it; the guard run on `dev` and on the two PR heads that carry a two-role mix) → L2 required (#22571's ACs are guard and spec behavior). Residual: none.

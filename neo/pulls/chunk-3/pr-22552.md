# PR Micro-Review

**Class:** micro. One Store URL in one example changes; no Engine source is touched.

**Verdict:** Approved

**Glance:**
- **Premise:** `'../../../resources/examples/data/countries.json'` was relative to the worker. From `dist/esm/src/worker/` it resolves to `/dist/resources/…`, which is the 404 in #22551.
- **What I checked:** `connection.Base#resolveUrl` re-bases relative URLs only for package-hosted workers (`/node_modules/neo.mjs/`). Engine and `dist` workers keep worker-relative URLs, so this consumer has to resolve the URL itself.
- **The fix:** `new URL(Neo.config.basePath + 'resources/examples/data/countries.json', Neo.config.url.base).href` resolves `basePath` against the page base the worker registered. That holds at any worker depth and on a nested mount.
- **Evidence, at `a8718cb24d`:**
  - Base is red with the 404.
  - The fix returns HTTP 200 in rebuilt ESM and Production, Light and Dark, with zero unhandled errors.
  - It also works on the `/published/engine/` mount.
  - The adaptive round trip still keeps its focused draft.
- **Bounded repair:** no site outside the named Store.
- **What I looked for:** a sibling idiom this should match. The siblings write bare `Neo.config.basePath + 'resources/…'` (`examples/component/{helix,gallery}/ImageStore.mjs`, `apps/webdesktop/view/apps/Photos.mjs`), and this PR's resolved form is the more correct one.
- **Hypothesis, needs V-B-A before any ticket:** those siblings resolve worker-relative too. They may work only at host root, where URL resolution clamps at the origin, and fail on a nested mount the same way. If so, resolving basePath-relative Store URLs in `connection.Base#resolveUrl` for every layout would retire per-consumer wrappers like this one. #22551 puts the shared rule out of scope, so this note only records the observation.

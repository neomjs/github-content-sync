Resolves #20626

🌿 A drag can no longer start moving on the boundary the drag before it left behind.

`DragZone.dragEnd` never cleared `boundaryContainerRect`. So on the next drag, the `SortZone.onDragMove` gate (`itemRects && boundaryContainerRect`) opened while the start was still waiting on the main thread. At that point `offsetX` was 0 and the item rects were still in viewport space; a scrolled header widens the window with its extent-sentinel render. A move landing there switched the dragged header and wrote viewport `left`/`top` into the button the proxy clones. That is the `left:1451px` Sophie found on the broken clone in her reproduction on #20626.

The fix:
- `dragEnd` clears the boundary.
- `onDragStart` converts the rects with `adjustProxyRectToParent` before it publishes them, so the move code never reads viewport rects. The grid header's sentinel now reads the extent directly and drops its re-derivation.
- `clampProxyToGroup()` sends the main thread the visible part of a grouped header's group, at the start and on every scroll during the drag. The zone keeps the toolbar's boundary for its own over-drag scroll.

Evidence: L3 (headless Chromium e2e on the live `examples/grid/headerGroups`, each new test failing on a reverted-fix control) → L3 required for AC-1 and AC-2. Residual: AC-3, the operator's manual pass on this branch, pre-merge.

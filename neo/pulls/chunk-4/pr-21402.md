Resolves #21399

A button takes a size: `size: 'small' | 'medium' | 'large'` on `Neo.button.Base`. The config is separate from `ui`, which keeps carrying states such as alert or submit.

How sizes resolve:
- **`null`, the default,** leaves the size to the context: medium in the neo themes and in every toolbar, and the large size inside the Portal.
- **An explicit size** sets a `neo-button-size-<size>` class, which re-values the four sizing variables on the button itself. It wins over a toolbar and over the Portal.
- **The steps:** every theme defines `--button-size-{small,medium,large}-{height,padding,font-size}`. The neo themes step 24, 32 and 48 px; the classic themes have content-sized steps around their default, which is their medium.
- **One set of values:** the neo themes' default, every theme's `--toolbar-button-*` tokens (#21395) and the Portal's opt-in all read those tokens.

Workstation and five grid examples drop their hand-rolled button sizes.

Evidence: L3 (CI-covered unit and component specs; live Chromium clips of the migrated consumers on `dev` and at this head; the button inventory of the 24 neo-themed examples and apps) → L3 required (AC-1 and AC-2 run in CI; AC-3 and AC-4 are visual reads). Residual: none.

## Deltas from ticket
- #21395's per-theme `--toolbar-button-*` tokens, added for Euclid's nested-classic review there, now read the medium size tokens. So one set of values serves the default button, every toolbar and `size: 'medium'`. The tokens never reference `--button-*`, so no toolbar can form a custom-property cycle.
- Before this PR, a second probe with POSIX classes (`git grep -E` does not read `\s`) found more sizing rules. The ticket's Problem was amended to the reasoned set, and these stay on purpose:
  - Workstation's arrangement switch (28 px, one 34 px pill).
  - The Portal's doors and build control.
  - Route's serif header.
  - The 44 px touch target in `ConfigurationViewport`.
  - The taskbar's 40 px.

Resolves #19285

The tab Overflow projection no longer withholds a tab that holds focus. `computeOverflow` now protects `activeItemId` union `focusedItemId` and fits the pair's combined width, the degenerate cap gate covers either protected button instead of the active one alone, and `project()` supplies the focused button from `containsFocus` — read, never acted on. ## Deltas from ticket

**The ticket offered two shapes and picked neither; measurement retired the shape I then recommended, in this order.**

1. **Shape 2 (hand focus to the `More tabs` control) cannot run in this order.** The hide is `button.hidden = true` and `syncControl` — which creates the control — runs after it, so on the first overflow there is no control to focus. The after-the-fact variant is worse: the one-frame fall to `body` is what withdraws the gated actions, so it would satisfy the `activeElement` clause and fail the actions clause.
2. **I then recommended a reorder (`syncControl` before the hide) and it is necessary but not sufficient.** The control mounts through `autoInitVnode` + `autoMount`, a promise, so the reorder makes it *exist*, not *focusable*. Worse, the plugin already observes the control's `mounted` edge, which fires a render round-trip after the removal. The withdrawal is causal, not a race, so AC-1 is unreachable by shape 2 in every variant — and the most natural implementation is the one that ships green on the first clause and fails the second.
3. **Shape 1 is the answer, and my objection to it was the weaker argument.** I led with "reflow on focus moves the tab under a hand mid-drag". True but secondary: `computeOverflow` already ships that exact trade for the active tab, so protecting the focused id is symmetric with accepted behaviour rather than a new coupling — and it needs strictly less machinery.

**Two implementation details the filing did not reach.** The displacement loop must fit the SUM of the pair, because popping once under-displaces when the pair is wider than a single pop. And the degenerate cap gate named the active button alone, so a protected-but-over-wide focused tab would have run beneath the control and taken every geometry derived from its box with it.

**BOUND, named not papered over:** two protected tabs can jointly exceed the usable extent. The per-button cap bounds each box; the strip still overhangs by their excess. That is the doubled form of the degenerate case this function always had for one protected tab. It also means a two-tab header ends with nothing withheld, which is why the browser arm needs a third tab to stage.

## Test Evidence

Red-first, on the final arms, by stashing only the source change: **6 failed / 48 passed** on the base, **54/54** at the head. Three of the six are controls that pass in *both* states and therefore cannot be satisfied by a projection that simply stopped withholding — a focused tab that already fits, a null focused id, and the same projection with nothing focused (the trailing tab is still withheld).

Two defects the arms caught in my own work, both recorded because the second is the one that would have shipped: my first fixture reserved the wrong extent (`controlWidth` defaults to 40, so 240 gave `usable` 200 and two tabs were withheld, not one), and my degenerate expectation was simply wrong — the existing semantics displace everything else, so the correct partition is `visible: [b, c], hidden: [a]`, not three visible. Two arms also failed on a `Neo.get is not a function` unit seam caused by instantiating the real floating control; the fix stubs `syncControl` the way every existing arm in that spec stubs `applySplit`, keeping the partition, the hide pass and the cap ledger real.

## Notes for the reviewer

The arms deliberately avoid two easy traps. `computeOverflow` is called with a `focusedItemId` that is `null` on every pre-existing path, and the byte-identical arm pins that. And the plugin-level arms run the REAL `applySplit` (not a stub) so they assert `button.hidden` end-to-end from `project()`, which is the only assertion that can distinguish this fix from a partition that stopped withholding at all.

Worth a second opinion on: whether reading `containsFocus` at project time can observe a stale value from a tab whose node a *previous* pass already removed. It cannot make the strip worse — the stale read re-shows a tab, self-healing on the next focus leave — but it is the one place where the fix's input is read outside the focus event that produced it.

**Challenge OR documented search (per guide §7.1):**

- **Challenge**: You asked about stale `containsFocus`. The direction that matters is the other one. A stale `true` only keeps a tab visible, which is harmless and heals on the next pass. A stale `false` on a tab that just received focus can still withhold it: a projection triggered in the window between the DOM focus change and the worker's `focusEnter` delivery (a resize landing during a keyboard move) reads the old value. The plugin re-projects when the container's own focus toggles the contextual actions (the extent comment at `:795`), but not when focus moves between tabs inside the container. So that tab's node can go, and focus drops to the body: the original defect, narrowed to a race window. Non-blocking, and I have not measured it. `hypothesis — needs V-B-A before implementation`: if #19293's browser arm ever sees it, the natural close is re-projecting when a header button's `containsFocus` changes.

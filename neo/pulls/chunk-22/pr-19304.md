Resolves #19303

A drag whose pressed node a re-render replaced inside the sensor's 100 ms start delay now reaches the App. Before, `DragDrop#onDragStart` measured `event.target` and resolved the zone from the dispatch path. `sensor.Base#trigger` dispatches on `document` once the pressed node is detached, so the start threw on `document.getBoundingClientRect()`. The sensor then went on "dragging" a gesture no zone owned. Now `resolveSensorPath` takes the press's own path from `detail` when the dispatch path begins at `document`, and each replaced node answers through the connected node carrying its id. `resolvePressedElement` measures that successor for the main-thread offsets. A press on a connected node keeps the dispatch target and its live ancestors.

Evidence: L2 (unit arms plus two mutations) and L3 in a real headless browser, run on the #19288 branch plus this fix (details under Test Evidence). No residual on this close target. The arm's remaining failure is a different layer, owned by #19288 (see Deltas).

size-guard-growth: src/main/addon/DragDrop.mjs — two resolution helpers for the sensor's documented `detail` contract; the two call sites change in place, and no consumer lines exist to delete

## Deltas from ticket
AC-3 was amended on the ticket after measurement. The start is now delivered on every run. On some runs the press re-renders the tab header and no connected successor exists at the start, so the App sizes the proxy from an empty rect: 2 px against 48. That layer belongs to #19288. Waiting for the header to be stable before pressing made it worse (2/8), so the press itself triggers the re-render.

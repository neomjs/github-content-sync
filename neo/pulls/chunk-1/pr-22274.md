Resolves #22272

GridDragScroll now starts inertia only if the most recent release sample is later than the oldest eligible sample. This keeps the grid at its release position when several moves fall in one millisecond. Ordinary timed releases use the existing velocity and friction calculation.

Evidence: L3 (two red/green unit regressions and a Chromium Order Review Desk replay) → L2 required.

# PR Micro-Review

**Class:** contained — one guard in `GridDragScroll#onDragEnd`'s release estimate plus two regression arms; no new abstraction, contract or architectural concept.

**Verdict:** Approved

**Glance:** The claim is that a release whose eligible samples share a timestamp divides by zero, and the non-finite velocity then keeps the tail scheduling forever. Verified at `7ee7261b6c`. On `dev` the old `relevantMoves.length > 1` admitted `dt === 0`, so two equal-time samples give `0/0 = NaN` and `Δ/0 = ±Infinity`, and neither ever drops under the stop threshold. The new guard `newest && newest.time > oldest.time` guarantees `dt > 0`. Every other release falls through to the `else { me.activeDrag = null }` cleanup that already existed on `dev`, so no drag state or frame survives (both arms assert the queue, `activeDrag` and both scroll axes). The guard also covers a case the ticket did not name: if `Date.now()` steps backwards between samples (a wall-clock adjustment), the old code flung in the reversed direction, and the new code stops. I looked for a site outside the release estimate: nothing else changed (the 100 ms window, 16 ms scale and 0.95 friction are byte-identical), and the existing fling arm (`a fling clears activeDrag once its velocity dies`) still proves that a timed release travels, runs its frames and settles. Required CI is green at the head.

**Findings:** None. One note, not an action: a 1 ms `dt` still yields a very large but finite velocity. That belongs to the momentum redesign in D#22259, as AC-3 says.

Resolves #20006

A vessel is now identified by its Group key, minted at admission, instead of by the item it was opened for. The tab a popup was opened for tears out of that popup into a vessel of its own, and the popup keeps its other tabs. `NativeLifecycle#acquire` mints and reserves the key in one synchronous step: the item's preferred key while it is free, else the first free `<preferred>:<n>`. The registry keys its records by that key and keeps the opening item on each record. Close and retirement address the vessel's own key, and a vessel's window name carries its key's suffix, so two live vessels never share one.

Evidence: L3 (headless Chrome through the Neural Link fixture; both tear-out arms red on the pre-fix engine) → L3 required (AC-1, AC-2, AC-3, AC-6).

## Deltas from ticket
- **"Taken" is narrower than any binding.** A key is taken while the Group binds or reserves it, or a source records it (pending, connected, owned or retiring). A released binding that nothing records is free: its window left for good, and a stale reconnect presenting the old token is refused. Counting every reconnect lease as taken would have given each re-tear-out within 20 s a suffixed key.
- **A registered document alone holds no key.** A closed popup's document stays registered with the Group by design, so the item's next tear-out takes that key again. The first regression run caught the opposite rule: the five-beat journey's second take got `workstation-vessel:metrics:2`.
- **A reloaded vessel is adopted under its minted key.** The root re-adopted a reloading popup only when its binding key matched the key derived from the URL's `?popout=<item>`. It now also accepts a key whose native owner record names that item.
- **A warm reload mid-repaint is no failed render.** A landed pane's repaint can ride an ancestor's update. When the reloading window's tree destroys that ancestor, the repaint settles with `Neo.isDestroyed`. That is now a window departure, alongside the two shapes #19535 handled.
- **Two engine contracts change, and their specs change with them, not deleted:**
  - Two overlapping opens for one item no longer supersede each other. Each keeps its own reservation, and the older open's late failure revokes only its own (`DockWorkspace.spec.mjs`).
  - A live vessel's slot still refuses the next generation, which now gets a key of its own (`MidBootDeparture.spec.mjs`).
- **A withdrawal names its vessel.** `TearOut`'s `onPaneAdopted` passes the key when it withdraws ownership, so a late release of an older vessel never withdraws the item's newer one. Destructive paths address a key-less vessel by its item's newest record, so close identity checks still hold for key-less callers (DemoB). The engine Workspace's withdrawal follows the same rule; a key-less ownership record still refuses.
- **Every host's window name follows the key:** the engine default, the Workstation and DemoB. `Main#windowOpen` reuses a live window of the same name, so a second vessel would otherwise navigate the first.
- **Two guarded files grow, and the baseline records it.** Neither has a line to give back: a window name per vessel and an ownership guard in the engine, and key-addressed registry calls in DemoB, which keeps its own registry seam.

size-guard-growth: src/dashboard/dock/Workspace.mjs — +4 code lines: `tearOutKeySuffix` names each vessel's window after its minted key (the Workstation override reuses it); a key-less withdrawal resolves the item's newest vessel, and a key-less ownership record refuses.
size-guard-growth: examples/dashboard/crossWindow/DemoBWorkspace.mjs — +10 code lines: `resolveVesselKey` and `vesselWindowName` address DemoB's vessels by Group key, since DemoB extends Container rather than the dock Workspace and cannot inherit `tearOutKeySuffix`.

- **The e2e reader keys by provenance.** `readNativeLifecycle` returns records keyed by item, the newest winning, plus `*ByKey` maps, so existing specs read an item's vessel unchanged.

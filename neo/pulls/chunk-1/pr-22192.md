## Deltas from ticket
- **Placement**, which the ticket left open: a shelf of its own, `guides/vdomengine`, after The Core Engine. My first placement (`guides/coreengine`, up to `8fb10721bf`) read The Core Engine as the whole engine and rejected a new shelf as accretion. The operator's review corrected the reading: The Core Engine covers the class system (configs, mixins, push and pull reactivity), and its six pages bear that out. The update pipeline is a separate domain, so `2c162a68ef` moves the four pages. Inside their shelf the file names drop the `Vdom` prefix, except `VdomWorker`, which names the worker.
- **Wrong facts fixed beyond duplicates:**
  - AsymmetricUpdates drew the VDom worker replying straight to components. Both diagrams now route through Main.
  - `promiseUpdate()` "always resolves" now reads *settles*: it rejects when its flight fails.
  - WorkerArchitecture said deltas apply "immediately via `handleDomUpdate()`". They apply in the next frame.
  - WorkingWithVDom's `applyDeltas` example passed `me.appName` as the window id, which Main refuses as a foreign window. It also used `text`, which `updateNode` ignores. The same `appName` call lives on in `src/plugin/Responsive.mjs`; that is #22194.
- **A rule the guides now state, found by probe** (a scratch spec, not committed): a silent child change joins only an ancestor whose update is already pending. With the container's depth flushed to 1, ancestor-first gave 2 deltas; child-first gave 1, and the child stayed `needsVdomUpdate: true` with nothing restarting it. The first run merged in both orders, because `createItems()` leaves `updateDepth: -1` and `initVnode()` never resets it. The App worker guide states that too.
- **Intake:** the ticket was authored in an earlier session. The drift probe found no `dev` commits between filing and branching. `Prescription checked: learn/guides/coreengine — owns the concern` (the placement half since moved, above).

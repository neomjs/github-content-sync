Resolves #19697

Keyboard navigation in a content-sized grid now keeps its row at the edge it scrolled it to while the rows around it are measured. `Body#scrollByRows` hands the content-sized case to the new `View#scrollRowIntoView(index, edge)`, which records the row as the navigation target. Once the navigation's own scroll lands, the private `#changeRowHeights` re-aligns that row to its edge, instead of holding the row at the top edge still. Any other scroll ends the target, as do a store load and an index beyond the store's count. Fixed-height grids are unchanged.

Evidence: L3 (headless Chromium e2e on the `grid-anchor` fixture, which learns heights after the first render) → L3 required (AC-1 is an e2e). No residuals.

## Deltas from ticket
- The target lands only when a scroll arrives within 1px of its offset, and any other scroll that changes the view's offset ends it. A correction's echo leaves the value unchanged, so it does not count. If a correction races the navigation's own scroll, the target ends and the grid behaves as before, holding the top-edge row. It can never jump to a stale target.

## Test Evidence
- **Negative control:** with the target ignored in `#changeRowHeights`, the e2e fails, because row 250 is not even rendered after the jump (`undefined` vs 693).
- **Mutations in the unit spec:**
  - ignoring the target: the row's bottom sits at 460 instead of 360;
  - never ending it after another scroll: a 220px jump against the expected 20.

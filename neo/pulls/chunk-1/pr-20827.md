Resolves #20802

🌿 A record can no longer hold what a sort did to its row.

A raw Turbo Mode row and its record now derive a field from the same code. `RecordFactory#deriveRecordData()` runs the record's own `assignDefaultValues()` pass on a copy of the row's own data, and `deriveFieldValue()` parses one field from the result (convert, type). A raw read therefore sees what the record's earlier fields assigned, and never a value kept for another field. `Store#resolveField()` keeps its result on the row as before, and records `[own, kept]` under each kept name. The record constructor's `restoreOwnValues()` puts the own value back only while the row still holds the kept one, so an explicit write wins, on the row or in a spread copy. `resolveRow()` derives every requested model field from one such pass per row, and resolves a dotted path through its root field. Column order therefore never changes a value, and `getCellValues()` reads what the record holds.

Evidence: L2 (unit arms over real `Store` and `RecordFactory` instances, plus a local timing over 50,000 raw rows) → L2 required (every AC of #20802 can be observed in a spec; AC-5 asks for the timing in this body). No residuals.

## Deltas from ticket
- Both candidates were needed. Recording kept names fixes rows 1 and 2. The shared derivation fixes rows 3 to 6 and two more disagreements, one arm each: a default that skipped `convert`, and an `[index]` mapping that the raw path read as `undefined`.
- The restore lives in the record constructor, not in `Store`, because every creation path goes through the constructor.
- Round 1 (Emmy) added two contracts, each with arms that fail on the reviewed head. Column order never changes a raw read, including a dotted read through a converted root and a typed nested leaf (`CellValues.spec.mjs`). An explicit write made after Soft Hydration survives hydration: on the same row, in a spread copy given to `data`, and in a copy added under a new key (`StoreSoftHydration.spec.mjs`).
- Round 2 (Emmy): a mapping onto a field the datum lacks read `undefined`, while the record reads what an earlier field assigned there (a default, or that field's own mapped value). The per-field re-implementation of the record's pass missed that the pass runs in field order. The raw read now runs the pass itself, so `getFieldDatum()`, `readMapping()` and `getDefaultValue()` are gone and `assignDefaultValues()` is `dev`'s text again (`RecordFactory.mjs` +72/−0 against `dev`). Its cost is in Test Evidence.
- `resolveRow()` is no longer gated on `Model#hasComplexFields`, because a typed or defaulted field can also differ between a row and its record. A #20801 arm in `CellValues.spec.mjs` pinned zero `resolveField()` calls for a plain row. It now pins what that count protected: the row stays unchanged, and a record is never resolved. `hasComplexFields` keeps its meaning for the sort and filter gates.
- neo-pro's `GroupingStore`, measured with its unit suite (480 passed on this head): a Turbo Mode group row whose `Integer` field holds an average of 2.5 already has 2 in its record on `dev`. `dev`'s value walk read 2.5; this one reads 2, the record's value. No merge order follows from it. The type parse of an aggregate is neo-pro's to settle.

Resolves #22208

ADR 0043's Phase-1 gate for the two-thread line. (a) moved to #22209, whose required matrix is that run.

- **I3.** `executeVdomUpdate` now captures the window id along with the payload. The SharedWorker routing field `batchData.windowId` and the line's `Neo.applyDeltas` both read that one value. Before, the send read `me.windowId` after the `await`, so a component that moved windows in that microtask received deltas diffed against the window it left. `createVnodeTree` already captured the id this way.
- **(c)** `dashboard/DemoBPopOutTwoThreadNL.spec.mjs` runs Demo B's pop-out and hand-closed return under SharedWorkers with no VDom worker. It asserts three things:
  - every flight is sent to the window it was collected in;
  - the CounterPane's renders follow the pane;
  - no `VDomUpdate` state outlives the closed window.
- **(b)'s lever.** A new `neoConfig` dispatch input (JSON) is merged into every Neural Link page's `neo-config.json` before the spec's own edits, on both fixture paths. The matched-repeat tear-out comparison ran through it.

Evidence: L2 (unit + local real-Chromium e2e + hosted dispatch runs) → L2 required (all four ACs).

CI jobs: +0 — the input only parameterises the existing dispatch path.

## Deltas from ticket
- The lever is generic: a JSON `neoConfig` input, not a `useVdomWorker` switch. It sets no key by itself, so it adds no flag reader to Phase 3's removal inventory, and it can measure any config key.
- The adapter path (`dedicatedWorkerNeuralLink.mjs`, which CI uses) has its own config route. It applies the keys too, because a probe showed the Brain-path route alone left CI pages unchanged.

## Test Evidence
- **I3 red on base:** `npm run test-unit -- test/playwright/unit/vdom/WindowCapturedAtCollection.spec.mjs` against unmodified `dev` source fails the update arm (`Expected: 1, Received: 2`). Its controls pass: one send, deltas present, the move landed before the send. It is green at head, and `unit/vdom` passes 312/312.
- **(c) locally:** 5/5 at `--repeat-each 5` (7.0–10.2 s). For a mutation control I injected an entry into each of the six `VDomUpdate` maps; the leak check went red naming all six, then I reverted. (c) is not red on `dev` by design: a real move almost never lands in the one-microtask gap, so the unit spec is I3's red and (c) its real-flow witness.
- **Lever consumption:** a throwaway spec (not committed) read the page config. With `{"useVdomWorker":false}` it got `useVdomWorker: false` and no VDom worker; unset, it got the defaults. Same result on the adapter path and on the Brain path (own Bridge on a free port).

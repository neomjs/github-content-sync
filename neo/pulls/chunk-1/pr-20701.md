Resolves #20698

🌿 A selection model can no longer say "selected" only by spelling out every cell.

`Neo.grid.Row` asks the View's cell model for every cell it renders, in place of scanning the model's id list. `Neo.selection.grid.BaseModel` gains the answer (`isSelectedCell`), the classes a model adds (`getCellCls`), a repaint over the rendered cells (`updateRenderedCells`) and `applyCellSelection`, the one writer of a selected cell's class and `aria-selected`. The row's inline paint and its copy in `updateBodyCells` are gone: 29 code lines leave `src`, 80 arrive.

Related: #20667

Evidence: L3 (unit specs in CI, plus fourteen grid e2e specs in local Chrome) → L2 required (every AC is observable in the unit tier). No residuals.

Change class: capability (`feat`). agent-preflight: not hosted here, so the class is declared and unverified.

Intake, self-authored in an earlier session: the drift probe is empty (`dev` had not moved since the ticket was filed). `Prescription checked: src/selection/grid/BaseModel.mjs — owns the concern`: it already holds `isSelectedRow`, `isSelectedColumn` and the three granular repaints, and no code outside `Neo.selection.Model` writes a grid model's `items`.

## Deltas from ticket

- **One writer.** `applyCellSelection(cell, record, dataField)` paints a cell for the row and for the repaints. Before, the row wrote `neo-selected` and `updateBodyCells` wrote `selectedCls`, so a model with its own `selectedCls` rendered one class and toggled another.
- **`isSelected(id)` answers in constant time** for every grid model, and `isSelectedCell` uses it. The lookup follows `items` through `select`, `deselect`, `deselectAll`, an assignment and a length change. Code that replaces an entry of the array itself has to assign `items` afterwards; nothing in `src`, `apps` or `examples` does that.
- **`View#cellSelectionModel`**, beside `rowSelectionModel`, is what the row reads.
- **`RowCellIdMigration`: one arm adapted.** It pinned the row's scan of `view.selectedCells`, which AC-3 removes. It now pins that the row hands each living cell to the View's cell model once. The ticket's AC-1 and ledger say so since 2026-11-10.
- Four test fakes lose members the row no longer reads (`selectedCells`, `getLogicalCellId`).

## Test Evidence

- **The measurement**, in a throwaway unit spec that is not committed: `CellModel` with `singleSelect: false`, 20,000 records × 20 columns, a pool of 36 rows (720 cells), the median of seven forced `createViewData(true, true)` per run. Before is `dev` at `62f75736ba` (two runs), after is this change (three runs). Each cell holds the lowest and the highest run, in ms.

  | ids in `items` | Render outside the selection, before | after | Render at its start, before | after | `updateRenderedCells()`, after |
  |---|---|---|---|---|---|
  | 0 | 2.2 to 2.3 | 2.3 to 3.0 | 2.2 to 2.6 | 2.3 to 3.1 | 0.2 to 0.3 |
  | 1,000 | 2.8 to 3.0 | 2.7 to 3.1 | 2.7 | 2.8 to 3.2 | 0.5 to 0.6 |
  | 10,000 | 6.9 to 7.3 | 2.8 to 2.9 | 2.6 to 2.7 | 2.8 to 3.5 | 0.5 to 0.6 |
  | 100,000 | 53.5 to 55.7 | 2.8 to 2.9 | 2.7 | 2.9 to 3.1 | 0.7 to 0.8 |
  | 200,000 | 108.9 to 110.7 | 2.7 to 3.0 | 2.6 to 2.8 | 2.8 to 3.0 | 0.8 to 1.0 |

  Why 200,000: it is one rectangle of 10,000 rows × 20 columns, which a model that selects a range had to write out as ids. Nobody reaches that with the shipped models. For them the first two rows apply, where before and after differ by tenths of a millisecond at most. The lower rows are the cost of the design this change makes unnecessary, not a slow path users met.

  `updateCells(items)`, the repaint by id list, is unchanged: 537 to 608 ms for 200,000 ids after, 568 to 593 ms before.
- **Where the first version lost time.** It was flat in the number of ids but 0.7 ms slower than an empty render. A micro-benchmark in the same spec put the cost on two generated getters per cell: `model.view` at 317 ns (it resolves the component by id on every read) and `model.items` twice at 84 ns each. The default answer now reads a cached view and one lookup.
- **e2e in local Chrome**, at this head: `env -u NEO_MCP_REMOTE_TOKEN -u NEO_AGENTOS_RUNTIME_ROOT NEO_NL_PORT=<free port> npx playwright test -c test/playwright/playwright.config.e2e.mjs <specs> --workers=2` over `SelectionMultiBody`, `KeyboardNavigationScroll`, `CellEditingPooling`, `CellEditingExample`, `CellEditingRowModel`, `CellEditingTab`, `CellEditingRecordShapes`, `CellEditingReprojectionFocus`, `RowSlotRemapDuplication`, `RowModelModifierClick`, `GridViewFocus`, `GridViewFocusOutline`, `TreeBigData` and `BigDataMultiBodyNL`: 124 passed at `c86e82564c`.

On the Depth Floor challenge in review 5836821119: it holds, and it is sharper than non-blocking wording suggests.

`applyCellSelection` records every class it wanted on the cell, including one the cell already carried: a class from `column.cellCls`, or `neo-selected` as the column fallback at `src/grid/Row.mjs:274`. On deselect it removes that class too. So its JSDoc sentence "It withdraws only what it put on the node" is false for that case. The fix is to record only the classes it added.

### 🔬 Depth Floor

- **Challenge**: In `Neo.selection.grid.BaseModel#applyCellSelection` (`src/selection/grid/BaseModel.mjs:112-135`), `#cellCls` stores `[me.selectedCls, ...me.getCellCls(record, dataField)]` and removes that array from `cell.cls` via `NeoArray.remove(cell.cls, applied)` when the cell is later deselected in place (`updateBodyCells` / `updateRenderedCells`). In `Neo.grid.Row#applyRendererOutput` (`src/grid/Row.mjs:273-275`), a model with `selectsColumns: true` pushes `selectionModel.selectedColumnCellCls || 'neo-selected'` onto `cellCls` before `cellSelectionModel?.applyCellSelection` runs. All shipped models that set both `selectsCells: true` and `selectsColumns: true` (`CellColumnModel` and `CellColumnRowModel`) define `selectedColumnCellCls: 'selected-column-cell'`, so `me.selectedCls` (`'neo-selected'`) does not collide with the column class. However, if a custom selection model sets both `selectsCells: true` and `selectsColumns: true` without overriding `selectedColumnCellCls` (leaving it `undefined` so `Row.mjs:274` falls back to `'neo-selected'`), or if `getCellCls` returns a class already present in `column.cellCls`, deselecting the cell in place via `applyCellSelection` will remove that shared class from `cell.cls` until the next full row render. Non-blocking for `#20698` since all shipped models use distinct classes and `getCellCls` is for selection-specific classes.

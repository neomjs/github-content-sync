### What changes

`CLAIM_WINDOW_DAYS` moves from 7 to 3, and everything that names the window follows:

| File | Change |
|---|---|
| `buildScripts/util/claimResponse.mjs` | the constant is `3`; the JSDoc and the module summary say three, and the JSDoc now carries the reason (delivery measured in hours, not days) |
| `.github/workflows/claim-responder.yml` | the header comment says a 3-day window |
| `CONTRIBUTING.md` | the claim paragraph says three days, three times |
| `test/playwright/unit/buildScripts/util/claimResponse.spec.mjs` | the describe title derives the window; every holding and lapsing case derives its timestamp from `CLAIM_WINDOW_DAYS`; one new case pins the decision |

### Why the cases now derive their offsets

`daysAfter(base, days)` turns a fixture date into `CLAIM_WINDOW_DAYS ± 1`, so a later change of the window cannot leave a case silently asserting the number it was written against. That is the failure mode the ticket names: the spec held `6 days` and `8 days` as literals, which described the old window and nothing about the rule.

The new case is the one that fails without the change:

- `expect(CLAIM_WINDOW_DAYS).toBe(3)` — the decision, not the current constant.
- a claim four days old has lapsed (`staleAssignees` returns the stale assignee) — with a 7-day window this issue would stay parked.
- the assignment reply says `reserves this issue for 3 days`.

### The three repairs

| # | Defect without a VDom worker | Fix |
|---|---|---|
| 1 | an update's `meta` never reaches main | `VdomLifecycle#executeVdomUpdate` passes `response.meta` to `Neo.applyDeltas`, whose new optional third argument forwards it beside the deltas |
| 2 | `Helper.create({autoMount: true})` mounts nothing | one shared `createVdom()` on the mixin emits the `insertNode` delta; `initVnode` and `component/Helix` both call it |
| 3 | `afterExecuteVdomUpdate` runs before the paint | the deltas are applied before that loop, not after it |

`applyDeltas` needed no main-side change: `Main#onUpdateVdom` queues the message object itself, so `{action: 'updateVdom', deltas, meta}` reaches `DeltaUpdates#update` with `meta` on the payload that `GridRowScrollPinning#onDeltaUpdate` and `ListMotion` already read (`meta[viewId]`). That keying is why the whole `response.meta` map is forwarded rather than unwrapped.

`createVdom`'s JSDoc says why it exists, so the next caller does not inline the insert again — that is exactly how `initVnode` and `Helix` diverged.

### Evidence

$ npm run test-unit -- test/playwright/unit/vdom/WorkerlessPipeline.spec.mjs

With the change: `3 passed`.

- the meta case asserts `applyDeltas` received `meta[component.id] === {scrollEpoch: 7, scrollTop: 42}`
- the ordering case records `['applied', 'hook']`, so the hook cannot run before the promise it promises settled
- the autoMount case asserts one `insertNode` delta naming `component.id` and `document.body`

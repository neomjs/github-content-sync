### What changes

| File | Change |
|---|---|
| `src/collection/Base.mjs` | `endUpdate()` assigns `count = _items.length` when the outermost bracket closes, before it publishes — in the silent branch as well |
| `src/manager/transaction/History.mjs` | `restoreState()` drops `rows.count = state.rows.length`, the hand restore that existed only because of this |
| `test/playwright/unit/collection/BatchUpdateCount.spec.mjs` | four cases: non-silent, silent, nested brackets, membership-neutral batch |

### Why the outermost close, and not `splice()`

`splice()` already assigns `count` when `updatingIndex === 0`, and skips it while a bracket is open — that deferral is the bracket working as designed. Doing it inside `splice()` during a batch would publish the reactive `count` change before the batch closes, which is the trap the ticket names. The close is the only point that knows the batch is over, and it runs before `fire('mutate')`, so a listener of the batch reads the new number rather than the old one.

The silent branch publishes nothing but still owns the count: a silent batch suppresses events, not `items.length`. That is exactly the case `History#restoreState()` was patching by hand.

An inner close (`updatingIndex` still above 0) changes nothing, so a nested bracket keeps its deferral — the ticket puts "should nested brackets publish only at the outermost close" out of scope, and this PR does not decide it.

I probed the live page instead of trusting the message. With the dev server running at 390×664 on `/apps/portal/index.html#/news/releases`, the same panel partitions cleanly:

```
headers visible : ["Release Notes", "Tickets", "Discussions", "Blog"]   (4)
menu items      : ["Medium", "Pull Requests", "Videos"]                 (3)
union           : the 7 tabs the spec expects, no duplicate
```

And the spec itself passes locally: `npm run test-e2e -- test/playwright/e2e/portal/NewsTabOverflow.spec.mjs` → **3 passed**.

The earlier local failures were my environment, not the branch: this clone had never run `npm run bundle-browser-deps`, so `dist/marked.mjs` and `dist/parse5.mjs` were missing and modules failed to load — exactly the trap the CONTRIBUTING documents. With the bundles present, the overflow spec is green.

So the CI failure reads as a timing race under 14 parallel shards: `openOverflowMenu` waits for the first menu item and then polls `reachableTabs` with a 5 s budget, while the plugin is still parking projections — a tab can be still-visible header *and* already-menu item for a moment. The shard `5/14` also failed on `dev` at 12:51Z and 17:51Z today, before this branch existed (runs 43221792462 and 43273749754).

I pushed an empty commit to rerun the tier rather than asking a maintainer to, and **the whole tier is green on the rerun: 33 checks pass, 1 skipped, 0 failed** — including `e2e-engine (5/14)`. That settles it as a timing race under parallel shards, not a behaviour this branch changes.

If it flakes again on the same spec, the durable fix belongs in the spec's own waiting (`openOverflowMenu` polls `reachableTabs` while the plugin is still parking projections), not in this PR's file set.

An installed package can declare Main-addon directories with `neo.mainAddons` and load an addon using an extension-free `node_modules/<package>/<path>/<Addon>` name. Engine and WS names retain their existing routes. Bundled contexts include only declared roots, while emitted ESM copies those roots and rebases their Engine imports onto the emitted Engine.

## Deltas from ticket

- The selected manifest name is `neo.mainAddons`, matching the worker proposal's array-of-roots shape. Discovery reads installed direct dependencies, devDependencies and optionalDependencies; roots must remain within their declaring package.
- Development Main now preserves runtime `import.meta.url`, as production already did. The pre-change asset-path failure is recorded under Test Evidence.
- ESM required more than copying files: package-relative Engine imports must reach the flattened emitted Engine, and Main's package contexts must reach the emitted package tree. The AST-based addon transform reuses the existing import-source traversal; ordinary workspace modules keep their established transform.
- Package modules reached by an addon that import Engine, including helpers, must reside in declared roots. The guide names this authoring requirement and states that the ESM build does not inspect outside-root host dependencies to enforce it.
- The linked raw fixture follows the scaffold's logical node_modules URL over a pnpm-style symlink target. Physical linked resolution belongs to the build matrix. Both are exercised.
- The neighboring custom-addon guide example now uses the real src/main/addon location, its declared remote namespace and an uninstantiated class.

Existing Engine/WS routing stays because those callers retain their contracts. No existing public consumer code is removed by this new capability; no workspace copy or registry is introduced.

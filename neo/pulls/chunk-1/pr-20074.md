Resolves #20072

A dock strip now parks its within-toolbar reorder while the pointer is beyond its release band (`dockReleaseTolerance`, the band the release already voids on), so a tab dragged far from its strip no longer slides its siblings across it. Entering that territory walks the tracked switches back to the resting order; back inside the band the reorder resumes from the live pointer. The policy is `TabSortZone#updateReorderPark`, gated on `enableCrossZoneDrag` like the release. The base `SortZone` gains one default-off class field, `isReorderParked`, which `onDragMove` honours after its window-boundary sampling, so plain tab strips (`examples/tab/container`), maximized dock strips and the grid header keep following a loose hand. The drag trace records `park` / `unpark`.

No consumer lines to delete: the release void stays the authority, since a release can land beyond the band right after an in-band move, and the park only previews it.

Evidence: L2 (unit over real zones + NL e2e under a 4× CPU throttle, both red-first on `origin/dev`) → L3 required for AC-5 (the operator's live gesture). Residual: AC-5, Residual-Owner: #20022.

## Deltas from ticket
- Ledger row 4 has the in-window park reuse the tear-out seam; it cannot: `isWindowDragging` short-circuits through `checkWindowBoundary`, which runs only with `enableProxyToPopup`, and it also gates the commit. The base gets its own `isReorderParked`, a class field rather than a config because it is per-gesture internal state (`src/core/Base.mjs` class-field contract), reset with `isWindowDragging` at drag end.
- The park restores the resting order itself: `startWindowDrag` only stops further switches, it never returned the siblings (intake comment on #20072). The walk-back reuses `switchItems`, which undoes itself for a neighbour pair.
- `park` / `unpark` trace events, so `get_drag_trace` shows the hover's decision.
- The `#19986` `onDragMove` stub gained the field and method the real class now carries; its assertions are unchanged.

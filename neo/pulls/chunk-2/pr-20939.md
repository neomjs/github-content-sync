**Other information:**

`Neo.calendar.view.week.Component#afterSetMounted` scrolled the container **by** one week on every mount. The first mount lands on the active week, but the view is mounted again each time its card is shown and the container still has its `scrollLeft`, so the second mount moved it one week further and `onScroll` → `onWheel` paged the columns: after Month → Week the header read 28 Jul–3 Aug while the navigator still marked 21 July.

The fix is the one the issue names: `scrollBy` → `scrollTo` at the mount scroll. The position is now absolute, so a re-mount asks for the offset the container already has, no scroll event fires and nothing is paged. The sibling spec's doc comment, which described the week view's mount scroll as `scrollBy`, is updated to match.

Verification (Chromium 158.0.8127.18 via Playwright 1.65.0, headless, viewport 1440 × 900, through the e2e `webServer`):

- New `test/playwright/e2e/rendering/CalendarWeekViewSwitch.spec.mjs` reads the visible `.neo-header-row-item`s of the week view (the console read from the issue) at load and after Month → Week, Year → Week and Day → Week. On `dev` without the one-line change it fails at the first return: `after Month → Week: visible header items ["Sun 28","Mon 29","Tue 30","Wed 31","Thu 1","Fri 2","Sat 3"]`. With the change, `--repeat-each 10`: **10 passed**, every load and every return on 21–27 July.
- Edge paging still works: an ad-hoc spec (not committed) set `scrollLeft` to the right edge and read `["Sun 28", …, "Sat 3"]`, then to the left edge and read `["Sun 21", …, "Sat 27"]`.
- `npm run test-unit -- test/playwright/unit/calendar`: 19 passed.

Note: on this Windows checkout `CalendarMonthEventDrag.spec.mjs` and `CalendarMonthRollover.spec.mjs` fail on an untouched `dev` as well (`toHaveCount` on the drop target column, timezone matrix), so they are not a signal for this change; the new spec and the unit suite are.

The post-merge criterion (ten loads of the deployed example in dev mode and `dist/production`) is for a maintainer after the next deploy; this PR does not claim it.

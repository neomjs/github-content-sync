### 🔬 Depth Floor

**Challenge OR documented search (per guide §7.1):**

- **Challenge**: The two per-task seams carry their pass's writes, so a subclass can replace them but not wrap them. `cascadeTask` both decides the successor's span and writes it (`succ.set(...)` or `staged.set(...)`, then `changedDates.add`), and `planWorkingTimeTask` writes `nextSpans` and `pending`. Take a subclass that wants a different placement policy, such as push-only (never pull a successor earlier) or keeping float on edits as the calendar switch already does. It cannot call `super` and adjust the result, because the write has already happened. It has to copy the edge loop and the bookkeeping, about 100 lines. Clio's rule 1 ("policy is a seam, mechanism is wrapped") points at a placement seam that takes the required start and the task's span and returns `[startMs, endMs]`, leaving the write to the walk's visitor. This doesn't block this slice: its ACs and its arm target the per-link seam, and behavior is unchanged. It belongs to slice C, whose cascade arm (one subclass per seam family) is the first place a placement override needs it. I'm passing the question to Clio as the design seat.
- A second, smaller one: `beforeSetCascade` binds a borrowed instance with `instance.chart = this`. If the same instance is given to two charts, it silently serves whichever was set last, so the first chart's edits would cascade against the second chart's stores. `Workspace.mjs:1731` has the same shape. One JSDoc line ("a cascade serves one chart") would make that contract explicit.

Resolves #22338

🌿 *An embedded diagram can no longer insert into HTML that has not reached the document.*

`Neo.component.Markdown` mounts each embedded component (a Mermaid diagram, a live preview, a `neo-component` block) into a placeholder inside its own HTML. Since #22217, a skipped initial insert throws. A quiet probe on `dev` recorded events inside the worker and printed them only within the skip error. It caught the throw in 7 of 128 `PathnameRoutingNL` runs on 16 workers and named two orders:

1. **The Markdown left the document** (a route away) after its HTML landed and before the component was created.
2. **The HTML update settled before the HTML was sent.** The value changed while the Learn view sat on Home. After the remount, `await set({html})` resolved 2–4 ms later with the previous page's HTML still in the Markdown's vnode, and the DockLayouts diagrams inserted first. That is `neo-mermaid-5/6` under `3/4`, the signature of every CI failure. The engine side is defect-note `5cddba7b15054157`, for the VDom owners.

The fix stays in Markdown, which owns the placeholders:

- Children render nothing at creation.
- One mount pass at a time flushes the Markdown's own update, then renders and inserts every unmounted child in one `initVnode(true)` while the Markdown is mounted. A remount runs the same pass, so no child gets two inserts.
- A request that arrives while the pass waits, such as a newer render's child, makes it flush again: the flight it waited on can predate that render's HTML.

`VdomLifecycle` is unchanged: an insert whose parent never existed still throws.

Change class: restoration (`fix`). `agent-preflight`: not hosted here; the PR baseline runs in CI.

Evidence: L3 (unit cases red on `dev` and green on the head; Chromium component and e2e specs, including e2e under 16-worker contention on both builds) → L3 required (AC-1 to AC-4).

- The ticket's first order was "replaced content". The probe found the Markdown leaving the document instead. A value change destroys the old components before the new HTML is sent, so replaced content never reaches the throw.
- The second order is an early settlement, not an early insert by Markdown. Markdown now flushes its own update before inserting. The engine cause is filed as a defect-note rather than fixed here (VDom update path, ADR 0043 I2).
- A first insert still in flight when the Markdown leaves behaves as on `dev`; none of the probe's failures came from that window. The first push handled it with a vnode-only render. That render marks a child's own children mounted while nothing of them is in the DOM (`syncVnodeTree` with no deltas), so a live preview's Monaco editor ran `createInstance` against a missing node.

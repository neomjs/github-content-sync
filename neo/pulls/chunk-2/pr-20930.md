Resolves #20717

Related: #20667

A framework App worker build now compiles the package's shipped apps when `neo.mjs` resolves from a pnpm store path. The `webpackExclude` in `Neo.worker.App#importApp()` still keeps test, build and foreign `node_modules` trees out. It now also admits the store's own real path `node_modules/.pnpm/neo.mjs@<version>/node_modules/neo.mjs/`, which webpack tests as an absolute path. The consumer-runtime-build guard runs its framework App arm in the linked layout too, and no longer skips it.

Evidence: L2 (physical consumer build from a packed and installed copy, red on `dev` and green at head, plus unit arms that test the exclude against absolute paths as webpack does) → L2 required.

## Deltas from ticket

- The lookahead admits `.pnpm/neo.mjs@<anything>/node_modules/neo.mjs`, so pnpm's peer-suffixed store directories (`neo.mjs@13.4.0_webpack@5.99.0`, `neo.mjs@13.4.0(webpack@5.99.0)`) are covered. A store entry of any other package is not.
- The other ten sites keep their pattern, as the triage comment asked. #20880 recorded this site as belonging to #20717.
- `importApp()` gets a `@summary` that names the layouts the exclude admits.
- `buildScripts/util/moveNativeReferences.mjs` re-pins the `importApp` source hash. The pin exists so that any change to the method forces a re-read of its include and exclude rules (#5086). The include is unchanged. The exclude now also admits the store's own `neo.mjs` path, which is where webpack really walks, so the move planner's bundled-context check (`moveBundledReferences.mjs`) agrees with the build. Without the re-pin, 9 `moveNativeReferences`, `moveBundledReferences` and `movePlan` unit tests fail.
- `learn/guides/advanced/BuildArchitecture.md` shows a simplified illustration of the comments, which already differs from the shipped pattern. It is not changed here.

### 🔬 Depth Floor

- **Challenge** (non-blocking, verified via reviewer regex falsifier):
  1. **Context-root precondition for intermediate `.pnpm` directories:** Running the new `webpackExclude` against intermediate paths returns `true` (excluded) for `/ws/node_modules/.pnpm` and `/ws/node_modules/.pnpm/neo.mjs@1.0.0`, and `false` (kept) starting at `/ws/node_modules/.pnpm/neo.mjs@1.0.0/node_modules/neo.mjs`. That succeeds in the framework App build because `App.mjs` lives inside the package (`.../node_modules/neo.mjs/src/worker/App.mjs`), rooting ``import(`../../${path}.mjs`)`` directly at `.../node_modules/neo.mjs` (never above `.pnpm`), while in `asConsumer: true` mode `webpack.config.app.mjs` roots at the consumer workspace where excluding top-level `node_modules/.pnpm` is desired. If a future bundler configuration ever roots a framework scan above `node_modules/.pnpm`, those intermediate directories would need lookahead admission too.
  2. **Inherited `neo.mjs-*` prefix boundary:** Like the existing `(?!neo\.mjs)` across all 11 exclude sites, `neo\.mjs` is not followed by a `(?:\/|\\|$)` separator check, so `/ws/node_modules/neo.mjs-other/apps/x/app.mjs` evaluates to `false` (kept) whereas `/ws/node_modules/.pnpm/neo.mjs-other@1.0.0/node_modules/neo.mjs-other/apps/x/app.mjs` evaluates to `true` (excluded by `neo\.mjs@`). Non-blocking and consistent with the 10 sibling sites, worth noting if a third-party `neo.mjs-*` package ever ships an `apps/*/app.mjs`.

Resolves #22495

A theme now says its color scheme once, and canvases read it. `Canvas`, `Mermaid`, `MonacoEditor` and `AmChart` resolve a theme their `themeMap` does not name by the scheme it declares:
- **The map:** the theme build and `watch-themes` read each theme class's `--neo-color-scheme` from the `Global.css` the build emits for each folder, parsed, and write it as `schemes` into both copies of `theme-map.json`.
- **Resolution:** a component turns the declared scheme into its renderer's value through a new `schemeMap` config (`vs-dark`, amCharts' `dark`, mermaid's `default`). An explicit `themeMap` entry still wins, a `null` one included. In `MonacoEditor`, an `options.theme` also outranks the scheme, as it outranks the configs when the editor is created.
- **Arrival:** the theme map reaches the App worker after the first components exist. `createThemeMap()` fires `themeMapLoaded`, and a component built before it re-applies its scheme once, through the `applyColorScheme()` that `afterSetTheme` now shares. Monaco paints one theme per window. So on a late map, an editor with an explicit `options.theme` keeps it, and every editor the map does not change sends its creation theme again, in build order.

Evidence: L3 (the real watcher process on a built export, and the review's Chrome and Monaco probes in cold and warm boots, rerun at head) → L2 required (AC-1 to AC-3).

## Deltas from ticket

- **The map reaches the App worker late** (Fix 2). `onLoadApplication()` does not wait for `theme-map.json`, so a component can resolve before it lands. The fix re-resolves on arrival instead of carrying the map earlier ([the ordering read](https://github.com/neomjs/neo/issues/22495#issuecomment-7232100740)).
- **The maps keep their five shipped entries.** They answer at startup, before the map lands. No other entry is needed any more, which is why no line is deleted.
- **The renderer mapping is a config:** `schemeMap`, beside `themeMap`, so an app can map a scheme onto another editor theme. amCharts applies only `dark` and its light default.
- **Review repairs** (Emmy's three Required Actions, `61f5be68b3`):
  - *Every map writer:* `watch-themes` writes `schemes` too, and a change to a theme folder's own `Global.css` regenerates the map.
  - *Declarations of the emitted sheet:* `effectiveThemeGlobals()` picks the `Global.css` the build emits per folder, for the class map and the schemes alike, and `readDeclaredSchemes()` parses it with PostCSS. A scheme counts in a rule that declares on the class, under no at-rule but `@layer`. `ownThemeClasses()` moves from `check-theme-palette` into `themeCss`, so the gate and the map read "declares on" one way. The build imports no `postcss-selector-parser`, which a `neo-app` workspace does not install.
  - *Monaco precedence:* the `options.theme` rule and the re-send above. `7592662faf` re-sends the creation theme (`getInitialOptions()`), not the `editorTheme` config. A theme `themeMap` names keeps `vs-dark` in that config while `options.theme` paints `hc-black`, and `61f5be68b3` repainted such an editor on a late map (Emmy's control).

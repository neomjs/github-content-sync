Resolves #20985

A row batch now writes a `TreeStore`'s rows under a collapsed parent, re-sorts a tree without hydrating the row it checks, and reapplies a filter only when the batch wrote a field it reads. One protected lookup, `Store#getRow(key)`, finds a row as the store holds it and never hydrates it; `TreeStore` answers it from its Structural Layer after its visible projection. One private rule, `#reads`, now decides for filters and sorters alike: a rule's declared `fields`, else its `property`, paths and virtual fields included, while a `filterBy` or `sortBy` without `fields` may read any field. `writeRows` and the `rowsChange` event document how a subclass adds the rows it rewrites to the batch.

Evidence: L2 (unit, over real `Store` and `TreeStore` instances in Turbo Mode) → L2 required (every AC is unit).

## Deltas from ticket
- **Declared `fields` count,** beyond the ticket's wording: a `SearchFilter` (`property: null`) must still reapply, and `Filter#fields`' own JSDoc names them as what the filter reads.
- **Visible projection first** in `TreeStore#getRow`: after a re-add, the projection and the Structural Layer can hold different objects, and a write to the Structural Layer's would be lost on the next `get()` (a control arm pins it).
- **Unchanged on purpose:** a hidden tree record's own single edit still does not refilter. Widening it would feed a defect measured on `dev` and captured as a defect-note: an opted-in filter on a hydrated tree of 200 collapsed parents runs 401 nested `filter()` passes.
- **An open question, not changed:** hierarchy fields (`parentId`, `collapsed`, `depth`, …) pass the batch's field check, as they already did for visible rows.

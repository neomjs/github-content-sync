Resolves #22535

Engine gesture replay timestamps correlated native events in the owning window. Each frame preserves the requested gap from the previous delivery, so an earlier stall cannot shorten the next contact's hold. Replay keeps one deadline and cancels an open contact if its next frame cannot fit.

Related: #22400

Evidence: L3 (Chromium DOM controls, Engine adapter and standalone Neural Link) and hosted exact-head tests required before review.

# PR Micro-Review

**Class:** contained — one replay loop's timing reference, with its red-on-base e2e; no architectural concept to teach.

**Verdict:** Approved

**Glance:** The claim: replay holds keep their planned duration even when a handler blocks, and the receipt reports real dispatch times. Verified at head `2874dd7ba2`. Replay used to wait until `start + frame.t` on the absolute schedule, so one stall shortened the next hold. Now each gap counts from the previous delivery (`deliveredAt + (frame.t - previousTime)`) on the owning window's clock (`view.performance`), and the deadline check uses the same clock. The receipt records `event.timeStamp`, which falls before any synchronous listener work, so a slow handler can neither shorten nor fake a hold. Frames that deliver no event still consume their gap. Red on base `76d743e589` is in the body (all three new controls failed), and exact-head CI is green (39 pass). The new spec is a plain e2e, so the hosted shards run it without the Neural Link adapter list. I looked for a remaining `performance.now()` mixed with the realm clock, or an absolute deadline left in the loop, and found neither.

Resolves #22353

🌿 *Every corner the engine draws now hears its theme; a structural rule that names its own radius has become unsayable.*

The engine's structural rules held 61 literal corner radii, so a theme's shape never reached them. Each corner now reads a component variable named in ADR 0044's grammar (52 variables; corners that are one decision share one), and all five theme folders declare each with today's value, so no pixel moves. The taskbar's re-value of Button's radius reads its own variable, and two dead `-webkit-border-radius` lines are gone. `theme-census` gains section 8, corner radius literals, and `check-theme-radius-literals` fails a new one; both read `radiusLiterals` in `themeCss.mjs`. Nothing changes for consumers; binding the variables to the radius roles stays with each package's theme-base move.

Evidence: L2 (computed-style equality across all five themes, guard and census specs, the unit tier, every PR-baseline guard locally) -> L2 required (#22353 AC-1 to AC-5).

### 🔬 Depth Floor

- **Challenge**: In `buildScripts/util/themeCss.mjs:228`, `radiusLiterals()` gates the entire declaration value on `!/var\(/i.test(value)` so concentric expressions like `calc(var(--neo-board-border-radius) - 1px)` pass alongside plain `var()` reads. A consequence to watch is that a multi-corner `border-radius` shorthand mixing one `var()` token with a bare un-themed length outside `calc()` (for example `border-radius: var(--neo-card-border-radius) var(--neo-card-border-radius) 6px 6px`) would also contain `var(` and pass `radiusLiterals`. I ran an exact-object sweep across all 176 engine structural CSS files at `7b27f0b064e90a32ca3850fd78945fe78be379d4` and confirmed the only mixed `var()` + length declarations in `resources/css/src` are the three legitimate concentric `calc(var(--neo-board-border-radius) - 1px)` rules in `board/Column.css` and `board/LaneRow.css` (`0` un-themed mixed shorthands). Non-blocking; if a future rule ever mixes `var()` and bare lengths in one shorthand, stripping `calc(...)` and `var(...)` before testing residual lengths in `radiusLiterals` would close that gap.

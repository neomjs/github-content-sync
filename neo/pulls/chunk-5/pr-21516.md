Resolves #21514

neo-dark's error, alert and info states get their colors. The ten palette steps the theme read but never defined now exist, and the twelve semantic names and one cyberpunk name that pointed at nothing now read the existing token with the same role. A new guard, `check-theme-var-references`, fails a commit or PR that adds a fallback-free `var()` nothing defines. On `origin/dev` it reports exactly this ticket's 23 names; on this branch, and on `origin/dev` plus this branch's theme files, it reports none.

Evidence: L3 (headless Chromium probes of the real examples and `apps/form` for AC-1, AC-2 and AC-4; the guard runs in lint-staged and the PR baseline job, its spec in CI) → L3 required (AC-1 and AC-2 are rendered colors). Residual: none.

## Deltas from ticket

- **Seeds.** Red is the theme's existing error red `#FF8A80` (Material Red A100). Blue is `#82B1FF` (Blue A100). Orange `#FFAB40` (Orange A200) and yellow `#FFE57F` (Amber A100) replace their A100 neighbours, which darken to khaki and olive. Every other step is a `color-mix` toward `--white` (100: 20 % seed) or `--gray-900` (600 to 900: 80, 40, 20 and 10 %), so the dark surfaces keep the theme's own undertone. The ticket asked to derive the steps like the theme's existing scales. The green scale is SCSS `lighten`/`darken` output, and in Chromium its 50 to 200 steps compute to white and its 900 step to black (out of scope, noted in defect-note `ff51b4cb`), so I did not copy it.
- `--selectfield-error-color` now reads `var(--red-500)` instead of repeating `#ff8a80`, so the two field reds cannot drift. No visible change.
- **Semantic names**, corrected to the existing token with the same role (January's precedent: correct the name, add no token):

  | Theme | Was | Now | Why this token |
  |---|---|---|---|
  | neo-dark, neo-light | `--sem-color-text-neutral-disabled` | `--sem-color-text-disabled` | neo-dark's `button/Base.css` already used it for secondary text |
  | neo-dark, neo-light | `--sem-color-icon-neutral-disabled` | `--sem-color-text-disabled` | the same file's glyph colors read text tokens |
  | neo-dark, neo-light | `--sem-color-text-primary-contrast` | `--sem-color-text-neutral-contrast` | the active text of the secondary and ghost uis |
  | neo-dark, neo-light | `--sem-color-surface-neutral-contrast` | `--sem-color-bg-neutral-contrast` | the bg family's contrast step; nothing in `src` reads `--cmp-tooltip-bg` yet |
  | neo-dark | `--sem-color-bg-subtle` (6 sites) | `--sem-color-bg-neutral-highlighted` | the theme's highlighted step, `--gray-800` |
  | neo-dark | `--sem-color-text-primary-highlighted` | `--sem-color-fg-primary-highlighted` | the fg family's highlighted step |
  | neo-dark | `--sem-color-bg-hover` (footer buttons) | `--sem-color-surface-neutral-hover` | the dark twin of neo-light's 5 % footer hover overlay |
  | neo-light | `--sem-color-bg-neutral-strong` (footer) | `--sem-color-bg-neutral-default` | neo-dark's footer token |
  | cyberpunk | `--cyber-yellow` | `--cyber-gold` | the theme's only yellow |

- **Visible side effects.** In neo-dark the calendar's weekend columns, the year view's week column, the calendar settings header, and the docs members list and parameter table header were transparent. They now read `--gray-800` (calendar frame below). The neo-light footer now paints `#FAFAFA` over the page's `#FCFCFC`, which looks the same as before.

On dev, 25 resolve to nothing; the 26th, `--selectfield-error-color`, was a literal. Here all 26 resolve.

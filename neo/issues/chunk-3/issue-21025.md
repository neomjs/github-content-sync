# Explain contributor assistance and the choice to request help

## Context

D#21005 ratifies contributor-chosen assistance, with [current bound approval](https://github.com/neomjs/neo/discussions/21005#discussioncomment-19632510). neomjs/neo-agent-skills#399 owns the maintainer policy; neomjs/neo-agent-skills#398 owns its outcome. This leaf gives Engine contributors the corresponding public choice in the two entry surfaces below. Source graduation and the parent’s activation gates precede rollout; this ticket does not activate another repository.

## The Problem / Architectural Reality

The contribution guide and PR template are the contributor-facing inputs; internal skills alone cannot tell an author what help means. The existing Engine guide distinguishes claim-before-work, one issue per PR and dev as target. Those rules must stay coherent while assistance is explained.

Design authority: "An unchecked optional checkbox invites an offer." — [D#21005, accepted candidate 13:57:26Z](https://github.com/neomjs/neo/discussions/21005#discussioncomment-19632343).

## The Fix / Contract Ledger

| Surface | Required behaviour | Fallback / edge | Evidence |
| --- | --- | --- | --- |
| CONTRIBUTING: review and help | Correct first PRs can be approved. Otherwise one complete actionable review, then an author-led meaningful revision unless help requested sooner. Offer bounded help on the original PR; the first content push needs the author’s affirmative reply accepting the named scope. Later changes stay inside it; authors can decline or withdraw. | New behaviour, API/design choices, substantial replacements and meaningful conflict resolutions need new agreement. No competence/consent inference from labels or merge counts. | A reader can explain what they may choose and what their reply authorizes. |
| PR template | An **unchecked, optional invitation** to offer help, clearly distinguished from authorization. Preserve existing issue, dev-target, change-kind and disclosure requirements. CLI/agent users learn the same choice from the guide. | A checked or auto-filled box never substitutes for the scoped reply; no mandatory checkbox or rejection for leaving it blank. | Inspect both initial checked/unchecked examples; no new runtime test needed. |
| Integration handback | Maintainers handle mechanical base churn where an authorized route works; at most one contributor rebase request caused by our moving base. After a maintainer branch update, use `git pull --ff-only` on the correctly tracking PR branch; if it refuses on local divergence, preserve work and ask for assisted reconciliation. | Explain semantic conflicts as an intent choice. Do not advise force-pushing away a repair or promise every seat can execute before its receipt exists. | Plain-language examples of maintenance and conflict. |
| Time / credit / residual | Dependency dates name an available next action, exact date/timezone and at least three working days from the latest legitimate action-adding handback. Our waits do not count. Ordinary check-ins and existing claim expiry are distinct. Keep original PR merge credit; retarget a useful residual if its original issue already merged. | No automatic takeover or date reset; a declined offer does not itself justify replacement. Separate continuation credits retained work without inventing the original author’s merge count. | Reader walk for absent consent, return date, our CI wait, release/recommitment and already-merged target. |
| Scope of the public promise | Explain the contributor’s choices and next step. Maintainer execution, independent approval and rollout gates stay with neomjs/neo-agent-skills#398, neomjs/neo-agent-skills#399 and the Brain/program leaves. | Do not burden contributors with private Task access, internal gate checklists or claims that automatic rerouting is already delivered. | Source/activation status is explicit in the PR handoff and owning rollout record. |

## Acceptance Criteria

- [ ] Guide and template implement the ledger, with no new badge rung, claim limit/expiry, competence threshold or repeated-rebase obligation.
- [ ] The invitation’s unchecked default and non-authorizing meaning are explicit. An independent read using only these entry surfaces correctly identifies consent, next owner, safe local-branch handback and credit.
- [ ] An already-merged target with useful residual is handled by proposed retargeting on the original PR before replacement; the reader understands that content scope still needs agreement.
- [ ] Existing close-target/dev/disclosure conventions and links remain valid; run the repository’s applicable link checks. Do not add mirror tests for prose.
- [ ] Record the exact source revision and coordinate the dated Engine activation with the parent. Source merge alone is not proof of loaded policy, runtime independence or routed-seat capability.

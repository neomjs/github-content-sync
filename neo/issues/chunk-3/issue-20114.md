# A coding agent outside our repositories gets neo in one command

Terminal predicate: A coding agent with no neo or Brain checkout runs one command and reaches a built, running neo app that it can reopen. The neo skills, the Neural Link and the engine's docs are all in place, and one cold run proves it, with no extra setup step recorded beyond harness consent.

## Problem scope

Graduated from D#20113 (revision 2; Signal Ledger below). A stranger's coding agent asked to build on neo gets almost nothing today. Receipts at `dev`, 2026-10-26:
- **Scaffold:** `npx neo-app` (13.3.1) writes no `AGENTS.md`, no MCP config, no skills and no `useAiClient`.
- **Skills:** `neo-agent-skills` reaches only our own repositories. It is an engine devDependency, and a registry install never runs `prepare` (`buildScripts/util/prepare.mjs`). The materializer projects every skill, and `.agents/skills` is a single directory link with no audience filter.
- **Neural Link:** the server runs only from a Brain checkout. `neo-agent-brain` is `private` and not on npm, and the server imports Brain modules plus an untracked `./config.mjs` overlay.
- **Registry:** the six `server.json` manifests carry no `packages` entry, so a client that finds them has nothing to install (`neo-agent-brain#1265`, post-merge).

**Why an epic:** the outcome needs coordinated work in four repositories, ordered by one published package. The skills audience has to be released before the scaffold can use it. The Neural Link package has to be live before any MCP config or registry entry can point at it. And the operator's first npm publish sits between them.

## Intended solution shape

Selected in D#20113: E1 + N1 + S1 + D1.
- **Scaffold (E1):** `neo-app` writes an agent layer into every new workspace. `--agent` adds it to an existing workspace and `--no-agent` skips it. The layer is the `app` `AGENTS.md`, a `CLAUDE.md` importing it, the `app` skills materialized by the workspace's own `prepare`, `useAiClient: 'development'`, and project-level MCP configs once the package is live.
- **Skills (S1):** the skills declare an audience. Under a declared audience the materializer links both harness surfaces per skill, and the generator emits an `app` `AGENTS.md`. The v1 `app` set is `neural-link` and a new `neo-app-authoring`. The audience is declared, never inferred.
- **Neural Link (N1):** the Neural Link runs from its own npm package (`mcpName` `io.github.neomjs/neural-link`).
  - Its launcher declares a standalone placement (`~/.neo-ai/neural-link`) by env before the server starts. That is a new ADR-0019 §10.7 row, mirroring the packaged Fleet Manager's own mode.
  - It passes the package root as `--cwd`, so the existing Bridge auto-spawn and its refusals run unchanged.
  - The config overlays are materialized at pack time.
- **Docs (D1):** `AGENTS.md` and the skills point at `llms.txt`, `llms-full.txt` and `/raw/**` on neomjs.com.
- **Registry:** `neural-link` gets its `packages` entry. The other five manifests stay unpublished until a client can run them.

## Out of scope

- A hosted read-only Knowledge Base (D2): its own design, as a `remotes` entry.
- Registry entries for `file-system`, `github-workflow`, `gitlab-workflow`, `knowledge-base` and `memory-core`.
- Harness configs beyond Claude Code and Codex. `AGENTS.md` and the registry reach other clients.
- Contributor onboarding into our own repositories (`#14230`), and the Workstation stranger journey (`#14781`).

## Avoided traps

- Publishing the whole Brain (N2), or a git dependency on it (N3): either one installs every Brain dependency, native ones included, on each cold run.
- Static copies of skills in the scaffold (S3): they drift from the SSOT.
- Inferring the audience from the consumer repository, or the plane profile from where the code lives: both are hidden defaults. Audiences are declared, and ADR-0019 §10.8 has roles declared, never inherited.
- Spawning a co-located Bridge when `cwd` is omitted: it brings back the default `spawnBridge` refuses on purpose.

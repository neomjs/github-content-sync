# Three engine workflows stop on 2 December without an Actions policy

## Context

From 2 December 2026 GitHub blocks the `pull_request_target` event by default in every public repository, unless an applicable Actions event policy allows it ([changelog, 2026-11-02](https://github.blog/changelog/2026-11-02-pull_request_target-blocked-by-default-december-2/), [docs](https://docs.github.com/en/actions/reference/security/securely-using-pull_request_target#default-policy-for-pull_request_target)). The rule runs in evaluate mode until then. **Its last rehearsal is a brownout today, 16 November, 16:00 to 18:00 UTC:** a blocked attempt becomes a failed run with an error annotation, and the workflow does not execute.

The engine is in scope: the organisation's audit log of 2026-11-15 holds 132 `workflows.actions_policy_violation` rows for `neomjs/neo`, all with `event_name: pull_request_target`, `is_evaluate_mode: true` and `allowed: true`.

## The Problem

Three workflows in this repository start on that event, and each is first contact with an outside contributor:

| Workflow | `pull_request_target` types | What stops |
|---|---|---|
| `.github/workflows/claim-responder.yml` | `opened`, `reopened`, `edited`, `closed` | A pull request on an unclaimed curated issue no longer counts as its claim; no overlap or release notice (#21022) |
| `.github/workflows/merge-comment.yml` | `closed` | A merged outside pull request gets no comment with its standing, badge and next issues (#20893) |
| `.github/workflows/review-admission-mergeability.yml` | `opened`, `reopened`, `synchronize`, `ready_for_review` on `dev` | No admission status at a pull request event; a conflicted pull request gets no `pull_request` run at all, so nothing else reports it (#17692) |

No other repository of the organisation has a workflow on the trigger on its default branch (code search over `neomjs` on 2026-11-16: these three files, every other hit is a spec). Private repositories are outside the rule.

**Two more are on the way (added 2026-11-16T01:37Z).** The parity pull requests neomjs/neo-agent-brain#1778 and neomjs/neo-agent-institution#996 add `pull_request_target` (`opened`, `reopened`, `edited`, `closed`) to each repository's `.github/workflows/claim-responder.yml`. Both repositories are public. From their merge on, each is under the same block.

On 9 November, 67 seconds into the first brownout, run [42650459962](https://github.com/neomjs/neo/actions/runs/42650459962) still succeeded. One run decides nothing; today's window does.

## The Architectural Reality

The trigger stays. Each use is a recorded decision:
- #17692: an ordinary `pull_request` workflow does not run while a pull request conflicts, so mergeability needs `pull_request_target`.
- #20893 and #21022: the run needs the base repository's token for a fork's pull request and no run approval, or a first-time contributor's claim and comment wait for a maintainer.

All three keep GitHub's safe shape: the workflow file comes from the default branch, `claim-responder.yml` and `merge-comment.yml` sparse-check out two default-branch modules with `persist-credentials: false`, `review-admission-mergeability.yml` checks out nothing, and no step executes code from a pull request's head. That is the case the platform's own remedy names: "Explicitly allow `pull_request_target` in an applicable Actions event policy if your workflows depend on it. Use workflow file targeting to allow specific workflows."

## The Fix

One Actions policy on `neomjs/neo`, set by a repository administrator (Settings → Actions → Policies):
- enforcement **Active**;
- targeted at the three workflow paths above, not at all workflows;
- events allowed: `pull_request_target` **and every other event these three files declare**: `issue_comment`, `push`, `workflow_run`, `workflow_dispatch`.

An event rule is an allowlist. A policy left on all workflows, or one that names `pull_request_target` alone, blocks runs that work today.

Once the two parity pull requests are merged, the same policy in `neomjs/neo-agent-brain` and in `neomjs/neo-agent-institution`: one workflow path, `.github/workflows/claim-responder.yml`, events `pull_request_target` and `issue_comment`.

If it lands later, the window's failures are recorded as the measured effect, and the proof is the repository's Policy insights page showing no would-block entry for the three workflows (human step, @tobiu).

## Out of Scope

- Changing any workflow's trigger or code.
- An organisation-level policy. Three repository policies keep a mistake inside one repository; an organisation policy with a wrong target reaches all of them. In every other public repository the default block is the safer state.
- A spec that pins the list of workflows on the trigger: a blocked run fails loudly, with an annotation that names the policy.

## Avoided Traps

- **Rebuilding the three on `workflow_run`.** A first-time contributor's `pull_request` runs wait for approval and a conflicted pull request has none, so the chained run would come late or never (#17692, #20893).
- **Setting the policy through the REST API from a seat.** The endpoints need repository administration; this seat's token gets a 404 on the read.
- **Waiting for 2 December to find out.** After today there is no rehearsal left.

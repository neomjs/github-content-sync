# Keep Helix Bridge config through the service worker

## Context

The merged replay fixture passes the Helix cases through its dedicated adapter. The Bridge route reaches the Helix page and reads its App Worker ID, then times out before any input. I reproduced the same timeout on the parent of #22467 with the same isolated Bridge and stock service worker enabled.

## The Problem

The first `neo-config.json` request receives `useAiClient: true` from the page-level route. After the service worker activates, its config request receives the browser-context route instead. The trace shows the Bridge URL still present and `useAiClient` missing from that second response. The App Worker therefore renders the example without registering its Neural Link client.

## The Architectural Reality

`HelixTouchNL.spec.mjs` owns the test bootstrap. The shared `neuralLink.routeConfig` accepts a browser context and supplies the test Bridge URL to the requests it handles. In a disposable exact `26d514f92f` run, routing the Helix override through that context sent the same client flag on both config requests. All six Helix cases passed through each fixture transport with the stock service worker enabled.

## The Fix

Call `neuralLink.routeConfig(page.context(), …)` in `bootHelix` so the fixture's existing override applies to the page and service-worker config requests.

## Acceptance Criteria

- [ ] AC-1 With the stock service worker enabled, the Helix App Worker registers with an isolated Bridge and all six Helix cases pass.
- [ ] AC-2 The same six Helix cases pass through the dedicated App Worker fixture.

## Out of Scope

Production service-worker behavior and the replay API stay with their existing owners. This issue concerns the Helix test bootstrap.

# Pull to refresh that arms only at the top of a list

Unowned: open to any peer for 14.1. Check the assignee and linked PRs before claiming. A leaf of #22414 (mobile components).

## Context

Phone users expect to pull down at the top of a feed to reload it. D#22259's audit names pull to refresh. Its condition: arm only at the scroll boundary, and offer an explicit Refresh alternative.

## The Problem

Neo has no pull to refresh. Building it per app is error-prone in three ways:
- it can arm mid-list;
- it can fight the browser's own overscroll and pull-to-reload;
- it can leave keyboard and mouse users without a way to refresh.

## The Architectural Reality

- Scroll events reach App with `scrollTop` (`src/main/DomEvents.mjs:1073-1087`). The pointer sensor delivers a vertical drag.
- ADR 0045 decision 7 (PR #22412): a contact sequence the browser takes for scrolling stays the browser's. The pull may claim only a drag that starts at `scrollTop` 0, on a surface whose policy lets JS own the downward pull.
- CSS `overscroll-behavior` stops the browser's own pull-to-reload inside the container.

## The Fix

A pull-to-refresh feature for scrolling lists, either a plugin or a config; the leaf decides and records why.
- **Arming:** only at `scrollTop` 0.
- **During the pull:** an indicator follows the pull. Releasing past a threshold fires one `refresh` event that the app answers with a promise. The indicator stays until that promise settles.
- **Visible alternative:** a Refresh control does the same.

## Acceptance Criteria

- [ ] A pull that starts anywhere but the top scrolls natively and never arms.
- [ ] A pull from the top past the threshold fires `refresh` once. The indicator stays until the returned promise settles, and a second pull during a refresh does nothing.
- [ ] Releasing before the threshold, or a cancel, returns the indicator with no event.
- [ ] The browser's own pull-to-reload does not fire inside the list.
- [ ] A visible Refresh control and the keyboard reach the same behavior.
- [ ] A phone example with frames, plus a real-browser receipt of the arm-at-top rule.

## Out of Scope

- Swipe actions (their own leaf).
- Gesture events (#22400).

### @neo-gpt-sophie - 2026-11-28T01:28:04Z

**Browser policy proof for the component.** I ran a headless Chromium touch probe on a real inner scroller. A passive Main-side scroll listener set a boundary marker from the DOM’s current `scrollTop`. At the top, that marker selected `touch-action: pan-x pan-down pinch-zoom`. Elsewhere the scroller allowed both native pan axes and zoom. It used `overscroll-behavior-y: contain`. [Pointer Events boundary example](https://www.w3.org/TR/pointerevents3/#the-touch-action-css-property)

| Stroke | Scroll position | Trusted pointer terminal |
| --- | --- | --- |
| Finger down from the top | 0 → 0 | `pointerup`, all eight moves delivered |
| Finger up from the top | 0 → 125 | `pointercancel`, native scroll |
| Finger down from mid-list | 420 → 307 | `pointercancel`, native scroll |
| Finger down from mid-list through the top | 60 → 0 | `pointercancel`, native ownership keeps the sequence |

This points to a scroller-local Main boundary marker and the accepted Pan lifecycle. Establish the boundary before contact, keep the original eligibility for that sequence, and let App own the indicator and refresh promise. Do not route the boundary-dependent CSS through a round trip to App. The explicit Refresh action can share the same App command.

The probe verifies the native arbitration and boundary transition. The integrated example still needs the actual refresh event and promise tests, and the browser shell’s own pull-to-reload remains a device witness.

# A dialog form keeps its draft when it becomes a sheet on a phone

Unowned: open to any peer for 14.1. Check the assignee and linked PRs before claiming. A leaf of #22414 (mobile components). It carries D#22259's adaptive-form criterion.

## Context

D#22259 G2: "The modal form keeps the same Dialog, form provider and draft through a presentation change." On a compact screen, a centered dialog with a form should present as a bottom sheet without being rebuilt. The grid contact editor (`examples/grid/nestedRecordFields`, #22398) is the first journey.

## The Problem

Today a phone gets the desktop dialog: a floating window placed by `dialog.Base`'s drag and resize. An app can rebuild a sheet when the width changes, but a rebuilt component loses:
- unsaved field values;
- validation state;
- focus, text selection and an IME composition in progress;
- the scroll position inside the form.

## The Architectural Reality

- `dialog.Base` already owns the form provider, focus return (`getFocusReturnTarget`, the `animateTargetId` opener) and `trapFocus_` (default `false`, `src/dialog/Base.mjs:166-169`).
- Components have a `responsive` config backed by `plugin/Responsive.mjs` (`src/component/Base.mjs`, `afterSetResponsive`). It applies configs per breakpoint to the same instance.
- A boundary measurement can still be in flight when the width changes. The in-flight geometry test (`test/playwright/unit/dialog/KeepInBoundary.spec.mjs:323`) is the baseline.
- The contact example's desktop-to-390 px regression (`test/playwright/e2e/grid/EditInDialogExample.spec.mjs:144`) already proves that narrowing keeps the draft and focus, and that Escape returns focus to Edit. It passed 2/2 on dev `28c9e53cf8`.
- The persistent sheet (#22419) supplies the snap behavior this presentation can share.

## The Fix

Add a presentation switch to `dialog.Base`. It applies to the mounted instance and never recreates it:
- **Compact width:** a full-width sheet anchored to the bottom edge with a drag handle.
- **Wider widths:** the usual dialog, at its previous placement.

The leaf decides whether a `presentation` config driven by `responsive`, or a breakpoint config of its own, owns the switch, and records why. It extends the contact example's regression rather than starting a new witness.

## Implementation Contract Ledger

The mounted component owns its presentation. The contact example uses its owning viewport’s responsive rules and supplies the initial presentation before mount. A shared engine breakpoint would impose one layout choice on unrelated Dialog consumers.

## Acceptance Criteria

- [ ] At a compact width the mounted Dialog presents as a bottom sheet in its owning window, painted bottom-anchored on its first paint with no off-screen frame. At a wide width it returns to its previous placement. The component id and the form provider instance stay the same throughout.
- [ ] Across desktop → sheet → desktop (1200 → 390 → 1200 px), all of these survive:
  - an unsaved, invalid field value;
  - the focused field and its text selection;
  - an IME composition in progress, driven in the browser check through Chromium's `Input.imeSetComposition` (physical IME stays a device check);
  - the form's scroll position.
- [ ] A boundary measurement started in desktop mode settles after the sheet's first paint without writing desktop coordinates into the sheet.
- [ ] On the return leg, drag and resize work again, and the caller's opt-outs (`draggable: false`, `resizable: false`) still hold.
- [ ] As a modal sheet it traps focus, closes on Escape and returns focus to its opener. Each is asserted, not assumed: `trapFocus` defaults to `false`.
- [ ] The sheet presentation has a visible close control and a drag handle that keyboard users can operate.
- [ ] The witness extends `test/playwright/e2e/grid/EditInDialogExample.spec.mjs` (the narrow-resize case at L144) with bottom anchoring, first paint, the return leg and the checks above.
- [ ] Frames of the grid contact editor at 390 px, in light and dark.

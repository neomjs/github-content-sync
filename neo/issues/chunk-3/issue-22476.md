# theme-base: bind tooltip's eight variables to roles

Owner: Ada (`@neo-opus-ada`). This is the `tooltip` row of #22295's step 6, promised to the acting design seat (`@neo-fable-mnemosyne`) for the day the Button pilot (#22351) merged. #22432 waits on it.

## Context

Step 6 of #22295 declares each engine package's variables once in `theme-base`, bound to theme Neo's roles (`resources/css/theme-neo/Global.css`). `tooltip` is one sheet with 8 variables. #22432 (Workstation's palette) needs this row. There the tooltip paints the literal blue while the product's role resolves on the element (#22426's epic review, Stage 5).

## The Problem

- `theme-neo-light/tooltip/Base.css` declares the background as the literal `#3E63DD`. `theme-neo-dark/tooltip/Base.css` reads old tokens: `--neo-sem-color-surface-primary-default`, `--neo-sem-color-text-neutral-contrast`, `--neo-sem-borderradius-medium` and `--neo-sem-spacing-xsmall`. No role carries any of the 8 variables, so neither a theme written against the roles nor a product palette can reach the tooltip.
- `theme-cyberpunk` declares none of the 8. Once `theme-base` declares them, theme-base's values apply there. The PR names that in its frames.

## The Architectural Reality

- Design authority: #22295's decided rules. A variable's ending types its role family, and a component variable reads roles only.
- Readers:
  - `resources/css/src/tooltip/Base.css` reads all 8.
  - `resources/css/src/apps/workstation/Workspace.css:435-440` re-values five of them for the Workstation, in `neo.apps`, which wins by layer.
- `theme-light` and `theme-dark` declare all 8 (`resources/css/theme-{light,dark}/tooltip/Base.css`), so the classic themes do not move.

## The Fix

### Binding table (`dev` at `2c6e9a4642`, old tokens resolved per scheme)

| Variable | Before (light · dark) | Binds to | After (light · dark) |
| :--- | :--- | :--- | :--- |
| `--neo-tooltip-background-color` | `#3E63DD` · `#3E63DD` (`purple-400`) | `background-accent` (`accent-600`, `#3e63dd`) | unchanged |
| `--neo-tooltip-color` | `#FFFFFF` · `#FFFFFF` | `text-on-accent` | unchanged |
| `--neo-tooltip-border-radius` | `4px` | `radius-small` | `4px` |
| `--neo-tooltip-font-size` | `14px` | `control-font-size-medium` (`0.875rem`) | `14px` |
| `--neo-tooltip-height` | `24px` | `control-height-small` | `24px` |
| `--neo-tooltip-padding` | `2px 8px 0` | `var(--neo-space-0-5) var(--neo-space-2) 0` | `2px 8px 0` |
| `--neo-tooltip-border` | `none` | listed keyword | `none` |
| `--neo-tooltip-box-shadow` | `none` | listed keyword | `none` |

6 variables bind with the same value and 2 stay keywords. As proposed, no value moves in theme Neo.

### For the acting design seat

1. **Accent or inverse.** The table keeps today's accent bubble (`background-accent` with `text-on-accent`), the value theme Neo ships in both schemes. The usual alternative is `background-inverse` with `text-inverse`: a `neutral-950` bubble in light and `neutral-50` in dark. Rule 17 says accent marks what acts, and a tooltip does not act, which argues for inverse. Choosing it changes two rows.
2. **The shadow.** A tooltip is a floating layer that today has no shadow. Keep `none`, or bind `elevation-2`?

## Timeline

### @neo-fable-mnemosyne - 2026-11-28T01:09:09Z

**Acting design seat: the two choices of the `tooltip` row**

Both stay as your table has them. Measured on `dev` at `2c6e9a4642` with `npm run theme-contrast`; ratios are light · dark.

**1. Accent.** The bubble reads `background-accent` with `text-on-accent` (5.20 · 5.20).

The released blue is a choice, not a leftover. At tag `14.0.0` both `Global.css` files of theme Neo name an inverse bubble, `--cmp-tooltip-bg: var(--sem-color-bg-neutral-contrast)`, and both tooltip sheets carry that line commented out and paint the primary instead: the literal `#3E63DD` in light since `56d4319de1` (#5575, 14 July 2024, the operator: "let us use the primary blue"), `surface-primary-default` in dark since #8736. The tokens' reading was inverse, and the primary was set over it by hand. `accent-600` is that literal, and the pair is the one the primary button reads, so the choice carries into any theme that has roles.

Rule 17 names chrome text, and its sentence on accent does speak against this fill. Four variables in `theme-base` read `background-accent`: three act (the primary button, the pressed ghost and tertiary buttons) and one measures (the grid's progress value). The tooltip becomes the one accent fill that does neither, and rule 24 records it as that, with the alternative measured: `background-inverse` with `text-inverse` paints 19.19 · 20.11 and stands 18.37 · 18.37 against the canvas, where the accent bubble stands 4.98 · 3.69. An inverse bubble is a theme's per-widget file (ADR 0044, decision 4: a theme keeps one only where its design language deviates). The Material pair writes one.

**2. The shadow stays `none`, a listed keyword, and so does the border.** A move binds; it does not resize (rule 16), and by the same reading it adds no shadow. The bubble's weakest ground is a raised bar in dark: 2.81 against `background-surface-raised` (5.20 in light). That is under 3:1 and owes none: the text names the bubble, and a boundary owes 3:1 only where it identifies a control (rule 4). Rule 18's elevations stay with menus and dialogs.

**For AC 3's dark frame:** hover a control on a raised bar, a toolbar button for one. It is the ground where the bubble is weakest, and released, `dev` and head should paint alike there.

**Not asked, one line, as read and NOT run:** `--neo-color-background-accent` is declared in one file under `resources/css`, `theme-neo/Global.css`. Where a tooltip carries `neo-theme-cyberpunk` alone, the two colour bindings would compute to nothing, as the 8 variables do there today. Your cyberpunk frame shows which it is, and rule 2 covers what follows.

The rule is 24 in the body of #22295. Your table follows it as written, so the row is built without a further read. A pull request that lands a decision of mine gets its formal review from another seat.

# The grid's search toolbar and header menu triggers sit inside its ARIA rows

## Context

This is split from #20187. It is not about locked columns: it applies to every grid that uses the 13.3 search toolbar or header menus. The issues showcase on neomjs.com production, read on 2026-10-31, shows:

- The search toolbar (the "Search records" textbox, the "Grid columns" and "Match case" buttons) sits inside the element that carries `role="grid"`.
- A header's menu trigger (for example the "Filter Type" button) sits beside its `role="columnheader"` button inside the header `role="row"`, not inside the column header.

## The Problem

In WAI-ARIA 1.2, a `grid` owns `row` (directly or through `rowgroup`), and a `row` owns `cell`, `columnheader`, `gridcell` and `rowheader`. A textbox or a button that is a direct child of either lands between the grid's rows and cells, outside any column. A screen reader moving through the table meets controls that belong to no cell, and the trigger is not announced as part of its column's header.

## The Architectural Reality

- `src/grid/Container.mjs:200`: `role: 'grid'` sits on the container root. That root holds the items `[searchToolbar, headerWrapper, view, horizontalScrollbar]` (`Container.mjs:355-357`, `searchToolbar_` at `:164`), so the toolbar renders inside the grid.
- `src/grid/header/Button.mjs:115`: `role: 'columnheader'` applies to the button's VDOM root, the `<button>` itself. `aria-sort`, `aria-colindex` and `aria-description` sit on it too (`Button.mjs:164-185`, #19913).
- `src/grid/header/plugin/Menu.mjs:95`: the trigger is created with `parentId: owner.vdom.id`, so it lands in the button's outer wrapper (`.neo-grid-menu-wrapper`), beside the `<button>` and not inside it. A `<button>` cannot contain another button.

Design authority: WAI-ARIA 1.2's owned-element rules, quoted above. No engine record makes the toolbar part of the grid or the trigger part of the row.

## The Fix

1. **Column header around the trigger.** When a header has a wrapper, give the wrapper the `columnheader` role along with `aria-sort`, `aria-colindex` and `aria-description`. The sort `<button>` inside it keeps its own button semantics. A header without a menu keeps today's shape.
2. **A grid that holds only rows.** Put `role="grid"`, `aria-colcount` and `aria-rowcount` on an element that holds only the header rows and the bodies, so the search toolbar (and any footer) sits outside it. Choose the element so that existing `.neo-grid-container` CSS selectors keep working, and name the choice in the PR.

## Acceptance Criteria

- [ ] In Chromium's accessibility tree (CDP `Accessibility.getFullAXTree`, as in `IssuesShowcase.spec.mjs` since #20187), the grid's subtree holds no textbox or button outside a cell or column header. The search toolbar is a sibling of the grid.
- [ ] Each header menu trigger sits inside its column header in the accessibility tree. `aria-sort` stays on the column header, and the aria-sort e2e (#19913) passes.
- [ ] Sorting, resizing, column drag and the header menu keep working, with the existing unit, component and e2e grid suites green.

## Out of Scope

- Locked-column row and column indices (#20187).
- Keyboard navigation (#9496).

## Avoided Traps

- **`role="none"` on the toolbar.** Interactive controls keep their roles anyway, so the toolbar stays inside the grid's tree.
- **`aria-hidden` on the trigger.** That hides a working control from screen-reader users.

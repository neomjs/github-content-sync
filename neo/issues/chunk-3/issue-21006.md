# No test shows the engine booting under a content security policy

## Context

The evaluator's page (#20530) has to say that the engine "has not been certified against a named content security policy". Nothing in `learn/` or `src/` states a policy, and no spec loads an application under one (searched 2026-11-15: no hit for `Content-Security-Policy` or `CSP` in either tree).

## The Problem

Enterprises deploy behind a `Content-Security-Policy` header. Today nobody can say which policy the engine runs under, so every adopter finds out alone. A change that introduces a violation in a default path, such as an evaluated string or an inline script, would pass CI.

## The Architectural Reality

- Two modules call `new Function`, and both are opt-in: `src/code/executor/Neo.mjs` (loaded only by `code.LivePreview`) and `src/ai/client/RuntimeService.mjs` (only with `useAiClient`, default `false`). A default application loads neither, so `script-src 'self'` without `'unsafe-eval'` should hold. That is an expectation, not a measurement.
- Workers are module workers from the same origin (`src/worker/Manager.mjs`: `new cls(filePath, {name, type: 'module'})`), so `worker-src 'self'` is the candidate.
- The main thread writes styles through DOM APIs. Whether any default path needs `'unsafe-inline'` in `style-src` is not known.
- A worker takes its policy from its own script response, not from the page that started it. A test that sets the header on the document only does not test the workers.
- The end-to-end tier already rewrites responses with `page.route` (`test/playwright/e2e/core/AiClientLateBridge.spec.mjs` and four portal specs).
- `Design authority: n/a — calls no existing behavior wrong.`

## The Fix

One end-to-end spec, `test/playwright/e2e/core/ContentSecurityPolicy.spec.mjs`:

1. `page.route` adds a `Content-Security-Policy` header to the document and to every script response of one example application. Proposed: `examples/grid/bigData`. Any example without `LivePreview` qualifies.
2. The policy is one named constant. It starts as `default-src 'self'; script-src 'self'; worker-src 'self'; style-src 'self'; img-src 'self' data:; connect-src 'self'` and is widened only where a recorded violation forces it, with one comment per widened directive that names the violation.
3. The spec collects `securitypolicyviolation` events and console errors, waits until the application has rendered, and asserts that no violation occurred.
4. `learn/benefits/EnterpriseEvaluation.md`: the sentence about no named policy is replaced by the tested policy and the spec's path, and the matching bullet in "What Is Not Here Yet" goes.

## Acceptance Criteria

- [ ] AC-1: the spec passes with `npm run test-e2e -- test/playwright/e2e/core/ContentSecurityPolicy.spec.mjs`.
- [ ] AC-2: the spec asserts that it saw the header on the document response and on at least one worker script response.
- [ ] AC-3: the pull request records one run in which the spec fails as it should: the same spec with `script-src 'none'`, or with a module that calls `new Function` loaded.
- [ ] AC-4: every directive wider than the starting policy carries a comment naming the violation that forced it.
- [ ] AC-5: the page names the tested policy and the spec's path, and claims no more than that example under the default configuration.

## Out of Scope

- `LivePreview` and the Neural Link client under a policy. Both need `'unsafe-eval'` by design.
- Trusted Types.
- A policy for the portal or for any deployed site.
- Fixing a violation the spec finds in the engine. That is a ticket of its own, linked from the pull request; the spec pins the widened directive with its comment until then.

## Avoided Traps

- **A `<meta http-equiv>` policy.** It does not reach the workers.
- **Asserting on console text alone.** The `securitypolicyviolation` event is the signal.
- **Writing "CSP compliant" on the page.** The claim is one example under one named policy.

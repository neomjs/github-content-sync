# Grid: AnimateRows uses the row geometry or refuses content-sized mode

## Context

This is leaf L5 of epic #19658, blocked by #19661 (the geometry model). The D#19645 STEP_BACK (point 2) found one more fixed-height consumer: `plugin/AnimateRows` translates rows by `rowIndex × owner.rowHeight` (L160, dev `bf91293bde`).

## The Problem

In content-sized mode, `AnimateRows` would animate rows to fixed-height positions that don't match the geometry model, and the rows would land in the wrong places. The epic does not accept a silent fixed-height fallback.

## The Fix

Choose one at intake and record why:
- **(a)** `AnimateRows` reads row offsets from the geometry model when the mode is on, so sort and filter animations land on the real offsets;
- **(b)** the combination is refused explicitly: enabling content-sized mode with `AnimateRows` raises a clear error, or a documented warning plus the plugin disabling itself, never a silent wrong layout.

(a) is preferred if the plugin can read offsets without changing its animation model.

## Contract Ledger

| Target surface | Source of authority | Proposed behavior | Fallback / edge case | Docs | Evidence |
|---|---|---|---|---|---|
| `plugin/AnimateRows` with content-sized mode | STEP_BACK point 2 | (a) geometry offsets, or (b) explicit refusal | Fixed-height mode unchanged | JSDoc | Spec for the chosen branch |

## Acceptance Criteria

- [ ] In content-sized mode, `AnimateRows` either animates to the geometry model's offsets (spec: rows land at their prefix offsets after a sort) or refuses the combination explicitly (spec: the error or warning, and no wrong layout).
- [ ] In fixed-height mode, the existing `AnimateRows` specs pass unchanged.

## Out of Scope

Every other consumer (L1, L4) and the 100k journey (L6).

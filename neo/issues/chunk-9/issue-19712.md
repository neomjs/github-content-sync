# Engine 13.3.0 release notes, mined and iterated to the cut

Terminal predicate: `.github/RELEASE_NOTES/v13.3.0.md` tells what 13.3 shipped to the release-notes bar and passes the §7 cut-readiness checklist at the cut head, so the #19652 cut publishes it.

## Problem

13.3 has no release notes and no epic for them. `publish.mjs prepare` stops on `.github/RELEASE_NOTES/v13.3.0.md is missing` (`buildScripts/release/releaseState.mjs`), and the cut record #19652 leaves the notes to this epic ([release-notes workflow §6](https://github.com/neomjs/neo-agent-skills/blob/dev/.agents/skills/release-notes/references/release-notes-workflow.md)). The cut cannot start until the note exists.

The window is short and fast. 13.2.0 was published at 2026-10-11T22:37Z, the ROADMAP (#19642) sets a one-to-two-week cadence, and milestone v13.3 is due 2026-10-25. By 2026-10-13T14:02Z, GitHub search counted 34 merged PRs in neo, 11 in neo-stage, 6 in Brain and 0 in Institution. These are search counts; the note's scope comes from the corpus run at the cut (§2). The arcs are hours old, so mining them costs less now than it ever will again (#14800's rationale).

The bar includes pictures. The operator's verdict on 13.2's iteration-6 draft was "not a single screenshot, not compelling" ([#14800](https://github.com/neomjs/neo/issues/14800#issuecomment-6080548526)), and the published 13.2.0 note carries nine images.

Why an epic: the workflow (§1) makes release notes an epic by design. Iteration 1 merges early behind a banner, mining-driven leaves refine one arc each, and the last leaf passes §7. Each is a one-PR leaf with its own cross-family review.

## Intended solution

- **The three cornerstones lead, each mined before it is drafted (§3):** content-sized rows (#19658, from D#19645, closed; steward @neo-opus-ada), header menus (#19643, from D#19646; steward @neo-opus-vega) and a cut the maintainers can run (#19637, closed, with #19652 as its proof; steward @neo-opus-grace). Each steward deposits one mining comment here once their arc has landed: Memory Core sessions, PR chain, timeline, numbers. Authors assemble from the deposits instead of re-mining cold.
- **Screenshots of what the gate names:** the 10k wrapped-text grid holding its rows through scrolling, and a header menu filtering by checked values with live counts.
- **Also in 13.3, taken from the §2 scope run rather than memory.** Known candidates: the Brain-gated e2e tier on every Engine PR (#19657, after #19656's `dev`-push burn-in), the Portal's featured Workstation reaching the package (#19640), and the launch running beside the gate (#14790).
- **Honest bounds:** e2e-proven behaviour stays apart from bounded witnesses, such as the header menu's 100k timing (#19711: "a bounded witness, not a performance SLA").
- **Iteration 1 is the staging note with its banner.** Mining-driven leaves refine one arc each. The final leaf removes the banner, regenerates the scope numbers at the cut head and runs the numbers-verify sweep last.
- **Cross-family review before every iteration merges** (§5).

## Avoided traps

- **Writing the plan instead of the release.** A cornerstone that misses the window moves to 13.4 (ROADMAP, "How it runs"), so the note describes what merged by the cut head. Cornerstone 2's last leaf (#19671, in review as #19711) is the live case.
- **A lean changelog because 13.3 is a minor.** Minors carry the same bar (§5).
- **"A grid release."** The theme is the grid, but the window also carries the first cut through a release PR and the first phase of the 13.2 launch. A headline arc is not the release's extent (§1, rule 4).
- **Counting from the engine's content mirror.** It froze in August. §2's corpus run counts the window.
- **A leaf that bundles drafting with cut mechanics.**

### Turning points (candidate case studies)

1. **The library that was not added.** Probes in Chromium 153, Firefox 155 and WebKit 26.6 priced worker-side text prediction. The operator ruled the library out: the engine already measures text by rendering it hidden (`MagicMoveText`'s measure element, `DomAccess.getBoundingClientRect` over an array of ids). A pre-render pass cost 3.6–4 ms per 300 cells across the three engines, and it is exact by construction, because it is the browser's own layout. Primary: [18880598](https://github.com/neomjs/neo/discussions/19645#discussioncomment-18880598), which paraphrases the operator. The operator's verbatim line, for a `[!NOTE]` sidebar, is in session `daac81df` around 12:27Z.
2. **macOS fonts hid a 1px defect that Linux CI found.** The hidden measuring cells kept the 1px right border that a region's last column drops (`neo-last-column`). Under Arial metrics, which Linux CI's fallback font shares, record 4 wrapped to three lines hidden and two shown, and CI's test 1 caught it (62 → 43). It passed in every local run on macOS and reproduced only under a font override. After the fix, no row changed under five fonts. Primary: `d209dfc7bc`, #19704's body.
3. **A recycled row took its previous record's height.** The DOM lagged the vdom with no flag set: a view's update waits for in-flight child updates (`VdomLifecycle#updateVdom`) without marking itself. Before the fix, 18 of 20 headless runs ended with the stale height; after it, 0 of 20. Primary: #19692, #19695.
4. **A hidden grid that kept measuring.** A grid under `display:none` retried zero-width measurements. The counter read 267 batches on the old behaviour and zero after @neo-gpt's fold, which pauses until the next layout resumes the work. Primary: [6135355216](https://github.com/neomjs/neo/pull/19688#issuecomment-6135355216).
5. **Measured, not estimated.** Scheduling on the integrated build: 3 runs, 14–16 and 21–23 rows/s, 0 frames over 20 ms, 0 rows visible at the estimate. Primary: the closing review's matrix.

### Honest bounds

- 10k rows, not 100k. Past 2^23 px Chrome rounds scroll offsets to 2 px, and browsers cap element heights at different limits (operator guidance, [6134339160](https://github.com/neomjs/neo/issues/19658#issuecomment-6134339160)). Scaled scrolling past 100k rows is deferred.
- Deferred by the epic: TreeStore, images and components, remote data, uniform or capped N-line modes.
- Residuals: #6858 (`AnimateRows`' pre-existing fixed-height breakage) and #19657 (the Brain-gated tier on every Engine PR).

### Turning points (candidate case studies)

1. **First-match lookup would have overwritten other writers' filters.** An [executed discriminator](https://github.com/neomjs/neo/discussions/19646#discussioncomment-18880470) on D#19646 showed property-first `getFilter` overwriting picker or application predicates in two creation orders. Ownership therefore moved into Collection/Filter as a (role, dataField) identity, with the legacy first match kept for old callers.
2. **Counting without touching the data.** Counts read the whole local population and apply every predicate except the picker's own: no remove/reapply cycle, no hydration, no raw writes. On the 100k `bigData` store, sampled raw keys and values stay unchanged through open, search and recount.
3. **Review caught what green tests passed.** In Round 1, one toggle on an open menu ran two full count passes, which the PR's own receipt prices at 85–155 ms each at 100k. Numbers also sorted `1, 10, 100, 2, 20`, and dates by weekday name. Both were fixed before the Round 2 approval.
4. **War-story candidate: a test that drove someone else's app.** During #19671's run, a fresh page's `connectToApp` bound an older same-name session, so the test wrote into another page's grid. The fixture's identity wait never polled, because Playwright treats an async predicate's Promise as truthy. #19713 tracks the fixture repair (PR #19715, open at deposit time); D#18775 records why the planned dispatch adapter removes the class.

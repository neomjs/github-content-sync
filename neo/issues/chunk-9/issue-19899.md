# A window that leaves mid theme-load can park every vdom update

## Context

This is mode B of the quarantined Workstation film tour (5 arms, 4 of them the viewer-driven arm; same runs as mode A). It fails with `journey hop 4 (target): the target did not take the drag…`: claim, preview and indicators all agree, but the cross-window proxy reads `settled:false`. The viewer arm's quarantine reason ("stops at journey hop 3") is therefore mostly wrong.

## The Problem (inferred, ~45 %)

`App#insertThemeFiles` decrements `countLoadingThemeFiles` only in `.then` (`src/worker/App.mjs` ~484–492). A reply from a window that has departed either rejects (`src/worker/Base.mjs` ~527) or never arrives, so the counter can stay above zero. The counter is shared across the whole App worker and parks every `initVnode(true)` and `updateVdom` (`src/mixin/VdomLifecycle.mjs` ~766, ~1362). The header proxy mounts that way (`src/dashboard/dock/window/VesselProxyEmbodiment.mjs` ~274–287), and the snapshot's `ready` requires `settled` (`apps/workstation/view/CrossWindowGestureSnapshot.mjs` ~121). The journey's short-lived vessels (see the mode-A ticket) supply the departing windows.

## The Fix

1. First, confirm: put `countLoadingThemeFiles` in the hop-4 diag. A 0 there falsifies this cause.
2. Decrement in `finally`, and preferably count per window, so one departed window cannot park another's updates.

## Acceptance Criteria

- [ ] AC-1: The hop diag reports the theme-file counter.
- [ ] AC-2: A unit arm: a theme-file reply that rejects (departed window) leaves the counter at 0 and does not park a later `updateVdom`; red before and green after.
- [ ] AC-3: The viewer film arm passes on every attempt across ≥ 5 hosted runs, and its quarantine entry is gone (together with mode A's fix).

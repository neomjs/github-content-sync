# PR CI waits for runners far longer than it runs

## Context

The operator, 19 Nov: "if we need to wait half an hour for one PR, this is severely slowing our team down." Measured on #21450's push at `364b5fc79e` (23:24:54Z), from each job's created, started and completed times in the Actions API:

| Job | Waited for a runner | Ran |
|---|---|---|
| E2E "Classify test scope" (created 3m48s after the run) | 5m16s | 16 s |
| 15 e2e shards | 1–16 min, two still queued at 23:50 | ~4 min each |
| Engine Tests classify | 5m38s | 3 s |
| unit | 4m14s | 3m41s |
| PR Baseline: guards, PR baseline, Skills materialized | 10–14 min | 20–90 s each |

At 23:50Z the organisation's pool of 20 runners also served neo-agent-brain's 28 running and 28 queued runs (neomjs/neo-agent-brain has its own ticket, filed alongside).

## The Problem

Most of a PR's CI wall time is spent waiting for a runner, and every fail-fast stage queues again. An examples PR starts about 30 jobs, 15 of them e2e shards that each pay their own setup, and the separate classify job puts one more full queue wait on the e2e path.

## The Architectural Reality

Design authority: n/a. This changes how jobs are packed, not what CI checks.

- `test-e2e.yml` and `test.yml` each run "Classify test scope" as their own job before the shards and units; it does seconds of work. It also decides what starts at all. Over 40 completed PR runs of `E2E (engine tier)` it ruled the tier out 10 times, sized it to 2 or 7 shards 9 times, and ran all 15 nineteen times: about 257 shard starts saved for 40 classify runners (issuecomment-7047158369).
- Shards are sized so that none passes a time ceiling (#21493, #21287), which is right on an idle pool and costs one setup per shard on a saturated one.
- `codeql-analysis.yml` has no `concurrency` group, so a superseded push still runs it (now #21635). `file-size-guard.yml` has none on purpose, because an `edited` re-run would leave a cancelled sibling red on an unchanged head (`#20064`). `test-e2e.yml`, `test.yml`, `build.yml`, `pr-baseline.yml` and `consumer-runtime-build.yml` already cancel in progress.
- #21504 folds the File Size Guard into the shared baseline's guards job: the first of the small jobs to merge.

## The Fix

1. One classification serves both test workflows, where each runs its own today; the tier skip and the matrix sizing stay. A workflow-level `paths-ignore` for files no tier reads would start neither workflow. *(Revised 2026-11-20. The first version removed the classify job, but a shard that classifies itself still takes a runner slot, which costs about five queue slots per push on this pool.)*
2. CodeQL cancels a superseded PR run: #21635.

Moved out of this ticket on 2026-11-20:
- A saturation signal for the shard planner, so a saturated pool gets fewer, longer shards. Where the signal comes from and what it changes is a design question for a Discussion before any ticket.
- Folding the remaining small jobs into one, which is #21504's scope.

**Intake (Grace, owner): accepted with sharpening; measurement contradicts Fix 1.** The body and ACs stay Vega's.

Over the last 40 completed PR runs of `E2E (engine tier)`, the classify job ruled the tier out 10 times, so no shard runner started. It sized the matrix to 2 shards 7 times and to 7 shards twice, and ran all 15 shards nineteen times (2 runs had no shard jobs). Against a static 15-shard matrix, that is about 257 shard starts saved for 40 classify runners: roughly five fewer queue slots per push. Fix 1 gives that back, because a shard that classifies itself still takes a runner slot to learn it has nothing to run. On the saturated pool this ticket measures, the classify job costs latency (one serial queue wait), not capacity; trading it for about five extra slots per push would lengthen every repository's waits.

Proposed sharpening:
1. **Keep classify's tier skip and matrix sizing, and cut its cost elsewhere.** `test.yml` and `test-e2e.yml` each run their own classify job on every push, so one classification serving both saves a runner and a queue slot per push. A workflow-level `paths-ignore` for files no tier reads would start neither workflow.
2. **AC-1 as written encodes the contradicted fix.** Proposed AC-1: one classify job per push serves both test workflows, and a tier it rules out still starts no runner (receipt: jobs API counts before and after).
3. **Fix 2 needs a saturation signal before the planner can weigh setup cost**, either the queue length from the Actions API or a fixed rebalancing against the six-minute ceiling. That design question deserves its own leaf.
4. **AC-2 is independent and small**, so I can ship it first as its own leaf. Its concurrency group has to key on the PR rather than the ref, so successive pushes to `dev` don't cancel each other's CodeQL analysis.

Fix 4 continues #21504, which still waits on the decision recorded there.

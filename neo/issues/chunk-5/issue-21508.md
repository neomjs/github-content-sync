# Taskbar clock spec fails when its two clock reads straddle a millisecond

Please comment to claim before starting; check current assignees and linked PRs.

## Context

The unit spec `test/playwright/unit/desktop/Container.spec.mjs` checks that the web desktop's taskbar clock waits until the next full minute. On 2026-11-19 it failed once on CI, on a pull request that doesn't touch the desktop at all:

```
Error: the wait ends on a full minute
expect(received).toBeLessThan(expected)
Expected: < 50
Received:   59999
```

It passed on retry. The clock itself is correct; the assertion is not.

## The Problem

The test reads the time twice, a moment apart:

1. The spec takes `started = Date.now()`.
2. `Taskbar#runClock()` (`src/desktop/Taskbar.mjs`) then takes its own `now = new Date()` and waits `60000 - now.getSeconds() * 1000 - now.getMilliseconds()` milliseconds, which is exactly the time left until the next full minute *as of `now`*.

The spec checks `(started + delay) % 60000 < 50`. When both reads land in the same millisecond, that is `0`. When the clock reads one millisecond later than the spec, `started + delay` ends 1 ms *before* the full minute, and the remainder wraps around to `59999`. The wait is still correct (it ends on the minute as measured by the clock), but the assertion only accepts a small offset *after* the minute, never one *before* it.

## The Architectural Reality

- `src/desktop/Taskbar.mjs`, `runClock()`: the loop that shows the time and then waits for the next minute. Its JSDoc says "each wait ends on the next full minute". This ticket keeps that behavior.
- `test/playwright/unit/desktop/Container.spec.mjs`, the test `the taskbar clock shows the time over the date, and its wait ends on the next full minute` (around line 302). It stubs `taskbar.timeout` to record the delay instead of waiting.

## The Fix

Change only the assertion, so that it measures the distance to the *nearest* full minute, on either side:

```js
const offset = (started + delay) % 60000;

expect(Math.min(offset, 60000 - offset), 'the wait ends on a full minute').toBeLessThan(50)
```

Keep the 50 ms tolerance. A real mistake in the clock, such as forgetting the milliseconds, would be off by up to a second and still fail.

## Acceptance Criteria

- [ ] The assertion in that test accepts a wait that ends up to 50 ms before or after a full minute, and nothing further away.
- [ ] `src/desktop/Taskbar.mjs` is unchanged.
- [ ] `npx playwright test -c test/playwright/playwright.config.unit.mjs test/playwright/unit/desktop/Container.spec.mjs` passes locally. The PR says so.
- [ ] One way to convince yourself (optional, don't commit it): temporarily make the clock's wait 1 ms shorter and check that the new assertion still passes, then make it 1 s shorter and check that it fails.

## Out of Scope

- Changing how the clock computes its wait, or stubbing `Date` globally in the spec.
- Other flaky specs, such as `test/playwright/unit/tooltip/Departure.spec.mjs`. They have their own causes.

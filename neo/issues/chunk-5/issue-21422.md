# Dialog title-bar controls show no hover state in the neo themes

Please comment to claim before starting; check current assignees and linked PRs.

## Context

In the neo-light and neo-dark themes, a dialog's title-bar controls (minimize, maximize and close) look exactly the same under the pointer as at rest. Nothing tells the user that a control is interactive, or which one the pointer is on, before they click.

Measured on `dev` at `b5f112239e`: `examples/desktop/basic` uses neo-dark. Opening an app there by double-clicking its icon opens a window. Its close control computes `background-color: rgba(0, 0, 0, 0)` and a glyph `color` of `rgba(226, 232, 240, 0.72)`, both at rest and hovered. Minimize and maximize behave the same way.

## The Problem

Every window and dialog built on `Neo.dialog.Base` has these controls: the web desktop's app windows, `examples/dialog` and the dashboard's dialogs. Every other neo-themed button changes its colour on hover (the `--button-*-hover` tokens in `resources/css/theme-neo-*/button/Base.css`). These three are the exception, and they sit in the most-clicked spot of a window.

## The Architectural Reality

- `resources/css/theme-neo-dark/dialog/Base.css` and `resources/css/theme-neo-light/dialog/Base.css` contain a structural rule at theme-root weight: `:root .neo-theme-neo-* .neo-dialog .neo-header-toolbar .neo-button {background-color: transparent; …}`. Its specificity is (0,5,0), so it outranks the button's own `.neo-button:hover` at (0,2,0) in `resources/css/src/button/Base.css`. The files' header comment explains why that weight is kept for now.
- `resources/css/src/dialog/Base.css:99` gives the glyph `color: var(--dialog-icon-color)`. That also outranks the button's hover glyph colour.
- **Design authority:** the button family gives every button a hover state through its `--button-*-hover` tokens, and this rule takes it away from these controls only. WCAG 2.2 SC 1.4.11 asks for 3:1 for the visual information that identifies a control's state.

## The Fix

1. **Add hover tokens** for the title bar's controls, for example `--dialog-header-button-background-color-hover` and `--dialog-icon-color-hover`. In the neo themes, pick values that reach 3:1 against the title bar.
2. **Declare them in every theme's `dialog/Base.css`**: the classic light, dark and cyberpunk themes too, with values that keep their current look. Per #18141 and #18145, a token that only some themes declare leaks across a nested theme boundary.
3. **Apply them in `resources/css/src/dialog/Base.css`** with a `:hover` rule on the title bar's buttons that outranks the theme's transparent rule. Selectors belong in `src/`; theme files declare values only (#18145).
4. **Optional:** many desktops tint the close control red on hover. If you take that, use a token for it, so each theme chooses its own red.

To measure, open `examples/desktop/basic`, double-click an app to open its window and hover the close control. Your browser's dev tools show the computed `background-color` and the glyph's `color`.

## Acceptance Criteria

- [ ] In neo-light and neo-dark, hovering a dialog's minimize, maximize or close control changes its computed background or glyph colour from the rest state.
- [ ] The hovered state measures at least 3:1 against the title bar behind it.
- [ ] The classic themes look as they did, at rest and on hover.
- [ ] The pull request shows a title bar at rest and with a control hovered, in both neo themes.

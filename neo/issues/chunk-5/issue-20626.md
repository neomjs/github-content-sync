# A grouped header's drag proxy loses its header styling and drifts out of its group

## Context

The operator's manual test of `examples/grid/headerGroups` (recording of 2026-11-08 23:57, 19 s) blocks the 13.4 release. Frames from it show three defects in the leaf-header drag:
- **The proxy's header loses its styling, sometimes.** Dragging `Oct` (Q4) shows a proxy whose header cell is white, with no header background and no "Oct" text. The body cells come with it. A later drag of `Sep` shows a proxy with the blue header and its text. So it is intermittent.
- **The proxy drifts out of its group.** Dragging `Sep` (Q3), the proxy travels over Q4's columns. The drop still lands inside Q3 (Jul | Sep | Aug afterwards), so what the user sees contradicts what the zone will do.
- **A group cell selects its text.** Pressing and dragging on the "Q3" group cell highlights "Q3" as a text selection.

## The Problem

Group membership is a hard rule of the reorder: a leaf never leaves its group. The proxy doesn't show that rule. It floats wherever the pointer goes, then snaps back, which reads as a broken drop. The half-styled proxy and the text selection make the demo look unfinished.

## The Architectural Reality

- Design authority: #20379, The Fix step 4: "Header drag can't move a leaf out of its group, and it can't move an ungrouped column into a group." The restriction is intended. Making the proxy honor it, and keeping the proxy's look, calls no decided behavior wrong.
- `src/draggable/grid/header/toolbar/SortZone.mjs#createDragProxy` builds the proxy's header part as `{...config.vdom, cls: ['neo-grid-header-toolbar', 'neo-toolbar']}` from the base zone's clone of the dragged button. Whether the clone keeps the button's own node, classes and text decides the header's look.
- `Neo.draggable.container.SortZone` already bounds a drag with `useItemSortBoundary` / `getSortBoundaryRect`. A grouped leaf's natural boundary is its group's first-to-last leaf extent.

## The Fix

- The proxy's header keeps the dragged button's classes and text on every drag. The run-time cause of the intermittent loss is found first, not guessed.
- While a grouped leaf drags, the proxy is clamped to its group's extent, so the refusal is visible as an edge. An ungrouped column's proxy keeps today's range.
- Group cells set `user-select: none`.

Decision Record impact: none.

## Acceptance Criteria

- [ ] Dragging any leaf, including after a horizontal scroll, shows the proxy's header button inside the proxy with its text (e2e on `examples/grid/headerGroups`: the button's left edge meets the proxy toolbar's, over repeated drags. A colour check alone passes a header shifted out of view, per the reproduction on this ticket).
- [ ] A grouped leaf's proxy never leaves its group's horizontal extent during the drag (e2e: drag Sep toward Q4; the proxy's right edge stays at or before Q3's right edge).
- ~~Pressing and dragging on a group cell selects no text.~~ Ships with #20630 (#20627), which restyles the group cells as drag handles and carries `user-select: none`.
- [ ] The operator's manual pass on `examples/grid/headerGroups` accepts the drag (Post-Merge Validation is not enough for a release blocker: reviewed in the PR).

## Out of Scope

- Dragging a whole group: its own ticket.
- Moving a leaf into another group, which stays refused (#20379). If the operator wants it, that rewrites a leaf's group and changes the data, so it is a separate decision.

Independent reproduction on `c29035cd9cd80716209095e0bb750b9fbb499be7`, system Chrome, default light theme, `examples/grid/headerGroups`, viewport **1991 × 1000**, horizontal scroll **230px**.

The apparent missing background is a **misplaced cloned header**, not a missing palette value. The source button was correctly positioned immediately before the gesture. During a bad Oct drag:

| Surface | x / y | Header background | Text |
|---|---|---|---|
| Proxy toolbar | 1562 / 34 | white | contains Oct |
| Cloned button | 3013 / 67 | `rgb(93, 131, 167)` | Oct |
| Clone after removing only inline `left` / `top` in the diagnostic page | 1562 / 34 | unchanged blue | Oct |

The bad clone carries `left:1451px; top:33px`. Nov also reproduces with `left:1601px`. Removing those two offsets restores the visible header without changing classes, background, text, opacity or visibility. This is a diagnostic intervention, not a proposed production patch.

Reproduction sequence:
1. Wait for the header group geometry; scroll 230px and wait until the actual Oct header has moved by that amount.
2. For **Oct, Sep, Nov, Oct, Sep, Oct**, press the header center, move +25px in four pointer steps, then +260px and +35px vertically in twenty steps.
3. Inspect the proxy while still pressed, then Escape, mouse-up, and wait for proxy removal and the toolbar to leave its dragging state.
4. Bad header offsets occurred on **3/6** gestures: Nov and the later two Oct drags. Adding **500ms between gestures** still produced the same 3/6 failures. No page errors occurred.
5. Waiting for the actual proxy header before the long pointer move removed the offset failures in an exploratory control; that run had an initial scroll/hit-test mismatch, so it is a lead rather than a clean causal proof.

The operator page's retained drag trace also shows an Oct switch and first move with `offsetX=0`, followed by moves with `offsetX=73`. This supports a startup-ordering hypothesis: `container.SortZone` exposes `itemRects` before awaiting `dragStart`/proxy creation and coordinate normalization; `onDragMove` can see the preceding gesture's retained `boundaryContainerRect`; `updateItem` writes the raw rect's left/top into the source VDOM before the proxy snapshot. The owner should prove/falsify that sequence in the repair.

**Acceptance refinement:** background equality plus `textContent` equality passes the broken state. Also assert that the cloned button's rectangle overlaps its proxy header slot at the expected local origin, and that the text/background are visibly painted there. Keep repeated drags and horizontal scroll in the witness. This finding is separate from proxy clamping and whole-group drag; release acceptance remains open.

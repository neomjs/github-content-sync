# Examples PRs collide on three shared catalog data files

## Context

On 19 Nov five open examples PRs touched the same catalog files: #21524 (`examples.json`, `example-captures.json`, `seo.json` and the catalog spec), #21522 (`example-captures.json`), #21515 (`examples.json`, the spec), #21479 and #21450 (all four). Between 17 and 19 Nov, 45 commits on `dev` touched `examples.json`. Each merge made the others conflict, each author merged `dev` in again, each push re-ran the full CI (about 30 jobs on the org's 20 runners), and the next merge started over. The operator: "i merge one, 4 go stale again. in parallel new PRs get in. cycle continues."

## The Problem

A PR that adds or renews one group's examples edits files that every other group's PR edits too: one array of all records (`examples.json`), one `families` line plus one recipe array (`example-captures.json`), and the generated `seo.json`, which examples PRs commit. #21523 already gives the catalog spec's count table one group per line, so only neighbouring groups collide there (98 → 20 of 210 group pairs). The three data files are still one shared surface, so different records in one file still conflict textually.

## The Architectural Reality

Design authority: n/a. This changes where the data lives, not what the catalog, the captures or the SEO output contain.

- `apps/portal/resources/data/examples.json` is read by `apps/portal/view/examples/MainContainer.mjs`, `buildScripts/docs/captureExamples.mjs`, `buildScripts/docs/seo/generate.mjs` with `seoJson.mjs`, and `buildScripts/util/moveDataTransforms.mjs`.
- `apps/portal/resources/data/example-captures.json` is read by `buildScripts/docs/captureExamples.mjs`.
- `apps/portal/resources/data/seo.json` is read by `Portal.service.Seo` (`apps/portal/service/Seo.mjs`), written by `buildScripts/docs/seo/generate.mjs` (also through `rebuildContentIndexesAndSeo.mjs`) and checked by `buildScripts/docs/seo/verify.mjs`.
- `test/playwright/unit/apps/portal/view/examples/MainContainerController.spec.mjs` keeps one count literal per group (#21484) on one line per group (#21523), plus one `recordCount`.

## The Fix

A direction; the PR settles the exact layout:

- Records per group (for example `apps/portal/resources/data/examples/<group>.json`), concatenated in group order by one loader that the Portal and the build scripts share.
- Capture recipes per family beside them, with `families` derived from the files that exist rather than written on one line.
- Examples PRs stop committing `seo.json`: it is generated where it is consumed (the build or the data-sync pipeline), or split per group like the records.

## Acceptance Criteria

- [ ] AC-1: #21520's pairwise rehearsal, extended to one throwaway commit per group that adds a record, a recipe and an SEO entry, merges all 210 cross-group pairs with `git merge-tree` and reports 0 conflicting pairs.
- [ ] AC-2: The Portal's catalog, the capture plan and the generated SEO output are identical before and after the split: records, order, recipes, routes.
- [ ] AC-3: An examples PR for one group edits no file that another group's PR edits, apart from the catalog spec's `recordCount` unless that derives from the data too.

## Out of Scope

- What any record, recipe or SEO entry says.
- The catalog's views.

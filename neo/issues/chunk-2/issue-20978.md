# dist/esm: a Main helper's dynamic import can still load the source Engine

## Context

Found while reviewing PR #20973 (#20963). With #20973, the ESM build refuses a declared Main-root module whose static edge reaches a helper the build does not emit, when that helper's static graph reaches the Engine. A dynamic import is no discovery edge (`createEsmBuildPlan()`: "Only imports and re-exports are discovery edges; dynamic imports retain their existing runtime admission"), so this package still builds and loads the source Engine:

- `node_modules/widget/package.json`: `neo: {mainAddons: ['main']}`
- `node_modules/widget/main/Addon.mjs`: `export {load} from '../outside/Helper.mjs';`
- `node_modules/widget/outside/Helper.mjs`: `export const load = () => import('../../neo.mjs/src/core/Base.mjs');`

Probe: the stub-engine workspace of `test/playwright/unit/buildScripts/esmWorkspaceBuild.spec.mjs`, built with `buildScripts/build/esmodules.mjs` on `dev` `05390906ea` and on #20973's head `93b004ed3d`. Both exit 0, and `(await Addon.load()).default` comes from `<workspace>/node_modules/neo.mjs/src/core/Base.mjs`, not from `dist/esm/src/core/Base.mjs`.

## The Problem

A Main helper outside every declared root has no runtime admission in `dist/esm`: the emitted addon imports it from its host location, and its dynamic import resolves from there. That is the second Engine graph #20963 closes for static edges.

## The Architectural Reality

- `staticModuleSpecifiers()` (`buildScripts/util/esmDistTransforms.mjs`) returns static imports and re-exports only. The same module already reads literal `import()` specifiers for its rewrite, and documents why a computed one names no module.
- #20973 classifies a Main root's edges over the module graph built from those static edges, after admission, without widening it.
- `learn/guides/fundamentals/MainThreadAddons.md` states the package-authoring rule this enforces.

## The Fix

A direction for the plan's owner: classify the literal dynamic-import specifiers of modules reached from a declared Main root, in the Main check only. Nothing is admitted. A computed specifier (`import(base + name)`) stays out, since it names no module.

## Acceptance Criteria

- [ ] The probe above fails the ESM build, naming the helper's importing edge and the `neo.mainAddons` remedy.
- [ ] A helper whose literal dynamic import reaches only ordinary modules keeps its host path.
- [ ] A computed dynamic import changes nothing.

## Out of Scope

App-side dynamic imports; admitting outside-root files; runtime `loadModule` (#20778).

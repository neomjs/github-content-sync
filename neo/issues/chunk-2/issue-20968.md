# A Turbo Mode store takes a batch of row edits as one change

## Context

A live grid over a large Turbo Mode store (`autoInitRecords: false`) is fed by a producer that edits many rows per tick. Today every edit goes through a record. `Store#get(key)` hydrates the raw row (`src/data/Store.mjs:876–888`), and `record.set()` fires `recordChange` for that row. The store re-applies filters and sorters per record (`onRecordChange`, `:1658`), and the grid's Body handles each event on its own (`src/grid/Body.mjs:644–645`).

So a producer that edits N rows per tick pays N events and N hydrations per tick. The records stay for the session: touching every row of a 100,000-row store hydrates all of them.

## The Problem

Neither cost buys anything when the edits land together. A grid renders only its visible rows, a few dozen. Turbo Mode exists so that raw rows stay raw until something needs a record, and per-row edits defeat it.

## The Architectural Reality

- Turbo Mode: `Neo.data.Store` keeps raw objects and sorts and filters them (`Store.mjs:34–65`). `get()` and `getAt()` hydrate (`:876–897`).
- `onRecordChange` (`:1658`) re-filters and re-sorts per changed record before it fires `recordChange`.
- A record can change silently (`setSilent`, `src/data/RecordFactory.mjs`), which fires nothing.
- `Neo.grid.Body` follows `load` and `recordChange` (`Body.mjs:644–645`). Its `createViewData(false, true)` refreshes the visible rows even when record identity is stable. `onStoreLoad` (`:1570`) wraps that call but also scrolls the view to the top 50 ms later.
- Prior art (March 2026): a silent update of mounted records left stale rows, because nothing told the grid to refresh. A batch must always end in one refresh.
- Design authority: n/a: this adds a path and calls no existing behavior wrong.

## The Fix

1. `Neo.data.Store` takes a batch of row edits, `[{key, values}]`; the method name is the implementer's.
   - Raw rows are written in place, without hydrating them.
   - Rows that are already records are updated silently through their records.
   - Filters and sorters are reapplied once.
   - One batch event names the changed keys.
2. `Neo.grid.Body` follows that event with a handler that calls `createViewData(false, true)`. The visible rows re-render once, without `onStoreLoad`'s scroll to the top.
3. A subclass can extend the batch. A grouping store, for example, applies each row's contribution and flushes its groups once.

## Acceptance Criteria

- [ ] A 1,000-row batch on a Turbo Mode store fires one batch event and no `recordChange` (unit).
- [ ] The batch hydrates no row that was not already a record (unit: hydration count before and after).
- [ ] Already-hydrated rows carry the new values, and a filter or sorter the batch affects is applied once (unit).
- [ ] A grid over the store shows the changed visible rows after one batch, and its scroll position stays (e2e).
- [ ] Existing store and grid specs stay green.

# Workstation panes keep the old theme after a layout change

## Context

At Engine `70b443e524`, Workstation retains a pane through a public dock split, but a later application theme change leaves that pane's logical theme behind.

A source-level replay with the real Workstation class and standard unit setup uses this sequence:

1. Construct dark; call `setWorkspaceTheme('neo-theme-neo-light')`.
2. Retain `paneCache.scale`.
3. Apply `splitNode` for `security` below `scale-tabs`, then await the document projection and `refreshPromise`.
4. Call `setWorkspaceTheme('neo-theme-neo-dark')`.

The cached ScalePane remains the same instance. Workspace and its projected ancestors become dark; the retained BodyContainer and ScalePane still report light through `theme` / `getTheme()`, with no local light CSS carrier. A component consuming its resolved theme can disagree with the inherited document styling.

## The Problem

The app action updates Workspace and the same-app main views. General container propagation preserves child themes that differ from the parent's replaced value. Reconciliation can retain a light body beneath a rebuilt tab whose prior theme was null; that body is then treated as a different scope, and its cached panes stay light.

CSS-only panes can conceal the mismatch because they inherit their ancestor's new CSS values. A pane that computes presentation from `getTheme()` still reads the old value.

## The Architectural Reality

Design authority: `apps/workstation/view/Workspace.mjs#setWorkspaceTheme` promises “Applies the theme to every render target of this app”; `src/component/Base.mjs#getTheme` supplies the theme consumed by components.

- Workstation owns `paneCache`, creates/resolves its panes and destroys that cache on teardown.
- `setWorkspaceTheme` is this app's existing theme action and already fans out to `Neo.appsByName[appName]`.
- `container.Base#afterSetTheme` intentionally preserves differing child scopes; this repair must not replace that with an unconditional subtree stamp.
- No renderer or theme token needs a new authority.

## The Fix

Extend the existing app action to include its retained pane population. A pane still using the replaced application theme, or no own theme, follows the new application theme. A different explicit pane theme remains its own.

Use the existing cache/instance ownership and keep the same-app main-view fanout. Do not recreate panes, add a theme registry, or install a color-consumer workaround.

## Acceptance Criteria

- [ ] The real Workspace dark → light → dock split/projection → dark replay leaves the same cached ScalePane on dark, and `getTheme()` agrees.
- [ ] A cached pane with a different explicit theme is unchanged; a live pane not currently presented follows the application when it has no own theme.
- [ ] Same-app render targets still follow the action, and unrelated app names remain untouched.
- [ ] No pane is recreated, no theme registry or renderer-side workaround is introduced, and the owning Workstation unit suite plus current-head required CI pass.

## Out of Scope

Generic container inheritance semantics; extracting app overrides into new themes; palette design; renderer color caching; any package's own styling.

## Avoided Traps

- Clearing a renderer's cache: its next `getTheme()` would still read light.
- Recreating panes: loses live identity to repair an app-owned propagation step.
- Unconditionally retheming all panes: overwrites different explicit scopes.
- Changing generic container inheritance for one app action.

# Emitted ESM package classes can load a second Engine graph

## Context

Leaf of #20667: an emitted workspace and a statically imported package class must use the same Engine module graph.

At Engine `1b12232214a5b36bec6ca0255c2b93b5ef51e3ed`, a bounded Node artifact probe using the actual ESM rewrite, template-processing and minification stages reaches two CoreBase module URLs:

- the emitted workspace class reaches `/dist/esm/src/core/Base.mjs`;
- its statically imported installed package class reaches `/node_modules/neo.mjs/src/core/Base.mjs`.

This is artifact-path evidence. No full application build or browser execution is claimed. The existing browser negative control already demonstrates that a page can mount despite a split Engine graph, so mount success is not an adequate identity oracle.

## The Problem

The workspace manifest names `neo.mjs` and `@fixture/widgets` as dependencies. The package uses ordinary static imports; no Main-addon or runtime-worker opt-in is involved. A minimal generic reproduction has this installed class:

```js
// node_modules/@fixture/widgets/src/Widget.mjs
import Base from '../../../neo.mjs/src/core/Base.mjs';
export default class Widget extends Base {}
```

The workspace imports both the Engine and that package statically:

```js
// apps/probe/view/Viewport.mjs
import Base from '../../../node_modules/neo.mjs/src/core/Base.mjs';
import Widget from '../../../node_modules/@fixture/widgets/src/Widget.mjs';
export default class Viewport extends Base {
    static widget = Widget
}
```

The ESM transform correctly changes the Viewport's Engine import to `../../../src/core/Base.mjs`. Its package import instead becomes `../../../../../node_modules/@fixture/widgets/src/Widget.mjs`, which resolves back to the source package outside the emitted tree. That package's unchanged Engine import then returns to the source Engine.

The direct import-existence check sees an existing package file. It does not establish the transitive Engine identity of the package's static closure. The package needs no runtime `loadModule()` call or Main addon to expose the problem.

Controls from the artifact probe:

- the source-layout workspace and package resolve to one source Engine;
- a separately declared Main addon is correctly rebased to the emitted Engine;
- the emitted Viewport's direct-import check reports no failures while the transitive paths still reach two CoreBase URLs.

## The Architectural Reality

Source anchors at `1b12232214a5b36bec6ca0255c2b93b5ef51e3ed`:

- `buildScripts/build/esmodules.mjs:39–42` selects workspace/Engine source roots plus dependency roots declared by `neo.mainAddons`; `:94–105` runs the shared rewrite/template/minify stages.
- `buildScripts/util/esmDistTransforms.mjs:100–107` sends ordinary third-party imports back to host `node_modules`.
- `rewriteMainAddonImports()` at `:124–162` rebases declared Main-addon modules onto the emitted Engine; ordinary App/package modules take the preceding generic transform.
- `resolveSourceRoots()` at `:233–262` adds workspace-owned roots. It does not currently discover a package's statically imported Engine-bearing graph.
- `findUnresolvableImports()` at `:488–523` validates the supplied emitted import records. A source-package target that exists does not reveal its transitive Engine edge there.
- `test/playwright/unit/buildScripts/esmWorkspaceBuild.spec.mjs` owns actual emitted-tree integration coverage; `esmDistTransforms.spec.mjs` owns the pure transforms.
- `test/playwright/e2e/core/DistEsmWorkspaceBoot.spec.mjs:452–467` demonstrates that an Engine-identity mutation can still mount and must be caught through module identity evidence.

Design authority: the existing `findUnresolvableImports()` contract explicitly rejects a second Engine module graph, and the existing browser mutation arm proves why identity is independent of successful mounting. This leaf extends that protection through statically imported installed package classes. It does not declare all third-party source imports invalid.

## The Fix

Keep the repair in ESM artifact discovery and import rebasing.

1. Add the generic package-class reproduction to the existing workspace-build fixture and record its pre-change identity failure.
2. Discover the transitive static import/re-export closure. For an installed package whose reachable graph integrates the Engine, emit its reachable package modules—including local helpers—under `dist/esm/node_modules/<package>/...`, preserving the logical package-relative path. Rebase package-local, inter-package and Engine edges through one finite source-to-output map, including the importing workspace edges. A direct Engine import is not required in every copied helper.
3. Preserve unrelated dependencies and the existing external treatment of ordinary packages that do not lead back to the Engine. Do not scan/copy every dependency tree or widen worker runtime contexts.
4. Make the build's identity validation cover the relevant transitive package edges. A package source fallback must not silently reintroduce the source Engine.
5. Review the shared `esmDistTransforms.mjs` seam with the owner of #20778 before implementation. Reuse one consistent destination map where appropriate; do not add a competing runtime package-path protocol.

Static imports and re-exports already declare reachability: do not reuse `neo.mainAddons`, require `neo.workerModules`, or introduce a new opt-in key for this static graph. This is a bounded implementation direction. The PR must explain its graph/admission rule and preserve the controls below. No new host option or package-specific naming rule is required by this leaf.

## Out of Scope

## Avoided Traps

- Redirecting only the workspace's import while leaving the package's Engine imports unchanged.
- Adding a private/vendor scope to an import filter or copying all of `node_modules`.
- Declaring App component trees as Main-addon roots merely to reuse their special rewrite.
- Weakening the one-Engine oracle to file existence, successful mounting or namespace arbitration.
- Calling a source-worker/compiled-Main test a complete compiled-App proof.
- Presenting a staged local package-layout probe as successful npm peer resolution or released-engine qualification.

- The destination you propose, `dist/esm/node_modules/<package>/<package-relative path>`, already exists:
  - `esmodules.mjs:134` writes a declared Main root there, since only Engine folders are flattened to `dist/esm/src`;
  - an emitted Main loads a package addon from there (`import(`../node_modules/${modulePath}.mjs`)`, `Main.mjs:502`).

  So the map generalizes an existing destination rather than adding a second one.

**Boundary condition: the Canvas worker's package path has no ESM layout yet.**
- `Canvas#loadModule` resolves `node_modules/<package>/<path>` as `../../../<package>/<path>` from the worker file. That fits the installed source layout.
- In a workspace's `dist/esm`, the worker sits in `dist/esm/src/worker/`, so the same template points at `dist/<package>/…`.
- Unlike `Main.mjs:500`, the worker has no layout switch. `esmodules.mjs` admits only `mainAddons` roots, never `canvasModules`, and neither ESM spec declares `neo.canvasModules`.

This comes from reading the code; I have not run the artifact. It is my seam, so I'll falsify it with an artifact probe. If it holds, it becomes a separate leaf that emits declared Canvas roots through your map, and #20863 does not widen.

**To make the map structurally sound:** one function should own the step from source module to emitted path for every admission: your static closure, declared Main roots, and later Canvas roots. The Main-root copy and `rewriteMainAddonImports` would then go through it. Otherwise a package that a workspace class imports statically and that also declares a Main addon gets written to the same destination by two different rewrites, and the last writer wins.

**AC implication:** cover that overlap in the identity check. The fixture is a package that a workspace class imports statically and that also declares a Main addon. Each of its modules is emitted once, and every Engine edge reaches the emitted CoreBase.

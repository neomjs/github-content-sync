# The guide names each way to take part, and the chooser routes it

## Context

`CONTRIBUTING.md` answers "where do I start with code" since #20803: the two curated labels, the claim, the three-day window. For every other way to take part it still carries three lines from an earlier time (`CONTRIBUTING.md:101–107` and `:125–127` on `dev` at `1a6e515c72`): an idea and a bug both go to the issue tracker, and the reader waits for approval.

Three things no longer match how the project works:

1. **Ideas are shaped in Discussions here.** The maintainers' own design work runs in the [Ideas category](https://github.com/neomjs/neo/discussions/categories/ideas) and becomes a ticket once it has settled. The guide sends an outside idea to the issue tracker instead, and `.github/ISSUE_TEMPLATE/feature_request.md` invites it there.
2. **The bug report asks the wrong questions.** `.github/ISSUE_TEMPLATE/bug_report.md` is GitHub's default text: a smartphone block, "Go to '...'", "Click on '....'". It never asks which example or command was run, which Neo.mjs version, or for a failing test.
3. **The two curated labels carry GitHub's default descriptions.** `help wanted` says "Extra attention is needed" and `good first issue` says "Good for newcomers" (`gh label list --repo neomjs/neo`). Neither is what the label means in this repository.

What the labels mean here (tobiu, 2026-11-13): maintainers can resolve every curated ticket themselves. A curated ticket is work the team offers, with everything needed in the ticket, because contributing is the fastest way to get to know the engine. "Help accepted" is the closer reading of `help wanted`.

## The Problem

Someone who found a bug, has an idea, or wants to join a design conversation finds no door that says what to do and what happens next. A coding agent reads the guide literally and files an idea as an issue. The label a contributor hovers over says the project needs extra attention on the ticket, which is not why it is labelled.

## The Architectural Reality

- `CONTRIBUTING.md` on `dev`: section "What you can do to help", item 2 ("Use the issues tracker", lines 101–107) and item 3.2 (lines 125–127). Lines 117–121 introduce the two labels.
- `.github/ISSUE_TEMPLATE/`: `bug_report.md` (front matter `labels: bug`) and `feature_request.md` (`labels: enhancement`). There is no `config.yml`, so the chooser shows both templates and a blank issue.
- Discussion categories on `neomjs/neo`: General, Ideas, Polls, Q&A, Show and tell.
- `npm run check-relative-links` (`buildScripts/util/check-relative-links.mjs`, spec `test/playwright/unit/buildScripts/checkRelativeLinks.spec.mjs`) checks the relative links of `CONTRIBUTING.md` against tracked files. The guide addresses the issues tab as `../../issues`, which the script accepts.
- The claim responder (`.github/workflows/claim-responder.yml`) answers on issues that carry a curated label. A fresh bug report carries `bug` only, so a claim assigns nobody there until a maintainer adds the curated labels.

## The Fix

**1. `CONTRIBUTING.md`: one table of doors.** Replace item 2 ("Use the issues tracker") with a section "Ways to take part" that holds this table, and keep item 3 for code:

| You … | Do this | What happens next |
|---|---|---|
| found a bug | open a bug report (the issue chooser's first entry) | a maintainer answers and labels it. If you want to fix it yourself, say so in the report |
| have an idea for a feature | start a Discussion in [Ideas](https://github.com/neomjs/neo/discussions/categories/ideas) | maintainers and contributors shape it there; an idea that has settled becomes a ticket |
| want to join a design conversation | comment on an open Discussion in Ideas | nothing to ask for: design threads are open to everyone |
| have a question | ask in [Q&A](https://github.com/neomjs/neo/discussions/categories/q-a) | |
| want to write code | take a curated issue (item 3) | |
| built something with Neo.mjs | post it in [Show and tell](https://github.com/neomjs/neo/discussions/categories/show-and-tell) | |
| want to talk to someone | join [Discord](https://discord.gg/6p8paPq) or [Slack](https://join.slack.com/t/neomjs/shared_invite/zt-6c50ueeu-3E1~M4T9xkNnb~M_prEEOA) | Discord is the main room and keeps a searchable history; Slack is real-time chat and keeps 90 days |

The last row follows the operator's word of 2026-11-14 that Discord and Slack stay wherever people are sent to reach the project; no contributing guide named them (proposed by `neo-fable-clio`, comment 6879429416). Its two invite links are the README's, under "Community"; the guide and the chooser copy them from there.

Rewrite item 3.2 to agree with the table: a pull request still needs an issue; for a bug the report is that issue; for an idea the Discussion comes first. The existing reply promise ("within 7d max") stays, in one place.

**2. One sentence where the labels are introduced**, after "…whether this is your first pull request or your tenth.":

> Maintainers could resolve these themselves. We leave them open because contributing is the fastest way to get to know the engine, so read `help wanted` as "help accepted".

**3. `.github/ISSUE_TEMPLATE/config.yml`** with `blank_issues_enabled: true` and four `contact_links`: "Idea or feature request" to the Ideas category, "Question" to Q&A, then "Discord" and "Slack" with the README's invite links. Remove `feature_request.md`. The chooser then shows: Bug report, Idea or feature request, Question, Discord, Slack, blank issue.

**4. `bug_report.md`** asks, in this order: what you ran (the example or app, and the command), what you expected, what happened (console output or a screenshot), the Neo.mjs version and the browser, and optionally a failing test under `test/playwright/unit/`. The smartphone and desktop blocks go. The front matter keeps `labels: bug`.

**5. Label descriptions.** They are repository settings, not files, so a maintainer sets them when the pull request merges:

- `good first issue`: `Ready for a contributor: everything needed is in the ticket. No promise that it is small.`
- `help wanted`: `Work the maintainers offer to contributors. Comment on the issue to claim it.`

## Acceptance Criteria

- [ ] `CONTRIBUTING.md` has the "Ways to take part" table with the seven rows above, and every link in it opens the page it names.
- [ ] No sentence in `CONTRIBUTING.md` sends an idea or a feature request to the issue tracker, and item 3.2 agrees with the table.
- [ ] The "help accepted" sentence stands where the labels are introduced.
- [ ] `.github/ISSUE_TEMPLATE/config.yml` exists with the four contact links, and `feature_request.md` is removed. The Discord and Slack links in the guide and in `config.yml` are character for character the README's.
- [ ] `bug_report.md` asks the five things in the order above and keeps `labels: bug`.
- [ ] `npm run check-relative-links` passes.
- [ ] After the merge (a maintainer step; owner: the reviewer of this pull request): both label descriptions are set and `gh label list --repo neomjs/neo` shows them, and the new-issue chooser on `neomjs/neo` shows the six entries.

## Out of Scope

- Renaming or adding labels.
- A section on contributor standing or badges; it follows in its own ticket.
- The pull request template.
- The contributor guides of the other repositories.
- Who is woken when an outside account opens an issue or comments in a Discussion.

## Avoided Traps

- **Renaming `help wanted` to `help accepted`.** The two names are the search key: GitHub's own contribute page (`github.com/neomjs/neo/contribute`) lists `good first issue`, and a coding agent starts from `label:"good first issue" no:assignee`. A renamed label is invisible to both. The honest sentence goes where a person reads it: the description and the guide.
- **Markdown links to `.agents/skills/…` in the guide.** Those paths are materialized by `npm install` and git-ignored, so `check-relative-links` rejects them (#20709). Keep them in code spans.
- **A faster reply promise.** This ticket changes where things go, not how fast we answer.

# SharedCanvas pointer input keeps a stale origin after a pane moves

## Context

A native Chromium witness on Engine `31c5dee502a7107ae4a112695e6e75385554afd6` reproduces incorrect pointer input in the existing public `examples/component/graphScene/` example after a position-only pane move. No production input, sizing or renderer logic was patched; a test-server copy of the example renderer's existing `getStats()` exposed its real inherited `mouse` state.

| Observation | Before translation | After `translateX(80px)` on the outer pane |
| --- | --- | --- |
| Native canvas box | (0,56), 1000×644 | (80,56), 1000×644 |
| Native event `clientX/clientY` | (30,76) | (110,76) |
| Native event `offsetX/offsetY` | (30,20) | (30,20) |
| Actual Canvas Worker `mouse.x/y` | (30,20) | **(110,20)** |
| Cached viewport origin | (0,56) | (0,56) |

The pre-move input control passed. The post-move correctness assertion failed over six observations in three seconds; the one-test run took 10.9 seconds. The server-module hit and a marker read back from the real renderer proved telemetry coverage. This is a position-conversion defect, not an admission failure.

## The Problem

`SharedCanvas.forwardPointer()` subtracts the viewport origin cached by the last size update. Moving a pane without changing its size does not cause a new ResizeObserver notification. A later real pointer therefore carries a current viewport position but is converted using an obsolete origin.

Minimal reproduction:

1. Open the public GraphScene example and wait for its canvas to draw and for its initial measurement to settle.
2. Expose `mouse: {...this.mouse}` from the example renderer's existing `getStats()` for observation only.
3. Move the real mouse to canvas-local (30,20); verify the renderer receives (30,20).
4. Move outside the canvas and observe its normal leave/reset.
5. Set the identified canvas outer pane's inline transform to `translateX(80px)`; verify only the native x coordinate changes.
6. Move the real mouse to (30,20) inside the moved canvas. The browser reports offsets (30,20), while the renderer receives (110,20).

## The Architectural Reality

Design authority: `src/app/SharedCanvas.mjs#forwardPointer` promises “the canvas-relative position.” The App Worker owns conversion; the Canvas Worker receives local coordinates.

- `src/main/DomEvents.mjs#getMouseEventData` already forwards native `offsetX/offsetY`, `clientX/clientY`, target identity and the event path. Mouse-event path entries carry viewport rectangles; scroll/wheel intentionally omit those layout reads.
- `SharedCanvas.forwardPointer` is the common input door for move/down/up/click/wheel, with existing readiness guards and canvas/window addressing.
- `SharedCanvas.updateSize` separates renderer content-box dimensions from viewport pointer geometry. The repair in `#19585` / PR `#19586` must remain intact; that leaf explicitly excluded generic position tracking without resize.
- `#20772` owns which button press starts an orbit. This issue does not change gesture ownership or `canvas.Base` state.

## The Fix

Correct conversion in the existing SharedCanvas host using current event-carried geometry or native local coordinates when their target identity proves they belong to this canvas. Do not use offsets from an unrelated delegated target. Preserve the existing fallback for programmatic/delegated reports that lack usable canvas-local facts, and preserve absent-position behavior.

Keep forwarding synchronous, with no added DOM round trip or continuous position observer. Keep content-box renderer sizing, DPR and remote routing unchanged. Expose the conversion as `SharedCanvas.getPointerPosition(data)` for subclasses with a custom input consumer, and use it from `forwardPointer`. It returns `{x, y}` or `null` for a report without a complete position; it performs no renderer call or geometry mutation. Keep one host-owned conversion rather than copying it into renderers.

Prescription checked (independent read): `src/app/SharedCanvas.mjs#forwardPointer` owns the concern. Main already supplies the event facts, and the Canvas Worker receives local coordinates; changing worker gestures, renderer dimensions, or ResizeObserver semantics would address the wrong owner. Match against `getCanvasId()` before accepting native local facts. [CSSOM View defines native offsets from the target’s padding edge, ignoring transforms](https://drafts.csswg.org/cssom-view/#dom-mouseevent-offsetx); that is not universally equivalent to subtracting a viewport border rectangle. Pin border/padding compatibility explicitly rather than silently changing origins.

## Acceptance Criteria

- [ ] The public native reproduction is red before the repair and green afterward: actual renderer input remains (30,20) after the outer pane translates 80px without resizing.
- [ ] Unit controls cover fresh canvas-targeted facts, border/padding origin compatibility, an unrelated delegated target, reports lacking native local facts, and a report without a position. Existing move/down/up/click/wheel facts and readiness guards remain correct.
- [ ] Existing resize-origin/content-box/DPR and canvas lifecycle controls pass; no extra DOM read or polling is added to pointer forwarding.
- [ ] Native input remains correct after a nonzero-offset resize as well as a position-only move. The receipt distinguishes browser event data, host state and actual renderer state.
- [ ] The owning JSDoc and any extracted host conversion surface describe their identity and fallback boundaries.

## Out of Scope

Admission retry; button/drag ownership; new gestures or pointer capture; continuous idle position tracking; making every cached rectangle update on every presentation frame; renderer or application-specific tooltip behavior; arbitrary CSS transform support beyond what the chosen native input facts establish.

## Avoided Traps

Adding a polling loop or per-movement DOM RPC; using another event target's offsets; feeding transformed viewport dimensions into renderer sizing; forcing a resize in the test; asserting only cached geometry while ignoring actual renderer input.

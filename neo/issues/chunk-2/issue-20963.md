# dist/esm: a Main addon's out-of-root helper loads the source Engine

## Context

Found while reviewing #20956 (static package graphs for #20863). A package declares `neo.mainAddons: ['main']`. Its `main/Addon.mjs` re-exports `../outside/Helper.mjs`, and that helper re-exports `../../neo.mjs/src/core/Base.mjs`.

The ESM build exits 0 on `dev` (`412a9c25d8`) and on #20956's head (`a678dbb220`). The emitted addon imports the helper from its source location, so the Main thread loads the source CoreBase beside the emitted one.

Reproduction: a synthetic workspace with the stub engine that `test/playwright/unit/buildScripts/esmWorkspaceBuild.spec.mjs` uses, built with `buildScripts/build/esmodules.mjs`, then the emitted addon imported in Node. Both trees print the same:

```
status 0
dist/esm/node_modules/widget/main/Addon.mjs: export{default}from"../../../../../node_modules/widget/outside/Helper.mjs";
Addon.default.engineUrl: <workspace>/node_modules/neo.mjs/src/core/Base.mjs
```

## The Problem

`findUnresolvableImports()` reads emitted specifiers. The addon's specifier names the package, not `node_modules/neo.mjs`, so the identity guard passes. The split happens one edge further, in a file the build never emits. Mounting still succeeds; `DistEsmWorkspaceBoot.spec.mjs`'s split-graph arm shows why mount success is no oracle.

This is the Main-side twin of #20863: a source fallback that silently reintroduces the source Engine.

Admitting the helper is not the fix. #20821's Avoided Traps exclude "admitting sibling paths outside declared roots", and #20956 keeps that boundary (its spec: "Main-only roots do not discover their outside-root helpers").

## The Architectural Reality

- `rewriteMainAddonImports()` (`buildScripts/util/esmDistTransforms.mjs`): for a declared-root module, a target outside every declared root and outside the Engine keeps its source location (`target = resolved`).
- After #20956, `createEsmBuildPlan()` (`buildScripts/util/esmBuildGraph.mjs`) walks the static edges of workspace modules only. Declared-root modules are copied, not walked, so their outside-root edges are never classified.
- Design authority: `rewriteMainAddonImports` on `dev`: "Rebases declared Main-addon modules onto the emitted tree's single Engine graph." And `enginePackagePath`: "Every specifier that still names it after the rewrite addresses a SECOND engine module graph".

## The Fix

1. Classify the static edges of declared Main-root modules without admitting their targets. An edge that leaves every declared root and transitively reaches the Engine fails the build. The error names the importer, the specifier and the remedy: declare the helper's directory in `neo.mainAddons`, or move it inside a declared root.
2. An outside-root helper with no Engine edge keeps today's host fallback.
3. Reuse #20956's plan and failure format; no second walker.

Decision Record impact: none.

## Acceptance Criteria

- [ ] The reproduction above fails the ESM build, naming the addon and its specifier. The same package with the helper's directory declared as a Main root builds, and its emitted addon reaches the emitted CoreBase.
- [ ] A declared-root edge to an outside helper without an Engine edge still builds and keeps its host path.
- [ ] Undeclared roots stay unadmitted: the outside helper is emitted in neither arm.
- [ ] The existing Main-addon controls stay green: the #20821 arms of `esmDistTransforms.spec.mjs` and the Main-addon lifecycle arms of `DistEsmWorkspaceBoot.spec.mjs`.

## Out of Scope

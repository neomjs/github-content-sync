# One map says what a theme is: class to folders, read by the loader

## Context

Seams 2 and 3 of the design system (epic and ADR 0044, graduated from [Discussion #22228](https://github.com/orgs/neomjs/discussions/22228)). The new tree has a folder no app lists (`theme-base`) and one folder for two classes (`theme-neo` for `neo-theme-neo-light` and `neo-theme-neo-dark`). Today's loader can load neither. Found by Julia's loader audit and widened by Grace's step-back.

unowned-rationale: critical path of the 14.1 cut and bound to a decision record, so it is for a maintainer seat. Claim by assignee and a `[lane-claim]`.

## The Problem

Class to folder is string arithmetic in two places, and both assume one folder per class:

- `src/main/addon/Stylesheet.mjs:123` requests a folder only when `config.themes.includes('neo-' + folder)`, so `theme-base` is never requested.
- `src/worker/App.mjs:1307` strips `neo-` to get the folder (`substring(4)`), and `Stylesheet#setCssVariable` then picks a sheet by `sheet.href.includes(data.theme)` (line 294). A shared `theme-neo` folder never matches, so the call returns `false` silently. The same line throws on a `<style>` sheet, whose `href` is null (`insertCssRules` creates one at line 226): a latent defect today.
- `setCssVariable` reads top-level `CSSStyleRule`s only (line 296), so a rule inside a layer block is invisible to it.

Stripping a suffix cannot give one folder for two classes: the classic `neo-theme-light` would map to `theme`.

## The Architectural Reality

- `buildScripts/build/themes.mjs` already writes `resources/theme-map.json` (class path to folders) and its copies under `dist/<env>/resources`.
- All five themes declare their class in `Global.css` and state `--neo-color-scheme` there.
- `Stylesheet#addGlobalCss` (lines 72 to 90) and `addThemeFiles` (108 to 131) build their hrefs from folder names; `worker/App.mjs` fetches the map once per worker (line 853).

Design authority: "The theme build writes, for each theme class, the folders whose `Global.css` declares it into `resources/theme-map.json`. The loader, `setCssVariable`, the census, the guards and `create-theme` read it; none globs `theme-*` or strips a prefix." (ADR 0044, invariant I7; Discussion #22228 at R3, seams 2 and 3.)

## The Fix

1. The theme build reads the class selectors of each folder's `Global.css` and writes class → folders into `resources/theme-map.json`. It is a list per class: theme Neo's old and new folders both serve its two classes while its packages move.
2. The loader admits `theme-base` like `src`, resolves an app's theme classes to folders through the map and requests each `Global.css` and per-widget file once.
3. `App#setCssVariable` and `Stylesheet#setCssVariable` resolve the sheet through the map, walk into layer blocks and skip a sheet without `href`.

The tree this serves:

<!-- binding-inventory: theme-tree -->
- `src/<pkg>/<Cmp>.css`
- `theme-base/<pkg>/<Cmp>.css`
- `theme-<name>/Global.css`
- `theme-<name>/<pkg>/<Cmp>.css`
<!-- /binding-inventory -->

## Acceptance Criteria

- [ ] AC-1 `resources/theme-map.json` maps every theme class to the folders whose `Global.css` declares it, derived from the CSS; no reader derives a folder from a class name or the reverse.
- [ ] AC-2 An app that lists both Neo classes loads each folder's `Global.css` once, and a `theme-base` file is requested when it exists. A fixture folder serves two classes in a test.
- [ ] AC-3 A spec sets a variable in each scheme of theme Neo and in a classic theme, with a runtime-inserted `<style>` sheet present and with the rule inside a layer block.
- [ ] AC-4 Every hosted app and example loads the same sheets as before on today's tree (a request list before and after).

## Out of Scope

- The build scripts that enumerate themes (`theme-census`, the guards, `create-theme`, the build's theme list): a follow-up leaf, once the map's shape exists.
- Adding `theme-base` or `theme-neo` content.

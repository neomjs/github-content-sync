# simulate_event cannot deliver a touch event that carries contacts

handoff: @neo-fable-mnemosyne, who offered on 11-27 to take the Engine half of the replay driver. If it is still unclaimed at 14:00Z, Ada takes it.

## Context

The touch discussion (D#22259) needs a peer to replay touch contacts through the Neural Link. Emmy saw the public `simulate_event` tool return `false` for a `touchstart` carrying a contact list (D#22259 body, "What works today"). Julia traced the failure to the `TouchEvent` constructor ([peer cycle](https://github.com/neomjs/neo/discussions/22259#discussioncomment-19934123)).

Measured at dev `7ec0d2932a` in Chromium (desktop browser pane, mobile emulation, `hasTouchEvents: true`):

- `EventSimulator.dispatchNative({id, type: 'touchstart', options: {touches: [{identifier: 1, clientX: 10, clientY: 10}], changedTouches: [...]}})` returns `{success: false, event: null}`. The constructor throws `TypeError: Failed to construct 'TouchEvent': Failed to read the 'changedTouches' property from 'TouchEventInit': Failed to convert value to 'Touch'.`
- Build `new Touch({identifier: 1, target, clientX: 10, clientY: 10})` in the same window first, and the same `TouchEvent` constructs with one contact.

## The Problem

`simulate_event` and the fixture's `nlApp.simulateEvent()` fail for every touch event that names a contact. A touch event without contacts still dispatches, but no consumer can use it: `TouchDomEvents` and `GridDragScroll` read `touches` and `changedTouches`. Specs that need touch go around the tool with CDP `Input.dispatchTouchEvent` (`test/playwright/e2e/component/HelixTouchNL.spec.mjs`). A peer driving a live app through the Neural Link has no such way around it.

## The Architectural Reality

- `src/main/addon/EventSimulator.mjs:273-277` selects `TouchEvent` for the four touch types. `dispatchNative` passes `options` straight into `new ctor(type, options)`. A worker-sent payload is JSON, so its contact lists can never arrive as `Touch` objects.
- A `Touch` needs an `EventTarget` in the window that dispatches it, so only Main can build one. `dispatchNative` already resolves its node there through `DomAccess.getElement(id)`.
- Two callers: the Neural Link `simulate_event` tool, and `simulateEvent` in `test/playwright/dedicatedWorkerNeuralLink.mjs:269`. Unit coverage lives in `test/playwright/unit/main/addon/EventSimulator.spec.mjs`.

## The Fix

For touch types, `dispatchNative` turns plain contact objects in `touches`, `targetTouches` and `changedTouches` into `Touch` instances. Each one carries `identifier`, the client, page and screen coordinates, and radius and force where they are given. `target` defaults to the dispatch node and may name another element id.

These stay as they are:

- explicit `screenX` / `screenY`, which Demo B's cross-window driver relies on;
- non-touch types;
- options that already hold `Touch` objects.

## Acceptance Criteria

- [ ] A unit spec in `EventSimulator.spec.mjs`: for each touch type, `dispatchNative` with JSON contacts returns `success: true`, and the event carries the given identifiers and coordinates in `touches` and `changedTouches`. The spec is red on dev.
- [ ] A Neural Link e2e in Chromium with `hasTouch`: `nlApp.simulateEvent()` replays the D#22259 partial-lift trace on the Helix example (13 down, 27 down, lift 27, move 13), and `rotationAngle` and `translateZ` stay finite.

## Out of Scope

- A contact-sequence API (`drive_gesture`, presets, input providers): D#22259 decides between R1, R2 and R3. This fix sits under each of them.
- Trusted input. Synthetic events stay `isTrusted: false`: they never scroll natively and never take pointer capture.
- The Brain-side description of `simulate_event` and the Neural Link capability matrix.

# A reusable empty state for File Explorer and Portal

## Context and problem
File Explorer renders an empty detail view in `examples/fileExplorer/DetailPane.mjs:38-47`; Portal example search builds its own no-results message in `apps/portal/view/examples/SearchResults.mjs:95-103`. Both communicate absence, but each owns presentation separately.

## Architectural reality and approach
Introduce a reusable Neo component using existing component, theme and accessibility conventions. Integrate the real File Explorer selection prompt and Portal search no-results state while preserving their distinct messages and behavior. Inspect existing primitives before choosing placement and API.

## Contract ledger
| Surface | Authority and behavior | Fallback / evidence |
| --- | --- | --- |
| Empty-state component | Consumer owns meaningful message, optional supporting content and actions | Text-only use remains legible; document configuration |
| File Explorer and Portal | Existing owning views decide when and why to display it | Normal populated and loading/error behavior remain distinct |

## Acceptance criteria
- [ ] Reusable component supports text, optional supporting content and optional action without requiring decorative artwork.
- [ ] File Explorer and Portal use it for the cited real empty states; populated transitions and Portal search recovery still work.
- [ ] Verify keyboard and screen-reader-accessible action and text, light/dark themes, narrow layout, and real consumer transitions.
- [ ] Document public configuration and focused tests.

## Out of scope
Changing data ownership or treating loading and errors as empty results.

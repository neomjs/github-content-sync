# theme-base pilot: Button's variables are declared once, bound to roles

## Context

The first of step 6's 42 moves (ADR 0044 §4; [the map on the epic](https://github.com/neomjs/neo/issues/22295#issuecomment-7217835670)) and the template for the other 41. Button is the grammar's exemplar (decision 4 names `--button-primary-glyph-color-hover`) and the largest reader of the old tokens.

unowned-rationale: critical path of the 14.1 cut, so it is for a maintainer seat and carries no contributor labels. Claim by assignee and a `[lane-claim]`. The binding table can be drafted today against the role list in #22350; the build waits for the two blockers.

## The Problem

Counted on `dev` at `9380db92d8`:

- `button/Base.css` exists once in `theme-neo-light` and once in `theme-neo-dark`, with 155 variables each. 18 values differ between the two; the other 137 are the same decision written twice.
- 104 of those values read a `--sem-*`, a `--cmp-*` or a hue-ramp name, the tokens that go.
- A model that changes how a button looks has to find and edit two files, and a pair can drift.

## The Architectural Reality

- `theme-base` is already admitted by the loader and by the theme tooling (`src/main/addon/Stylesheet.mjs`, `buildScripts/util/themeCss.mjs`, the theme guards, `buildScripts/create/theme.mjs`), and no folder `resources/css/theme-base` exists yet. This leaf creates it.
- The classic pair and Cyberpunk keep their own `button/Base.css` until step 10. Their values sit in `neo.theme`, above `neo.base`, so they keep winning there.
- Open, for the pilot to settle: `check-theme-var-references` resolves a role read against each theme's `Global.css`, and three themes declare no roles until step 10.

Design authority: "Every component variable is declared once, in `theme-base`, bound to roles. A theme keeps a per-widget file only where its design language deviates." (ADR 0044, decision 4.) And: "A generic component variable works on every variant. A variant re-values the generic variable on its own element, inside the rules layer".

## The Fix

1. `resources/css/theme-base/button/Base.css` declares every Button variable once, under the base selector `[class*="neo-theme-"]`, each value a role read.
2. `theme-neo-light/button/Base.css` and `theme-neo-dark/button/Base.css` go.
3. The pull request carries a binding table: variable, role, and the literal or old token it replaces. A variable that cannot bind without a literal is listed apart; that is the record's first revalidation trigger.

## Acceptance Criteria

- [ ] AC-1 One file declares Button's variables for theme Neo; neither Neo folder holds a Button file, and `npm run theme-census` reports no Button read of a `--sem-*`, `--cmp-*` or hue-ramp name.
- [ ] AC-2 Every value is a role read or a keyword. No raw colour value; a component's own translucent mix with `transparent`, if one is used, is listed.
- [ ] AC-3 Pixels move only where a literal collapses into a role: each difference `npm run theme-equality` reports for the two Neo themes is declared in the pull request, and the design seat reads a light and dark frame pair of the Button example.
- [ ] AC-4 The classic pair and Cyberpunk paint as before: the equality run reports no difference in those three themes.
- [ ] AC-5 Both hooks work, shown by a component spec: `--button-background-color` set inline takes effect on every variant, and a variant's variable set on an ancestor takes effect on that variant.
- [ ] AC-6 `WorkstationPaletteBridgeNL` is green and the theme guards pass. A guard that has to change for a theme without roles is changed in this pull request and named.
- [ ] AC-7 Reverting the pull request restores the two files and touches nothing else.
- [ ] AC-8 The pull request body states its structure as the template for the remaining moves (binding table, declared differences, frame pair), and the map on the epic records what the pilot changed.

## Out of Scope

- Any other package: 41 leaves, filed in one batch when this pull request is open and its shape holds.
- Button's structural rules under `resources/css/src`, beyond a variant re-valuing the generic variable.
- The classic pair's and Cyberpunk's Button files: step 10.
- A new role. A role enters with its reader, through a comment on the epic.

## Avoided Traps

- **Binding a variable on the component's root.** It breaks an ancestor's override (ADR 0044 §3, rejected).
- **Keeping a per-theme copy "for now".** The two copies are the problem; the move is revertable by itself.
- **Frames as the only proof.** The equality run lists every moved value; the pair shows whether the move reads well.

**Structural finding for AC-5:** the variants paint with their own variables. `src/button/Base.css` has `.neo-button-primary { background-color: var(--button-primary-background-color) }`, and so on for every state, so `--button-background-color` set inline does nothing on a variant today. AC-5 needs each variant block to re-value the generic variables instead (`--button-background-color: var(--button-primary-background-color)`), with the generic rules doing the painting. That rewrite is the template the other multi-variant packages copy. It also has to keep today's order of `:hover`, `:active` (the variants use `!important` there) and `.pressed`; the equality run is the check.

**AC-4 holds by construction:** `theme-light`, `theme-dark` and `theme-cyberpunk` each declare all 155 Button variables, so their `neo.theme` values win over theme-base everywhere. Vega's finding (her DMs of 14:58Z and 15:03Z): once `src/button/Base.css` re-values the generic variables per variant, a classic or Cyberpunk value that reads a generic variable cycles when the theme class sits on the button itself, and the equality run's scoped pass reported 556 undeclared differences. Resolving those references to what they read today brought it to PASS, 0 of 192,000.

**The ruling.** Those values are resolved in this pull request. This amends the ticket's Out of Scope line: what stays for step 10 is the three themes' move onto roles, not every edit of their Button files.

**Why (A) and not a wait for step 10.**
- It is the rule decision 4 needs, stated once: **a theme's value never reads a variable that the rules re-value.** The rules own the direction from variant to generic; a theme value pointing back is the cycle.
- It loses nothing. With the theme class on an ancestor, a custom property resolves where it is declared, so the variant already inherited a resolved value and never followed a later override of the generic one. The scoped case now paints what the inherited case paints.
- (B) would ship a template without an answer for multi-variant packages, and 41 moves copy the template.

**No new guard.** The equality run's scoped pass found this at once, and it is every move's gate. The template says so: a multi-variant package resolves these references in its own move, and the scoped pass is what catches a miss.

**Two conditions for the pull request.**
1. **The opposite direction, as a receipt.** A generic Button variable declared at a theme class outside the engine's Button files (apps, examples, tests) reached a classic variant through the cross-wiring until now and stops doing so. List each one, or state that a search found none.
2. **The ten revived overrides are read one by one.** Per button: what it paints today, what the revived override paints, and the frame pair. One that reads worse than today is deleted in this pull request; a dead line that comes alive by accident is not a design.

Read and accepted as declared differences: a variant loses its `background-image` while `:active` without hover (classic dark, primary), and a disabled ghost no longer shows its hover fill. The second is a repair.

# theme-base: bind toolbar's six variables to roles

Owner: Ada (`@neo-opus-ada`). Step 6 row `toolbar` of #22295. Its build waits for the Button pilot (#22351). The acting design seat (`@neo-fable-mnemosyne`) has [read the table](https://github.com/neomjs/neo/issues/22397#issuecomment-7228277839): it stands, with one reader added to the move.

## Context

#22295 Step 6 declares each engine package's variables once in `theme-base`, bound to theme Neo's roles (`resources/css/theme-neo/Global.css`, #22350 / PR #22352, merged). Clio's map lists `toolbar` as 1 file, 6 variables, 1 differing in dark ([map](https://github.com/neomjs/neo/issues/22295#issuecomment-7217835670)). The epic is at the comment ceiling, so the row's table lives here, like `form` (#22368) and `grid` (#22389).

## The Problem

`resources/css/theme-neo-{light,dark}/toolbar/Base.css` writes the toolbar's six variables twice, once per scheme. The background reads an old token in dark (`--neo-sem-color-surface-neutral-default`), and the four button sizes read Button's own variables (`--neo-button-size-medium-*`). No role carries them, so a theme written against the roles cannot reach the toolbar.

## The Architectural Reality

- Design authority: #22295's decided rules ([hand-over](https://github.com/neomjs/neo/issues/22295#issuecomment-7222268056)): a variable's ending types its role family, and a component variable reads roles only (the acting design seat's `tab` read, [7223146905](https://github.com/neomjs/neo/issues/22295#issuecomment-7223146905)).
- Readers: `resources/css/src/toolbar/Base.css` reads all six, `calendar/view/MainContainer.css` the padding, and the Portal's `home/parts/References.css` the background.
- `theme-light`, `theme-dark` and `theme-cyberpunk` each declare all six (`resources/css/theme-*/toolbar/Base.css`), so their values win over theme-base and the classic themes do not move.

## The Fix

### Binding table (`dev` at `5ff17dedc8`; values resolved per scheme through the old tokens and through the roles)

| Variable | Before (light · dark) | Binds to | After (light · dark) |
| :--- | :--- | :--- | :--- |
| `--neo-toolbar-button-font-size` | `0.875rem` | `control-font-size-medium` | `0.875rem` |
| `--neo-toolbar-button-height` | `32px` | `control-height-medium` | `32px` |
| `--neo-toolbar-button-min-width` | `32px` | `control-height-medium` | `32px` |
| `--neo-toolbar-button-padding` | `0 12px` | `0 var(--neo-control-padding-inline-medium)` | `0 12px` |
| `--neo-toolbar-background-color` | `#fff` · `#0D0F12` | `background-surface-raised` | `#fff` · `#252834` |
| `--neo-toolbar-padding` | `5px` | apart (literal) | `5px` |

4 variables bind with the same value, 1 binds and moves a value, and 1 stays a literal. None is a keyword, and none lacks a reader.

### Decided by the acting design seat ([read](https://github.com/neomjs/neo/issues/22397#issuecomment-7228277839))

1. **The background binds to `background-surface-raised`.** A toolbar is chrome. Today it is a bar in light only (1.04 against the page) and flat in dark. On the raised role it is a bar in both schemes (1.04 · 1.31), the fill of the grid's header and footer (#22389). Whatever hovers on a toolbar reads the translucent `background-neutral-hover` (epic rule 15): an opaque subtle fill is no step on a raised region in dark (1.01).
2. **The four sizes read the control roles.** The rules re-value Button's variables inside a toolbar (`toolbar/Base.css:11-14`), so a theme value must not read them (rule 2). The min-width on `control-height-medium` is a square button's rule.
3. **`5px` stays a listed literal, as a named debt.** On `space-1` a toolbar is 40px high instead of 42px, a layout move in every app. Its trigger is the first density scope, like the field height's in the `form` read.
4. **The Portal's `home/parts/References.css:23` moves in this pull request.** It borrows the toolbar's fill for a 90px block over the carousel, which would turn `#252834` on the dark home page. It reads the surface it sits on instead.

- [ ] AC-2: Every declaration is a role read or the listed `5px` literal, and every `check-theme-*` guard exits 0.
- [ ] AC-3: `npm run theme-equality` reports 0 undeclared differences in `theme-light`, `theme-dark` and `theme-cyberpunk`, and the only `theme-neo-light` / `theme-neo-dark` difference is the toolbar background as decided.
- [ ] AC-4: Light and dark frame pairs of a stock Neo-themed panel header toolbar and the calendar's toolbar are posted for the acting design seat. The Portal home's References section is unmounted on `dev`, so its witness is the reachability and source receipt the design seat accepted ([ruling](https://github.com/neomjs/neo/issues/22397#issuecomment-7230294898), rule 21 of #22295).
- [ ] AC-5: Reverting the pull request cleanly restores the pre-move state.

## Out of Scope

- Button's own medium size (#22351).
- App and example toolbars (`HeaderToolbar.css` and others); they take the grammar at their own move.
- The `5px` padding's move to the space scale (its trigger is the first density scope).

## Avoided Traps

- Binding the padding to `space-1` silently. That is a 1px move per side on every toolbar, a visual change that needs a frame pair, not a rounding.

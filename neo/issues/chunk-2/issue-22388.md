# Three grid unit specs wait on fixed sleeps and fail on Windows

Please comment to claim before starting; check current assignees and linked PRs.

## Context

A contributor ran the grid unit specs on Windows while preparing `#20704` (merged) and wrote: "Full `test/playwright/unit/grid`: 419 passed, 6 failed. The same 6 tests (`RowPoolGrowth`, `ScrollFlightMerge`, `Teleportation`) fail identically on unmodified `dev` in this local Windows environment." No failure output was posted. No maintainer machine runs Windows, and hosted CI runs Linux only, with two retries per failed unit test (`test/playwright/playwright.config.unit.mjs:36`). The failure is reported, not reproduced: this ticket needs a contributor with Windows.

## The Problem

What `dev` (`4d5236b292`) shows: the three specs wait for the grid's asynchronous updates with fixed sleeps rather than with the updates themselves, 14 times:
- `test/playwright/unit/grid/RowPoolGrowth.spec.mjs:120, 126` (50, 20 ms)
- `test/playwright/unit/grid/ScrollFlightMerge.spec.mjs:69, 73, 94, 100, 107` (50, 50, 20, 5, 150 ms)
- `test/playwright/unit/grid/Teleportation.spec.mjs:87, 92, 95, 146, 175, 274, 309` (50, 50, 50, 20, 50, 20, 50 ms)

A lead, not a measured cause: every component update passes at least one `timeout(1)` hop before its payload is collected (`src/mixin/VdomLifecycle.mjs:364`), and timers on Windows commonly fire at the system timer resolution (about 15.6 ms). A chain of 1 ms hops can then outlast a 20 ms sleep on Windows and still fit on macOS and Linux.

## The Architectural Reality

The same files already use deterministic waits: `await grid.view.promiseUpdate()` (`RowPoolGrowth.spec.mjs:144`, `Teleportation.spec.mjs:166, 300`) and `await expect.poll(() => view.isVdomUpdating || view.needsVdomUpdate).toBe(false)` (`ScrollFlightMerge.spec.mjs:150, 165`). Some sleeps create a race on purpose (a scroll that lands while an update is in flight), and the rewrite must keep the ordering they force.

## The Fix

1. Reproduce on Windows from a clean `npm ci` of `dev`:
   `npx playwright test -c test/playwright/playwright.config.unit.mjs test/playwright/unit/grid/RowPoolGrowth.spec.mjs test/playwright/unit/grid/ScrollFlightMerge.spec.mjs test/playwright/unit/grid/Teleportation.spec.mjs --workers=1 --retries=0`
   and post the failure messages on this issue.
2. Replace each fixed sleep with what it waits for: `promiseUpdate()` for an update, `expect.poll` on the flight flags for "settled". A sleep that creates a race becomes a step driven by flight state (for example, start the scroll once `view.isVdomUpdating` is true), with a comment naming the race.
3. If a failure is an engine defect rather than a timing defect in the spec, fix the engine in the same PR and say so.

## Acceptance Criteria

- [ ] The Windows failure messages on unmodified `dev` are posted on this issue.
- [ ] No fixed sleep remains in the three specs, except race-creating steps that are now driven by flight state and commented.
- [ ] The three specs pass on Windows with `--workers=1 --repeat-each=10 --retries=0` (receipt in the PR).
- [ ] The three specs pass on macOS or Linux with `--workers=4 --repeat-each=10 --retries=0` (receipt in the PR).
- [ ] Each rewritten race test still fails with the fix it pins reverted locally (`git log` on the spec names the fix), or the PR says why that cannot be shown.

## Out of Scope

- Other grid or unit specs; the same pattern can follow in later tickets.
- A Windows job in hosted CI.
- The engine's `timeout(1)` hop before collection (row B5 of D#22199).

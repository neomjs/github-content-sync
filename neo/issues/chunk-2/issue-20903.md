# The shared-state example opens its second window itself

## Context

`examples/stateProvider/multiWindow` shows two browser windows whose labels are bound to one state provider. It enters the Portal's Multi-Window overview with #20891, and its card has to tell a visitor to open a second page by hand:

> Open this page first, then its sibling multiWindow2/index.html in another window using the same origin and build.

Found in the review of #20891. The card is honest; the example is what makes it say that.

## The Problem

- The example has no control that opens its companion. `examples/stateProvider/multiWindow/MainContainer.mjs` renders one header with the label `Current user: …` and one button, `Edit user`.
- The companion `examples/stateProvider/multiWindow2` is an empty viewport. It gets its content when it connects: `multiWindow/ViewportController.mjs#onAppConnect` adds a `MainContainer` to every connecting app and gives each later one the first provider as its parent.
- So a visitor who opens the card sees one window and nothing that points at a second. The capability the example proves stays invisible unless they edit the address bar.

## The Architectural Reality

- `Design authority: n/a — adds a control; the example's binding stays as it is.`
- Sibling examples open their window themselves: `examples/component/multiWindowHelix/ViewportController.mjs` calls `Neo.Main.windowOpen` with a URL relative to the example's page.
- The companion's page sits beside the primary's in all four builds (`examples/stateProvider/multiWindow2/index.html`, and the same path under `dist/development`, `dist/esm` and `dist/production`), so a relative URL serves every build.
- The catalog record is `multi-window-state-provider` in `apps/portal/resources/data/examples.json`; `test/playwright/unit/apps/portal/view/examples/TabContainerController.spec.mjs` fails on a family record without `feature` or `lookFor`.

## The Fix

1. A second header button in the primary window, `Open second window`, which opens `../multiWindow2/index.html` through `Neo.Main.windowOpen`, as the Helix example does.
2. The body's line names it, so the page explains itself: what the button does and what `Edit user` then shows.
3. The catalog record's `lookFor` becomes one action and one observation (press the button, use `Edit user`, watch the name change in both windows), and its `scope` shrinks to the popup permission.

## Acceptance Criteria

- [ ] From the card's page, one click opens the companion, and `Edit user` changes `Current user` in both windows. Checked in source and in one built mode; the pull request names the build and the browser.
- [ ] The button is offered in the window that owns the provider; the companion does not offer to open a third.
- [ ] A whitebox journey under `test/playwright/e2e` opens the page, presses the button, and asserts both headers before and after an edit.
- [ ] The catalog record names the button, and `npm run test-unit -- test/playwright/unit/apps/portal/view/examples` passes.

## Out of Scope

- The provider's binding and the `connect` listener.
- A cover image for the card.
- The other multi-window examples.

## Avoided Traps

- **A link in the card instead of a button in the example.** A card has one destination per build, and the example would still not explain itself when opened from anywhere else.
- **An absolute URL.** It would pin one build.

# Serialize Tooltip mounts and honor hides during the flight

## Context

A tooltip can receive another `show()` or a `hide()` before its first native mount is acknowledged. The observed failure is two tooltip DOM nodes with the same id, one aligned and one unaligned. The corresponding hide-during-mount case can leave a tooltip visible after it was hidden.

## The Problem

`src/tooltip/Base.mjs#show` starts `initVnode(true)` whenever `mounted` is false. A second call during that promise starts another mount. `hide` only unmounts an already-mounted tooltip and does not record the pending hidden intent.

This is the Tooltip override of the body-rooted mount race fixed for `component.Base` in `#19265` / PR `#19268`. For a newly created, unmounted Tooltip, call `show(); show()` or `show(); hide()` before the first App → VDOM → Main → App round trip completes. The former must mount once; the latter must land unmounted.

## The Architectural Reality

- `src/component/Base.mjs#show` guards `!mounted && !mountFlight` and delegates the returned promise to `startMountFlight`. Settlement clears the latch, then reads the latest `_hidden`, with a destroyed-instance guard.
- `src/tooltip/Base.mjs#show` and `#hide` bypass that primitive while owning Tooltip's existing show/hide/dismiss timers.
- Recording only the flight is insufficient: Tooltip's `hide` must record `_hidden = true`, and `show` must record `_hidden = false`, so the existing landing hook sees the last intent.
- Design authority: `component.Base#show` documents: “A component rooted at `document.body` mounts in one flight at a time, which lands on the latest `hidden`.”
- Prescription checked: Tooltip owns these specialized lifecycle overrides; `component.Base#startMountFlight` already owns the shared-flight lifetime. Consumer debounce or a new scheduler would treat the symptom.

## The Fix

Reuse `startMountFlight` from the Tooltip override, guard repeated startup, and record show/hide intent directly as the base class does. Keep Tooltip's timer clearing, delay values, stay-on-hover behavior, alignment and public call shape.

Add focused Tooltip flight units beside the existing tooltip suites. Update the delay-test fixture's `initVnode` mock to honor the existing Promise contract. Add a native Neural Link witness using the existing `tooltip-nested-theme` test application, holding only a genuine Main insert message and releasing its original payload unchanged.

Decision Record impact: none; restores the existing lifecycle contract in a specialized override.

## Acceptance Criteria

- [ ] Repeated `show()` calls during one pending mount start one mount and leave exactly one native tooltip node. Demonstrate the regression before the repair.
- [ ] Hide during the flight lands unmounted; show → hide → show lands mounted once; a later show after a hide-landed flight mounts again.
- [ ] Destroy during the flight does not issue a late unmount on the destroyed instance, and the flight settles without stale ownership.
- [ ] A real App → VDOM → Main → App witness verifies current target text/alignment and ordinary mounted retargeting, with no duplicate tooltip or descendant IDs and no page/worker errors.
- [ ] Existing Tooltip delay, cancellation, stay-on-hover and theme behavior remains covered and passing; no new scheduler, public config or consumer workaround.

## Out of Scope

Changing the hide-delay duration or hover policy; changing `component.Base`'s mount primitive; parent-owned rendering; redesigning tooltip consumers or focus behavior.

## Avoided Traps

Debouncing consumer hover events; using `isVnodeInitializing` instead of the full returned promise; guarding show without recording hide intent; treating final DOM count alone as proof that no duplicate was inserted.

# The Workstation shows a board, a scheduler and a Gantt chart as panes

## Context

Leaf of #20874. Each of the four family leaves brings one basic example. None of them shows what the engine adds to these views: several of them, in several windows, on one runtime and one set of records. `apps/workstation` is the engine's desk for exactly that. Its panes dock, pop out into their own windows and return, and the arrangement survives a reload.

## The Problem

A stranger who opens `examples/board/basic` sees a board like any other. The claim that sets these families apart has no public proof for them: an edit in one view is a record change, and every other view and window on the same store shows it with no wiring. The Workstation's panes today are grids (`apps/workstation/view/FeedPane.mjs`, `ScalePane.mjs`, `ResidentComponent.mjs`).

## The Architectural Reality

- `apps/workstation/view/Workspace.mjs` is the composition entrypoint: it declares the shipped perspective and the root state provider and selects the pane classes (`apps/workstation/README.md`, "Composition and ownership"). Stores live in `apps/workstation/store`, the model in `apps/workstation/model`.
- The app runs in a shared worker. A pane that moves into a second window keeps reading the same store instance.
- What the families bind to: the board projects one `data.Store` of card records (#20875); the scheduler shows event records by resource and time (#20877); the Gantt chart shows a task tree with a dependency store (#20878).
- The rules for code under `apps/**` (`AGENTS.md`, authoring gate): start from the matching engine primitive; a data view binds a `data.Store` of `data.Model` records, never a hand-mapped array; state providers stay at view roots; styles stay in SCSS.
- The Workstation's e2e specs live in `test/playwright/e2e/dashboard/` and drive the app through the Neural Link.

Design authority: n/a — the ticket adds panes and calls no existing behaviour wrong.

## The Fix

Three panes in `apps/workstation`, offered as a planning arrangement beside the shipped one:

- **A board pane and a scheduler pane on one store instance** of work items. A status field decides the card's column; a resource and two dates decide the bar's row and position.
- **A Gantt pane** with a task store and a dependency store of the same plan.
- **Seeded data** that is generated deterministically in the app, with no network request.

Each pane docks, pops out and returns like the existing panes. No pane keeps a copy of its records.

## Acceptance Criteria

- [ ] The Workstation offers a planning arrangement with a board, a scheduler and a Gantt pane, reachable from its own interface.
- [ ] The board and the scheduler are bound to the same store instance. A card moved to another column is one record change, and the scheduler's bar for that record shows it; a bar moved in the scheduler is one record change, and the card shows the new date.
- [ ] The same holds with the scheduler popped out into its own window.
- [ ] A task moved in the Gantt pane cascades to its linked successor.
- [ ] The arrangement, including a popped-out pane, survives a reload.
- [ ] An e2e spec beside the existing Workstation specs covers criteria 2 and 3.
- [ ] The pull request carries a screenshot of the arrangement in one window and in two.

## Out of Scope

- The board and the Gantt chart on one store. A card list and a task tree are two shapes; it is a later leaf if the families' stores allow it.
- A tour or a film of the arrangement.
- Themes beyond those the family leaves bring.

## Avoided Traps

- **A new demo app for these three views.** The Workstation already owns docking, pop-out windows and layout persistence; a second shell would rebuild them.
- **A store per pane that is synchronized by listeners.** That is the wiring the claim says is not needed.

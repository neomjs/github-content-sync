# A batched collection update leaves count at its pre-batch value

## Context

`Neo.collection.Base#startUpdate()` / `#endUpdate()` bracket a batch of splices so the collection fires one `mutate` instead of one per splice. Inside the bracket, `splice()` updates `_items` but skips the `count` assignment (`src/collection/Base.mjs`, the `if (me[updatingIndex] === 0)` block that sets `me.count = me._items.length`). `endUpdate()` then fires the batched `mutate` (non-silent mode) or nothing (silent mode), but never reassigns `count`.

So after any batch that changes membership, `count` and `getCount()` keep their pre-batch value while `items.length` has moved on. The engine's only internal caller already works around this by hand: `src/manager/transaction/History.mjs` `restoreState()` brackets its splice with `startUpdate(true)` / `endUpdate(true)` and then writes `rows.count = state.rows.length`, with the comment "Silent update brackets leave count unchanged; restore its public cache explicitly." Found while measuring a consumer that batches store membership changes, which also restores `count` by hand.

## The Problem

Reproducer (unit, engine `9acd854d0f`):

```js
const c = Neo.create(Collection, {items: [{id: 1}, {id: 2}]});
c.on('mutate', () => console.log(c.getCount(), c.items.length));
c.startUpdate();            // or startUpdate(true) / endUpdate(true)
c.add({id: 3});
c.remove(1);
c.add({id: 4});
c.endUpdate();
c.getCount();               // 2, items.length is 3
```

Measured output, both modes:

| mode | inside the bracket | after `endUpdate()` | `mutate` listener sees |
|---|---|---|---|
| `startUpdate()` / `endUpdate()` | `getCount` 2, `count` 2, `items.length` 3 | `getCount` 2, `count` 2, `items.length` 3 | `getCount` 2 with 3 items |
| `startUpdate(true)` / `endUpdate(true)` | 2 / 2 / 3 | 2 / 2 / 3 | no event (silent) |

Every reader of `count` after a batch is wrong: `getCount()`, `Store#findBy()`'s default `end=this.count`, `Store#onCollectionMutate()`'s first-chunk test (`me.count === opts.addedItems.length`), and any binding to the reactive `count` config. A `mutate` listener, the first observer of the batch, already reads the stale value. Earlier count desyncs had the same shape, a path that moves `_items` without the `count` assignment (`afterSetSourceId`, `TreeStore` filtering).

## The Architectural Reality

Design authority: `count_` in `src/collection/Base.mjs` is documented as "Stores the items.length of the items array in use"; `startUpdate()` "Prevents the collection from firing events until endUpdate gets called" and `endUpdate()` "Resumes the collection events." The bracket defers events; nothing in either record says it defers or drops the count, and the measured behavior contradicts the `count_` sentence.

- `splice()` defers `count` and `calcValueBands()` together with `mutate` while `updatingIndex > 0`.
- `endUpdate()` re-runs `calcValueBands()` (non-silent branch) and fires `mutate` with the cached arrays, but leaves `count` untouched in both branches.
- `getCount()` returns `this._count` directly ("skipping beforeGetCount() on purpose"), so the stale value is what every caller gets.

## The Fix

In `src/collection/Base.mjs` `endUpdate()`: once the outermost bracket closes (`updatingIndex` back at 0), assign `me.count = me._items.length` before firing `mutate`, in the silent branch as well (a silent batch suppresses events, not the item count). Then delete the hand restore in `History#restoreState()` (the `rows.count = ...` line and its comment), which the fix makes redundant.

## Acceptance Criteria

- [ ] After `startUpdate()` + membership splices + `endUpdate()`, `getCount()` and `count` equal `items.length`.
- [ ] The same holds for `startUpdate(true)` / `endUpdate(true)`, and the silent batch still fires no `mutate`.
- [ ] A `mutate` listener of a non-silent batch reads the new count.
- [ ] `History#restoreState()` no longer assigns `count` by hand, and its existing unit coverage stays green.
- [ ] A unit spec under `test/playwright/unit/collection/` covers both modes (fails on `dev` before the fix).

## Out of Scope

- `endUpdate()` fires `mutate` on every call, including a nested one whose `updatingIndex` is still above 0. Whether nested brackets should publish only at the outermost close is a separate question; this ticket only makes `count` correct.
- Reading the new count from inside an open bracket (before publication). This fix republishes at the close.

## Avoided Traps

- Assigning `count` inside `splice()` during a bracket would publish the reactive `count` change before the batch closes, which defeats the bracket.
- Overriding `getCount()` in a subclass to paper over the stale value: two consumers already patch around this by hand, and a third patch would make the drift permanent.

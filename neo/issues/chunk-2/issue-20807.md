# An event still calls its listener after the listener's scope is destroyed

## Context

A live observable keeps calling a listener whose scope instance has been destroyed. The handler then runs on an instance whose fields `destroy()` has deleted. So a class that listens to a longer-lived instance, such as a store, has to remove its listeners in its own `destroy()` by hand, and a class that forgets it gets handler calls on a dead instance. Measured on `dev` at `41e5632698` with a unit probe.

## The Problem

Reproducer, in a unit spec with `setup({neoConfig: {unitTestMode: true}})`:

```js
class Firer extends Neo.core.Base {static observable = true; static config = {className: 'Test.Firer'}}
class Listener extends Neo.core.Base {static config = {className: 'Test.Listener'}}

const firer    = Neo.create(Firer),
      listener = Neo.create(Listener);
let calls = 0;

firer.on('ping', () => calls++, listener);
firer.fire('ping');   // calls: 1
listener.destroy();
firer.fire('ping');   // calls: 2, though the scope is destroyed
```

After `destroy()`, `listener.id` still reads `neo-base-2` and `listener.isDestroyed` is `true`, and the second `fire` calls the handler again.

## The Architectural Reality

- Design authority: `fire` means to drop such a listener. Its loop says "remove the listener if the scope no longer exists" (`src/core/Observable.mjs:268`), and the test it runs is `cb.scope && !cb.scope.id` (`:269`).
- That test cannot fire for a Neo instance. `core.Base#destroy` keeps `_id` (`src/core/Base.mjs:543`), and its JSDoc says that afterwards "its configs keep their last values readable" (`:510`), so `id` stays truthy. `destroy()` sets `isDestroyed = true` last (`:554`), after it deletes the other own keys.
- `delayedCallback` (`:241–245`) has the same gap: a listener registered with `delay` runs after the timeout even if its scope was destroyed in the meantime.
- `destroy()` already guards a destroyed firer: `me.fire = Neo.emptyFn` (`:550`, "to prevent delayed event calls after an observable instance got destroyed"). #20720 fixed delayable methods that still ran on a destroyed instance. A live firer with a destroyed listener scope is the case left open.

## The Fix

In `src/core/Observable.mjs`:

- `fire`: treat a scope that `isDestroyed` like a scope without an `id`. The listener is removed and not called: `if (cb.scope && (!cb.scope.id || cb.scope.isDestroyed))`.
- `delayedCallback`: skip the call when `cb.scope?.isDestroyed` is true once the timeout has run.

Update the comment above the test to name both cases.

## Acceptance Criteria

- [ ] A listener whose scope instance is destroyed is no longer called by `fire`, and the firer drops it from its listeners. The unit arm is red on `dev` before the fix.
- [ ] A listener registered with `delay` is not called when its scope is destroyed before the delay ends. The unit arm is red on `dev` before the fix.
- [ ] A listener whose scope is alive, and a listener without a scope, are called as before.
- [ ] The arms live in `test/playwright/unit/core/` (the closest siblings are `ObservableListenerObjects.spec.mjs` and `ObservableListenersDiff.spec.mjs`), and the whole unit tier passes.

## Out of Scope

- Removing listeners eagerly when a scope is destroyed. The firer drops them on its next `fire`, as it does for a scope without an `id` today.
- Changing what `destroy()` keeps (`_id`) or the rule that configs stay readable afterwards.

## Avoided Traps

- **Deleting `_id` in `destroy()`** would make the existing test work, but it breaks the documented contract that configs stay readable after `destroy()`.
- **Walking every observable's listeners when a scope is destroyed** costs work in proportion to all observables, for a check that `fire` can make in place.

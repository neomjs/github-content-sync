# Set color-scheme once on the neo-theme- base selector

## Context

Order-of-work row 5 and Seam 5 of Design System Epic #22295 (`learn/agentos/decisions/0044-design-system.md` §2.7 & §4 step 2, graduated from [Discussion #22228](https://github.com/orgs/neomjs/discussions/22228) at R3): set `color-scheme: var(--neo-color-scheme)` once in structural CSS on the `[class*="neo-theme-"]` base selector and retire the three per-component declarations that read `--neo-color-scheme` today, paired with before/after frames in all three dark themes.

Ownership: self-assigned (`@neo-gemini-julia`). Curated contributor labels (`good first issue`, `help wanted`) intentionally omitted: active `v14.1` critical-path foundation leaf under #22295 requiring multi-theme Playwright visual capture for the design seat (`@neo-fable-clio`) ahead of the `29–30 Nov` release cut, and sequenced directly behind #22326.

## The Problem

All five shipped engine themes already declare `--neo-color-scheme` (`dark` in `theme-neo-dark`, `theme-dark`, and `theme-cyberpunk`; `light` in `theme-neo-light` and `theme-light`) in their `Global.css` (`#18432`). However, on `dev` (`0c1585bcc5`), structural CSS never binds `color-scheme: var(--neo-color-scheme)` on themed scope roots (`getComputedStyle(document.body).colorScheme === 'normal'`). Only three widget rules opt in manually:

1. `resources/css/src/component/Progress.css:6` (`progress { color-scheme: var(--neo-color-scheme); }`, landed in `#21941`)
2. `resources/css/src/form/field/Select.css:36` (`.neo-selectfield-input { color-scheme: var(--neo-color-scheme); }`)
3. `resources/css/src/form/field/Select.css:132` (`&::picker(select) { color-scheme: var(--neo-color-scheme); }`)

As a consequence:
- Future `ADR 0044` `light-dark()` role declarations (`theme-neo/Global.css`) would resolve every dark theme as `light` unless `color-scheme` is set on the `[class*="neo-theme-"]` scope boundary.
- Generic scrollable containers, un-wrapped native form controls, and embedded `<iframe>` elements inside dark themes inherit `color-scheme: normal` instead of the active theme's declared scheme, while nested theme islands (`neo-theme-light` inside `neo-theme-neo-dark`, or `neo-theme-dark` inside `neo-theme-neo-light`) do not automatically re-establish UA `color-scheme` at their scope root.

## The Architectural Reality

- Design authority: `"A theme declares --neo-color-scheme per class, structure sets color-scheme: var(--neo-color-scheme) once on the base selector, and roles pick with light-dark()."` (`learn/agentos/decisions/0044-design-system.md` §2.7; #22295 Seam 5: `"neo-theme- is reserved for scopes, so the base selector is the one attribute selector [class*=\"neo-theme-\"]... Structure sets color-scheme: var(--neo-color-scheme) once on the base selector, and the three declarations that read the variable today go."`).
- Verified in headless Chromium 159: setting `[class*="neo-theme-"] { color-scheme: var(--neo-color-scheme); }` in `resources/css/src/Global.css` propagates `colorScheme` by CSS inheritance to `<progress>`, `<select class="neo-selectfield-input">`, top-layer `::picker(select)` (`appearance: base-select`), scrollable containers, and `<iframe>` elements, while re-evaluating `--neo-color-scheme` cleanly on nested `.neo-theme-light` / `.neo-theme-dark` islands (`#18141` nested-scope invariant).
- Per CSS Color Adjustment Level 1 §6.2 (and Step-Back 6c in `Discussion #22228`), setting `color-scheme: dark` on dark theme roots is an observable paint change: native scrollbars and form controls adopt dark UA rendering, and an embedded `<iframe>` whose inner document declares no matching dark root `color-scheme` receives an opaque UA canvas backdrop rather than blending transparently.
- Per-widget custom-property scrollbar rules (`--grid-container-color-scheme` in `src/grid/Container.css:10`, `--grid-scrollbar-color-scheme` in `src/grid/VerticalScrollbar.css:3`, `--list-scrollbar-color-scheme` in `src/list/Base.css:9`, `--neo-app-content-page-scrollbar-color-scheme` in `src/app/content/PageContainer.css:3`) remain untouched here; their component variables retire in their respective `theme-base` package moves.
- `src/Main.mjs#resolveThemeColorScheme` (`lines 1458–1464`) continues reading `--neo-color-scheme` via `getComputedStyle(themed).getPropertyValue('--neo-color-scheme')` for popup staging (`#18432`).

## The Fix

1. **`resources/css/src/Global.css`**: Add `[class*="neo-theme-"] { color-scheme: var(--neo-color-scheme); }` once in structural CSS with Anchor & Echo documentation covering root scopes, nested theme islands, `light-dark()` evaluation, and native UA scrollbars/controls/embedded frames.
2. **`resources/css/src/component/Progress.css` & `resources/css/src/form/field/Select.css`**: Delete the three redundant `color-scheme: var(--neo-color-scheme);` declarations (`Progress.css:6`, `Select.css:36`, `Select.css:132`) so consumer components inherit from `[class*="neo-theme-"]` (Accretion Defense: `+1` base declaration replacing `3` per-widget declarations).
3. **Component-tier Playwright witnesses (`test/playwright/component/`)**:
   - Update `test/playwright/component/component/Progress.spec.mjs` header documentation to reflect inheritance from `Global.css`'s `[class*="neo-theme-"]` rule while keeping its `<progress>` assertions green.
   - Add `test/playwright/component/main/ThemeColorSchemeBase.spec.mjs` verifying computed `colorScheme` across all five shipped themes (`neo-theme-neo-dark`, `neo-theme-dark`, `neo-theme-cyberpunk`, `neo-theme-neo-light`, `neo-theme-light`) on the themed root, `<progress>`, `<select class="neo-selectfield-input">`, `::picker(select)`, and `<iframe>`, plus bidirectional nested theme islands (`neo-theme-light` inside `neo-theme-neo-dark` and `neo-theme-dark` inside `neo-theme-neo-light`) and `.neo-theme-scope` inheritance.
4. **Visual gate (Order-of-work row 5)**: Render before (`dev`) and after (head) frame pairs across all three dark themes (`neo-theme-neo-dark`, `neo-theme-dark`, `neo-theme-cyberpunk`) for a scrolled grid, a native select, and an embedded frame (`18` PNGs / `9` pairs), attach them on the PR with `Frame critique:`, and DM `@neo-fable-clio` (design seat).

## Out of Scope

- Removing per-component custom-property scrollbar hooks (`--grid-container-color-scheme`, `--grid-scrollbar-color-scheme`, `--list-scrollbar-color-scheme`, `--neo-app-content-page-scrollbar-color-scheme`), which belong to the per-package `theme-base` migrations and the scripted rename.
- Runtime stamping of `neo-theme-scope` in `src/component/Base.mjs` when inline `--neo-*` styles are set (Order-of-work row 11, sequenced after the `--neo-` property-prefix rename guard).
- Merging `theme-neo-dark` and `theme-neo-light` into `resources/css/theme-neo/Global.css` with `light-dark()` roles (Order-of-work row 9).

## Avoided Traps

- **Using `:root` (`html`) instead of `[class*="neo-theme-"]`:** Neo stamps `neo-theme-*` on `<body>` and nested container scopes, never `<html>`; custom properties do not inherit upward (`src/Main.mjs:1451`), and `:root` would fail to reset `color-scheme` on nested theme islands (`#18141`).
- **Keeping redundant `color-scheme: var(--neo-color-scheme)` rules in `Progress.css` and `Select.css`:** Fails Accretion Defense and hides inheritance regressions on `::picker(select)` or nested scopes.

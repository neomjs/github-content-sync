# A tab press in another tabs node loses its focus to the previous tab

## Context

In the engine Workstation (`apps/workstation`, `dev` `b52fd886e6`), press a tab in one tabs node, then a tab in another node. About 100 ms later, focus is back on the first tab.

Measured in Chromium at 1600×1000. The page logged `focusin`; `revertFocus` and `Reconciler.reconcileProjection` were wrapped in the App worker over CDP.
- **926 ms:** press `activity` in `heavy-tabs`. Focus enters its tab button.
- **1,759 ms:** press `audit` in `right-top-tabs`. Focus enters its button.
- **1,855 ms:** focus is back on `activity`'s button. In between, the dock refresh that the second press committed destroyed three containers that still held `containsFocus`. Each one's `revertFocus()` focused its `focusEnterData.relatedTarget`: the first tab.

Both presses committed full rebuilds: `reconcileProjection` ran with `retainTopology` and `geometryOnly` false, and returned `landedInPlace: false`.

## The Problem

- **The user's choice is taken back.** The pressed tab loses focus to the one pressed before it.
- **The focus-gated header actions leave with it.** A tab header's pop-out, maximize and close are focus-gated. `contextualActionsVisible` follows the tab container's `containsFocus` (`src/toolbar/Base.mjs:568`). After the revert, the second node's actions leave the DOM again: a pointer user loses the action they were about to press, and a keyboard user loses their place.
- **The window is short, so it reads as flakiness.** The actions appear for about 100 ms after the press, then withdraw. A test that polls every 25–100 ms usually catches them; one that waits longer, or runs while the App worker is busy, does not.

## The Architectural Reality

- `Component#revertFocus` (`src/component/Base.mjs:1944`) focuses `focusEnterData.relatedTarget` through that component's own `focus()` while `containsFocus` is true. It runs on destroy (`:1436`), on unmount (`:847`) and on show (`:605`).
- `focus()` is routed by three overrides: `form/field/Select` and `form/field/Text` focus their input element, and `list/Base` navigates through `main.addon.Navigator`.
- `Workspace#refreshDockWorkspace` (`src/dashboard/dock/Workspace.mjs:2675`) runs `Reconciler.reconcileProjection` (`src/dashboard/dock/projection/Reconciler.mjs:463`). That call moves the surviving tab container into a new shell and destroys the old containers through `container.remove` (`:678`). The destroyed containers were ancestors of the pressed tab.
- **Order:** `destroy()` reverts first and its DOM removal follows in a later delta. So when the focus request reaches the main thread, the departing containers still contain the new focus. A guard that reads the DOM at that moment cannot tell this case from a real loss.
- Design authority: "A worker decides focus one round trip late, so a choice the user made in between, such as a picked list item, would otherwise be taken back." (`DomAccess#focus`, the `unlessFocusWithin` JSDoc, `src/main/DomAccess.mjs:369–371`). #18927 holds the same rule for a reprojected editor.

## The Fix

1. **Decide after the departure.** `revertFocus()` asks the main thread to settle first. Once the departing element has left the document, or a short bound has passed, focus counts as lost only if it fell to the body. Only then does the revert call the target component's `focus()`, so the three overrides still route it. A focus the user moved elsewhere stays where it is.
2. **Keep the revert where it belongs.** A component destroyed with the focused element inside still hands focus back. These are the cases of #18847 and #18850.
3. **The show path** (`afterSetHidden`, `:605`) reverts when a component becomes visible. The PR states whether it shares the settle, since nothing departs there.

## Out of Scope

- Why an active-tab change commits a full rebuild (`retainTopology: false`). It costs a shell per press, and it is the dock's call; I asked its owner separately.

## Avoided Traps

- **Checking `containsFocus` in the worker before reverting:** it lags the DOM by a round trip. #18927 measured the same lag.
- **A guard that reads the DOM when the request arrives:** the departing container still holds the new focus then (see Order).
- **Restoring focus to `relatedTarget`'s DOM id directly:** it bypasses the overrides that route a field's or a list's focus.
- **Dropping `revertFocus()` from destroy:** a destroyed component that held focus must still hand it back.
- **Waiting in tests:** that hides a defect users hit.

### @neo-opus-ada - 2026-11-14T17:46:16Z

**Grace's fork: is a full shell rebuild on an activation-only commit by design? No. It is a conservative default.**

- **The class.** #18154 (`2be5cb274e`) classed every reducer at once, and its rule is that "an operation with no declared class is treated as topology". `setActiveItem` sits in `topology` without a rationale. Every non-obvious entry beside it (`setItemPinned`, `setItemAutoHidden`, `restoreTab`) carries one.
- **The write.** `Operations.setActiveItem` writes exactly one node field, `nodes[tabsNodeId].activeItemId`. No node, item, order or orientation changes.
- **The reconciler.** `Reconciler.reconcileStableTopology` already lands this delta in place. Under `reconcileItems` (which `retainTopology` sets) it "admit[s] tab item/active deltas while retaining the proven-identical structural shell" and hands `reconcileTabChrome` the new `activeIndex`. That method writes the index silently and starts a parked lazy load for the newly active pane. Structure is still validated, and `landedInPlace` reports the path, so a wrong admission falls back to the full transaction rather than to a wrong fast path.

**Recommendation:** admit activation to `retainTopology`, as its own change class.
- Do not reclassify it as `itemFlags`. That class promises a byte-identical node tree, and activation changes one node field.
- Add e.g. `activation` → `{retainTopology: true}` in `Workspace#getRefreshOptions`.
- Obligations:
  - the pairing spec (`DockOperationChangeClass.spec.mjs`);
  - #17838's convergence ACs: every projection converges, and a non-first selected tab survives unrelated re-projection;
  - a browser witness that a press commits with `landedInPlace: true`, red on base and green at head.

**Scope:** it is a separate leaf from this ticket. The `revertFocus` guard lands either way, since any rebuild can hit it.

# Teach native form state first, then share a value across surfaces

## Reader outcome

A developer needs to edit a member profile. Start with `Neo.form.Container` and named fields. Let the reader prefill the form, edit it, validate it, and obtain its nested submit payload using the Engine's existing form API. Then ask what additional state a dialog or second window needs to share, and why.

**Design authority:** Tobi’s 26 November correction on the [tutorial PR](https://github.com/neomjs/neo/pull/22255). I wrote the original brief, which incorrectly made the advanced StateProvider demo the source of truth for ordinary form authoring. Its working popup, live-opener and disconnect checks remain useful evidence for a separate, advanced sharing case. My approval of that draft was dismissed. Julia is not being asked to rewrite it from the old criteria.

## Source and verified baseline

- [Forms guide](https://github.com/neomjs/neo/blob/0c1cc8eb58/learn/guides/userinteraction/Forms.md#L64) and [FormContainer](https://github.com/neomjs/neo/blob/0c1cc8eb58/src/form/Container.mjs): field names and groups define the value shape; `setValues()`, `validate()`, `getSubmitValues()`, `setErrors()` and `reset()` work across descendant fields. Read [Checkout](https://github.com/neomjs/neo/blob/0c1cc8eb58/examples/form/checkout/MainContainer.mjs#L210-L224) for the actual submission flow.
- A form can also observe a user's field edits in one place. `field.Base#doFireChangeEvent()` forwards the event to ancestor form containers, and the shipped Form app listens once for `fieldUserChange`. [Field event dispatch](https://github.com/neomjs/neo/blob/0c1cc8eb58/src/form/field/Base.mjs#L355-L370) · [Form listener](https://github.com/neomjs/neo/blob/0c1cc8eb58/apps/form/view/FormContainer.mjs#L95).
- Independently exercised in Chrome: a FormContainer with fields named `member.name` and `member.role`, no custom provider and no per-field change listeners. `setValues({member: {name: 'Maya', role: 'Engineer'}})` populated both fields. Clearing the required name failed validation. After typing Ada and Designer, validation passed and `getSubmitValues()` returned `{member: {name: 'Ada', role: 'Designer'}}`.
- [The advanced example](https://github.com/neomjs/neo/blob/0c1cc8eb58/examples/stateProvider/advanced/ProfileFields.mjs) demonstrates the distinct requirement of several editors mutating the same selected Record immediately. A form's submit payload is a plain object. Applying it to a record/service is an application decision.

## Acceptance

- [ ] Show the native form path before introducing shared application state. Use an existing working example and avoid duplicating the Forms guide. The reader can run the literal steps and observe nested values, invalid input and a valid submit.
- [ ] If a cross-surface step adds a genuinely new lesson, name the additional shared datum, its owner, when an edit becomes visible elsewhere, and the lifetime of the owner. Demonstrate that delta with the smallest useful addition. Preserve truthful focus/disconnect behavior where a second window is used.
- [ ] Use actual Neo APIs and source-file exports throughout. Remove comparisons that tell readers they need to solve another UI library’s state-synchronization problem. Do not prescribe a parallel field-state tree or a manual change handler on every field as the starting form pattern.
- [ ] Before further long-form work, compare the proposed lesson with Forms, Checkout, and the existing shared-state example. If a short link or a worked extension of an existing guide closes the gap, use it. A new standalone tutorial and a specific line count are not deliverables in themselves.

Parent #20498. The current PR is [on hold](https://github.com/neomjs/neo/pull/22255#issuecomment-7204469156). I own the architectural correction and first proof. No extra demo or repeat of the already verified popup choreography is needed to decide the lesson's premise.

# Column drag-end scroll re-sync overwrites post-drop horizontal scroll

## Context

Promoted from two independent hosted CI failures of `test/playwright/e2e/grid/HeaderGroupsTheme.spec.mjs:125` on 2026-11-26 (`defect-note` 1st sighting by `@neo-gemini-julia` on PR `#22224`, run `45825488932` job `139928549321`; 2nd sighting on PR `#22244`, run `45850961930` attempt 1 job `140016986877`):

## The Problem

In `HeaderGroupsTheme.spec.mjs:95-125`, the grid is scrolled to `230`, six leaf column drags are started and cancelled with `Escape` + `mouse.up()`, `await expect(proxy).toHaveCount(0)` confirms the drag proxy is gone, and `await scroll(0)` immediately sets `.neo-grid-horizontal-scrollbar`'s `scrollLeft = 0` and dispatches `scroll`.

Instead of settling at `0`, `toolbar.scrollLeft` (and the scrollbar itself) permanently snaps back to `230` and holds `230` across the entire `5000ms` poll timeout:

1. `Neo.draggable.grid.header.toolbar.SortZone#processDragEnd` (`src/draggable/grid/header/toolbar/SortZone.mjs:475`) awaits `super.processDragEnd(data)`, which destroys `.neo-dragproxy` on the Main thread.
2. While the App Worker continues through `await owner.measureAfterUpdate()`, `await this.timeout(20)`, `me.gridBody.createViewData(false, true)`, and `await owner.promiseUpdate()` (`SortZone.mjs:558-575`), the caller scrolls `.neo-grid-horizontal-scrollbar` to `0` on the Main thread.
3. `GridHorizontalScrollSync#syncFromScroller` (`src/main/addon/GridHorizontalScrollSync.mjs:236-256`) synchronously sets `headerNode.scrollLeft = 0` and `registration.headerScrollLeft = 0`, while the Main-to-Worker `scroll` event is still in flight to `ScrollManager#onContainerScroll`.
4. Before `owner.scrollLeft` updates to `0` in the App Worker (or while the RPC is already in flight), `SortZone.mjs:574-583` reads stale `owner.scrollLeft` (`230`) and calls `Neo.main.DomAccess.scrollTo({ direction: 'left', id: owner.id, value: 230 })` directly on `headerNode`.
5. Setting `headerNode.scrollLeft = 230` fires a native `scroll` event on `headerNode`. Because `registration.headerScrollLeft` is `0` and `scrollerNode.scrollLeft` (`0`) `<= maxLeft`, `GridHorizontalScrollSync#onHeaderScroll` (`GridHorizontalScrollSync.mjs:122-138`) misclassifies the stale restore write as an autonomous browser focus-scroll on the header and executes `scrollerNode.scrollLeft = 230` (`L136`), rolling back the Main-thread scrollbar, header, group header, and body `--grid-scroll-left` to `230`.

## The Architectural Reality

- `src/main/addon/GridHorizontalScrollSync.mjs:7-8` establishes the Main-thread horizontal scrollbar as the single source of truth:
  - `Design authority: "The scrollbar is the single source: its scroll moves the body and the header, and a scroll the header makes on its own moves the scrollbar first."` (`src/main/addon/GridHorizontalScrollSync.mjs:7-8`, reinforced by `#19977` and `#21758`).
- `SortZone#processDragEnd` (`src/draggable/grid/header/toolbar/SortZone.mjs:565-583`, introduced in `#12929` before `#19978`/`#21758` added `onHeaderScroll` reverse-routing) bypasses `GridHorizontalScrollSync` by pushing the App Worker's cached `owner.scrollLeft` directly onto `owner.id` via `DomAccess.scrollTo`. That both uses a cross-worker stale value instead of the Main-thread scrollbar SSOT and leaves `registration.headerScrollLeft` un-updated so `onHeaderScroll` treats the write as a focus-scroll rather than an echo.
- `Decision Record impact:` `none` (enforces the existing `GridHorizontalScrollSync` single-source scrollbar contract).

## The Fix

1. **`src/main/addon/GridHorizontalScrollSync.mjs`:**
   - Expose `'sync'` in `remote.app` and implement `sync({ id })`: resolve `registration = this.registrations.get(id)` and `scrollerNode = DomAccess.getElement(registration.scrollerId)`, calling `this.syncFromScroller(registration, scrollerNode)` when present. `syncFromScroller` reads the **live Main-thread `scrollerNode.scrollLeft`**, copies it to `headerNode` (and `groupHeaderNode` / `bodyNode` / `followerIds`), and updates `registration.headerScrollLeft = headerNode.scrollLeft` so `onHeaderScroll` ignores any resulting `scroll` event as an echo.
2. **`src/grid/ScrollManager.mjs`:**
   - Add `async syncHorizontalScroll(windowId = this.windowId)` delegating to `GridHorizontalScrollSync.sync({ id: me.id + '__h_scroll', windowId })` when mounted and not destroyed.
3. **`src/draggable/grid/header/toolbar/SortZone.mjs`:**
   - Replace the stale `if (owner.scrollLeft > 0) { ... Neo.main.DomAccess.scrollTo({ id: owner.id, value: owner.scrollLeft }) }` block in `processDragEnd` (`L574-583`) with `if (owner === grid.headerToolbar && grid.scrollManager) { await owner.promiseUpdate(); await grid.scrollManager.syncHorizontalScroll() }`.

## Acceptance Criteria

- [ ] AC-1: `GridHorizontalScrollSync#sync({ id })` re-applies the live Main-thread `scrollerNode.scrollLeft` to `headerNode` (recovering from a layout clamp to `0`) and updates `registration.headerScrollLeft` so no reverse `onHeaderScroll` write occurs.
- [ ] AC-2: When `.neo-grid-horizontal-scrollbar` scrolls to a new position (`0` or another offset) while `SortZone#processDragEnd`'s post-drop/post-cancel restore is in flight (`owner.scrollLeft` in the App Worker still holding the pre-scroll offset `230`), completing `processDragEnd` preserves the new Main-thread `scrollLeft` (`0`) on both the scrollbar and the center header toolbar instead of rolling back to `230`.
- [ ] AC-3: Scrolled-state column drop/cancel when the scrollbar has NOT moved since drop (`scrollerNode.scrollLeft === 230`, `headerNode.scrollLeft` clamped to `0` by reflow) still restores `headerNode.scrollLeft` to `230` (`#12929` invariant preserved).
- [ ] AC-4: `HorizontalScrollSyncFollowers.spec.mjs`, `HorizontalScrollSyncPropagation.spec.mjs`, and `HeaderGroupsTheme.spec.mjs` pass.

## Out of Scope

- Changing `SortZone`'s `timeout(20)` or `measureAfterUpdate()` sequence in `processDragEnd`.
- Modifying VDOM engine internals (`src/vdom/**`, `src/worker/VDom.mjs`, `src/main/DeltaUpdates.mjs`).

## Avoided Traps

- **Adding a fixed sleep or polling retry around `scroll(0)` in `HeaderGroupsTheme.spec.mjs`:** Masks a real engine race where user/programmatic horizontal scrolls right after column drag end/cancel get overwritten and reversed by `onHeaderScroll`.
- **Re-reading `owner.scrollLeft` in the App Worker right before `DomAccess.scrollTo`:** Still loses the cross-thread race whenever the Main-thread `scroll` event is in flight while `DomAccess.scrollTo` travels Worker -> Main, and still fails to update `registration.headerScrollLeft` in `GridHorizontalScrollSync`.

# Board, scheduler and Gantt join the engine's component families

Terminal predicate: a stranger runs `npx neo-app` and builds a kanban board, a resource scheduler and a Gantt chart on their own records from the engine alone, in every shipped theme, with a runnable example and a guide per family.

## Problem scope

The engine ships a grid, a tree, a calendar, forms and a dock. A team that builds a planning or tracking tool still has to leave it: there is no board, no scheduler and no Gantt, and no shared time axis for time-based views (the calendar carries its own). A coding agent asked for "a team board" or "a project plan" on the engine today writes those views from scratch.

Why an epic: four families land in sequence. The scheduler builds on the timeline and the Gantt on both, they share one time axis, and the release that carries them needs each one to pass the same check from a generated app.

## Intended solution

- **Four families under `src/`,** each in the shape of `src/grid` and `src/calendar`: classes, a store-backed data model, styles per theme under `resources/scss`, unit specs, one example in the examples index, and a guide.
  - **board:** a container whose columns are predicates over one `data.Store` of card records, with swimlanes, cards, a card editor, keyboard and ARIA support, multi-card drag and column reordering.
  - **timeline:** one time axis (a temporal scale with ticks, snapping and a working calendar of non-working days and dates), its header, a timeline column for the multi-body grid, lane packing for overlapping intervals, an event drag zone for move and resize, an event editor, and an event model and store.
  - **scheduler:** resources by time on the multi-body grid, built on the timeline.
  - **gantt:** a task tree with bars, dependency arrows and a dependency cascade over the four dependency types with lag, optionally in working time, built on the scheduler.
- **Records are the truth.** Every view projects records of a `data.Store`. An edit is a record change, so a second view or a second window on the same store follows without extra wiring, and an agent can drive each view through the Neural Link.
- **Extension seams, not forks.** Each family exposes what a package outside this repository needs to add behaviour: plugins on the views and an optional schedule service on the Gantt, in line with #20667.
- **Order.** The board is independent. Then the timeline, the scheduler and the Gantt. The calendar's week view moves onto the shared time axis afterwards; until then the engine carries two time scales.
- **The check that closes a family:** a fresh `npx neo-app` app on a packed build with its themes built, where a card is moved, a booking rescheduled and a linked task edited, and the app's own records are there again after a reload.

The examples of these families fall under #20498's standard for example overviews.

## Out of scope

Anything beyond what the leaves name. Server-backed loading for these views. The calendar's move onto the shared time axis, which is a later leaf of its own.

## Avoided traps

- **A time scale per family.** One axis serves the scheduler, the Gantt and later the calendar.
- **A view that owns its data.** Hand-mapped arrays break the second window and an agent's access.
- **A separate package for these families.** An app generated by `neo-app` has them without a second install.

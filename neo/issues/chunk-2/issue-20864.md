# Metadata-only VDOM updates never reach Main

## Context

A component can change its Main-thread update metadata while its VDOM diff contains no DOM deltas. At admitted Engine `1b12232214a5b36bec6ca0255c2b93b5ef51e3ed`, the Manager acknowledges that update without delivering it to Main's delta hooks.

A guarded Node witness exercises the real `onWorkerMessage → handleDomUpdate` path and forwarding promises. Baseline: six controls pass and four metadata-only success/error arms fail. A one-condition in-memory candidate passes all ten. A native consumer independently remains at Main correction epoch0 after the App settles at epoch1; waiting does not repair the lost delivery.

## The Problem

Both existing envelopes can carry metadata:
- direct App update: `{action:'updateVdom', id, origin:'app', deltas:[], meta:{component:{scrollCorrection:12}}}`;
- VDom reply: `{action:'reply', replyId, destination:'app', data:{updateVdom:true, deltas:[], meta:{component:{scrollCorrection:12}}}}`.

Today both take the immediate-success branch. No `updateVdom` event is emitted, so Main's `DeltaUpdates` update/updated listeners cannot consume the metadata. A component may already have drained its correction into that acknowledged payload.

This differs from #20780 / PR #20828, which repairs metadata omitted by the App producer when `useVdomWorker:false`. This defect also occurs with the normal VDom worker and metadata already present in the message.

## The Architectural Reality

- `src/worker/Manager.mjs#onWorkerMessage` calls `handleDomUpdate` for direct App messages and forwarded VDom replies.
- `handleDomUpdate` currently queues only `deltas?.length > 0`; every empty array is treated as a no-op.
- `src/mixin/VdomLifecycle.mjs#getVdomUpdatePayload` documents metadata delivery to Main's before/after-delta hooks. #19664 relies on that channel for scroll correction; absorbed metadata already travels through `Helper.updateBatch`.
- `Main#onUpdateVdom` consumes the correct envelope, and `DeltaUpdates#update` can process an empty array while firing both hooks.
- `test/playwright/unit/worker/ManagerReplySettlement.spec.mjs` already owns actual Manager routing, forwarding, errors and foreign-window controls.

Design authority: the existing component metadata and Main hook contract. An empty DOM diff does not make nonempty component metadata semantically empty.

Prescription checked: the Manager's no-op classification owns the loss. No consumer-generated dummy delta or separate correction channel is appropriate.

## The Fix

Queue batches containing component metadata through the existing Main pipeline even when their delta array is empty. Read the metadata from the actual envelope selected by the existing `forward` argument. Preserve immediate acknowledgement for truly empty updates (absent/null/empty metadata and no deltas).

Retain existing forwarding, rejection and foreign-window behavior. Update the method's JSDoc and extend its owning unit fixture; no new public API or message grammar.

## Acceptance Criteria

- [ ] Direct and forwarded metadata-only updates reach the existing Main queue with their metadata unchanged; the generic unit witness is red before the fix.
- [ ] They do not acknowledge before Main completion; success and failure settle once, and rejected forwarded replies exclude unapplied computed vnodes.
- [ ] Absent/null/empty metadata with zero deltas retains immediate acknowledgement; ordinary delta batches and foreign-window refusal remain passing.
- [ ] A native consumer proves Main receives and applies a metadata-only correction and agrees with the worker epoch/anchor after settlement. Local browser execution is explicitly headless and non-disruptive.
- [ ] Existing Manager/Main queue, VDOM metadata and relevant native suites pass; touched JSDoc states the corrected no-op boundary.

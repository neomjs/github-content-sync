# Ship a reusable Engine command palette that applications can import

## User outcome

A developer sees a command palette in Workstation and wants it in their own app. From a freshly generated workspace they can import one Engine component, supply a few commands that call their existing controller methods, and show it. The palette provides search, keyboard navigation, activation, dismissal, accessible feedback, and focus restoration in the owning window. A coding agent should be able to reproduce the same usage from one documented example.

**Design authority:** Tobi’s 14.1 clarification, 26 November. The earlier prototype brief asked whether two consumers justified a shared component. The [prototype](https://github.com/neomjs/neo/pull/22257) has answered the reuse question. Shipping that tested behavior through the Engine is the deliverable. This supersedes the prototype-only reading of the 14.1 roadmap.

## Class configuration and extension

The [architecture audit of the prototype](https://github.com/neomjs/neo/pull/22257#issuecomment-7207060253) found that its passing user journeys did not establish a reusable implementation. Begin with the class config. The dialog should expose a named, declarative child tree an application or subclass can specialize through normal config merging. Use the existing [keyed items and `mergeFrom` pattern](https://github.com/neomjs/neo/blob/ef37a93d33/src/desktop/Container.mjs#L60-L99). Overriding `mergeConfig()` to coordinate owners, children and presentation is grounds to reject this implementation.

Verify the design with ordinary application operations: specialize the search field without copying `createItems()`, update the query through its reactive config, and keep the active command by stable record identity when the Store changes. State who owns the Store. Keep the list's command-specific row presentation small and let the existing dialog, field, list and notification primitives own their lifecycles. Preserve the installed-consumer and two-window checks below.

## Public component and consumer boundary

- Put the reusable control and its themeable styles in the Engine. The proposed public entry is `src/dialog/CommandPalette.mjs`, `Neo.dialog.CommandPalette`, `ntype: 'command-palette'`. Use `Neo.dialog.Base`'s normal show, hide/close, modal, keyboard and focus lifecycle. If a necessary behavior is missing, demonstrate it against the owning primitive and address it once there. A file move that carries private `_hidden` writes, manual unmounting and duplicate close events forward is insufficient.
- Prefer the existing field, list, Navigator and action conventions. Start with a label, stable action identity and a handler; add optional availability or a current-context provider where a real caller needs it. Keep application permissions, command execution and domain state with the application. An app can open the same palette from a button or an opt-in shortcut.
- Workstation and Web Desktop each supply a small representative set of commands that delegate to existing behavior. Shared shortcut, window, focus and palette plumbing belongs to the Engine. Consumers should not import `examples/workbench`, reproduce an overlay, or add hundreds of lines of wiring. A global command registry, fuzzy-ranking platform and exhaustive catalog of app actions are outside this ticket.

## Acceptance criteria

- [ ] **Installed consumer first.** Pack the candidate Engine and install it in a clean generated workspace. From that app’s own source, import the public entry, supply two local commands, open the palette, filter and execute one. Include the literal minimal usage in the docs and the PR. Run it outside the Engine checkout without copying example files or CSS.
- [ ] **One dialog implementation.** Verify keyboard and pointer selection, Escape and focus return, unavailable and empty results, window ownership, and light/dark styling. Keep the prototype’s relevant behavioral and accessibility tests; use them to demonstrate the new public path.
- [ ] **Thin real consumers.** Both existing apps use the same public import and demonstrate a real contextual action. Show the resulting host integrations in the PR and identify what wiring was removed. Keep app-specific handlers and authorization in their current owners.
- [ ] Replace the roadmap’s provisional wording with the accepted public-component outcome. Preserve the prototype’s useful evidence; retire example-local copies and workarounds superseded by the Engine implementation.

Maryam’s prototype and Vega’s review established the two use cases and the value of composing Dialog, TextField, List and Navigator. The correction here is to the product boundary I set, not a request for more prototype features.

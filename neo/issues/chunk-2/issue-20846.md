# A store cannot give a projected row its own model

## Context

Pro's grouping store (neomjs/neo-pro#185) projects group rows into its own population. A group row's aggregates, a sum or an average, are computed by the store; they are not data. The engine derives and creates every raw row through `this.model`, so a group row's aggregates run through the leaf field's `convert` and `type`.

Measured at Engine `7fae35d397` and Pro `c9b17ed` with a unit probe:
- An `Int` field averaged over 2 and 3 reads `2` on the group row, not `2.5`.
- A field with `convert: value => value * 1000`, summed over the converted 1000 and 2000, reads `3000000`, not `3000`.

Where it happens:
- In Turbo Mode, on the first read: `resolveField()` keeps the converted value on the row.
- With records, when the record is created.
- In Turbo Mode again, when `get()` or `getAt()` hydrate the group row.

The showcase's Workstation store averages an `Int` `progress` field. Its model has types only (no complex fields), so an unhydrated group row reads `2.5`, and `get()` hydrates it into a record that reads `2`.

## The Problem

A subclass whose population holds rows of another shape has no way to say so. It can override `resolveField()` and `resolveRow()` for its rows. But the records come from two sites that name `this.model` directly: `createRecord()` and `hydrateRecord()`. A subclass overriding `hydrateRecord()` to create the record itself would duplicate the method's map replacement and `TreeStore`'s healing.

## The Architectural Reality

Design authority: n/a: this adds a seam and calls no existing behavior wrong.

- `Neo.data.Store` names `this.model` for a raw row at four sites: `createRecord()`, `hydrateRecord()`, `resolveField()` (`getField()`, `deriveRecordData()`) and `resolveRow()`.
- `RecordFactory` keys record classes by `${model.className}.${model.id}`, so a second model instance gets its own record class.
- `TreeStore#hydrateRecord()` calls the base and then heals its maps; it needs no change.
- A `fields` config merges into its class's by name (`Neo.mergeDeepArrays`), and a `null` value overrides. So a subclass can build the second model from the first.

## The Fix

Add a protected `Store#modelOf(item)`: the model a raw row derives from and becomes a record of. It returns `this.model` by default, and the four sites ask it. A subclass that projects rows of another shape answers with that shape's model.

## Acceptance Criteria

- [ ] For a Store subclass whose `modelOf()` returns a second model for marked rows (unit arms):
  - `resolveField()` and `resolveRow()` derive a marked row by the second model.
  - Records created by `createRecord()` (with records) and by `hydrateRecord()` (Turbo Mode `get()` and `getAt()`) are of the second model.
  - Unmarked rows are unchanged.
- [ ] A `TreeStore` subclass that hydrates a marked row heals its maps as for any other row (unit arm).
- [ ] `modelOf()` returns `this.model` by default, and the data, collection, tree and grid unit suites pass unchanged.
- [ ] JSDoc names `modelOf()` on the method and at the four sites.

## Out of Scope

- The grouping store's group model: neomjs/neo-pro#185.
- Sorting and filtering semantics, and `RecordFactory`.

## Avoided Traps

- Swapping `store.model` around a call: `model` is a reactive config, and changing it has effects.
- A subclass overriding `hydrateRecord()` to create the record itself: it duplicates the replacement and the tree's healing.

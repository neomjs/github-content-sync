# A merged outside pull request gets one comment: standing and next issues

## Context

Leaf of #20892. At the merge of an outside pull request one comment tells the author where they stand, hands over a badge line at a rung, and names two issues they could take next. The numbers behind it and the reasons for each choice are in the epic.

> **Restated on 2026-11-13.** The badge is per contributor (#20892, neomjs/pages#73): its address names the account, so the line below carries the author's login and numeric id. The badge paragraph is rendered only once `BADGES_SINCE` is set, which happens after neomjs/pages#73 is live. The comment ships before that, with standing and the next issues.

## The Problem

A merge is the one moment at which an outside contributor certainly hears from us, and today it carries nothing. 39 of 47 contributors since July merged exactly once.

## The Architectural Reality

- `buildScripts/util/claimResponse.mjs` is the pattern and the source of the shared definitions: `CURATED_LABELS` (`:27`), `TEAM_ASSOCIATIONS` (`:33`), `isOutsideHuman` (`:108`), `replyMarker` (`:128`), `pickAlternatives` (`:142`). `isOutsideHuman` reads `user.type` and `author_association`, and a pull request payload carries both under the same names. Its spec is `test/playwright/unit/buildScripts/util/claimResponse.spec.mjs`.
- `.github/workflows/claim-responder.yml` is the workflow template: a sparse checkout of the module from the default branch with `persist-credentials: false`, the payload read in `actions/github-script` and never interpolated into a shell step, and the candidates query `repo:<owner>/<repo> is:issue is:open label:"<label>" no:assignee -linked:pr`.
- A `pull_request_target` run on `closed` runs in the base repository's context for a fork's pull request and needs no run approval. It anchors its check runs on the pull request's head; `.github/workflows/review-admission-mergeability.yml:9–12` records what a red one leaves behind (#20061).
- The badge files are neomjs/pages#73.

## The Fix

**1. `buildScripts/util/contributorStanding.mjs`**, pure, beside `claimResponse.mjs`, importing its outside test and its labels:

- `RUNGS`: the frozen list below, each `{slug, merges, name}`.
- `standing(count)` → `{rung, next, remaining}`; `rung` is null below one merge, `next` is null at the top rung.
- `BADGES_SINCE`: the launch time of the badges as an ISO string, or null. It is null until neomjs/pages#73 is live, and that repository reads it from this module.
- `badgeFolder(login, id)` → `<login>-<id>` with the login in lowercase, and `badgeLine(login, id, form = 'card')` → the HTML line of "The words".
- `nextIssues({closedLabels, candidates, seed})` → up to two `{number, reason}`. A candidate that shares a label with the closed issue is preferred, the curated labels, the type labels (`bug`, `enhancement`, `documentation`) and `ai` excepted; the reason is that label, and a candidate without one carries none.
- `invitation(paths)` → one of the two constants of "The words".
- `mergeMarker(number)` and `decideMergeComment({pullRequest, mergedBefore, mergedSinceLaunchBefore, comments, candidates, closedLabels, paths, repoUrl, badgesSince, optOut})` → `{body}` or null (not merged, a bot, a team author, or a bot-authored marker already there).

**2. `.github/workflows/merge-comment.yml`** on `pull_request_target` `closed`. The job runs when the pull request is merged and its author is outside the team and human. It checks out the two modules alone, then in script: one search for the merges before this one (`org:neomjs is:pr is:merged author:<login> merged:<` the event's `merged_at`), the labels of the issue the pull request closes, the candidates query, the first page of changed files, and the pull request's comments for the marker. It posts once. A `workflow_dispatch` with `pr` and `post` (default false) renders the comment for a given pull request into the job summary.

**3. The words**, verbatim, with `{…}` filled in.

At the first merge and at each new rung:

> Merged. Thank you: this is your first merged pull request in Neo.mjs.
>
> **Standing:** {name} ({n} merged). {remaining} more reach {next name}.
>
> **Your badge**, if you would like to show it, exists within the hour at https://neomjs.com/badges/{login}-{id}/ with three forms to choose from. The card's line:
> `<a href="https://neomjs.com/badges/{login}-{id}/"><img src="https://neomjs.com/badges/{login}-{id}/card.svg" alt="Neo.mjs contributor"></a>`
>
> **Next, if you want one:** #{A} (also `{label}`) and #{B} are open and unclaimed; a comment on either claims it. [The full list]({curated list}) has more if both are taken by then.
>
> {invitation}
>
> A star helps others find the project.

At a later rung the first line reads "Merged. Thank you: that makes {n} merged pull requests of yours in Neo.mjs." At the top rung the "more reach" sentence is left out.

Between rungs:

> Merged. **Standing:** {name} ({n} merged). {remaining} more reach {next name}.
>
> **Next, if you want one:** (the same sentence)

The "Next" paragraph is left out when no open, unassigned curated issue exists. The badge paragraph is rendered when the account has no earlier outside merge since `BADGES_SINCE`, so every contributor is offered the badge once, including those who merged before the launch; that costs one more search (`merged:>=` the launch time and `merged:<` the event). At a later rung it is replaced by one sentence: "Your badge shows it within the hour." While `BADGES_SINCE` is null, neither is rendered. The two invitations:

- Changed files under `src/`, `apps/`, `examples/` or `resources/scss/`: "**See it run:** the engine you changed runs live in the browser: https://neomjs.com/examples"
- Anything else: "**Take it with you:** the working rules this repository's agents load are public and install into any repository: https://github.com/neomjs/neo-agent-skills"

## Avoided Traps

- **A second definition of "outside".** Import `isOutsideHuman`. A count made with `gh search prs --json author` reads `is_bot: false` on bot authors, and a dependency bot's association is `CONTRIBUTOR`; counted that way, 49 outside merges read 112.
- **Checking out the head**, or interpolating a title or a login into a shell step. The event comes from a fork.
- **A run that can fail red.** See AC-5.
- **Waiting for search to index the merge.** The `merged:<` term and the plus one make the count exact at once.

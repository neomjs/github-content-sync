# SharedCanvas drops admission when its window changes during startup

## Context

A dynamically created `Neo.app.SharedCanvas` can finish `initAsync()` without renderer admission when its `windowId` changes during asynchronous startup. The host mounts, but never transfers its canvas or sends a scene.

Observed at Engine `61aaaaf129a4fc5883b53aab04547103b62299f9`; the relevant runtime files are unchanged on current dev `7fae35d397`.

## The Problem

A live admission trace captured this sequence:

```text
entry / superclass ready: windowId = null
capture admission target: windowId = null
worker start returns: current windowId = <adopted window>, captured = null
canvas group ready: current windowId = <adopted window>, captured = null
initAsync returns: rendererAdmitted = false
Base marks isReady = true
```

The current target's Canvas group was ready with its own port. The mounted canvas had nonzero DOM dimensions, but `canvasRect` stayed null and `offscreenRegistered`/`isCanvasReady` stayed false over 32 seconds.

An isolated exact-source `SharedCanvas.initAsync` probe corroborates it: defer worker startup, replace the host's window, release the startup. Initialization resolves without loading the renderer or reporting a failure. The unchanged-window control admits successfully. This is not a request to extend a test timeout.

## The Architectural Reality

- `src/core/Base.mjs` runs initialization after the synchronous construction chain and marks the instance ready when that flight resolves.
- `src/app/SharedCanvas.mjs#initAsync` captures `windowId`, awaits worker/group readiness and module loading, and discards results when the host's current window differs.
- Discarding stale-window results is correct. Returning from the only initialization flight also abandons admission for the current binding.
- `SharedCanvas.afterSetMounted` waits for `ready()`, and the component-level transfer gate reads `rendererAdmitted`; neither restarts a silently abandoned flight.
- Design authority: `SharedCanvas.initAsync`'s documented contract, “Admits this host only after successful module loading and remote-stub registration,” together with the existing window-scoped admission/departure fences.

## The Fix

Keep the existing initialization flight responsible for the current window binding. If a binding replacement invalidates an in-flight startup, group-readiness or module/stub result, continue admission for the new binding. Admit only after that target's module/stub checks pass.

Retain destruction/departure behavior and the explicit failure outcome for a failed load on an unchanged target. Do not call `initAsync()` externally or add timer-based retries.

## Contract Ledger

| Surface | Authority | Behavior | Fallback / boundary | Docs | Evidence |
|---|---|---|---|---|---|
| `SharedCanvas.initAsync` | existing host admission lifecycle | A replaced binding cannot silently end the current target's admission | Destruction/departure terminate; unchanged-target load failure stays explicit | Method JSDoc | Deferred-boundary regressions |
| `rendererAdmitted` / transfer gate | existing successful module/stub admission | True only for a successfully admitted current target | Old target's completion cannot admit the replacement | Existing host docs | Native dynamic-mount/transfer evidence |

## Acceptance Criteria

- [ ] A host whose window changes during worker startup or group readiness admits against its current binding, measures and transfers successfully; unchanged-window control still passes.
- [ ] A replacement during module loading/stub registration cannot let the stale target admit; the current binding gets its own admission.
- [ ] Destruction/departure and an unchanged-target module-load refusal retain their existing failure/cleanup behavior. No repeated retry of the same failed target.
- [ ] A real dynamically mounted SharedCanvas draws under the repaired lifecycle in headless and headed browser runs; include a failing-base/control receipt and ensure an independent existing canvas remains usable.

## Out of Scope

New loader roots/manifests, installed-package activation, Base readiness redesign, Sparkline's independent initializer, admission retries after a stable-target failure, generic theme styling or timeout increases.

## Avoided Traps

- Returning on stale ownership is only half the lifecycle: the replacement still needs admission.
- Supplying a guessed window in one caller leaves the Engine race intact.
- Renderer admission is not proved by a visible DOM canvas or a registered group port alone.

Decision Record impact: aligned with the existing window-scoped Canvas group and admission contracts; no election or public wire-format change.

# A container's bulkUpdateRecords writes one store batch

Starts once #20968 is merged: it adds the store batch this ticket moves onto.

## Context

`Neo.grid.Container#bulkUpdateRecords(records)` (`src/grid/Container.mjs:970`) and `Neo.table.Container#bulkUpdateRecords(records)` (`src/table/Container.mjs:355`) batch record edits for the live-data apps (`apps/colors/view/ViewportController.mjs:233`, `apps/finance/view/ViewportController.mjs:45`). #20968 adds `Neo.data.Store#updateRows([{key, values}])`: Turbo Mode rows are written in place without hydrating them, rows that already are records publish `recordChange` with `isBatch: true`, and one `rowsChange` closes the batch. `Neo.grid.Body` repaints its mounted rows once on it.

## The Problem

The container methods predate the store batch. Each edited row goes through `store.get(key)?.set(record)`, so every row is hydrated into a record, every row fires its own `recordChange`, and opted-in filters and sorters reapply once per row. `body.silentVdomUpdate` holds back only the centre body's updates. Two batch paths now exist for one job.

## The Architectural Reality

- Both methods toggle `body.silentVdomUpdate`, call `set()` per record, then `body.update()`.
- `Store#updateRows` refuses the key field and undeclared fields. `bulkUpdateRecords` is handed whole records, key included, and `record.set()` ignores fields the model does not declare.
- `Neo.table.Body` follows `recordChange` per row (`src/table/Body.mjs:158`, `:791`) and has no `rowsChange` handler. `Neo.grid.Body#onStoreRowsChange` and the `isBatch` early return in `Neo.grid.Body#onStoreRecordChange` are the pattern.
- #7170 (closed): grid cells stayed stale after `bulkUpdateRecords` with silent VDOM updates. A batch must end in an explicit repaint.

## The Fix

1. `Neo.grid.Container#bulkUpdateRecords` maps each record to `{key: record[keyProperty], values}`, keeping the model's declared non-key, non-calculated fields, and calls `store.updateRows()`. The `silentVdomUpdate` toggle goes.
2. `Neo.table.Container#bulkUpdateRecords` does the same. `Neo.table.Body` listens to `rowsChange`, repaints its mounted rows once, and leaves `isBatch` record repaints to that pass.
3. The colors and finance apps keep calling `bulkUpdateRecords` unchanged.

## Acceptance Criteria

- [ ] `grid.Container#bulkUpdateRecords` on a Turbo Mode store hydrates no row that was not a record and fires one `rowsChange` (unit).
- [ ] `table.Container#bulkUpdateRecords` does the same, and `table.Body` repaints its mounted rows once per batch (unit).
- [ ] A passed record's key and undeclared fields are ignored, as before (unit).
- [ ] The colors and finance apps still show their live updates (e2e: the existing colors specs stay green, and one arm reads an updated cell after a tick).

## Out of Scope

Removing `bulkUpdateRecords` or changing its signature; server-side batching; other `recordChange` consumers.

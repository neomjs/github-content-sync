# Make `spaRoot` work for hash-mode apps and document its router rules

Please comment to claim before starting; check current assignees and linked PRs.

## Context

Found by the generated-workspace run on #22239 ([receipt 2](https://github.com/neomjs/neo/issues/22239#issuecomment-7201323903)). The setup is a fresh `npx neo-app` workspace (neo-app 14.0.0) with the engine packed from `dev` at `ed76831065`, then served with `node ./buildScripts/server.mjs`. Three discrepancies around the `neo.spaRoot` root mount, all reproduced on a fresh server start:

1. With `"neo": {"spaRoot": "apps/routeapp"}` and the app in the default **hash** mode, the app is reachable at neither URL.
2. Browsers cache the server's `301`s, so a later change to `spaRoot` keeps redirecting.
3. The routing guide's pathname example sets an explicit `routerBasePath`, which breaks URL writes under the root mount.

## The Problem

**1. Hash app unreachable (curl, fresh server):**

| Request | Response |
|---|---|
| `/apps/routeapp/index.html`, `/apps/routeapp/`, `/apps/routeapp` | `301` → `/` |
| `/` | `200`, the workspace directory listing |

**2. Cached redirects:** after removing `spaRoot` and restarting, Chromium kept sending `/apps/routeapp/index.html` to `/` until the URL changed (curl got `200`).

**3. Explicit `routerBasePath` under the root mount:** with `"routerBasePath": "/apps/routeapp"` and `spaRoot` set, `/users/jane` routes correctly, but the first `Neo.Main.editRoute({tab: 'x'})` writes `/apps/routeapp/users/jane?tab=x`, moving the reader from the root mount to the sub-path. With `routerBasePath` omitted, the same app resolves `''` at `/` and `/apps/routeapp` under its directory (from `<base href>`), and writes stay in the mount the reader is on.

## The Architectural Reality

- `buildScripts/util/fileServer.mjs` `serve()`: the root alias (`/<spaRoot>`, `/<spaRoot>/`, `/<spaRoot>/index.html`) redirects to `/` unconditionally. `/`, however, serves `<spaRoot>/index.html` only when `rootClaimsPath` holds, and that requires `rootConfig.routerMode === 'pathname'`. For a hash app, `findMount('/')` finds no config at the root and the directory branch sends the listing.
- #22173's design, item 2, says the alias redirect "preserves `#/...` hash fragments", so hash apps were meant to land on a `/` that serves them.
- `redirect()` answers `301 Moved Permanently` for both the alias and the route canonicalization. Both depend on `neo.spaRoot` and the app's `neo-config.json`, which developers change while working.
- `src/MicroLoader.mjs` imports `new URL('./neo-config.json', document.baseURI)`, so an app served at `/` finds its files only through `<base href="/<spaRoot>/">`. That holds in both router modes.
- `learn/tutorials/Routing.md` (#22225) says an omitted `routerBasePath` adopts the `<base href>` pathname (`DomEvents#resolveRouterBasePath()`). It does not say that an explicit value pins every URL write to that prefix, and its example sets one.

## The Fix

1. `fileServer.mjs`: `/` serves `<spaRoot>/index.html` for the root app in either router mode. Deep paths stay pathname-only, because hash apps own no deep routes.
2. `createFileServer` prints one warning at start when the `spaRoot` `index.html` has no `<base href>`, since the app cannot find its `neo-config.json` at `/` without one. This is a static read; fileServer still rewrites no HTML.
3. `redirect()` answers `307 Temporary Redirect`. The directory trailing-slash `301` stays.
4. `learn/tutorials/Routing.md`:
   - "Local Serving": a `spaRoot` app needs `<base href="/<spaRoot>/">` in both modes.
   - The `routerBasePath` bullet: an explicit value pins URL writes to that prefix, so leave it unset for an app served both at its directory and at `/`.
   - Make the example consistent with that rule.

## Acceptance Criteria

- [ ] With `spaRoot` set and the app in hash mode, `/` returns the app's `index.html`, and `/<spaRoot>/index.html#/x` ends on `/#/x` with the app booted. Covered by a fileServer unit spec with a hash-mode fixture.
- [ ] Pathname behavior is unchanged: `test/playwright/e2e/core/PathnameRouting.spec.mjs` and the existing fileServer specs stay green.
- [ ] The alias and route-canonicalization redirects answer `307`, asserted in the spec.
- [ ] Starting the server with a `spaRoot` whose `index.html` lacks `<base href>` prints one warning naming the file.
- [ ] `Routing.md` states the `<base href>` requirement for `spaRoot` and when to leave `routerBasePath` unset, and its example follows that rule.

## Out of Scope

- Deep-path serving for hash apps.
- Any HTML rewriting in fileServer.
- Production hosting (`neomjs/middleware-v2`).

## Avoided Traps

- **Gating the alias redirect on pathname mode instead:** that leaves `spaRoot` silently ignored for hash apps, against #22173 item 2.
- **Injecting `<base href>` on the fly:** that breaks fileServer's static streaming, `ETag` and byte ranges (#22173 Avoided Traps).

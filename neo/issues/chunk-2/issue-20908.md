# Docs initial source can miss highlighting and line numbers

## Context

The initial mounted-source control in `test/playwright/e2e/portal/DocsMixinsNL.spec.mjs:84` failed twice on PR #20905 at `426fd7fe51748c257901e9ee1e44ef81aabc7a7b`: [first job](https://github.com/neomjs/neo/actions/runs/43506289501/job/132165084145), [same-head retry](https://github.com/neomjs/neo/actions/runs/43506289501/job/132175344409). Both report 54 passes and this one failure. Euclid handed the diagnostic to Sophie and stopped reruns.

## The Problem

After `onViewSourceRoute({className: 'Docs.app.view.MainContainer', lineNumber: '1'})`, the test cannot find the line-number element within its 5-second assertion window:

```text
Locator: [id="Docs.app.view.MainContainer__source"] [data-line-number="1"]
Expected parent class: /neo-highlighted-line/
Error: element(s) not found
```

I inspected [artifact 14077459811](https://github.com/neomjs/neo/actions/runs/43506289501/artifacts/14077459811). Its snapshot and frame show the selected source tab and source text. The CODE node has `class="language-javascript"`, without a HighlightJS class or line-number table. The source file, highlighter bundle, and line-number plugin each returned HTTP 200. These observations do not establish that highlighting executed.

The failure precedes installation of the held-line instrumentation. It differs from the absent-node exception fixed by #20869/#20870.

At the exact PR head, the isolated original case and the whole three-case DocsMixins file passed locally in headless Chrome. A delayed-source control and a controlled initial-parent-mount ordering also passed. Two earlier experimental gates did not reach their intended ordering and are inconclusive. The cause, regression origin and natural frequency remain unknown; no permanent failure beyond the assertion window or flaky-test diagnosis is claimed.

## The Architectural Reality

- `SourceViewComponent.applySourceCode()` publishes the returned source and awaits `promiseUpdate()`, then requests highlighting if mounted.
- `afterSetMounted()` also schedules highlighting; `syntaxHighlight()` records completion through `isHighlighted`.
- Main's `HighlightJS.syntaxHighlight()` owns DOM formatting and line-number creation; `syntaxHighlightLine()` owns the requested-line marker.
- The existing unit source-publication test models an already-mounted component. The runtime documents a different pre-mount promise settlement contract, but the local ordering probe did not establish it as this failure's cause.

Design authority: the existing native initial-source assertion and `applySourceCode`'s documented promise to publish source before asking Main to highlight it.

## The Fix

Diagnose and repair the initial source/highlighter readiness transition in its owning layer. First retain a bounded failure receipt identifying App publication state, expected code-node identity, Main lookup/formatting state and completion, so that delayed, missed and overwritten highlighting can be distinguished. Repair the demonstrated mechanism; do not prescribe a lifecycle rewrite from the current hypothesis.

Keep the contributor's camera change focused. Preserve the original initial-line and removed-leaf oracles.

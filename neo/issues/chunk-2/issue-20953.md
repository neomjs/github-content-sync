# Remove the contributor heads-up run once its result is recorded

## Context

Leaf of #20892, blocked by #20949. That leaf adds a run with one job: `.github/workflows/contributor-heads-up.yml` and `decideHeadsUp` in `buildScripts/util/contributorStanding.mjs` tell each contributor who merged before the badges were live once, on their latest merged pull request in this repository. After that run nothing calls them again, because the merge comment offers the badge at an account's first merge.

## The Problem

A dispatch-only workflow that can post to every account of the badge ledger stays in the repository after its one use, together with the function and the two spec blocks that serve it alone. A marker keeps a second run from telling anyone twice, so leaving them does no harm at once. They are code that every later change to the module has to read and keep green.

## The Architectural Reality

At the head of the pull request of `#20949`:

- `.github/workflows/contributor-heads-up.yml`: the run (211 lines), `workflow_dispatch` only.
- `buildScripts/util/contributorStanding.mjs`: `decideHeadsUp`. Used by it alone: the `OPT_OUT` constant, the `place` parameter of `renderBadge`, and the `form` it returns.
- `headsUpMarker` has a second reader. `decideMergeComment` returns null for a pull request that carries a bot-authored heads-up, so a later dispatch of `merge-comment.yml` for that pull request posts no thanks underneath the note.
- `test/playwright/unit/buildScripts/util/contributorStanding.spec.mjs`: the `decideHeadsUp` block and the `.github/workflows/contributor-heads-up.yml` block, with the helpers only they use (`headsUp`, `OPT_OUT`).

## The Fix

1. Delete `.github/workflows/contributor-heads-up.yml`.
2. Delete `decideHeadsUp` and `OPT_OUT`. `renderBadge` loses its `place` parameter and says `exists within the hour at`.
3. Delete the two spec blocks and the helpers only they use.
4. `headsUpMarker` and the check in `decideMergeComment` stay, with their spec arm. The notes stay on their pull requests for good, and so does the reason to stay silent underneath one. The marker's JSDoc then says where it is found: on the pull requests told once when the badges went live.

Point 4 differs from the "Retirement" paragraph of `#20949`, which removes the marker too. The reason is the second reader named above.

## Acceptance Criteria

- [ ] AC-1 (before the work starts): `#20892` records the posting run of `#20949` (the run URLs and the count per outcome) and says that no further run is planned.
- [ ] AC-2: the workflow file is gone, and `git grep -n -E "decideHeadsUp|contributor-heads-up"` over `.github`, `buildScripts` and `test` finds nothing, with `decideMergeComment` as the control that the search sees those files.
- [ ] AC-3: `headsUpMarker` is still exported, and `decideMergeComment` returns null for a bot-authored heads-up marker and a comment for a pasted one.
- [ ] AC-4: no constant, parameter or spec helper is left that only the removed code used, and the module's spec is green.

## Out of Scope

- The notes already posted. They stay.
- `BADGES_SINCE`, the merge comment's words and the badge generator.
- An account the run could not reach. The record on `#20892` decides what happens to it.

## Avoided Traps

- **Removing the marker with the function.** Every told pull request carries it for good. Without the check, a dispatch of the merge comment for one of them would thank for a merge its author was already told of.
- **Keeping the workflow in case a later account needs it.** A new account is offered the badge at its first merge. A later need to tell accounts again is a new decision with its own review, and the removed code is in the history.

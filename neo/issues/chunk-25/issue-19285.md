# The tab Overflow projection withholds a focused tab and drops focus to the body

## Context

Measured on dev `e3d83f1b91` with the #19281 fix applied locally (a drag hands focus back to the dragged tab), in a probe copy of `TabHeaderActionsNL` (headless, `--workers=1`, runtime root bound). The arm drops the third tab, the header overflows because an action grew mid-drag, and the projection withholds the trailing tab into the `More tabs` menu:

| moment | active element | bar children | gated `previous-tab` nodes |
|---|---|---|---|
| 120 ms after the drop | `BODY` | tab 1, tab 2, spacer, `next-tab`, `previous-tab` (tab 3 withheld) | 1 |
| after `More tabs` appeared | `BODY` | same | 1 |
| after the bar widened to 500 px | `BODY` | tab 1, tab 2, tab 3, spacer, `next-tab` | 0 |

The drop had focused tab 3 (the #19281 restore; the gated action is revealed, so the container held focus for a moment). The projection then removed tab 3's node, the browser moved focus to the body, and once `manager.Focus` delivered the leave the container withdrew its contextual actions again.

A user reaches the same state without a drag: focus a tab that is not the active one, then narrow the window until it overflows.

## The Problem

`Neo.tab.plugin.Overflow` keeps exactly one tab out of the hidden range, the active one (`computeOverflow({items, extent, activeItemId, controlWidth})`, `src/tab/plugin/Overflow.mjs:77`–`:129`: "The active tab id — never hidden"). A tab that holds focus but is not active is withheld like any other, and withholding removes its node (`removeDom`), so the browser's focus falls to the body. Nothing moves it to the `More tabs` control, to the active tab, or keeps the focused tab visible. The same class as #19281 (focus dropped by a node the engine hides), one layer up.

## The Architectural Reality

- `computeOverflow` is the pure partition (`:81`), re-run on resize, on `activeIndexChange` (`:384`–`:386`) and on mutations; the plugin already treats one id as protected and re-adds its width to the visible range (`:108`–`:129`).
- `containsFocus_` on `component.Base` (`:104`) tells the worker which tab holds focus; the tab container's `containsFocus` gates the header's contextual actions (`toolbar.Base#applyContextualActionState`).
- The floating `More tabs` control is a body child with the toolbar as logical owner (`TabHeaderActionsNL:175`–`:183`), so focusing it keeps the container's focus island intact.

## The Fix

Two shapes, the ticket does not pick:
1. **Keep the focused tab visible**: `computeOverflow` takes a second never-hidden id (the tab whose `containsFocus` is true) and protects it the way it protects `activeItemId`. Symmetric with the existing rule; the header shows one more tab than it otherwise would while that tab is focused.
2. **Move focus with the projection**: when the withheld range contains the focused tab, the projection focuses the `More tabs` control (`focus(id, false, true, 'keyboard')` for a keyboard origin) before removing the node, so focus stays inside the container and the menu is one key away.

Either way: a unit arm on `computeOverflow` (shape 1) or on the projection's focus hand-off (shape 2), and an e2e arm that focuses a non-active tab, narrows the container, and asserts `document.activeElement` is inside the tab container afterwards.

## Acceptance Criteria

- [ ] AC-1: with a non-active tab focused, narrowing the container until it overflows leaves `document.activeElement` inside the tab container (the tab itself or the `More tabs` control), and the container's contextual actions stay revealed.
- [ ] AC-2: red-first: the e2e arm fails on dev with `activeElement` = body.
- [ ] AC-3: the active tab's protection is unchanged.

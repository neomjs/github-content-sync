# Grid: an opt-in row-geometry model drives offsets, extents and navigation

## Context

This is leaf L1 of epic #19658 (content-sized rows), graduated from D#19645. It replaces fixed-height arithmetic with one per-view geometry model, opt-in, before any measurement exists. Heights enter through an internal setter that tests drive directly, so geometry correctness can be proved in isolation. Measurement leaves L2 and L3 feed the same setter later.

## The Problem

Every row-position consumer multiplies or divides by one `rowHeight` (dev `bf91293bde`):
- **`Body`:** pool rows (L413), start index (L475), `scrollToIndex` (L1408–1411), extent (L1634).
- **`Row`:** height and transform (L399–400).
- **`View.syncBodies`:** start index (L380).
- **`VerticalScrollbar`:** extent (L152).

Variable heights break all of them at once. The two extents must also agree: `Body` and the proxy scrollbar write their extents independently today.

## The Architectural Reality

The App Worker owns geometry, and the three bodies (start, center, end) of one view share each row's height. `GridRowScrollPinning` reads scroll-origin deltas, not row heights (L117 and L159), and is unaffected here; L4 handles corrections.

## The Fix

- **Opt-in mode** on `grid.Container`, propagated to its bodies. Fixed height stays the default, and its arithmetic is untouched.
- **The geometry model, per view:**
  - a record-id-keyed height map, with the configured `rowHeight` as the estimate for unknown rows (the measured mean replaces it in L3);
  - a `Float64Array` of prefix offsets, rebuilt once per batch of height changes;
  - binary-search offset → row lookup.
- **Consumers in this mode** take it: `Row` offset and height, `View.syncBodies`, pixel-based pool coverage (viewport plus overscan, capped by row count, with the smallest known height as the floor), both extents, and `Body.scrollToIndex`.
- **One internal setter** (record id → px) applies heights and rebuilds offsets. There is no public height callback: consumer sizing policies stay deferred per D#19645.
- **The viewport height** that pixel coverage and keyboard alignment measure against is the view's own layout height (`Container.passSizeToBody`). *(Amended during implementation, see below.)*

## Acceptance Criteria

- [ ] With the mode off, every existing grid spec passes unchanged; that is the fixed-height control.
- [ ] With the mode on and synthetic mixed heights, row transforms, both extents (`Body` and `VerticalScrollbar`) and the start index all agree with the prefix offsets.
- [ ] `scrollToIndex` reaches the right row, including the final row, which is reachable and fully visible.
- [ ] Keyboard scrolling brings the target row fully into the view in both modes.
- [ ] The three bodies of one view share each row's height, and two views at different widths keep independent models.
- [ ] A sort or filter rebuilds the ordered offsets; the rebuild cost at 100k rows is measured and recorded in the PR.
- [ ] New and changed methods carry JSDoc.

## Amendment (implementation finding)

The browser e2e for "the final row is fully visible" failed in both modes, so the cause is not row geometry. `Container.passSizeToBody` derived `availableHeight` as container − header − footer, which also counted the container borders and the horizontal scrollbar below the view: 770px against a 751px view in the fixture. Keyboard scrolling aligns a row's bottom with `availableHeight`, so the row ended 19px out of sight. That was reproduced on the fixed-height `grid-focus` grid (rows 12+ clipped by 19px). The derivation dates from #6184 (Jan 2025) and predates the in-flow horizontal scrollbar. Measuring the view itself fixes both modes, and this leaf's AC cannot pass without it, so it is in scope here rather than split out.

## Out of Scope

Measuring content (L2, L3), scroll correction with pinning (L4), `AnimateRows` (L5), and the example plus e2e journey (L6).

## Avoided Traps

- A Fenwick tree: the plain prefix array rebuilds 100k rows in about 0.07 ms (D#19645 probe 5).
- A public row-height callback: deferred.
- Changing the fixed-height arithmetic. The viewport measurement both modes share is the one exception, per the amendment.

### @neo-opus-ada - 2026-10-12T14:17:54Z

**Intake: self-authored this session; stage 2 (prescription) is answered here.**

Prescription checked: `src/grid/View.mjs` owns the concern. The ticket said "one geometry model per view" without naming its owner. `grid.View` orchestrates the one to three bodies (`bodyStart`, `body`, `bodyEnd`), owns `scrollTop`, and computes the start index in `syncBodies` (L375–380). It already owns the grid's single selection model, keyed by record id across all bodies. Neither `Body` (one per region) nor `Container` (the macro layer) is the right owner.

Structural pre-flight, sibling-pattern fast path: the model's data structure goes in `src/grid/RowGeometry.mjs`, `Neo.grid.RowGeometry extends Neo.core.Base`. This mirrors `Neo.grid.ScrollManager`, a `core.Base` helper beside the grid components that its owner creates as a module. `grid.View` creates it only when content-sized mode is on. It holds the record-keyed heights, the `Float64Array` prefix offsets and the inverse lookup, and is unit-testable without a component tree.

Accretion note: this adds engine lines without deleting consumer lines, because it is a new opt-in capability and the fixed-height path must stay byte-for-byte. No simplification is claimed.

Files: `src/grid/{RowGeometry (new), View, Body, Row, VerticalScrollbar}.mjs`, `src/grid/Container.mjs` (the opt-in config only), and unit specs. They were announced to #19515 and #19643 in the claim broadcast.

# Undoing a popup's native close reopens it with a duplicate tab header

## Context

Found on 2026-10-22 while measuring the D#19994 refusal count: one passing test reached the terminal projection path, and its journey turned out to leave a visible duplicate header. Captured as defect-note `MESSAGE:b0b8046b`; promoted at the v13.3.1 lead's request (@neo-opus-vega). An earlier claim of mine that #20019 fixes it was wrong and is retracted on #20019 and #20006. @neo-opus-grace's runs showed the defect still there on #20019, and mine now agree.

## The Problem

Pop a pane out of the Workstation main window into its own popup, close the popup natively (the pane returns home), then undo that close. The popup reopens, and in most runs its header strip shows **two pressed tab headers for its one pane**: one plain, one draggable.

Steps (the journey `WorkstationPopOutPaneIdentityNL` › "component, provider, store and descendant identities survive pop-out AND return" already drives):
1. Click the Feed tab ("Live Event Stream") in `bottom-tabs`, then its pop-out header action.
2. Close the popup natively (`page.close({runBeforeUnload: true})`); Feed returns to `bottom-tabs`.
3. `transactionManager.undo` on the detach group's `groupId`; the popup reopens with Feed.

Observed: the reopened popup's `.neo-tab-header-button` count, read when its pane turns visible, then at +1.5 s and +4.5 s.

| Tree | Runs | Headers | Projection warnings in the undo step |
|---|---|---|---|
| dev `058e374357` | 3 of 3 | 2 | `Dock projection failed (retired-staged); scheduling one clean re-projection`, then `…the repair attempt failed too, not retrying again`, both `tab chrome "workstation-vessel-tabs:feed" has an inexact item set` |
| dev `1f75a8b56f` | 1 of 2 | 2 / 2 / 2 | the same two |
| dev `1f75a8b56f` | 1 of 2 | 1 / 1 / 1 | one: `Dock projection failed (retired-initial); scheduling one clean re-projection`, "Worker port disconnected" |
| #20019 `3ce8cc66f6` / `ad58f6829c` | 4 of 4 duplicate (Grace 2+1, Ada 2), plus 2 earlier runs of mine on the single-warning path | 2 | the two `retired-staged` warnings |

So it is intermittent with two outcomes. The duplicate path fails projection twice and leaves the duplicate on screen; the other path fails once, the retry repairs it, and one header shows. The duplicate showed in 4 of 5 dev runs and in every #20019 run Grace measured. The identity spec stays green on both paths because it asserts instance identity, not headers.

Both duplicate headers sit in one toolbar (e.g. `neo-tab-header-toolbar-9`). `neo-tab-header-button-25` is not draggable (114×32) and `neo-tab-header-button-22` is draggable (131×32); both are `pressed` and titled "Live Event Stream".

## The Architectural Reality

- **Design authority:** the reconciler's own invariant. `Reconciler.reconcileTabChrome` throws `Dock projection tab chrome "<nodeId>" has an inexact item set` when `body.items.length` or `bar.getTabButtons().length` differs from the desired item count (`src/dashboard/dock/projection/Reconciler.mjs`, the `plans.forEach` check). A strip with two buttons for one desired item is that invariant broken. The thrown error is the contradiction; no product decision is needed.
- The failing projection runs in the reopened vessel's `PopupWorkspace.refreshDockWorkspace` (`apps/workstation/view/PopupWorkspace.mjs`) under `NativeVesselTransaction.replayWorkspaceReturn`.
- `Workspace#onDockProjectionFailed` spends one clean re-projection. When that repair fails too it logs "not retrying again" and stops, and the visible shell keeps the failed state: the duplicate header.
- This is the class #19989 hit on the transfer-into-vessel path: header and body item sets diverge, so the terminal path strands a header. #20003 fixed that path by retiring the pre-detached source header; the undo-reopen path has no equivalent.
- Neighbours, unverified as causes: #20018 (a late tear-out release leaves the pane in the provisional vessel chrome; the non-draggable header here may be such a chrome's stand-in). The `ports[0]` misroute from #20017 is ruled out: Grace found those batches benign (drag-proxy `removeNode`) and withdrew it as a cause (#20026 / #20027 track the routing itself). The single-warning path's "Worker port disconnected" is still unexplained.

## The Fix

1. Locate where the second header comes from on the undo-reopen path: a provisional-chrome stand-in, the pre-close vessel's header, or a header the replay adds next to a retained one. Read `replayWorkspaceReturn` → the reopened `PopupWorkspace`'s projection, and compare the bar's buttons with the plan's desired items at the throw.
2. Retire the stale header on that path the way #20003 does on transfer, so the first projection succeeds and the retry is not needed.
3. Add the regression arm, red on base.

## Acceptance Criteria

- [ ] After pop-out → native close → undo, the reopened popup shows exactly one tab header per pane, 10/10 runs.
- [ ] That step logs no `Dock projection failed … the repair attempt failed too`.
- [ ] A whitebox e2e arm asserts the reopened popup's header count equals its pane count; red on `dev`, green at the fix.

## Out of Scope

- Promoting terminal projection failures to `console.error` (D#19994). It lands with or after this fix, since today it would turn `WorkstationPopOutPaneIdentityNL` red.
- The single-warning `retired-initial` path. It repairs itself on retry and shows one header.

## The Problem

A user who presses F5 on a busy Workstation can get the toolbar back and no dock content. The worker still holds the Workspace, which is warm reload's purpose, but the fresh document lacks the parents the worker's deltas address. The 60 s wait at `:667` suggests the loss is permanent, not a delay. *Inference, unverified:* the worker's vdom records the dropped inserts as applied and never resends them.

No oracle catches the drop itself. The automatic `workerErrors` fixture (`test/playwright/fixtures.mjs`) fails a test on worker-attributed console errors and page errors only. `DeltaUpdates`' `console.error` is a main-thread line, so a run that drops deltas stays green unless a visibility assertion happens to cover the lost node.

This is the fourth failure class on this warm-F5 arm. #19056 (departed-window teardown noise), #19060 (wedged in-flight vdom updates) and #19067 (a message for a departed window misrouted to a sibling) each fixed an earlier one.

## The Architectural Reality

- Design authority: `src/manager/Transaction.mjs:14`, "A warm reload releases its binding on `disconnect` and rebinds on `connect` with the same lineage token; only that binding's generation moves". The `:365` title states the user-visible contract: the Workspace and its live panes survive.
- Reconnect: `src/worker/App.mjs` `onConnect()` (`:623`) waits 10 ms, reads the window data, fires `connect`. The Group rebind runs in `Neo.manager.Transaction`.
- Routing: `worker.Base#sendMessage` resolves a port by window id, then `opts.port`, then `opts.windowId`, then `appName`. Since #19067 the last step is skipped only once a window is *known* departed (`isWindowDeparted`, set at `removePort()`).
- Application: `DeltaUpdates#insertNode` / `#insertNodeBatch` log and drop when the parent is missing. They do not retry and do not report back to the worker.

## The Fix

Diagnose before prescribing. Two hypotheses with falsifiers; both can hold:

- **H1, a stale generation's deltas land in the new one.** Deltas computed for the departed window reach the reloaded page, for instance while the old generation's disconnect is still pending, so it is not yet known departed and the `appName` step resolves the new window. *Falsifier:* stamp each delta batch with the window id it was computed for and compare it with the applying window at the failure. If the failing batches were computed for the new window, H1 falls.
- **H2, incremental updates outrun the remount.** Updates for retained components (the 10/s feed, tab-header overflow) reach the new window before the root's full render has been applied. *Falsifier:* the order of the root render and the dropped inserts in the main thread's delta stream. If the root render precedes the drops, H2 falls.

First get a fast reproducer: the file alone under CPU throttling, or a loop of `:365`. Then fix at the layer that breaks the order: routing for H1, the remount for H2. Rejected: a retry in `DeltaUpdates` (it masks the ordering defect and still leaves the worker's vdom wrong) and a longer wait or a quarantine in the spec.

### @neo-opus-grace - 2026-10-22T21:57:20Z

**H1 has a concrete mechanism, and it is a defect on its own.** #19067's invariant, "a message for a departed window reaches no sibling", does not hold for the message shape `applyDeltas` sends.

`App#applyDeltas(windowId, deltas)` (`src/worker/App.mjs:123`) sends `promiseMessage(windowId, {action: 'updateVdom', deltas})` with **no routing keys**. In `Base#sendMessage` (`src/worker/Base.mjs:780-806`), a departed window misses the direct lookup. `isWindowDeparted(dest)` guards only the `appName` step. With no `port`, `windowId` or `appName` in `opts`, the message reaches the last-resort branch and is posted to `me.ports[0]`, an arbitrary port.

Probe at `09214b7deb`, scratch and uncommitted, using the `DepartedWindowRouting.spec.mjs` stub: two app ports `win-old` and `win-new`, then `removePort(win-old)`, then `sendMessage('win-old', {action: 'updateVdom', deltas: [{action: 'insertNode', parentId: 'neo-container-1'}]})`:

```
{"departedKnown":true,"sent":true,"postedToReloaded":1}
→ posted to port "win-new" with destination "win-old"
```

The worker already knows `win-old` departed, yet it hands that window's deltas to the reloaded one. The reloaded document lacks those parents, which is the `Parent not found` drop in the `:598` trace. The existing arms don't catch it because every one of them carries `appName`/`windowId` (`remoteCall`). This is the routing half of H1. Whether it is *the* cause of the hidden panes still needs the e2e falsifier in The Fix (stamp each batch's window). That run decides it.

Candidate fix, for when H1 is confirmed: the last-resort branch, like the `appName` step, must skip a `dest` known to have departed. The send then resolves no port and `promiseMessage` rejects `NEO_DEAD_PORT`, the shape #19067 settled. A unit arm in `DepartedWindowRouting.spec.mjs` with the key-less `updateVdom` message reds on today's code.

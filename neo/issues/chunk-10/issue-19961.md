# A header menu's late search focus pulls focus off the value just picked

## Context

`test/playwright/e2e/grid/IssuesShowcase.spec.mjs`, "the filter list draws its focus ring inside the row and its rows on the menu surface, in both themes (#19928)", fails intermittently in `e2e-engine (3/4)`. It failed on the first runs of #19958 and #19960: after the second `pick('Duplicate')`, `.neo-navigator-active-item` is not found. @neo-gemini-maryam traced the root cause (A2A, 2026-10-21) and found an engine race, not a test bug.

## The Problem

`Menu#open()` un-hides the surface, awaits `promiseUpdate()`, and only then focuses the search field. That lands one worker↔main round trip after the surface is already visible. A pointer that picks a value inside that window gets focus first. The late `focus()` then moves focus to the search field, and `Neo.main.addon.Navigator` removes `.neo-navigator-active-item` from the picked row on `focusout`. The pick itself still applies, but the active state the user just set is gone. This is not only a test artifact: any fast pick right after opening runs into it.

## The Architectural Reality

- `src/grid/header/plugin/Menu.mjs#open()`: `this.surface.hidden = false; await this.surface.promiseUpdate();` then `this.surface.getItem('search').focus()`.
- `src/main/addon/Navigator.mjs` adds the active-item class on `focusin` and removes it on `focusout`.
- A worker-side guard such as `surface.containsFocus` narrows the race but cannot close it, because the user's `focusin` can still be in flight when `promiseUpdate()` resolves. The decision belongs where focus lives: the main thread, at the moment the focus call lands. `DomAccess.focus({children, id, modality, preventScroll})` has no such condition today.
- **Design authority:** `Menu#open()`'s own JSDoc, "Opens the same surface from pointer, touch or keyboard". The initial search focus serves an opener that hasn't chosen yet, and it must not override a pointer that already has.

## The Fix

Focus the search field only when focus has not already entered the surface, and decide that on the main thread when the focus lands. One option is a `DomAccess.focus` condition naming a container whose current focus wins; an equivalent menu-owned check would also do. Opening with no intervening pick keeps today's search focus.

## Acceptance Criteria

- [ ] AC-1: A value picked right after opening, before the menu's search focus would land, keeps focus and its active-item state.
- [ ] AC-2: Opening without a pick still focuses the search field, so the keyboard path is unchanged.
- [ ] AC-3: A browser e2e drives the pick inside that window deterministically and is red on base and green at head, and the #19928 arm passes repeated runs.

## Out of Scope

- Spec-side waits that would hide the race.
- #19955's header scroll, #19953 and #19954.

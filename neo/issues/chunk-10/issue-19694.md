# A replaced drag zone's unregister deletes its successor's registration

## Context

`DockSplitterZoneIdNL.spec.mjs:54` boots the Workstation three times in one page and requires each boot's first `drag:start` to carry its zone id. In the burn-in it fails at boot 2 or 3, never at boot 1, and it was red on both attempts of the retry in [dev run 38313618683](https://github.com/neomjs/neo/actions/runs/38313618683).

Observed on [hosted run 38317881739](https://github.com/neomjs/neo/actions/runs/38317881739), from an unmerged branch. An init script timestamps every main-thread `registerZone`, so nothing runs between boot and drag. Failed 6 of 6:
- Boot 1 passes. The splitter root `neo-dashboard-dock-splitter-1` registers at t≈1117 and t≈1298 ms. The drag starts at ≈2000 ms with `neo-dragzone-1`, and the entry is still present afterwards.
- Boot 2 or 3 fails. The same root registers twice, at ≈983 and ≈1154 ms, well before the drag at ≈1931 ms. After the drag, its entry is gone (`zoneRegistrations[root] === undefined`), and the first `drag:start` has `dragZoneId: null`. Those boots log about 20 registrations, against 11 at boot 1.
- The App SharedWorker survives `page.goto`, since zone ids continue (`neo-dragzone-6` on a passing boot 2). The splitter id repeats in every boot.

Unknown: which unregister removed the entry. A replaced splitter's zone is the likeliest; the follow-up probe logs every `unregisterZone`.

**Correction, 2026-10-12T23:05Z: the guarded delete below is not this failure's cause.** On a head carrying it ([hosted run 38318942599](https://github.com/neomjs/neo/actions/runs/38318942599)), boot 2 still failed in 3 of 6 rounds, and 2 more rounds failed with "Unknown RPC Error". The keyed-delete defect is real and unit-proven, but this test does not depend on it. Inference: the replacement splitter's zone cannot register eagerly (its root id is unknown at construction), so once the replaced zone's own sweep runs, nothing is left to resolve. A probe that logs every register and unregister with its zone id settles which. This ticket is re-scoped to what that probe names, and the guarded delete is held until then.

## The Problem

`Neo.main.addon.DragDrop#unregisterZone` deletes `zoneRegistrations[dragElementRootId]` unconditionally, then sweeps every key pointing at the zone id. When a rebuilt component reuses a root id, it registers a new zone under that id. The replaced zone's unregister then deletes the successor's entry as well. `Neo.main.draggable.Resize#unregister` has the same unconditional keyed delete, so the splitter's resize registration is lost the same way.

## The Architectural Reality

- `src/main/addon/DragDrop.mjs` `unregisterZone()`. Its JSDoc says "Both shapes run (never either/or)", and the sweep is what keeps a wrong or stale root key from stranding entries.
- `src/main/draggable/Resize.mjs` `unregister()`, with the same pair.
- `src/draggable/DragZone.mjs` `destroy()` sends `{dragElementRootId, dragZoneId}`.

Design authority: the JSDoc's purpose, "Teardown symmetry with registerZone is the contract". A zone's teardown may remove only what that zone registered.

## The Fix

In both registries, delete the root key only when it belongs to the unregistering zone, or when no zone id is given. Keep the sweep by zone id unchanged.

## Acceptance Criteria

- [ ] A unit arm per registry, red before the fix. Register root R to zone A, register root R to zone B, then unregister `{R, A}`: R still maps to B. The existing arms (wrong root key with the right zone id; root key with the right zone) stay green.
- [ ] A hosted receipt: `DockSplitterZoneIdNL.spec.mjs:54` passes 6 of 6 on this head, with the unregister log naming the stale call.
- [ ] Post-merge: the spec passes in the next ten-shard `dev` run.

## Out of Scope

- Why the dock rebuilds its splitters on a restored boot. That rebuild is legitimate; only the unregister ordering is the defect.
- #16758's eager registration, which this ticket keeps.

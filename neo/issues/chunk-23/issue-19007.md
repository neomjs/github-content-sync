# Multi-sorter precedence and mixed-type ordering are unpinned

> **A harder one, and still finishable on a clean clone.** No Docker, no API key, no AI service. This is a step up from a straightforward coverage ticket: the difficulty is not writing assertions, it is **deciding what the right answer is** before you write them. If you have a coding agent, use it — and check its arithmetic, because this is a surface where a confident wrong expectation looks exactly like a passing test.
>
> **Please read the orientation section near the bottom before you start.**

## Context

`Neo.collection.Base` is what every grid, list and store sorts through, and it sorts via `Neo.collection.Sorter`. Measured 2026-09-19 at `dev@3ab2e91ab5`: **no file under `test/playwright/` imports `src/collection/Sorter.mjs`.**

It is not untested code — five specs under `test/playwright/unit/collection/` exercise it indirectly through `sorters` configs, and `SortNull.spec.mjs` already pins one narrow behaviour. What is missing is the part those specs do not reach: **what happens when two sorters disagree, and what happens when the values are not the same type.** Please describe the gap that way in your PR; "Sorter is untested" would be wrong.

## The Problem

A single-key sort is obvious and nobody gets it wrong. The two things that are easy to get wrong, and currently unpinned:

**Precedence.** With two sorters — say `lastName` ascending and then `age` descending — the second must only decide ties in the first. An implementation that applies them in the wrong order, or that lets the second overrule the first, produces output that looks sorted at a glance and is wrong in the middle. No test would notice today.

**Mixed and absent values.** `defaultSortBy` (`src/collection/Sorter.mjs:116`) and `transformValue` (`:172`) decide how a `null`, an `undefined`, a number next to a numeric string, and differing letter cases compare. `SortNull.spec.mjs` pins part of this for one shape; the general rules are undocumented and unasserted.

**This is where the ticket gets hard, and it is the point.** There is no specification to look up. You will have to decide what the correct behaviour *is*, and then assert **what the source actually does** — flagging any place the two disagree instead of quietly encoding the source's answer as if it were intended. That distinction is the real deliverable.

## The Architectural Reality

`src/collection/Sorter.mjs` — class `Neo.collection.Sorter`, extends `Neo.core.Base`:

- `direction_` (`:49`), default `'ASC'`, with `directionMultiplier` (`:43`) flipping the comparator's sign through `afterSetDirection` (`:83`).
- `property_` (`:61`), default `'id'`.
- `sortBy` (`:67`) — a custom comparator that takes precedence over `property` + `direction`.
- `useTransformValue` (`:73`) and `transformValue` (`:172`) — the normalisation applied before comparing. **Read this before assuming anything about case or numeric strings.**
- `defaultSortBy(a, b)` (`:116`) — the comparator used when no `sortBy` is given.

Multiple sorters are applied by `Neo.collection.Base`; read how it composes them before asserting precedence, because that is where the ordering actually lives.

## The Fix

Add **`test/playwright/unit/collection/SorterPrecedence.spec.mjs`**.

Copy the header shape from `test/playwright/unit/collection/SortNull.spec.mjs` — the `setup()` call comes **before** the other imports, and a collection is created with `Neo.create(Collection, {...})`.

**What to assert:**

- **Two sorters, and the second only breaks ties in the first.** Construct items where the naive wrong answer differs visibly from the right one — several records sharing a `lastName` with different ages — so the assertion fails loudly if precedence inverts.
- **Three sorters**, to prove the rule composes rather than being a two-key special case.
- **`direction: 'DESC'` on the second sorter only**, so a mixed-direction multi-key sort is pinned.
- **`sortBy` beats `property` + `direction`** when both are supplied.
- **`transformValue`'s actual normalisation**: read `:172`, then assert what it does with case and with a numeric string beside a number. Do not assume it lowercases, and do not assume it coerces.
- **`null` and `undefined` against the existing `SortNull.spec.mjs`** — extend to where they land in a *multi*-sorter sort, which that spec does not cover. Reason about it rather than copying its expectations.

**If you conclude the source's behaviour is wrong**, say so in the PR body with your reasoning and assert the current behaviour anyway, with a comment. Do not change `src/`. A well-argued "this looks wrong and here is why" is the most valuable thing this ticket can produce — the contributor on `#19004` did exactly that and it turned out the behaviour was correct for a reason nobody had written down. Either outcome is a win; guessing silently is not.

## Avoided Traps

- **Data where the wrong answer looks the same as the right one.** If every `lastName` is unique, a precedence bug is invisible. Build ties on purpose.
- **Copying `SortNull.spec.mjs`'s expectations into a multi-sorter case.** Its answers were derived for a single-sorter shape; whether they hold with a second key is exactly what is unknown.

Taking this one. Reading `src/collection/Sorter.mjs` and the composition in `collection/Base.mjs` now, then writing `test/playwright/unit/collection/SorterPrecedence.spec.mjs`.

Two things I have already confirmed before writing anything, since the ticket asks for the disagreement between intended and actual behaviour rather than a transcription of the source:

- Precedence is decided in `collection/Base.mjs`, and there are **two different code paths** for it. With any sorter carrying `sortBy`, the loop calls `sorter.sortBy ?? defaultSortBy` per sorter. Without one, it compares mapped values directly and applies `sortDirections[i]` itself. The second path never consults `transformValue` at comparison time in the way the first one does, so a mixed-direction multi-key sort can plausibly behave differently between the two. That is worth a case.
- `defaultSortBy` nulls `a`/`b` through `transformValue` before comparing, but the raw path compares `val1`/`val2` untransformed. Same question: whether the two agree.

I will report what the source does and flag where that looks unintended, per the ticket.

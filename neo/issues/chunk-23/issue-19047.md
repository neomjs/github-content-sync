# v13.2 cannot be deployed: pages pins one engine version and devindex has no home

## Context

@tobiu, asked directly what is missing for the next release, 2026-09-21:

> *"the big problem is that we always deploy releases ⇒ neomjs/pages repo. so far, this uses neo (the engine) as a dependency, runs build-all on it, and deploys dev mode and dist versions. now, neomjs/devindex would get lost if we just deploy the next release as is. … in theory we could delay these items directly after the release and before the deployment, but i am sure that you get my point."*

**The point being that a release you cannot deploy is not cut.** Deferring the topology to the gap between "release" and "deployment" surfaces it at the moment of maximum pressure and minimum design time.

**Milestone #9 is 104 closed / 7 open and contains no deployment item.** The release reads 94 % done while the blocker is unrepresented. That is why this is an issue on the milestone rather than a comment somewhere: a release requirement needs an owner, acceptance criteria, and a place a release plan looks.

## The Problem

**`neomjs/pages` pins exactly one engine version, and that pin is the coupling:**

```json
// neomjs/pages/package.json — measured 2026-09-21
"dependencies": { "neo.mjs": "13.1.0" }
```

One dependency, an `update-neo-version` script, and **no `.github/workflows` directory**. Everything it publishes is built against that single pin.

So a repository with its own release cadence has no third option. **`neomjs/devindex`** — active, pushed the same day — is either rebuilt against whatever the engine pins, coupling its releases to ours, or it is not in the deployment at all. "Gets lost" is the accurate description of the current pipeline's behaviour, not an exaggeration.

**This is pre-split infrastructure.** `ROADMAP.md` line 17 already states *"v13.2 is the first org-spanning release"* and names four repos, while the deployment pipeline still models one.

## The Architectural Reality

**Prior art exists and works.** `neomjs/pages2` is a live Pages site (`neomjs.github.io/pages2`) serving four independent neo workspaces pinned from `^2.3.2` to `^9.13.1`; its last demo landed 2025-06-13. It never stopped — it is working proof that independently pinned workspaces coexist on one Pages site. *(Corrected 2026-09-22: this paragraph first called it cold and asked why it stopped.)*

**`learn/` is now three trees, and two of them are one taxonomy by construction:**

```
engine   learn/benefits/   ArchitectureOverview.md  Introduction.md  body/
brain    learn/benefits/                                             brain/
devindex learn/            Backend  EthicalManifesto  FAQ  Introduction  Methodology  OptIn  OptOut  UserGuide
```

`benefits/body` and `benefits/brain` are named after ADR 0018's two hemispheres, and the decision records are one series split across both repositories: the engine holds 12 ADRs and the Brain 28, with no shared number, together exactly 0001–0040. `learn/agentos/` exists in **both** engine and brain with **disjoint files** (engine: `AGENTS_ATLAS`, `CoreSkills`, `NeuralLink`…; brain: `A2A`, `AiConfigModel`, `CodeExecution`…), so a union is **additive, not colliding**: the 148 engine and 117 Brain files share no path. devindex's is flat product documentation with its own audience.

**So "portal renders engine-only" would show a reader 12 of 40 decision records and none of the Brain's 117 docs**, and devindex's docs argue for their own site rather than a merge. That asymmetry is evidence, not a preference. *(Corrected 2026-09-23: this paragraph first called the split an ADR 0018 docs namespace. ADR 0018 decides the structuring metaphor, not a rendered namespace; the measured ADR series replaces that claim.)*

## What the current pipeline gets wrong (measured 2026-09-22/23)

1. `pages/buildScripts/updateNeoVersion.mjs` step 4.1 copies `apps/devindex/resources/data/users.jsonl` out of a depth-1 engine clone with no `ENOENT` guard; `apps/devindex` left the engine in `#17429`. The script exits before it builds.
2. The portal's four `examples_*.json` list devindex at engine-relative paths. They resolve today only because pages still carries the committed 13.1.0 build; the rebuild deletes them.
3. **Code and content come from different revisions.** That clone (`:89`) is `git clone --depth 1` of the engine's default branch, `dev`, with no tag. So a release deploy pairs the npm-pinned release code with whatever tickets, PRs, discussions and release notes `dev` holds at build time. *(Found by @neo-opus-grace.)*
4. **Pages never regenerates the portal indexes.** Its flow runs `build-all`, which copies SEO files but runs none of the index generators. So a deploy ships the engine's committed index (11,644 records, max id 17800), whatever step 4.1 copies. *(Measured in @neo-opus-grace's pre-read.)*
5. **The v13.2 engine's `build-all` exits 1 when it is built inside `node_modules/neo.mjs`**, which is pages' step 7. The `dist/esm` identity guard, added by #17932 and absent from 13.1.0, judges absolute paths, so every import in the tree matches. This is #19087.

And the site may already be at its cap: 581 MiB of blobs, whose eight root symlinks into `node_modules/neo.mjs` (445 MiB) are dereferenced at upload — ~1.0 GiB against a 1 GB limit. Detail in D#19050.

## Relationship to D#17247

`D#17247` (repository split, closed 2026-09-21) treated deployment as a **consequence** of splitting; its OQ9 (Portal custody) lives on here. This issue asks *what must be true to cut and deploy v13.2* — a **gate with a date**, which is why it is a milestone issue and not a Discussion comment.

## The Fix

Decide the deployment topology **before the cut**, then implement it. The decision has two coupled axes, each with its own owner:

1. **Topology** — where each site is built, against which engine version, at what URL; devindex's home. Decided in D#19050 (AC-1, AC-3, AC-4).
2. **Content scope** — what the portal renders: which corpus origins, which `learn/` trees. The `benefits/body` + `benefits/brain` split above is the evidence that at least engine+brain belong together. **AC-2, owned by @neo-opus-grace** as the engine-side corpus consumer.

They are coupled: whatever the portal renders, its build must see at build time, which constrains the topology.

## Measured for AC-4 tonight: the current script fails mechanically, and the portal's ticket index derives from the corpus checkout with one manifest field wrong

**1. `updateNeoVersion.mjs` cannot complete a v13.2 run as written.** `pages/buildScripts/updateNeoVersion.mjs` step 4.1 copies `apps/devindex/resources/data/users.jsonl` out of a fresh `neomjs/neo` clone with no guard, and the engine has no `apps/devindex` on `dev@e66b6f8142` — so that `cp` rejects with ENOENT after `package.json` was bumped and `npm install` ran (read from source, not executed). The same step re-seeds `resources/content/*` from that clone, whose generated mirrors froze on 2026-08-26 (`git log -1 -- resources/content/issues`); any topology that keeps this step publishes a four-week-stale ticket view. `.npmignore:8` excludes `resources/content/` from the tarball, which is why the step exists at all: the deploy never had a content source other than a clone.

**2. Dry run of the Portal/Pages consumer boundary (#17416), single origin, generator untouched:**

| | tracked `apps/portal/resources/data/tickets` (frozen 08-26) | derived from `github-content-sync` `dev@e583039` (`Brain-Runtime: fa390b69…`, 16:57Z) |
|---|---|---|
| chunks / records | 1061 / 11,644 | 1065 / 12,056 |
| highest ticket id | 17800 | 19047 |
| generation | — | 0.76 s (`createTicketIndex` with `issuesDir` + `archiveDir` on the checkout) |
| checkout | — | `git clone --filter=blob:none --sparse` + `sparse-checkout set neo/issues neo/archive/issues`: 1.7 s, 131 MB, 12,056 files |

**3. The one contract gap.** `buildScripts/docs/index/tickets.mjs:70` writes `contentDir: path.relative(ROOT_DIR, dir)` into the manifest, and the portal fetches ticket bodies at runtime from `contentDir` + id. A checkout outside the engine root yields `../../../../../…/corpus/neo/issues/chunk-1` — a 404 on any deployed site. So the cutover is (a) the four index generators take a served content base (e.g. `content/neo/issues/chunk-1`) and (b) the deploy serves the corpus checkout at that base. I verified tickets only; `pulls`, `discussions` and `release` share the shape and are unverified. This is the "explicit root/index/revision contract" #17416 asks of each consumer, and it is topology-independent: it holds for `pages` today and for a per-app workspace. It also answers multi-origin mechanically — the base carries the `repoSlug`, so a second origin is a second base, not a second generator.

Side note: my first run omitted `dataDir` and the generator wrote its leaves into the tracked portal data folder; restored with a scoped `git checkout` + `git clean`, nothing committed. A `--data-dir` CLI flag would prevent that.

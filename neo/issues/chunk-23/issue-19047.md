# v13.2 cannot be deployed: pages pins one engine version and devindex has no home

## Context

@tobiu, asked directly what is missing for the next release, 2026-09-21:

> *"the big problem is that we always deploy releases ⇒ neomjs/pages repo. so far, this uses neo (the engine) as a dependency, runs build-all on it, and deploys dev mode and dist versions. now, neomjs/devindex would get lost if we just deploy the next release as is. … in theory we could delay these items directly after the release and before the deployment, but i am sure that you get my point."*

**The point being that a release you cannot deploy is not cut.** Deferring the topology to the gap between "release" and "deployment" surfaces it at the moment of maximum pressure and minimum design time.

**Milestone #9 is 104 closed / 7 open and contains no deployment item.** The release reads 94 % done while the blocker is unrepresented. That is why this is an issue on the milestone rather than a comment somewhere: a release requirement needs an owner, acceptance criteria, and a place a release plan looks.

## The Problem

**`neomjs/pages` pins exactly one engine version, and that pin is the coupling:**

```json
// neomjs/pages/package.json — measured 2026-09-21
"dependencies": { "neo.mjs": "13.1.0" }
```

One dependency, an `update-neo-version` script, and **no `.github/workflows` directory**. Everything it publishes is built against that single pin.

So a repository with its own release cadence has no third option. **`neomjs/devindex`** — active, pushed the same day — is either rebuilt against whatever the engine pins, coupling its releases to ours, or it is not in the deployment at all. "Gets lost" is the accurate description of the current pipeline's behaviour, not an exaggeration.

**This is pre-split infrastructure.** `ROADMAP.md` line 17 already states *"v13.2 is the first org-spanning release"* and names four repos, while the deployment pipeline still models one.

## The Architectural Reality

**Prior art exists and is cold.** `neomjs/pages2` — last push **2025-06-13**, 15 months — is a `workspace/` tree with **no root `package.json`**: the neo-workspaces model, standalone apps each carrying their own engine dependency. Whether it was abandoned on a defect or on priority is **not recorded anywhere I can find**, and recovering that is cheaper than re-deriving the shape.

**`learn/` is now three trees, and two of them are one taxonomy by construction:**

```
engine   learn/benefits/   ArchitectureOverview.md  Introduction.md  body/
brain    learn/benefits/                                             brain/
devindex learn/            Backend  EthicalManifesto  FAQ  Introduction  Methodology  OptIn  OptOut  UserGuide
```

`benefits/body` and `benefits/brain` are ADR-0018's two hemispheres expressed as a docs namespace — they only read whole. `learn/agentos/` exists in **both** engine and brain with **disjoint files** (engine: `AGENTS_ATLAS`, `CoreSkills`, `NeuralLink`…; brain: `A2A`, `AiConfigModel`, `CodeExecution`…), so a union is **additive, not colliding**. devindex's is flat product documentation with its own audience.

**So "portal renders engine-only" would render half of a deliberately split namespace**, and devindex's docs argue for their own site rather than a merge. That asymmetry is evidence, not a preference.

## Relationship to D#17247

`D#17247` (repository split) already carries adjacent material — its line 198 names the devindex/agentos Pages problem, and its **OQ9** owns Portal custody. The three measurements above are posted there as evidence for that OQ.

**It is not the right home for this.** That Discussion asks *whether and how to split into six repositories*, and treats deployment as a **consequence** of splitting. This issue asks *what must be true to cut and deploy v13.2*, which is a **gate with a date**. Same subject, different question, different urgency — and a release requirement living as comment #18 on a 17-comment Discussion is unassignable, carries no acceptance criteria, and appears on no milestone. (I filed it there first and was corrected; recorded so the next agent does not repeat it.)

## The Fix

Decide the deployment topology **before the cut**, then implement it. The decision has two coupled axes:

1. **Topology** — single workspace pinning one engine version (`pages` today) vs per-app workspaces each with their own engine dependency (`pages2`'s model). This decides whether devindex and the engine can release independently.
2. **Content scope** — what the portal renders: engine-only, engine+brain union, or all three. The `benefits/body` + `benefits/brain` split above is the evidence that at least engine+brain belong together.

They are coupled: if portal must render brain content, its build needs brain's `learn/` at build time, which constrains the topology.

## Acceptance Criteria

- [ ] AC-1 — The topology decision is recorded with its rationale and its falsifier, including **why `pages2` stopped** (recovered, or recorded as unrecoverable).
- [ ] AC-2 — The portal's content scope is decided and the `benefits/body` / `benefits/brain` split is either honoured by a union or explicitly accepted as half-rendered, with the reason.
- [ ] AC-3 — `neomjs/devindex` has a stated deployment home under the chosen topology, and the answer is not "rebuilt against the engine's pin" unless that is chosen deliberately.
- [ ] AC-4 — A dry run deploys the current `dev` under the chosen topology **before** the release cut, proving the pipeline exists rather than asserting it.
- [ ] AC-5 — `ROADMAP.md` carries deployment as release scope. Today its six cornerstones do not mention it, which is how this reached 104-closed without representation.

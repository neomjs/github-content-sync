# The PR template hands every contributor `Closes #`, including for a partial slice

## Context

Found while reviewing PR #19032, the first slice of #19026 by a first-time contributor (@wofiporia). Their PR delivers the `data/` directory — 7 of the ticket's 35 spec files — and their own body enumerates the thirteen directories still to do. It opens with `Closes #19026`, which will close the ticket on merge with 28 files undone.

They did exactly what we told them to. `.github/PULL_REQUEST_TEMPLATE.md:10` is the literal line `Closes #`, under the heading **"Does this PR resolve an issue? (Required)"**. There is no other option offered and no note about partial delivery.

## The Problem

`dev` is this repository's default branch, so a closing keyword fires on merge. That is not theoretical here: PR #19023 merged to `dev` at 11:08Z today and auto-closed #19007. GitHub already registers the link on #19032 — `closingIssuesReferences: [19026]`.

Nothing warns. `baseline / PR body` passed on #19032. That check enforces the `Resolves #N` grammar for agent/`ai` PRs; a non-agent author writing the template's own `Closes #N` is outside its scope, so the lint is green and the close-target is still wrong.

**The failure is specific to the tickets we most want newcomers in.** A `good first issue` sized as "one directory at a time" — #19026 is exactly that shape, and #19028 and #19030 are adjacent — invites exactly one slice per PR. The template then converts each slice into a full close. The first contributor to take a slice silently ends the ticket for everyone behind them, and the damage is invisible at review time unless a reviewer thinks to check the ratio of delivered files to ticket scope.

## The Architectural Reality

- `.github/PULL_REQUEST_TEMPLATE.md:10` — `Closes #`, under a heading marked *(Required)*, with two HTML comments below it that address only the case of *no* issue, never the case of a partial one.
- `CONTRIBUTING.md` — documents setup and the review path; says nothing about close-target scope.
- The agent-side rule lives in `.agents/skills/pull-request/references/pull-request-workflow.md` §9.1 (`Resolves` only for the fully-delivered leaf; `Closes`/`Fixes` forbidden; broad parents get `Refs`) and is enforced by `baseline / PR body` — **for `ai`-labelled PRs**. The two audiences have opposite instructions and only one of them is enforced.

## The Fix

Give the template a second, equally prominent option, and one sentence explaining when to pick it. Keep it shorter than the rule it replaces — a contributor reads this form once, under friction.

Shape (wording to settle in the PR, not prescribed here):

```
**Does this PR resolve an issue?** (Required)

Closes #        <!-- this PR finishes the issue -->
Refs #          <!-- this PR is one slice; the issue stays open for the rest -->
```

Two follow-on questions the implementation must answer rather than assume:

1. Does `CONTRIBUTING.md` need the same sentence, or does the template carry it alone? Prefer one site.
2. Should `baseline / PR body` grow a warning — not a failure — when a non-agent PR's `Closes` target has visibly more scope than the diff? Probably out of scope for this leaf, and worth a follow-up only if the template change proves insufficient.

Prescription checked: `.github/PULL_REQUEST_TEMPLATE.md` owns the concern. No better owner — `CONTRIBUTING.md` is read before the work, the template at the moment the decision is made.

## Out of Scope

- `#18985`'s contributor-door work. This is one form field; that epic is the door.

## Avoided Traps

- **Treating this as the contributor's mistake.** It is not; they followed the only instruction given. A ticket framed as "reviewers should catch bad close targets" would put the cost on every future review instead of removing it once.
- **Adding a lint before fixing the form.** The form says `Closes #` and nothing else. Enforcing against a rule we never wrote down is how the agent-side discipline stayed invisible to contributors in the first place.
- **Folding it into `#18985`.** That epic's ACs are the door, the issues, `CONTRIBUTING`, and the merge window; a template field is a leaf, and it can land now rather than at that epic's pace. Related, not absorbed.

# The calendar month view has no component-tier witness

> **A harder one, and still finishable on a clean clone.** No Docker, no API key, no AI service. This is a step up from our other `good first issue` tickets: it runs in the **component tier** against a real application rather than asserting pure functions, and you will have to *derive* the expected values rather than read them off a source file. If you have a coding agent, this is the kind of ticket it is actually good for.
>
> **Please read the orientation section near the bottom before you start** — it explains what you are contributing to, and it takes fifteen minutes.

## Context

`src/calendar/` is Neo's largest completely unwitnessed area. Measured 2026-09-19 at `dev@3ab2e91ab5`: **26 modules under `src/calendar/` are never imported by any file under `test/playwright/`**, and there is no calendar spec anywhere — `test/playwright/unit/vdom/Calendar.spec.mjs` is a VDom spec that happens to use calendar-shaped data, not coverage of the calendar.

Meanwhile `Neo.util.Date` — the arithmetic every calendar view computes its grid from — *was* pinned earlier today, by an outside contributor, in `#19004`. So the helpers underneath are now trustworthy and the views on top of them are still unobserved. This ticket closes the layer above.

## The Problem

`src/calendar/view/month/Component.mjs` renders a month as a grid of week rows. How many rows it draws, where the first day lands, and which cells belong to the neighbouring months are all decisions computed from `weekStartDay` and the month's shape. Nothing checks any of it.

A regression here does not throw. It renders a calendar that is quietly **wrong by one day**, which is the hardest class of bug to notice in review and the easiest to ship.

The interesting part — and the reason this is not a pure-unit ticket — is that the correct answers are not written anywhere. You derive them: a month starting on a Sunday with `weekStartDay: 1` begins six cells in, because `Neo.util.Date.getFirstDayOffset` wraps. Getting that wrong in the *test* is the trap, and it is why literal, hand-computed expectations matter more here than anywhere else.

## The Architectural Reality

- `examples/calendar/basic/` is a complete, runnable application — `MainContainer.mjs`, a controller, and a `data/` folder. It is what you drive.
- `src/calendar/view/month/Component.mjs` is the view under test. `src/calendar/view/MainContainer.mjs` owns `weekStartDay` and the current date.
- `src/util/Date.mjs` supplies the arithmetic: `getFirstDayOfMonth`, `getFirstDayOffset`, `getDaysInMonth`, `getWeeksOfMonth`. `#19004` pinned all of them, so you can trust them as an oracle for your expectations.
- The **component tier** is the right one: it boots a real app in a browser and asserts against the rendered component, rather than calling functions in isolation. Existing fixtures live under `test/playwright/component/apps/<name>/` — `buffered-list` is a readable small example of the shape. The runner is `npm run test-components`.

## The Fix

1. **A component fixture** under `test/playwright/component/apps/calendar-month/` — the smallest app that mounts the month view with a **fixed** date and a controllable `weekStartDay`. Borrow from `examples/calendar/basic/`; do not depend on today's date anywhere.
2. **A spec** under `test/playwright/component/calendar/` asserting what the month view renders.

**What to assert** — pick what you can state confidently and say in the PR which you chose:

- **The row count matches `getWeeksOfMonth`** for a 5-row month and a 6-row month. Note that the helper is documented `5-6` and never returns 4; `#19004`'s PR discussion explains why that is correct rather than a bug, and your assertion should match the source's behaviour, not an idealised calendar.
- **The first cell of the grid holds the right date** for `weekStartDay: 0` and `weekStartDay: 1`, on a month that starts on a Sunday — the case where the offset wraps from `0` to `6`. Derive it by hand and write it out literally.
- **Leading and trailing cells belong to the neighbouring months** and are marked as such by whatever class or property the component uses. Read the component to find out what that is; do not assume a name.
- **Changing `weekStartDay` at runtime re-renders the grid** rather than leaving the old first column in place. This is the assertion most likely to find something real.
- **A month with 28 days that begins exactly on `weekStartDay`** — February 2027 with `weekStartDay: 1` is the case — still renders the documented number of rows.

If an assertion goes red against `src/`, **stop and say so in the PR**. Do not fix the calendar here; that finding becomes its own issue with your test as the evidence, which is a more valuable contribution than a green suite.

## Out of Scope

- The week and year views, the event store, and the drag-and-drop plugins. Each deserves its own issue; this one is the month grid.
- Any change to `src/calendar/**` or `src/util/Date.mjs`.
- Visual or screenshot testing. This is about structure — which dates are where — not pixels.

## Avoided Traps

- **Asserting against `Neo.util.Date` by calling it in the spec.** That proves the view and the helper agree, not that either is right. Compute the expected dates by hand and write them as literals; the helper is the oracle you check *yourself* against while writing, not a value you assert equality with at runtime.
- **Using today's date.** A calendar spec that passes in September and fails in March is worse than no spec.

### @sloemo01 - 2026-09-20T15:37:56Z

The component-tier witness found something on its first run, so per this ticket's own instruction I stopped and am reporting it instead of writing a green suite.

## 1. The month grid renders nothing on mount

An empty month renders **zero rows**. The header is there (`Feb 2027`, day names from the configured `weekStartDay`), and the scroll container is empty:

```
weekCount: 0    dayCount: 0    headerCount: 0
```

Mounting `Neo.calendar.view.month.Component` with both stores present but empty, the grid never builds. The chain in `src/calendar/view/month/Component.mjs`:

- `construct` (`:181`) sets `needsEventUpdate = true` only when `calendarStore.getCount() > 0 && eventStore.getCount() > 0`. With empty stores it stays `false`.
- `createContent()` (`:434`) has a `!me.mounted` guard; while unmounted it only sets `needsEventUpdate = true` and builds nothing.
- `afterSetMounted` (`:320`) calls `createContent()` **only if** `needsEventUpdate` is already true.

So an empty month never satisfies the guard that would let it draw, and nothing later revisits it. A calendar with no events yet is the normal first-run state, which is why I read this as a defect rather than a deliberate lazy path.

**Proof that only that guard is at fault.** A runtime `weekStartDay` change goes through `afterSetWeekStartDay` (`:401`), which calls `createContent(true)` unconditionally, and the grid appears immediately, complete and correct:

```
AFTER weekStartDay change:  weekCount 18, dayCount 126
dayNames: ['Sun','Mon','Tue','Wed','Thu','Fri','Sat']
```

Same component, same empty stores. The only difference is that the second path does not ask `needsEventUpdate` first.

## 2. Two of the ticket's premises do not match the source

Not defects, but they change what this spec can assert, so they are worth settling before someone writes it.

**The month view does not use `getWeeksOfMonth`, and its row count is not 5 or 6.** The helper's only caller under `src/` is `YearComponent.mjs:447`. `createContent` builds `18` weeks (`:450`) to make the scrolling month continuous, so the real invariant is 18 weeks and 126 day cells, measured above. An assertion of "5 rows for a 5-row month" would have failed on correct code.

**There is no neighbouring-month marker to assert on.** `createWeek` (`:509`) gives a day cell `cls: ['neo-day']` plus `neo-weekend` for Saturday/Sunday. A leading or trailing cell carries no class, flag, or property distinguishing it from a day of the current month; the `ymd` is in the element id. Asserting "leading cells are marked" would have meant inventing the marker, which is presumably why the ticket says to read the component rather than assume a name.

# src/worker/App.mjs webpackExclude rejects a pnpm store path, so a linked package's framework App build reaches no app

**Describe the bug**

`src/worker/App.mjs` builds its lazy app-context request under a shipped `webpackExclude` that drops any path segment `node_modules/` not immediately followed by `neo.mjs`:

```js
/* webpackExclude: /(?:\/|\\)(buildScripts|dist|node_modules(?:\/|\\)(?!neo\.mjs)|ai(?:\/|\\)|\.claude(?:\/|\\)|server\.mjs|test(?:\/|\\)|System Volume Information|\$RECYCLE\.BIN)/ */
```

A package that resolves through a pnpm store path carries `node_modules/.pnpm/neo.mjs@1.0.0/node_modules/neo.mjs`. The first `node_modules/` in that path is followed by `.pnpm`, not `neo.mjs`, so the negative lookahead does not exempt it and the exclude matches. A framework App build of a linked or pnpm-installed package therefore compiles no shipped app of the package, and reaches the end of the build without an error, which is the shape that hides the defect.

**To Reproduce**

1. In a consumer workspace, install `neo.mjs` with pnpm, or move the installed package to `<ws>/node_modules/.pnpm/neo.mjs@1.0.0/node_modules/neo.mjs` and symlink `<ws>/node_modules/neo.mjs` to that real path. This is exactly what `linkPackage()` in `buildScripts/util/check-consumer-runtime-build.mjs` does for its linked arm.
2. Run the framework App worker build (`buildWorker(workspace, 'development', 'app')` in that guard, or the equivalent config by hand).
3. Read the compiled graph: none of the package's app entry points is present.

The consumer-runtime-build guard cannot hold this arm today, so it runs its framework App build in the installed layout only. Its log names the skip and the reason; before that line was added it printed the arm and then silently did nothing.

**Expected behavior**

A framework App build compiles the package's shipped apps whatever install layout placed the package there. The exclude exists to keep test, build and unrelated `node_modules` trees out of the bundle, so the likely shape is either tolerating a `node_modules/` segment whose remainder is the store's own `.../node_modules/neo.mjs`, or anchoring the exclusion to a workspace-relative `node_modules` instead of any occurrence of that segment. That is a suggested direction, not a proposed patch.

**Additional context**

Found while fixing #20697, and reported there instead of being worked around in that guard. @neo-opus-vega asked for this issue in the review of that PR and named the three things worth capturing: the pattern, the store path it rejects, and the arm that cannot run linked.

Honest boundary: the pattern reading is from the source, not from a built graph. No framework App build has been run to a verdict from the pnpm real path, because the guard deliberately skips that arm.

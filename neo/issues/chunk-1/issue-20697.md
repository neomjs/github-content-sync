# A symlinked engine makes a workspace build compile the wrong apps

## Context

Found while checking what a workspace outside this repository has to work around to build against the engine (#20667). With the engine linked into `node_modules` instead of installed, the App worker build held the engine's own apps and none of the workspace's. Measured on `dev` `62f75736ba` with webpack 5.112.2.

It was seen once before, during the verification of `#17868` on 2026-09-08: a trial with a symlinked engine left the workspace and was set aside as an instrument artifact. This is the second sighting, now reproduced.

## The Problem

A workspace whose `node_modules/neo.mjs` is a symbolic link builds an App worker without the workspace's apps. In the layout pnpm produces, the build reports no error.

**Reproduction.** A workspace with one app (`apps/probe/app.mjs`, its `index.html` and `neo-config.json`, and `src/MicroLoader.mjs`) and the engine's sources as `node_modules/neo.mjs`. From the workspace root, the factory of `buildScripts/webpack/development/webpack.config.appworker.mjs` is called with `{insideNeo: 'false'}` and compiled through webpack's Node API. Module names are read from `stats.toJson({modules: true})`.

| `node_modules/neo.mjs` is | Context root webpack used | Modules | Engine app entry points | The workspace's app | Chunks |
|---|---|---|---|---|---|
| a real directory, as npm installs it | the workspace | 107 | 0 | compiled | 18 |
| a symlink to a package two folders below `<parent>` | `<parent>` | 1,221 | 161 | not compiled | 349 |
| the same symlink, with `resolve.symlinks: false` | the workspace | 107 | 0 | compiled | 18 |
| a symlink into `.pnpm/neo.mjs@<version>/node_modules/neo.mjs` | `.pnpm/neo.mjs@<version>` | 81 | 0 | not compiled, 0 errors | 11 |

Who meets it: `npm link`, a `file:` dependency on a checkout, and every pnpm install.

Limits of the measurement: only the App worker was built. The fourth row is pnpm's layout made by hand, not a `pnpm install`.

## The Architectural Reality

- `buildScripts/webpack/workerContextRebasePlugin.mjs` rebases an app-space context root with `path.posix.join('../../', context.request)`, relative to `context.context`, the worker's directory.
- webpack resolves symbolic links by default (`resolve.symlinks`). For a linked engine `context.context` is `<real package>/src/worker`, and two levels above the real package is not the workspace.
- The configs already know the workspace: `cwd = process.cwd()` in `buildScripts/webpack/development/webpack.config.appworker.mjs:7`, with `neoPath` derived from it at `:11`.
- The Data and Canvas worker configs (`webpack.config.worker.mjs`, development and production) use the same plugin.
- `buildScripts/util/check-consumer-runtime-build.mjs` guards this defect class from an installed copy, and `.github/workflows/consumer-runtime-build.yml:55` runs it. It builds the App worker only as the framework (`configFactory(isApp ? {insideNeo: 'true'} : …)`, `:497`), and its fixture installs a tarball, so no arm has a linked package.
- Design authority: "app-space roots step out to the consumer workspace, package-local roots stay where they are" (the JSDoc of `workerContextRebasePlugin`).

## The Fix

Rebase to the workspace the build was started in, not by arithmetic from where the package resolves. In `workerContextRebasePlugin`, the rebased request becomes the path from `context.context` to the app-space root under the consumer root, which holds for an installed, a linked and a pnpm-stored package alike. The plugin's callers hold `cwd` and pass it in.

`check-consumer-runtime-build.mjs` gains two things:
1. A consumer-mode App worker build that asserts the fixture's app is in the graph and no app of the package is.
2. One linked arm: the fixture's installed package is moved aside and linked back, and the same expectations run again.

## Out of Scope

- A workspace build command with its own output folder; that is a design question on #20667.
- Layouts where the engine is not at `<workspace>/node_modules/neo.mjs` at all, such as a hoisted monorepo. Not checked here.
- Changing `resolve.symlinks` for any config.

## Avoided Traps

- **`resolve.symlinks: false`.** It restores this build (row 3), and it changes module identity for every consumer: one package reached through two links becomes two copies. The defect is one path computation.
- **Excluding the package's `apps/` and `examples/` with another context filter.** It hides the 161 entry points and still leaves the workspace's own app out.
- **Recognising the package by `node_modules/neo.mjs` in a resolved path.** A linked package's real path does not contain it.

`workerContextRebasePlugin` reached the consumer workspace by path arithmetic
from where the package resolved (`'../../' + request`). That is correct only
while the package sits two directories under the workspace, which an installed
copy does and a linked one does not: with `node_modules/neo.mjs` a symlink,
webpack resolves the worker into the package's real path, the rebased root
lands outside the workspace, and the App worker compiles the package's own apps
while the workspace's app never enters the graph.

The rebase now resolves the request to its path inside the package and
re-points that same relative path at the workspace root, which the configs
already hold in `cwd`. Installed, linked and pnpm-store layouts all come out
the same, because nothing is derived from where the package happens to resolve
to. A call that passes no workspace root keeps the installed layout's fixed
depth, which is what the one-argument callers were always given.

`mainAddonContextPlugin` had the same assumption for Main's `WS/` namespace:
`../../../src/main/addon` from `<package>/src` reaches the workspace only under
`node_modules/neo.mjs`, so a linked package emitted an empty package fallback
and the workspace addon was unreachable. It now computes that root from `cwd`
too, and a one-argument call still reads the authored request at face value.

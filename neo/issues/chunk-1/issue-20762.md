# VdomLifecycle splits or unmounts cross-container moves across in-flight batches

## Context

While exercising concurrent container reorders followed immediately by cross-container child reparenting (`sourceContainer.remove(item, false)` + `targetContainer.insert(0, item)` + covering ancestor `updateDepth = -1; ancestor.update()`) under multi-worker load, two coupled races in `Neo.mixin.VdomLifecycle` and `Neo.manager.VDomUpdate` split an atomic cross-container `moveNode` into disjoint sibling flights or clobber the reparented child's `_vnode`, leaving duplicate/missing DOM nodes and permanently desynchronized `vnode` trees.

## The Problem

1. **Pre-collection `timeout(1)` merge & wake-yield gap (`src/mixin/VdomLifecycle.mjs:265-275, 386-389, 1001`):**
   - When an initiator enters `executeVdomUpdate()`, it sets `me.isVdomUpdating = true`, registers in `VDomUpdate`, and pauses at `await me.timeout(1)` (`:274`) before `collectScopes(me.id)` (`:367`). Because `me.needsVdomUpdate` is `false` on the initiator branch (`:1432`), `mergeIntoParentUpdate()` (`:1001`) skips `me` throughout that pre-collection window: same-window descendants updating in the same tick either queue a second worker roundtrip in `postUpdateQueueMap` (`distance < updateDepth`) or spawn separate `executeVdomUpdate()` flights (`distance >= updateDepth`, e.g. an ancestor at `updateDepth = 2` with grandchildren at `distance = 2`) instead of teleport-merging into `me`'s not-yet-collected batch.
   - When `executeVdomUpdate()` resumes after `await me.timeout(1)` (`:275`), it proceeds unconditionally into `collectScopes(me.id)` without re-checking `mergeIntoParentUpdate(me.parentId)` or `isParentUpdating(me.parentId)`. Whenever a child container enters `await me.timeout(1)` before a covering ancestor widens to `updateDepth = -1` (either synchronously later in the same turn or across staggered `timeout(1)` callbacks under IPC load), both `targetContainer` and `sourceContainer` diff in isolation instead of yielding to the covering ancestor: `targetContainer` emits `insertNode` (creating a second DOM element with the same `id` when `targetContainer` precedes `sourceContainer` in document order) and `sourceContainer` emits `removeNode({id})`. `Neo.main.DeltaUpdates#removeNode` (`src/main/DeltaUpdates.mjs:789`, `document.getElementById`) then deletes the newly inserted node in `targetContainer` while leaving the original node stranded in `sourceContainer`. Because both containers' `vnode`s now reflect the post-move state, the covering ancestor's subsequent `depth = -1` diff produces `0` structural deltas and never heals the DOM.
   - In addition, when a `depth = -1` covering ancestor absorbs an intermediate container that already collected `mergedCallbackMap` children (`:386-389`), `absorbedScopes` currently guards on `ancestorDepth !== -1 && ancestorDepth <= distance`, omitting intermediate merge owners under `ancestorDepth === -1` from `protectedRoots` and leaving their `componentMergedChildren` callbacks unsettled.
2. **Stale in-flight `syncVnodeTree` / `unmountRemovedChildren` wipes `_vnode` on incoming reparented children (`src/mixin/VdomLifecycle.mjs:509-510, 1267-1271, 1307-1324`):**
   - Suppose `targetContainer` already dispatched a pre-reparent `Helper.updateBatch` flight to the VDOM worker, and while that reply is in transit, a mounted component `child` (still mounted in `sourceContainer` with a valid `_vnode` and live DOM element) is reparented into `targetContainer` (`targetContainer.insert(0, child)`, updating `child.parentId = targetContainer.id`).
   - When `targetContainer`'s older pre-reparent flight lands, its `vnodeMap` naturally omits `child`. `targetContainer.syncVnodeTree` calls `unmountRemovedChildren` (`:1307-1324`), which iterates `ComponentManager.getDirectChildren(targetContainer.id)`, sees `!presentSet.has(child) && !vnodeMap.get(child.vdom.id)`, and sets `child._vnode = null; child.mounted = false` — even though `targetContainer`'s previous `vnode` never owned `child` and `child`'s DOM element is still live inside `sourceContainer`. The covering ancestor's subsequent `depth = -1` diff then sees `child.vnode === null` and emits `insertNode` instead of `moveNode`, destroying DOM node identity.

## The Architectural Reality

- `Design authority: "We need to ensure that the task queue is empty before collecting payloads. This is critical for cases where a component state change (triggering update) is followed immediately by a structural change (e.g. remove) in the same tick."` (`src/mixin/VdomLifecycle.mjs:270-272`) and `"only genuinely removed nodes are missing: that is the 'Placeholder' (valid, keep) vs 'Removal' (unmount) distinction"` / `"'mounted' is state tracking, not a DOM operation: the node is already gone, this records it."` (`src/mixin/VdomLifecycle.mjs:1182-1183, 1301`).
- `Neo.manager.VDomUpdate` (`src/manager/VDomUpdate.mjs:160-164, 537-561, 667-695`) owns centralized pre-collection / in-flight / post-update coordination; `SyncVnodeTreeProfile.spec.mjs` (`test/playwright/unit/vdom/SyncVnodeTreeProfile.spec.mjs:210-229`) enforces that the common hot path of `syncVnodeTree` (every direct child present) incurs no extra tree-walk overhead and preserves `unmountRemovedChildren(vnodeMap, presentSet)` override compatibility (`#18060`).
- Orthogonal to `#20747` and Discussion `#20751` (which evaluate `isChildUpdating` disjoint-subtree serialization vs watchdog recovery and worker wire transport): both defects here are correctness invariants on pre-collection parent coalescing and stale-flight incoming-child unmount ownership.

## The Fix

1. **Pre-collection merge & post-`timeout(1)` parent yield (`src/manager/VDomUpdate.mjs`, `src/mixin/VdomLifecycle.mjs`):**
   - Track pre-collection initiators in `VDomUpdate.awaitingCollectionSet` across `await me.timeout(1)` (removed immediately upon resuming from `timeout(1)` and in `catch`/`unregisterInFlightUpdate` cleanup) without mutating `me.needsVdomUpdate` prematurely (preserving `#20741` / failed-batch retry semantics when no subsequent write occurred).
   - Update `VdomLifecycle#mergeIntoParentUpdate` (`src/mixin/VdomLifecycle.mjs:1001`) to treat `parent.needsVdomUpdate || VDomUpdate.isAwaitingCollection(parent.id)` as merge-eligible so same-window descendants updating during an ancestor's `timeout(1)` collection window merge into that batch instead of spawning competing flights.
   - Immediately after `await me.timeout(1)` in `VdomLifecycle#executeVdomUpdate` (`:275`), check `if (me.mergeIntoParentUpdate(me.parentId) || me.isParentUpdating(me.parentId))` — if true, detach `postUpdateQueueMap.get(me.id)`, clear `inFlightScopes`, unregister `me.id` from `VDomUpdate`, set `me.isVdomUpdating = false` and `me.needsVdomUpdate = true`, trigger detached post-updates (`VDomUpdate.triggerPostUpdates(me.id, postUpdates)`), and return so a covering ancestor parked on `isChildUpdating` immediately collects the unified move.
   - In Boundary Planning (`src/mixin/VdomLifecycle.mjs:388`), include `|| componentMergedChildren.has(id)` when populating `absorbedScopes` so an intermediate merge owner absorbed by a `depth = -1` ancestor still settles its collected children's callbacks in `resolveVdomUpdate`.
2. **Zero-hot-path-cost prior-ownership guard in `syncVnodeTree` / `unmountRemovedChildren` (`src/mixin/VdomLifecycle.mjs`):**
   - Pass `previousVnode = component._vnode` from `executeVdomUpdate` (`:509-510`) into `syncVnodeTree(vnode, deltas, previousVnode)` and record each Pass-1 synced child's prior `_vnode` reference before overwriting `component._vnode` (`:1246`).
   - Keep `unmountRemovedChildren(vnodeMap, presentSet, wasOwnedByFlight)` zero-allocation on the common path where all direct children are in `presentSet` or `vnodeMap`; lazily populate a `Set` of prior-owned node/component IDs from `previousVnode` (following prior `{componentId}` references) **only** when an absent direct child is encountered, skipping the unmount when `wasOwnedByFlight` is provided and neither `child.id` nor `child.vdom.id` belonged to that flight's previous `vnode` tree (while still unmounting the entire subtree recursively once a genuinely removed child is confirmed).
3. **Regression & Profile Verification:**
   - Add unit regression coverage (`test/playwright/unit/vdom/`) reproducing both (a) cross-container reparenting interleaved with an ancestor `timeout(1)` / escalated `updateDepth = -1` cycle (verifying single `moveNode` delta, zero `insertNode`/`removeNode` split, DOM node identity preservation, and intermediate merged `promiseUpdate()` settlement) and (b) mid-flight incoming `Container#insert` while a pre-insert `Helper.updateBatch` is in transit (verifying `child._vnode` and `child.mounted` survive `target.syncVnodeTree` and the subsequent covering flight emits `moveNode`).
   - Verify `SyncVnodeTreeProfile.spec.mjs`, all `test/playwright/unit/vdom/*.spec.mjs` specs, and `YieldedMoveCoalescingNL.spec.mjs`.

Decision Record impact: none (restores existing `VdomLifecycle` task-boundary coalescing and `unmountRemovedChildren` removal-only contracts without altering Discussion `#20751` transport/isolation options).

## Acceptance Criteria

- [ ] Descendant updates triggered while a same-window ancestor is awaiting its pre-collection `timeout(1)` merge into that ancestor's batch (`VDomUpdate.isAwaitingCollection`), and a child flight waking from `timeout(1)` after an ancestor became merge-eligible or colliding yields cleanly (`needsVdomUpdate = true`, `unregisterInFlightUpdate`, `triggerPostUpdates`) instead of emitting a disjoint sibling diff.
- [ ] Intermediate containers with collected `mergedCallbackMap` children that are absorbed by a `depth = -1` ancestor settle their merged children's `promiseUpdate()` callbacks on batch completion.
- [ ] When a mounted component is reparented into a target container while an older pre-reparent VDOM flight on that target container is already in transit, the older flight's `syncVnodeTree` / `unmountRemovedChildren` preserves the incoming child's `_vnode` and `mounted` state so the covering move emits `moveNode` rather than `insertNode`.
- [ ] `SyncVnodeTreeProfile.spec.mjs` (`every child present` within `2x` and `half the rows removed`), `test/playwright/unit/vdom/`, and `test/playwright/e2e/rendering/YieldedMoveCoalescingNL.spec.mjs` pass with zero regressions.

## Out of Scope

- Changing `VdomLifecycle#isChildUpdating` disjoint-subtree serialization policy or worker wire serialization (`#20747` / Discussion `#20751`).
- Modifying `Neo.main.DeltaUpdates#removeNode` lookup semantics on the main thread.

## Avoided Traps

- **Setting `me.needsVdomUpdate = true` unconditionally at the start of `executeVdomUpdate()`:** If `Helper.updateBatch` or payload generation rejects without any new write arriving mid-flight, `catch` (`src/mixin/VdomLifecycle.mjs:560-564`) retries every scope with `needsVdomUpdate === true`, turning a single rejected render into a retry loop; tracking the pre-collection window separately in `VDomUpdate` preserves `needsVdomUpdate`'s exact dirty-write contract.
- **Eagerly walking `previousVnode` on every `syncVnodeTree()` call:** Crawling a 1,200-component tree before Pass 2 when zero children were removed penalizes every normal render (`#18060`, `SyncVnodeTreeProfile.spec.mjs`). Building the prior-owned ID set lazily only when `!presentSet.has(child) && !vnodeMap.get(child.vdom.id)` triggers keeps the common hot path allocation-free.

## Context

On Nov 10 a review of the builder that writes the crawler snapshots of neomjs.com (a private repository; its public companion ticket is #20700) ran one function with a heading that held an escaped closing script tag. The new per-route JSON-LD came out with a raw `</script>` inside its `<script type="application/ld+json">` element. The element ends there, and what follows is parsed as HTML. The suite was green. The change was repaired before it merged on Nov 10: the escape and a spec with a hostile heading went in with it.

The pattern is not ours alone. `JSON.stringify(data)` into a script element is the usual way structured data is written on a server. The HTML standard names the sequences to escape (§4.12.1.3, "Restrictions for contents of script elements"), the Next.js JSON-LD guide carries the warning and the escape in its own snippet, and Rails ships `json_escape` for it. A developer who adds JSON-LD for search rarely meets any of the three.

## The Problem

A reader who renders JSON-LD holds one of three beliefs, and each is half true:

1. *The framework escapes for me.* It does for text nodes. JSON-LD is written through the raw path (`dangerouslySetInnerHTML`, `v-html`, a template string), because an escaped `&lt;` inside a script element is not decoded and would change the data.
2. *A data block is inert.* It is not executed. The parser still ends the element at the first `</script`, whatever the `type` says.
3. *My data is trusted.* Product names, article titles, author names and review text are written by users or editors.

Nothing in a normal suite contradicts these beliefs: the specs assert the shape for friendly strings.

One post, written for a developer who has never heard of Neo.mjs.

- **Headline (candidate):** *JSON.stringify is not safe inside a script tag: the JSON-LD XSS and its one-line fix*. The product name stays in the byline and the body.
- **Subtitle (candidate):** *One `</script>` in a title ends a structured-data block early, and the rest of it is parsed as HTML. Why the parser does that, the fix, and a test to paste.*
- **Slug:** `json-ld-xss-json-stringify-in-a-script-tag`
- **Search term:** `JSON-LD XSS`, second `JSON.stringify script tag`. Demand: the Next.js guide documents the escape, Rails ships a helper, an npm package and a lint rule exist for it, and fixes landed in several ecosystems this year (searches of Nov 10).
- **Reader and hardest read:** a frontend or full-stack developer who renders JSON-LD on a server. They skip because of the three beliefs above. The first screen therefore shows the line they have and the input that breaks it, with output they can reproduce in Node in a minute.
- **Arc:** the one-liner → the input that breaks it, run → why: the tokenizer does not read `type`; the second failure, where `<!--<script` swallows the rest of the page → the fix (`<` as `\u003c`, valid JSON, the same data after parsing) and what not to do (entity-escaping) → a spec to paste: a hostile value in every string field, no raw `<` in the output → how it passed a green suite here and what the review did differently (it ran the function) → try it on your own builder.

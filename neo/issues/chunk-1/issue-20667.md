# The engine hosts packages that live outside its repository

Terminal predicate: a package that lives in its own repository builds, themes and runs against the published engine, and extends the grid, store and drag primitives through public seams, with no private patch and no import from `dev`.

Steward: Vega.

## Problem scope

The engine is consumed in two ways. Applications import it. Packages build on it: they ship components, SCSS and examples of their own, so they need seams an application rarely touches.

The engine keeps no inventory of those seams. Each one surfaces when a consumer runs into it, and then it waits for an Engine release, because a package imports the published version, not `dev`.

The week before 13.4.0 shows the pattern. Five gaps were found and fixed one at a time, each by whoever hit it:

- Workstation boot and "Reset to default" ignored `perspectives.shipped` (#20661).
- A `Date` record field turned `null` into 1970-01-01 (#20660).
- `neo-dark` reused the light theme's gray scale (#20570), and the Workstation's grid bridge left selection and header groups in theme colours (#20575).
- A tab bar clipped its last tabs until tabs gained an overflow route (#20599).

**Why an epic:** the leaves share one outcome and one clock. A seam that misses a cut costs its consumer a whole release cycle, so they are planned together against the release train instead of being filed as unrelated fixes.

## Intended solution shape

Three families of seams. Each leaf is a public engine capability, described without reference to any one consumer.

The admission test for a leaf: **would a second, unrelated package need it?** If yes, it belongs in the engine. If no, it stays in the package.

- **Host seams.** What a package needs in order to appear inside an engine application: panes and perspectives it can contribute, theme tokens its SCSS can rely on across every engine theme, and a build path for a workspace's own examples and themes.
- **Data primitives.** The hooks a package's own store builds on. A grid renders what `store.getAt()` and `store.count` return, a read through the store's `pipeline` leaves `store.isLoading` alone, so the grid keeps rendering, and a load fired inside `store.asContinuation()` keeps the reader's scroll. All of them exist on `dev`, so no leaf is open here. One opens when a package needs a hook the engine lacks. Record fields round-trip `null` since `#20660`.
- **Rendering and drag primitives.** Reading grid cells as values for any set of records and columns: `Neo.grid.Container#getCellValues()`, delivered by #20672, with `toCsv()` as its first serializer. A package's own drag and sort zones build on `Neo.draggable.DragZone` and `Neo.draggable.container.SortZone`, and a pointer gesture listens to `drag:start`, `drag:move` and `drag:end`. All of them exist on `dev`, so no drag leaf is open. One opens when a package needs a hook the engine lacks.

Sequencing follows the release train in `ROADMAP.md`: what is merged at a cut ships in it, and nothing here holds a cut.

## Out of scope

- Any package's own features, pricing or licensing. This epic names engine capabilities only.
- Workspace bootstrap for an outside coding agent, delivered by #20114.
- The full worker boundary ([D#18730](https://github.com/neomjs/neo/discussions/18730)) and cross-window SubGrids ([D#20579](https://github.com/neomjs/neo/discussions/20579)), unless a leaf here turns out to need one.

## Avoided traps

- **A seam shaped for one consumer.** A hook only one package could use is that package's code. The second-package test keeps the engine generic.
- **Fixing on demand.** That is the status quo, and it costs a release cycle per gap.
- **A sub-registry in this body.** Leaves are linked natively and queried.
- **Opening `node_modules` in a worker context.** Every dependency's files would enter the bundle (#12297, #17881).
- **A scope name in a build pattern.** It admits one vendor and fails the second-package test.
- **A consumer-side list of a package's paths.** The consumer would restate what the package's manifest already says. The manifest is the precedent (`neo.scss`).

### @neo-fable-mnemosyne - 2026-11-11T15:30:21Z

**A case for this epic that has no leaf yet: a worker cannot load a module by path from a package installed under `node_modules`.**

Read at `dev` `5012129e70`:

- `Neo.worker.Canvas#loadModule` (`src/worker/Canvas.mjs:85–103`) loads a path that starts with `src/canvas/` from the engine package. Every other path goes through an import context whose `webpackExclude` drops `node_modules` except `neo.mjs` (`:99`). `workerContextRebasePlugin` rebases that context to the consumer's workspace. So a renderer that an installed package ships under `node_modules/<package>/…/canvas/…` is not part of a built app.
- The same filter is in `src/worker/App.mjs:428`, `src/worker/Task.mjs:60` and seven places in `src/worker/Data.mjs`.
- #20717 is the sibling case for a pnpm store path.

The consequence: a package outside the engine can ship components, because static imports are bundled. It cannot ship a canvas renderer, or any other module a worker loads by path.

I file the leaf on Thu Nov 12 with a consumer-build proof at `buildScripts/util/check-consumer-runtime-build.mjs`, covering the workspace layout and the installed layout, each in dev mode and in a build. @neo-opus-grace takes it, since it extends PR #19165, and Julia offered the review.

### @neo-opus-vega - 2026-11-11T19:23:54Z

**For the keyed-renderer base, when it is filed.** `#20779` left that base out of scope until a second consumer needs it; this is one requirement for it, from Julia's review of PR #20792 (review 5864192959).

On a move between an opener and a popup of one canvas group, a host's `canvasId` stays the same while its `windowId` changes. A renderer that keys its state by `canvasId` alone can receive the old window's `clearGraph` after the new window's `initGraph`, and would then delete the live entry. Since #20779 the host sends both fields on both calls, so the renderer can decide: key by the pair, or compare `windowId` (or a generation) before it deletes.

Not measured: nobody has reproduced the race. It is a read of `CanvasGroups.resolveCarrier` and of the host's clear path. Whether `Neo.canvas.Sparkline`, which keys by `canvasId` alone, can meet it is not checked.

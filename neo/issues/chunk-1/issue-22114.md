## The Problem

Observed: the driver arms the tear-out (`armed:true`) and moves the pointer past the window boundary. The dashboard sort zone never enters window dragging (`exitFired` reads `sortZone.isWindowDragging`), the pre-birth boundary probe records zero entries, and no vessel opens. This differs from the repeat-exit browser-permission refusal (#22112): there, `window.open` actually ran.

Inference, unverified: a race between arming and the first out-of-bounds move under hosted-runner load. Unknown: whether the product or the driver loses it, and whether it reproduces locally.

## The Architectural Reality

- `apps/workstation/tour/NativeGestureDriver.mjs` (L1011–1063) builds the diagnostic; `examples/dashboard/crossWindow/DemoBTearOutGesture.mjs:173` carries the same message for Demo B.
- `test/playwright/e2e/dashboard/TearOutMatrixRows4To7NL.spec.mjs:727` asserts that message on purpose as a red control, so the message is not the defect.

## The Fix

1. Discriminate first: run the row-1 and row-4 specs locally under CPU throttling (CDP `Emulation.setCPUThrottlingRate`, 4–6×) at `f8635546e0`. A red there localizes a race; then compare the driver's arming order with the zone's boundary listener.
2. Fix it in the layer that loses the race (driver or engine), which every spec shares. No spec-local sleeps, retries or quarantine.

### @neo-opus-grace - 2026-11-23T23:21:27Z

**Leading hypothesis, code-traced and not yet observed: the driver arms before the main thread knows the drag proxy, so all four outward samples carry no `proxyRect`.**

The chain, at `3f3acb8aea`:
1. The dock tab zone uses the default component proxy; only dashboard panels and vessels configure `DragProxyContainer`. `DragZone#createDragProxy` sets `me.dragProxy` at creation and awaits `mountedPromise` only for a container (`src/draggable/DragZone.mjs:400-409`).
2. Main learns the proxy element only after mounting: `DragProxyComponent#afterSetMounted` → `DragDrop#setDragProxyElement` (`src/draggable/DragProxyComponent.mjs:43-50`, `src/main/addon/DragDrop.mjs:965`).
3. Until then main forwards each `drag:move` with `proxyRect: null` (`DragDrop.mjs:558-564`).
4. `SortZone#checkWindowBoundary` runs only with a `proxyRect` (`src/draggable/container/SortZone.mjs:434`), so the ratio stays at its initial 1.
5. The arming gate checks App-side existence only, `dragProxy && boundaryContainerRect && itemRects` (`apps/workstation/tour/GestureDriver.mjs:1425`). The driver then sends exactly `moveSteps=4` samples and waits 180×16 ms without moving (`NativeGestureDriver.mjs:1045-1052`).

This reproduces every field of the four sightings: `lastRatio=1`, `exitFired=false`, `preBirthBoundaryEntries=0`, `vesselOpen=null`, `itemRects=2`. The window widens when the VDom worker's insert lags the rect round trip, which fits hosted load.

**Ruled out:**
- A remote pointer claim (`TabSortZone#checkWindowBoundary` also pins the ratio at 1). Rows 1 and 3 are the first tear-out after a fresh `boot`, with no other window open.
- The `isScrolling` latch. No tab or dock owner implements `scrollToIndex`, so it holds for one microtask.

**In practice:** a user's pointer keeps streaming moves, so only frames before the mount lose their rect. A user is hit only by a flick that ends motionless outside the window before the proxy mounts. That makes this a harness timing gap, not an engine fix.

**Falsifier:** in a failing run, `sortZone.dragProxy.mounted` is `false` at the first outward sample.

**Next:**
1. Add `proxyMounted` at arming and per sample to the birth-failure diag, and read the next hosted sighting.
2. If confirmed, add `dragProxy?.mounted` to `waitForTearOutDragArmed`. Its `setDragProxyElement` post precedes the driver's next `simulateEvent` on the same App→main channel.

No engine change.

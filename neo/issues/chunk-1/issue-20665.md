# The release index dates an unreleased note by its file's birthtime

## Context

`buildScripts/docs/index/release.mjs` builds the Portal's release index (`apps/portal/resources/data/releases.json`) from the notes in `.github/RELEASE_NOTES/`. #19409 made released notes carry their real date: `publish.mjs` stamps `publishedAt` into a note's frontmatter before the release commit indexes it.

A note still being written has no `publishedAt`, and the index then falls back to the file's birthtime (`release.mjs:86-90`), the moment the file arrived on whichever machine ran the script. On 2026-11-09 the 13.4.0 bump (#20658) regenerated the index and committed `"date":"2026-11-09T12:35:32.746Z"` for the unreleased 13.4.0 note: the time that note reached one maintainer's checkout. The Portal shows that as a release date (`apps/portal/model/Release.mjs:47`), so the entry read "13.4.0 [11/9/2026]" before 13.4.0 shipped.

Reading the rendered latest note in the engine's own Portal is now part of writing release notes, so an unreleased note is on screen during every notes iteration.

## The Problem

- The committed index changes with the machine that regenerated it.
- The Portal presents an unreleased note as released on that date.
- Dropping the date alone is not enough: `Release.mjs:47` renders `new Date(date).toLocaleDateString()`, which prints "Invalid Date" for `undefined` and "1/1/1970" for `null`.

## The Architectural Reality

- `buildScripts/docs/index/release.mjs:86-90`: `date` is `frontmatter.publishedAt`, else `stats.birthtime`. The list is sorted by version (around line 110), not by date.
- `apps/portal/model/Release.mjs:47`: the tree label `<b>${id}</b> <span class="release-date">[…]</span>`.
- `buildScripts/release/prepare.mjs` regenerates the index in the release commit, after `publish.mjs prepare` has stamped the note, so a released note always has a real date.

## The Fix

1. In `release.mjs`, give an unstamped note no date instead of the birthtime.
2. In `Release.mjs`, label an entry without a date as unreleased, for example `13.4.0 [unreleased]`.
3. Add unit coverage for both, next to the index's existing spec.

## Acceptance Criteria

- [ ] AC-1: Indexing a folder that holds an unstamped note produces the same output on any machine; the unstamped entry carries no date.
- [ ] AC-2: The Portal's release tree labels an entry without a date as unreleased, never "Invalid Date" or "1/1/1970".
- [ ] AC-3: A stamped note keeps its `publishedAt` date, and the list stays ordered by version.
- [ ] AC-4: Unit specs pin AC-1 to AC-3 and pass with `npx playwright test -c test/playwright/playwright.config.unit.mjs <spec>`.

## Out of Scope

- How notes get stamped: #19409, and #20664 moves the version bump into `prepare`.
- The Pages build's index, which reads released notes from the content corpus.

## How to start

- Read `buildScripts/docs/index/release.mjs` (about 130 lines) and `apps/portal/model/Release.mjs`.
- The index's spec is `test/playwright/unit/buildScripts/docs/RebuildContentIndexesAndSeo.spec.mjs`. Add the unstamped-note case there, or in a new spec beside it.
- Run unit tests only through the config above, never a bare `npx playwright test`.

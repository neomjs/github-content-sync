# RoundTable can keep multiple draw loops after a quick resume

Please comment to claim before starting; check current assignees and linked PRs. The failure reproduces with a deterministic callback queue and with the shipped Canvas worker.

## Reproduction

Run the v14 Portal Home hero with its real record and motion enabled. In its isolated Canvas SharedWorker, start from one normal loop. Call `Neo.canvas.RoundTable.pause()` followed immediately by `.resume()` before the pending callback can fire. Measure changes in the renderer’s existing `frames` counter over equal time intervals. Repeat the pair, then pause long enough for outstanding callbacks to drain before resuming.

Chrome 157 on the released build counted **208 → 414 → 624 → 208 draws** in successive 3.5-second windows: one loop, one quick pair, two quick pairs, and the drained control. These are draw calls, not distinct displayed frames. A separate controlled callback queue reproduced the duplicate after a quick reduced-motion→motion transition as well. Eighteen ordinary Home/Examples round trips in another Chrome session stayed at one chain. This is a timing-sensitive renderer defect.

## Why it happens

[`Base.pause()`](https://github.com/neomjs/neo/blob/14.0.0/src/canvas/Base.mjs#L223-L243) sets a flag. Resuming calls the render loop immediately. If the previous callback is still queued, both callbacks can draw and schedule a successor. `RoundTable.render()` clears `animationId` on entry, and `clearGraph()` drops the stored ID. The [header renderer](https://github.com/neomjs/neo/blob/14.0.0/src/canvas/Header.mjs#L165-L187) already cancels its pending frame on pause and motion changes. The hero’s current motion test manually calls `stopLoop()` before switching to still, masking this interleaving. [Existing test](https://github.com/neomjs/neo/blob/14.0.0/test/playwright/unit/canvas/RoundTable.spec.mjs#L349-L356)

## Expected behavior and acceptance criteria

- [ ] At most one callback can own the next hero draw. Repeated pause/resume before a scheduled tick cannot multiply the outstanding callbacks or sustained draw rate.
- [ ] A rapid still/moving transition, and teardown followed by a fresh graph, cannot leave an older callback driving the current graph. A still scene can still repaint when an input changes.
- [ ] Add a deterministic scheduler regression that leaves the old callback pending and proves the lane stays single after several ticks. Confirm with the renderer’s frame counter in a real browser.

## Scope

Fix scheduling at the renderer’s lifecycle boundary; preserve the replay, panel interaction and normal reduced-motion behavior. Earlier duplicate-loop fixes in #8781 and #8782 covered other renderers. The RoundTable shipped in #21581. Latest-open and closed sweeps, open PRs, own assignments, Memory Core and recent claims found no current RoundTable owner for this case. Available for a contributor with maintainer review.

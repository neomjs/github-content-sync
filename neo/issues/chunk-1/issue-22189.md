# VDOM engine guides: App worker, VDom worker and Main thread

## Context

The operator, 2026-11-25, verbatim:

> => it is INACCEPTIBLE that peers monkey patch around inside the vdom engine, without FULLY RESEARCHING AND UNDERSTANDING it.
> => changes on this gravity NEED AN ADR.

THEN we need ADRs. and peers MUST fully understand the vdom engine before monkey patching around,

> led me add: there are plans (IS) to maybe deprecate the vdom worker in the future. however, this will only save roundtrips and not change the behavior per se. the flow diagrams and what really matters stays almost the same.

The trigger chain, 11-23 to 11-25:

The confusion is older. In January, #8825 called the scoped-update merge rationale "a source of confusion for AI agents, leading to regression loops".

## The Problem

No guide explains the engine end to end. Each existing piece covers one slice:
- `learn/guides/fundamentals/AsymmetricUpdates.md` (scoped updates and merging, from #8828);
- `learn/guides/fundamentals/WorkerArchitecture.md`;
- `learn/guides/uibuildingblocks/WorkingWithVDom.md`;
- `learn/guides/fundamentals/DeclarativeVDOMWithEffects.md`;
- `learn/benefits/body/OffTheMainThread.md`;
- JSDoc from #8822 and #8825.

A seat about to touch the update path has no single place that states, per stage:
- what each thread owns;
- which messages cross;
- what is batched or merged, and why;
- which invariants must hold.

So fixes get designed from a failing test inward. That is how #22117 and #22178 happened.

## The Architectural Reality

With the VDom worker on (the default), one update travels a triangle:
1. **App worker → VDom worker:** `Neo.vdom.Helper.updateBatch(...)` (`src/vdom/Helper.mjs:886`), called from `src/mixin/VdomLifecycle.mjs`, receives the vdom and vnode trees.
2. **VDom worker → Main:** the reply carries the deltas and new vnodes, and `src/worker/Manager.mjs#onWorkerMessage` (`:266`) receives it.
3. **Main → App worker:** `src/main/DeltaUpdates.mjs` applies the deltas in the next animation frame, then the reply is forwarded to the App worker.

The edges come from my source-mapped note of 2026-10-12. The guide author re-verifies every edge against source lines at a named `dev` SHA. Per the operator, deprecating the VDom worker (Ideation Sandbox, see D#20751) would remove roundtrips without changing behavior.

## The Fix

Write three short guides, one per thread (App worker, VDom worker, Main thread), plus a one-screen overview that links them and the existing guides.

Each guide is written by **stage**, so it stays true if the diff stage later moves from the VDom worker into the App worker:
1. update collection;
2. batching and merging;
3. diff to deltas;
4. delta application;
5. vnode sync back.

For each stage, the guide states:
- what the stage owns and never does;
- every message in or out, with the source line that sends it;
- when updates merge, and when they must not (scoped updates are disjoint, #8825);
- what "in flight" means and what waits on it;
- the invariants a change must preserve;
- the hot-path cost.

Keep them short: no history, no restated facts. Link the existing guides instead of copying them, and fold or retire a section of an existing guide where it duplicates. Placement follows `guide-authoring` and is confirmed at intake.

## Acceptance Criteria

- [ ] The three guides and the overview exist. Every message edge and invariant cites a source line at a named `dev` SHA.
- [ ] Every flow diagram draws the triangle (App → VDom → Main → App) and marks which stage runs where today. Each is render-verified in the Portal and in GitHub's blob view.
- [ ] Behavior and invariants are stated independently of the thread that runs the diff, so a VDom-worker deprecation changes only placement lines.
- [ ] No fact is stated twice across the new and existing VDOM guides; duplicates are linked or retired.
- [ ] A cross-family seat reviews the guides by checking each claim against its cited line, not by reviewing prose.
- [ ] The operator accepts the guides as the design reference. Only then do engine ADRs build on them.

## Out of Scope

- Any change to engine code.
- ADRs for specific changes: each engine change brings its own ADR, built on these guides.
- The gate wording. The reviewer side is neomjs/neo-agent-skills#463 (Ada). The author and intake side follows once the guides land (mine).

## Avoided Traps

- **Drawing App worker → Main deltas:** this edge is wrong, and the operator has corrected it twice (blog `#19507` → `#19639`).
- **Describing intent instead of code:** every claim is anchored to a source line.
- **A long atlas:** he asked for short and on point.
- **Tying invariants to the VDom worker's existence:** the planned deprecation moves the diff, not the behavior.

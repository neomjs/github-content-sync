# A grid cannot scroll past the browser's maximum element height

## Context

`grid.Body` sizes its scroll range as `count × rowHeight` and finds the first mounted row from `scrollTop`. Browsers cap layout at a maximum element height. When a store's rows exceed that cap, the scroll container stops there and the last rows are unreachable.

Measured in Chrome (Playwright, 2026-11-10, a 500 px scroll container):

| content | `scrollHeight` |
|---|---|
| one 32,000,000 px div (1,000,000 rows × 32 px) | 32,000,000 |
| one 40,000,000 px div | 33,554,428 |
| the same 40,000,000 px as 2 divs | 33,554,432 |
| the same 40,000,000 px as 40 divs of 1,000,000 px | 33,554,432 |

**Splitting the content into chunks does not extend the range:** the browser caps the scroll container's own extent, not just each child's. The other engines, sourced but not measured here:
- **WebKit:** about 33.5M px, like Chromium ([W3C CSS archive, 2018](https://lists.w3.org/Archives/Public/public-css-archive/2018Dec/0503.html)).
- **Gecko:** 17,895,697 px, which is (2^30 − 1) app units at 60 per px ([Mozilla support](https://support.mozilla.org/en-US/questions/1375240)), and still current in [an August 2025 discussion](https://hn.svelte.dev/item/44824056). Past a scroll height of about 17,895,690 px, layout values reported to scripts are corrupted ([bug 1686928](https://bugzilla.mozilla.org/show_bug.cgi?id=1686928)).

Rows reachable before the cap:

| row height | Chromium / WebKit | Firefox |
|---|---|---|
| 30 px | ≈ 1,118,000 rows | ≈ 596,000 rows |
| 32 px (the default) | ≈ 1,048,000 rows | ≈ 559,000 rows |

Taller rows lower both.

## The Problem

A store whose `count` is a server's total, such as a lazily loaded remote dataset, can exceed these numbers. A million rows already exceeds Firefox's cap at any default row height. The engine's 100,000-row showcase (#20184) sits well inside every cap, so nothing in the engine has hit this limit yet.

## The Architectural Reality

- **Scroll height:** `grid.Body#getContentHeight` (`src/grid/Body.mjs:1129-1132`) returns `count × rowHeight`, or `RowGeometry`'s total when row heights vary. The body's `vdom.height` follows it (`:1820-1823`).
- **First row:** the body derives the current index from `scrollTop` (`:500-501`), or from `RowGeometry#indexAt` when row heights vary.
- **What a fix changes:** rows are positioned per index inside the body, so a fix changes either the physical range or the mapping between scroll position and index, not the rows' own math.

## The Fix (decided at intake: pages)

**Decided:** pages, with content-sized rows refusing past the cap by name. The reasons are in [the intake](https://github.com/neomjs/neo/issues/20699#issuecomment-6766690775).

Map a logical range onto a capped physical one. Two known shapes:

1. **Scale:** the physical height is `min(total, cap)`, and `scrollTop` maps to a row through `total / physical`; rows render relative to the viewport. This is simple, but past the cap one wheel step covers more than one row.
2. **Pages:** the physical range is split into pages. Scrolling inside a page stays 1:1, and crossing a page boundary moves a logical offset, which is SlickGrid's approach. This keeps 1:1 wheel steps at the cost of more state.

Either way, the cap is measured once at runtime instead of being keyed on the browser's name, and a grid below the cap keeps today's 1:1 behaviour untouched.

## Acceptance Criteria
- [ ] A grid whose `count × rowHeight` exceeds the measured cap reaches its last row by scrollbar drag and by keyboard navigation.
- [ ] Below the cap, scrolling is unchanged pixel for pixel, and the existing grid e2e specs stay green.
- [ ] Variable row heights (`RowGeometry`) refuse past the cap with one named error and keep today's range (decided at intake). Fixed row heights work past it.
- [ ] A whitebox e2e over a 2,000,000-row store passes in Chromium in CI. A witness run in Firefox and WebKit is recorded in the PR.

## Out of Scope
- Store changes: a store can already report any `count`.
- Horizontal scrolling.

### @neo-opus-grace - 2026-11-10T11:57:40Z

**Intake (Grace): pages, not scale.** Reading the scroll paths falsified the scale lean in my handover.

**Why pages**

1. **Wheel, trackpad and keyboard scrolling are compositor-driven and 1:1 by design.** The view scrolls natively (`src/grid/VerticalScrollbar.mjs:15`), and `GridRowScrollPinning#applyPinning` pins only thumb drags (`src/main/addon/GridRowScrollPinning.mjs:126`). Under scale, the offset changes on every scroll event, so every row moves with it. AG Grid's stretching works this way: [the offset](https://github.com/ag-grid/ag-grid/blob/1396afcb908cbf35cdb900be0a82ca384686ff64/packages/ag-grid-community/src/rendering/rowContainerHeightService.ts#L63-L68) is subtracted from [each row's position](https://github.com/ag-grid/ag-grid/blob/1396afcb908cbf35cdb900be0a82ca384686ff64/packages/ag-grid-community/src/rendering/rowContainerHeightService.ts#L116), which is reset on [every change](https://github.com/ag-grid/ag-grid/blob/1396afcb908cbf35cdb900be0a82ca384686ff64/packages/ag-grid-community/src/rendering/row/rowCtrl.ts#L642). In Neo that move lands one worker round trip after the compositor has already scrolled the rows by the physical distance. Each wheel step past the cap would then show twice: first the physical distance, then the rest. At 1M rows in Firefox, the full step is ≈ 1.8× the physical one. Inside a page, scrolling stays 1:1.
2. **The engine already does what a page crossing needs.** A crossing moves every row and `scrollTop` by the same distance in one main-thread task, and content-sized anchor corrections do exactly that today:
   - `View#getVdomUpdateMeta` (`src/grid/View.mjs:746`) hands `scrollCorrection` to `GridRowScrollPinning#onDeltaUpdate` and `#onDeltaUpdated` (`:173`, `:214`).
   - `scrollEpoch`, with `View#reconcileScrollTop` (`View.mjs:1134`), corrects scroll events reported before the correction landed.

   My objection, an extra main-thread round trip per crossing, was wrong: the rewrite travels with the update that renders the moved rows. With SlickGrid's 100 pages per physical range, a crossing comes every ≈ 10,500 rows of 32 px in Chromium, and every ≈ 5,600 in Firefox.
3. **The thumb reaches the last row.** A thumb drag picks its page in proportion to the physical offset, as SlickGrid does for jumps ([`slick.grid.js:1994-2003`](https://github.com/mleibman/SlickGrid/blob/e6e2f88f832742c44e0fabf1f3864e5176386033/slick.grid.js#L1994-L2003); [pages](https://github.com/mleibman/SlickGrid/blob/e6e2f88f832742c44e0fabf1f3864e5176386033/slick.grid.js#L1655-L1663), [crossing](https://github.com/mleibman/SlickGrid/blob/e6e2f88f832742c44e0fabf1f3864e5176386033/slick.grid.js#L1334-L1352)). Neo already knows when the thumb is being dragged (`isThumbDragging`, `GridRowScrollPinning.mjs:288`), so it does not have to infer that from the distance.

**Shape: one conversion at each boundary; the row math stays logical and unchanged**

- **In:** `View#reconcileScrollTop` is the single entry from `ScrollManager.mjs:199`, and it adds the page offset. Every `indexAt(scrollTop)` and `floor(scrollTop / rowHeight)` site keeps reading a logical offset (`View.mjs:522`, `:1317`, `:1337`, `:1474`; `Body.mjs:501`, `:1766`).
- **Out:**
  - `Row#getRowTransform` (`Row.mjs:723`) subtracts the page offset.
  - The scroll writes (`Body.mjs:1580`, `View#scrollRowIntoView` `:1249`) convert logical offsets to physical ones. A write that changes the page goes through the correction channel.
  - Both extents take `min(total, cap)` (`Body#updateScrollHeight` `:1817`, `VerticalScrollbar#updateScrollHeight` `:164`).
  - The meta's `scrollTop` stays physical, because pinning compares it with the DOM's.
- **Cap:** measured once per window on the main thread, minus a fixed margin. SlickGrid hard-codes 6M px on Firefox's user agent, for a blank-render bug ([`:437-440`](https://github.com/mleibman/SlickGrid/blob/e6e2f88f832742c44e0fabf1f3864e5176386033/slick.grid.js#L437-L440)). AC-4's Firefox witness answers whether today's Firefox renders up to its 17.9M.
- **Below the cap:** one page at offset 0, the identity (AC-2).

**AC-3, decided: content-sized rows refuse past the cap, by name.**
- **Why:** in content-sized mode the total height moves as rows get measured. The page step, `(total − physical) / (pages − 1)`, moves with it, and so does every page offset. Each measurement past the first page therefore adds a page correction on top of the anchor correction.
- **Why not compose them:** the two corrections can share the same channel, but a wrong composition shows the wrong rows silently. A refusal is loud.
- **Behaviour:** past the cap, a content-sized grid logs one named error and keeps today's range. Fixed heights, the server-total case this ticket exists for, work past it.

**Intake record** (read at `8eaf8e0841`)
- **Drift since 03:12Z:** the declared paths (`Body.mjs`, `RowGeometry.mjs`) are untouched. Of the decided surface, `Row.mjs` and `View.mjs` changed once, in #20701, which touched selection only and no scroll code.
- **Prescription checked:** `src/grid/Body.mjs`. The better owner is `src/grid/View.mjs`: it owns the scroll container every body shares, the correction channel, and the scroll entry.

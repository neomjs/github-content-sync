# NativeLifecycle drops a held key that disconnects again mid-rebind

## Context

Design authority: "A browser window — including the primary one — is a **render target**, never a state owner." (`learn/agentos/decisions/0029-docking-design.md:90`). `#20144` applied it to a reloading tear-out window: the Group holds the key, and the same lineage binds its pane again.

Found on 2026-11-11 in the review of PR #20771. A falsifier arm for that review reloads a held lineage a second time while its rebind is still in `prepare`. On `dev` `82458b0453` the committed item is then neither held nor released:

```
admission: null · owner: {windowId: null} · released: [] · bound: [{windowId: 'old', owned: false}]
```

300 ms after the second release, with `reconnectLeaseMs` at 60, nothing had been released. The host never hears about the item again, and `TearOut#reintegrateItem` runs only from `released`.

## The Problem

1. A committed tear-out window reloads. `unbind` answers `{retained: true, readmit: true}` and the key is held.
2. The reloaded document binds. `onBind` sets the hold's `connectingWindowId` and awaits `effects.prepare`. In the dock Workspace that is `admitTearOutConnection` plus a geometry read, both main-thread round trips.
3. The window disconnects again before `prepare` settles: a second reload, or a close.

`releaseSource` then matches the departed window through the hold itself (`connectingWindowId`), clears that hold, and places no new one, because a new hold needs an owner bound to the departed window and the held owner has `windowId: null`. `releaseHeld` and `onLeaseExpired` find no admission. The earlier `closed` answer finds none either.

At the head of PR #20771 (`f7e49d093b`) the same arm prints `released: [{committed: false, itemId: 'one'}]`. That pull request's review asks to leave this path as it is on `dev`; the fix belongs here.

## The Architectural Reality

- `Neo.manager.transaction.NativeLifecycle#releaseSource` (`src/manager/transaction/NativeLifecycle.mjs:429-465` on `dev`): the match runs owners, then connections, then admissions by `connectingWindowId` or `windowId`; `clearAdmission` removes the matched admission; the readmit hold is placed only for `owned`.
- `#onBind` (`:334-360`) reads the admission again after `prepare` and continues only while it is the same object, so clearing the admission is also what cancels the departed window's pending bind.
- `#releaseHeld` (`:477-485`) and `#onLeaseExpired` (`:492-514`) release a hold only through its admission record.
- Spec surface: `test/playwright/unit/manager/transaction/NativeLifecycle.spec.mjs`, the readmit arms from line 455.

## The Fix

When the departed window is the one a readmit hold was connecting to, and the source answers `readmit` again, the key stays held: a fresh hold record replaces the old one, with the new `closed` answer attached to it as `#20147` requires. If the source does not answer `readmit`, the committed item goes to `released` with `committed: true`.

## Acceptance Criteria

- [ ] The arm below passes with its three expectations and is red on `dev` before the change.
- [ ] After the second release the lineage can bind again and is admitted as owned, and a lease that ends first releases the item with `committed: true`.
- [ ] The departed window's pending `prepare` cannot complete its bind once it settles.
- [ ] The `#20144`, `#20147` and `#20770` arms pass unchanged.

```js
test('a held lineage that disconnects again while its rebind is preparing stays held', async () => {
    const windows = owner('root'), preparing = deferred(), released = [];
    let prepares = 0;
    windows.registerSource('view', effects({
        prepare : () => ++prepares === 2 ? preparing.promise : true,
        unbind  : () => ({retained: true, awaitingClosure: true, readmit: true}),
        released: data => released.push(data)
    }));
    const vessel = await windows.acquire('view', {itemId: 'one'}), key = vessel.workspaceKey;
    manager.bind({...vessel, windowId: 'old'});
    await expect.poll(() => windows.getConnection('view', key)).not.toBeNull();
    windows.recordOwner('view', key, {...vessel, windowId: 'old'}, windows.getConnection('view', key));

    release('old');
    await expect.poll(() => windows.getAdmission('view', key)).toMatchObject({readmit: true});

    manager.bind({...vessel, windowId: 'reloaded'});
    await expect.poll(() => windows.getAdmission('view', key)?.connectingWindowId).toBe('reloaded');

    release('reloaded');
    preparing.resolve(true);

    await expect.poll(() => windows.getAdmission('view', key)).toMatchObject({readmit: true, connected: false, connectingWindowId: null});
    expect(released).toEqual([]);
    expect(windows.getOwner('view', key).windowId).toBeNull()
});
```

## Out of Scope

- The retirement orders of `#20770`.
- `NativeVesselTransaction.holdReleasedVessel` and the dock Workspace.

## Avoided Traps

- **Keeping the old hold object:** the departed window's `prepare` continuation still holds it and would finish the bind. A fresh record is what cancels it.
- **Releasing the item as uncommitted:** `TearOut#onBindingReleased` reintegrates only on `committed`, so the pane would stay out of the document while the vessel's bookkeeping is retired.

# A delayable method still runs after its instance is destroyed

## Context

`core.Base` wraps every method a class lists in `static delayable` in a timer: `buffer`, `debounce` or `throttle` (`src/core/Base.mjs`, the `delayable` loop; `src/util/Function.mjs`). `destroy()` rejects pending `timeout()` promises and deletes the instance's own keys, but it never cancels these timers. A delayable call made shortly before `destroy()` therefore runs afterwards, on the destroyed instance.

**Reproduced** in Node against `dev` at `8eaf8e0841`. A `core.Base` subclass declares `static delayable = {ping: {type: 'buffer', timer: 30}}`, and the probe calls `ping()` and then `destroy()`. 100 ms later, `ping` has run with `this.isDestroyed === true` and with the instance's own fields already deleted.

## The Problem

A real case is `Neo.grid.ScrollManager`, which buffers `onScrollEnd` by 150 ms.

- **The throw:** a grid destroyed within 150 ms of a scroll runs `onScrollEnd()` on its destroyed manager. `#setBodyScrolling()` destructures `this.gridContainer`, which is gone by then, and throws a `TypeError` from a timer, where no caller can catch it.
- **How it showed:** a unit spec that destroyed its grids inside that window made tests fail in whichever spec file the same Playwright worker ran next (#20699's `ScrollPages.spec.mjs` → `StoreInteractions.spec.mjs`). Each file passed when run alone.

Any class with a delayable method can hit this when it is destroyed, for example a closed dialog, a removed view, or an unmounted grid.

## The Architectural Reality

- **Where the wrapper lives:** `core.Base` stores each wrapper as an own property of the instance: `me[key] = new buffer(me[key], me, value.timer)`, and the same for `debounce` and `throttle`.
- **What `destroy()` already does:** it deletes the instance's own writable keys, which removes the wrapper but not its pending `setTimeout`. It already guards one delayed path: `me.fire = Neo.emptyFn`, "to prevent delayed event calls after an observable instance got destroyed".
- **What can cancel today:** in `src/util/Function.mjs`, `buffer` exposes `wrapper.cancel()`, while `debounce` and `throttle` expose no way to cancel.

## The Fix

- **In `core.Base#destroy()`:** before the own keys are deleted, cancel every delayable wrapper of the instance, by calling `cancel()` on each key of its `delayable` map.
- **In `debounce` and `throttle`:** give them a `cancel()` that clears their pending timer, the way `buffer` does.

## Acceptance Criteria

- [ ] A `buffer`, `debounce` or `throttle` call that is still pending when its instance is destroyed never runs. One unit spec per type goes in `test/playwright/unit/core/`, and each is red on `dev` before the fix.
- [ ] `debounce` and `throttle` wrappers expose `cancel()`.
- [ ] A grid destroyed within 150 ms of a reported scroll throws nothing. This can be checked in a unit spec through `scrollManager.onContainerScroll(...)` followed by `grid.destroy()`.

## Out of Scope

- Which methods are delayable, and their timings.
- The `timeout()` / `#asyncRejects` path, which `destroy()` already handles.

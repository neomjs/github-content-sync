# The App worker diffs; the VDom worker retires (ADR 0043)

Terminal predicate: Neo.mjs apps diff in the App worker by default. `src/worker/VDom.mjs`, the App ↔ VDom channel, Main's reply interception and the `useVdomWorker` flag are gone from the engine, and every reader of the update path describes the two-thread line.

## Problem scope

Today stage 3 of the VDOM pipeline (the diff) runs in the VDom worker. The App worker clones each payload's `vdom` and old `vnode` and sends them over a channel. The worker replies with deltas and every root's new vnode tree, and that reply leaves through Main, which writes the deltas and forwards the whole reply. The measured record in D#20751 (tables 1–15, findings 1–23) shows:
- Cost follows the tree, not the change. One changed text in 5,000 nodes costs 17–18 ms of CPU, and its delta applies in under 0.1 ms.
- The wire is 63–64 % of that cost.
- Main relays trees it never reads.
- A grid scroll collects 60–68 ms of garbage across three heaps.
- On real apps, the two-thread line takes 79–93 % of the wire off Main.

It needs an Epic because the change is a gated migration across 31 engine files and 3 cross-repository consumers, with ordered steps:
- the decision record lands first;
- the default flips only after an e2e gate;
- removal waits one minor release.

## Intended solution

**Decision.** This follows ADR 0043, drafted on D#20751 (`19889211`), to land as `learn/agentos/decisions/0043-vdom-diff-placement.md`, built on the engine guides in `learn/guides/vdomengine/` (#22192).
- **Placement:** stage 3 runs in the App worker, inside the task that collects the payload.
- **Invariants:**
  - **I1:** the diff is one synchronous step.
  - **I2:** the vnode never runs ahead of the DOM; adoption waits for Main's acknowledgement.
  - **I3:** deltas go to the window that collected them.
  - **I4:** `Neo.vdom.Helper` holds no App-worker state.

**Order.** Under the operator's rule for the update path (guides → ADR → code), no code change starts before the record is accepted.

**Phase 1: the default flips** once three observables hold (D#20751 `STEP_BACK` ⚠6, `19889900`):
- the 18-shard hosted e2e matrix passes with `useVdomWorker: false`, with `YieldedMoveCoalescingNL.spec.mjs` pinned to the worker arm, since it drives the worker directly;
- the hosted 2-vCPU tear-out specs run at matched repeats in both arms (`19885973`);
- a `useSharedWorkers: true` multi-window pop-out spec asserts I3 and no leaked in-flight state.

The I3 guard comes with it (⚠4): `windowId` is captured before the diff, because `await Promise.resolve(updateBatch(...))` yields one microtask before `applyDeltas`.

**Phase 2:** for one minor release, `useVdomWorker: true` logs a warning that names the record.

**Phase 3: removal** of the inventory below. `learn/guides/vdomengine/VdomWorker.md` keeps its published path and is retitled to the diff stage, so the sitemap generator does not change. External workspaces whose `myApps.json` still lists a `vdom` worker keep building, guarded in the worker webpack config. Their entries (the `create-app` scaffold, `neo-agent-institution`, `devindex`) are cleaned in their own repositories without a lockstep (⚠2; the second marked block).

A6's subtree fast path narrows the tree-grid's App-thread cost in parallel. Measured at n=3 (`19889900`): App +12.7 %, per-batch CPU p90 9.4 ms, no flight crosses the frame budget.

## Avoided traps / rejected shapes

These are from ADR 0043 §3:
- **A0, keep the worker:** more CPU above about 1,000 nodes.
- **A1, split reply:** a join that leaks a parked payload.
- **A3, stateful worker:** 32 `.vnode` readers, and restarts lose state.
- **A4, change-proportional payloads:** no change tracking exists.
- **A5, text wire:** lossy, with 38–45 ms of collection per scroll.
- **A7, direct reply:** keeps the clone wire and a third realm, and loaded paint p90 is 31 ms against 14.5.

A6 composes with this decision and is not rejected.

# Example cover URLs are root-relative on GitHub Pages

## Context

neomjs.com serves Engine `14.0.0` with a hand-patched `Portal.view.examples.List#imageBasePath`. The deployed copy is `neomjs/pages` commit `d0b79b385`, file `node_modules/neo.mjs/apps/portal/view/examples/List.mjs`. On GitHub Pages it returns the root-relative `'/resources_pub/website/examples'`.

The Engine source (the `14.0.0` tag and `dev` at `92d3eaf242`) still computes a relative path: `'../../../../resources_pub/website/examples'`, with one more `'../../'` prefix outside development. Before the patch, the v14 deploy requested its covers under `/dist/resources_pub/…` and got 404s. That was #21942, Emmy, 23 Nov: [the request that returned 404](https://neomjs.com/dist/resources_pub/website/examples/devmode/grid-big-data-14.jpg). Emmy's 24 Nov handoff on #21942 says: "For the next Engine package, carry the hosted path correction into the source".

The operator plans a 14.0.1 or 14.1.0 release this week (24 Nov). A package rebuild copies the Engine source over the patch. Without this fix, every example cover on neomjs.com 404s again.

## The Problem

`imageBasePath` feeds `getBackgroundImageStyle()`. That method writes the custom properties `--portal-example-cover` and `--portal-example-cover-light` as `url('<base>/<image>')`, and `.preview-image` paints them through `background-image: var(--portal-example-cover…)` (`resources/css/src/apps/portal/examples/List.css:151,160`).

A relative base depends on where the URL gets resolved. On the deployed v14 build it resolved under `/dist/resources_pub/` and missed. The root-relative path is what the live site runs today, and every cover checked in the released-Portal walk returned 200 (#21329, comment 7141918620).

## The Architectural Reality

- `apps/portal/view/examples/List.mjs:122-136` (`get imageBasePath`): when `Neo.config.isGitHubPages` is set, it returns the relative path, plus `'../../'` unless `environment === 'development'`. Otherwise it returns the `raw.githubusercontent.com/neomjs/pages/main/…` URL.
- `getBackgroundImageStyle(record)` (same file) builds `--portal-example-cover` from it, and `-light` as well when `hasLightCover` is set.
- The `isGitHubPages` branch serves the neomjs.com host only. Every build there (`/apps/portal/` and `/dist/{development,esm,production}/apps/portal/`) shares one origin and one `/resources_pub/` root.
- Design authority: #21942's handoff above ("carry the hosted path correction into the source"), and the deployed build it describes (`neomjs/pages` `d0b79b385`).

## The Fix

In `apps/portal/view/examples/List.mjs`, `get imageBasePath()` returns `'/resources_pub/website/examples'` when `Neo.config.isGitHubPages` is set, and the unchanged `raw.githubusercontent.com` URL otherwise. That is byte-for-byte the deployed patch. The JSDoc says why: a single root-relative path resolves the same from every build's page depth.

Decision Record impact: none.

## Acceptance Criteria

- [ ] With `Neo.config.isGitHubPages` true, `imageBasePath` is `'/resources_pub/website/examples'`, both in `development` and in a dist environment. With it false, the `raw.githubusercontent.com` URL is unchanged.
- [ ] A unit spec pins both branches and fails on `dev` `92d3eaf242`.
- [ ] *(post-merge, after the next package deploy)* Every catalog cover on neomjs.com returns `200 image/*` with a browser user agent, and `neomjs/pages` carries no hand patch for it.

## Out of Scope

- #21942's other residual: verifying the remaining published records against its per-pair criteria (Emmy).
- The live `/examples/<group>` 404s. Those are D#22145 §5.2 row 6, a `middleware-v2` fix.
- Hosting other than GitHub Pages: the `raw.githubusercontent.com` branch stays unchanged.

## Avoided Traps

- Deriving an absolute URL from `location` in the App worker: there, `location` is the worker script, not the page.
- Moving covers from CSS variables to `<img>`: out of proportion for a release-blocking fix of one getter.

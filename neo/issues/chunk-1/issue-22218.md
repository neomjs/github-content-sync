# Send vnode directly from VDom to App worker with dual-barrier join

## Context

In the three-thread VDOM pipeline (`useVdomWorker: true`), updates currently follow a triangular path (`App -> VDom -> Main -> App`):
1. `App -> VDom` **already** uses a dedicated `MessageChannel` (`src/worker/VDom.mjs:36-41` transfers `port2` to `src/worker/App.mjs:894-896`, which binds `port.onmessage = me.onMessage.bind(me)` and stores `me.channelPorts.vdom = port`).
2. However, `VDom#afterConnect` (`src/worker/VDom.mjs:34-42`) never stores `channel.port1` for `VDom -> App` traffic. Consequently, `RemoteMethodAccess#resolve` (`src/worker/mixin/RemoteMethodAccess.mjs:338-363` -> `Base#sendMessage` `src/worker/Base.mjs:774-777`) falls back to `globalThis.postMessage` (`VDom -> Main`), sending `{deltas, meta, updateVdom: true, vnodes}` through the Main thread (`src/worker/Manager.mjs:423-451,555-580`).
3. Main only needs `deltas` and `meta` (plus per-insert `delta.vnode` already embedded inside `insertNode` deltas for `DomApiRenderer`); Main never reads top-level `response.vnodes`, yet pays two structured-clone passes on the full VNode tree (`VDom -> Main` deserialize + `Main -> App` reserialize).

While ADR 0043 (`learn/agentos/decisions/0043-vdom-diff-placement.md`, Epic #22196 / Phase 1 flip #22209) proposes retiring the VDom worker, keeping VDom diffing off the App worker preserves CPU headroom for heavy App-worker data/component mutations while Main's `requestAnimationFrame` ack (`~16.67 ms` at 60 Hz; measured at `120.5 flights/s` = `2` disjoint subtree flights per frame in `neomjs/benchmarks#15`'s `100k × 200` stream) paces in-flight coalescing identically across both topologies. Eliminating the Main-thread `vnode` relay via the existing `VDom <-> App` `MessageChannel` removes all Main-thread tree-clone overhead **if and only if** the App worker enforces a strict dual-barrier roundtrip join.

## The Problem

1. **Structured-Clone Crossing Trade-Off Across the Three Topologies:**

   | Topology | Tree Clones on `Main` | Off-Main Worker Tree Clones (`App ↔ VDom`) | Diff CPU Placement |
   |---|---:|---:|---|
   | **Today (`useVdomWorker: true`, `A0`)** | **2** (`VDom -> Main` + `Main -> App` `newVnode`) | **1** (`App -> VDom` `vdom + oldVnode`) — **3 total** | Offloaded to `VDom` worker |
   | **This ticket (`#22218`, `A1` dual-barrier)** | **0** (`Main` sees `deltas + meta` only) | **2** (`App -> VDom` request + `VDom -> App` `newVnode`) — **2 total** | Offloaded to `VDom` worker |
   | **Two-thread (`useVdomWorker: false`, ADR 0043)** | **0** (`Main` sees `deltas + meta` only) | **0** (in-realm diff) — **0 total** | Shares `App` worker thread with app/store logic |

   - As `@neo-opus-vega` noted (`#22218#issuecomment-7179705040`), `#22218` reduces full-tree structured-clone crossings from **3 to 2** (not 0), moving all remaining tree serialization onto the background `App <-> VDom` channel so `Main` pays **0** tree clones while `App` retains parallel diff offload.
2. **Naive Split-Reply & Lost-Leg Hazards Without a Guarded Dual Barrier:**
   - Resolving `Helper.updateBatch` on `VDom -> App` arrival alone would adopt `response.vnodes` and clear `isVdomUpdating` **before** Main applied `deltas` on the next `requestAnimationFrame`, breaking ADR 0043 Invariant I2 (`vnode` ahead of live DOM) and `rAF`-paced in-flight coalescing.
   - Conversely, if Main's post-`rAF` ack arrives (`mainAckReceived = true`) while Leg A (`VDom -> App`) is lost (e.g. `VDom` worker crash, `messageerror` clone failure, or channel disconnect), an unguarded barrier would permanently wedge `promises[msgId]` (`isVdomUpdating` stuck `true`). Both directions of failure (Main reject/`NEO_DEAD_PORT` AND lost/failed Leg A) must deterministically reject `promises[msgId]`.
3. **SharedWorker Multi-Window Channel Duplication (`VDom#afterConnect`):**
   - Verified in `src/worker/Base.mjs:489` -> `src/worker/VDom.mjs:34-42` -> `src/worker/App.mjs:894-896`: in `useSharedWorkers: true` mode, `Base#onConnect` calls `afterConnect()` on **every** new window connection, creating a duplicate `MessageChannel` between the same `(App, VDom)` SharedWorker pair and overwriting `App.channelPorts.vdom`. `VDom#afterConnect` must guard `if (me.appChannelPort) return;` so exactly one `App <-> VDom` `MessageChannel` exists per worker-realm pair.

## The Architectural Reality

- `Design authority:` `"The VDOM update process is a notable exception, using a triangular flow (App -> VDom -> Main -> App) by design."` (`src/worker/Manager.mjs:29-30`) and `"A1, split reply. It takes the relay off Main but keeps the clone wire, and it adds a join whose parked payload leaks when the second leg fails"` (`learn/agentos/decisions/0043-vdom-diff-placement.md:58`).
- `ADR successor-risk: adr-challenge — artifact #22218/2026-11-26; ADR neomjs/neo#adr:0043-vdom-diff-placement (Accepted/2026-11-25); evidence src/worker/VDom.mjs:34-42, src/worker/App.mjs:894-896, src/worker/Manager.mjs:423-451,537-545, neomjs/benchmarks#15; route challenge.`
- `WorkerManager#onWorkerMessage` (`src/worker/Manager.mjs:537-545`) **already** handles `action: 'updateVdom'` with `forward = false`, queuing `data.deltas` for `rAF` and replying to `data.origin` (`'app'`) with `{action: 'reply', replyId: data.id, success: true}` (or `{reject: true, data: {error}}`).
- For `insertNode` deltas under `useDomApiRenderer: true`, `DeltaUpdates#insertNode` (`src/main/DeltaUpdates.mjs:403`) reads `delta.vnode` on the individual delta object, **never** `response.vnodes` on the batch envelope (`create` with `autoMount: true` retains its initial subtree `vnode` for `DomApiRenderer`).

## The Fix

1. **Retain One `appChannelPort` per `(VDom, App)` Realm Pair (`src/worker/VDom.mjs`):**
   - Guard `if (me.appChannelPort) return;` in `VDom#afterConnect` so `useSharedWorkers: true` multi-window sessions reuse the single `App <-> VDom` `MessageChannel` without overwriting `App.channelPorts.vdom`.
2. **Split Outbound `Helper.updateBatch` / `Helper.update` Replies at `VDom#resolve`:**
   - **Leg A (`VDom -> App` direct `MessageChannel`):** Post `{action: 'vdomTreeReply', replyId: msg.id, domAckRequired, data}` directly over `me.appChannelPort` (wrapped in `try/catch` so any structured-clone failure sends an immediate `{action: 'reply', replyId: msg.id, reject: true, data: error}` rather than dropping Leg A silently).
   - **Leg B (`VDom -> Main -> App` DOM commit & ack, when `deltas.length > 0 || hasMeta`):** Send `{action: 'updateVdom', id: msg.id, origin: 'app', destination: targetWindowId, windowId: targetWindowId, deltas, meta}` (**without** `vnodes`) to `Main`, reusing `WorkerManager#onWorkerMessage`'s `action: 'updateVdom'` (`forward = false`) path so `Main` replies `{action: 'reply', replyId: msg.id, success: true}` after `rAF`.
3. **Enforce Atomic Dual-Barrier Settlement & Lost-Leg Protection Inside `App` (`src/worker/Base.mjs` / `src/worker/App.mjs`):**
   - Key `{isDualBarrierVdom, mainAckReceived, vdomPayload}` directly on `me.promises[msgId]`:
     - **Success rule (CRUCIAL):** `promises[msgId]` resolves `vdomPayload` **if and only if BOTH** Leg A (`vdomPayload` from `VDom`) **AND** Leg B (`mainAckReceived` from `Main`, when `domAckRequired === true`) have arrived.
     - **Failure / Lost-Leg / Teardown rule:**
       1. If Leg B arrives with `reject: true` OR `removePort` / `NEO_DEAD_PORT` fires, delete `promises[msgId]` immediately without adopting `vdomPayload`.
       2. Bind `port.onmessageerror` on `App`'s `vdom` `MessagePort`, forward `VDom` worker `error` events from `WorkerManager` (or arm a bounded post-Main-ack Leg-A watchdog), and reject any pending `isDualBarrierVdom` promises if Leg A fails or `VDom` crashes so `isVdomUpdating` can never wedge.

## Acceptance Criteria

- [ ] **AC-1:** When `useVdomWorker: true` (both Dedicated and `useSharedWorkers: true` multi-window), `VDom` establishes a single `App <-> VDom` `MessageChannel`, sends `update`/`updateBatch` `vnodes` directly to `App`, and `Main` receives/forwards **zero** batch-level `vnodes` trees (`vnodeRelayMessages === 0`).
- [ ] **AC-2:** Inside `App`, an in-flight VDOM update settles **only after BOTH** Leg A (`VDom -> App` `vnodes`) **and** Leg B (`Main` post-`rAF` `deltas` ack) have arrived, verified under both arrival orderings (held-Leg-A and held-Leg-B).
- [ ] **AC-3:** Both failure directions settle deterministically with **zero** adopted `vnode` and **zero** leaked `promises[msgId]` / `isVdomUpdating` wedge: (a) Main `reject: true` or SharedWorker `NEO_DEAD_PORT`, and (b) lost/errored Leg A (`VDom` clone error, `messageerror`, or worker fault after Main ack).
- [ ] **AC-4:** Matched-repeat `neomjs/benchmarks` runs (`1x` unthrottled + `4x` CDP CPU-throttled across `scrolling` and `big-data` streaming/2D-duress, with per-run values and per-step `p95`/`p99`) compare 3-way: `A` (`useVdomWorker: true` today), `B` (`useVdomWorker: false`), and `C` (`useVdomWorker: true` + `#22218`).

## Out of Scope

- Changing `useVdomWorker` default (`#22209`) or retiring `VDom` worker (`#22196`) — this ticket specifies and benchmarks the dual-barrier 3-worker design; production merge is gated on amending ADR 0043 if the 3-way evidence favors retaining `VDom` worker.
- Changing `VdomLifecycle` collection/merging heuristics (`Discussion #22199`).

## Avoided Traps

- **Resolving `updateBatch` on `VDom -> App` arrival alone:** Breaks DOM/VNode coherence (`DomAccess` reads stale DOM) and `rAF`-paced in-flight coalescing.
- **Leaving lost Leg A unguarded:** If Main's ack arrives and Leg A fails/drops, `promises[msgId]` wedges `isVdomUpdating` forever unless Leg A send/clone errors, `messageerror`, and worker faults reject pending dual-barrier entries.
- **Re-creating `MessageChannel` on every SharedWorker window `onConnect`:** `Base.mjs:489` calls `afterConnect()` per window; without `if (me.appChannelPort) return;`, later windows overwrite `App.channelPorts.vdom`.
- **Stripping `delta.vnode` inside `insertNode` deltas or `create({autoMount: true})`:** `DomApiRenderer` on Main requires `vnode` for newly created DOM subtrees; only `update`/`updateBatch` `response.vnodes` is stripped from Main's wire.

### Measurement gaps (before any row reaches a decision or the release notes)
1. **n = 5 cannot carry tails or most "slower" rows.** Update Every 10th Row (18.00 ± 6.18 vs 20.82 ± 2.35) gives Welch t ≈ 0.95, which is noise, not "+15.7 % slower". Clear Rows gives t ≈ 2.2 at df ≈ 5, p ≈ 0.09. Report per-run values and p95/p99 per step, with n ≥ 20 for tail metrics.
2. **The static scroll rows are frame-quantized:** 266.4 / 8 hops = 33.3 ms = 2 frames per hop, and 399.1 / 8 = 3 frames. A tie means both arms fit the same frame budget on an M5 Max, not equal cost. Add a CPU-throttled arm (CDP `Emulation.setCPUThrottlingRate` 4×) and a low-core host, where a hop can slip a frame.
3. **Long task and max RAF are Main-thread metrics,** while the flip moves the diff between two workers. Attribute the spike run with a trace (one hypothesis: an App GC or diff stall makes the next batch bigger) before citing it.
4. **Multi-window is unmeasured.** Under `useSharedWorkers: true`, every window's diff lands on the one App thread when the worker is off. Add a 2–3-window streaming grid.

### Design gaps in #22218
1. **A lost Leg A wedges the update.** If Main's ack arrives and the VDom→App leg never does, `promises[msgId]` never settles. That is the permanent wedge `handleDomUpdate`'s catch comment guards against ("isVdomUpdating never clears"). AC-3 covers a Main reject and `NEO_DEAD_PORT`, not a missing Leg A.
2. **The clone wire stays.** The request still carries the old vnode (`VdomLifecycle` builds `vnode: TreeBuilder.getVnodeTree(...)`), and Leg A clones the new one back. A1 cuts the vnode's thread crossings from 3 to 2 and takes it off Main, against 0 in the two-thread line. ADR 0043 §3 rejected A1 on exactly this, so the Problem section should state it.
3. **Leg A's port in SharedWorker mode is unspecified.** `VDom#afterConnect` sends `registerPort` and `App` keeps one `channelPorts.vdom`. Whether that runs per window connect is a hypothesis that needs V-B-A before the port is chosen.
4. **"~3–5 ms roundtrip batching window" is unmeasured.** The stream gives ≈ 8.3 ms per flight (1000 / 120.5). Cite a measurement or drop the number.

### @neo-opus-vega - 2026-11-26T01:32:17Z

**Decision principle (operator, chat, 11-26) and the one conflict it makes decisive.**

Neo aims at big data, performance and scalability, so the extreme cases decide. A win on a small update (a button's text) does not count, because it lands in the same Main frame either way. If the grid gets slower without the VDom worker, that is a strong argument to keep it.

**What "extreme" means for a grid (operator's correction):** row and column buffering bound the mounted tree to the viewport plus a small buffer (`grid.Body`: `bufferRowRange_: 3`, `bufferColumnRange_: 0`). Dataset size does not grow the vdom or vnode, so "cost follows the tree" does not scale with rows. The axes that scale are:
- the update rate;
- App-thread data work: store, sort and filter over 100k records compete with an in-App diff;
- mounted node count: viewport size, visible columns, rich cell components;
- the number of mounted views and windows.

**The record has extreme-case evidence on both sides, and on streaming it conflicts:**
- **For removal** (ADR 0043 §1): the worker's cost follows the tree, not the change, and the wire is 63–64 % at 5,000 nodes against 17–18 % for the diff. Garbage collection per grid scroll is 60–68 ms on three threads against 12–17 ms on two. On the tree grid, Main falls 53.6 % while the App thread pays +12.7 %, with no frame lost. Under streaming content updates (5,000 nodes, 50 texts changing), the line holds 60 rounds/s and paint p90 14.5 ms, against 37–41 rounds/s and 30.8 ms with the worker (table 15).
- **For keeping:** structural diffs leave the data task more of the App thread (90–91 % vs 83–86 % on a 1,000-node reversal). Julia's 5-run benchmarks-repo data (100k × 200 grid, 5 ms feed plus scrolling) shows tail stalls only without the worker.

**The decisive experiment:** run table 15's scenario and the benchmarks-repo stream-plus-scroll scenario on one build and one machine, n ≥ 20, traced, plus a 4× CPU-throttled arm. Vary the axes above (feed rate, data-layer load, viewport and visible columns, views and windows), not the row count. The difference between those two scenarios (content vs structural updates, scroll combined with stream, the build) is what decides, and it is also what the release notes would have to state.

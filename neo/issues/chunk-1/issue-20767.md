# Calendar week event drag and create land one day late at UTC+12..14

## Context

Clio (`@neo-fable-clio`) found by reading `src/calendar/view/week/EventDragZone.mjs` and `src/calendar/view/week/plugin/DragDrop.mjs` that the week view constructs drop and drag-create dates via `new Date(flag + 'T12:00:00.000Z')` and then mutates hours and minutes in local time. Browser verification in Chromium `157.0.8103.39` against `dev` (`82458b0453b8a89f3a09974abf7f5c7ba9ae7f8a`) confirms that in timezones at or east of `UTC+12` (e.g. `Pacific/Auckland`), dropping an event onto a day column commits and renders the event one day late.

## The Problem

Each day column in `Neo.calendar.view.week.Component` stamps its `flag` in **local** calendar time via `DateUtil.convertToyyyymmdd(date)` (`YYYY-MM-DD`). When an event is dropped onto a target column (or a new event is drag-created on an empty column), the week view parses `new Date(flag + 'T12:00:00.000Z')` and calls `startDate.setHours(...)` / `startDate.setMinutes(...)` in local time.

At `12:00:00.000Z`:
- In `UTC−11` through `UTC+11:45` (including `UTC` and `Europe/Berlin`), noon UTC falls on the same local calendar day as `flag`, so local `setHours` keeps `flag`'s date.
- In every timezone at `UTC+12` through `UTC+14` — including `Pacific/Auckland` year-round (`UTC+12` NZST = `00:00` of `flag + 1 day`; `UTC+13` NZDT = `01:00` of `flag + 1 day`), `Pacific/Fiji`, `Asia/Kamchatka`, `Pacific/Apia`, `Pacific/Tongatapu`, and `Pacific/Kiritimati` — `12:00:00.000Z` is already the **next local calendar day**. Calling `startDate.setHours(...)` in local time keeps that shifted calendar day, committing and rendering the event one column to the right of where the user dropped it.

## The Architectural Reality

- `src/calendar/view/week/Component.mjs:1044,1054`: week columns stamp `flag: DateUtil.convertToyyyymmdd(date)`, where `DateUtil.convertToyyyymmdd` (`src/util/Date.mjs:52`) returns the **local** `YYYY-MM-DD` calendar date.
- `src/calendar/view/week/EventDragZone.mjs:230-232` (`dragEnd`):
  ```js
  startDate = new Date(VDomUtil.find(owner.vdom, me.proxyParentId).vdom.flag + 'T12:00:00.000Z');
  startDate.setHours(me.axisStartTime);
  startDate.setMinutes(me.currentInterval * me.intervalSize);
  ```
- `src/calendar/view/week/plugin/DragDrop.mjs:209,214-215` (`onColumnDragStart`, drag-to-create on an empty column) repeats the exact same `flag + 'T12:00:00.000Z'` + local `setHours` / `setMinutes` pattern.
- By contrast, `src/calendar/view/month/EventDragZone.mjs:149-152` parses `[year, month, day] = dayFlag.split('-').map(Number)` and applies `setFullYear(year, month - 1, day)` in local calendar coordinates without round-tripping through UTC noon.

Design authority: `src/calendar/view/week/Component.mjs:1044,1054` (`flag: DateUtil.convertToyyyymmdd(date)` — local `YYYY-MM-DD` column identity) and `src/calendar/view/month/EventDragZone.mjs:149-152` (local `[year, month, day]` drop target resolution).

## The Fix

Replace `new Date(...flag + 'T12:00:00.000Z')` in both:
1. `src/calendar/view/week/EventDragZone.mjs:230-232` (`dragEnd`), and
2. `src/calendar/view/week/plugin/DragDrop.mjs:209,214-215` (`onColumnDragStart`)

with local `[year, month, day] = columnFlag.split('-').map(Number)` construction — e.g. `new Date(year, month - 1, day, me.axisStartTime, me.currentInterval * me.intervalSize, 0, 0)` (and `new Date(year, month - 1, day, axisStartTime, minutes, 0, 0)` in `onColumnDragStart`) — so the local calendar date matches `columnFlag` across all IANA timezones from `UTC−12` through `UTC+14`.

## Out of Scope

- `src/form/field/Date.mjs` (`submitDateObject`), which intentionally uses noon UTC for date-only form values (`#19005`).
- Replacing `record.setSilent` in `EventDragZone#dragEnd` (tracked separately).

## Avoided Traps

- **Switching `'T12:00:00.000Z'` to `'T00:00:00.000Z'` or `new Date(flag)`:** ECMAScript parses bare `YYYY-MM-DD` as `00:00:00.000Z`, which breaks every western-hemisphere timezone (`UTC−1` through `UTC−12`) by shifting the local day `-1` day backward. Parsing `[year, month, day]` into the local multi-argument `new Date(year, month - 1, day, ...)` constructor is exact in every timezone.
- **Testing only in default CI `TZ=UTC`:** As documented in `#19005`, `UTC` cannot discriminate `T12:00:00.000Z` from local-date construction; the Playwright context must explicitly set `timezoneId: 'Pacific/Auckland'` (or `Pacific/Kiritimati`).

# Closing a Workstation popup leaves stale canvas bindings

## Reproduce with one main app and its own popup

In the v14 [Workstation](https://neomjs.com/dist/production/apps/workstation/index.html), focus **Live Event Stream**, use its **Pop out** tab action, and wait for the Feed sparklines to paint in the generated popup (`?popout=feed`). Close that window with the native window control. Repeat three times. In a fresh session, repeat with **Group Undo** as the way to return the same pane. The existing [Workstation sparkline test](https://github.com/neomjs/neo/blob/14.0.0/test/playwright/e2e/workstation/WorkstationPopOutSparklinesNL.spec.mjs#L74-L107) exercises this product path.

| Canvas SharedWorker measurement | Native close | Group Undo |
| --- | ---: | ---: |
| Keys in `map` before the first pop-out | 35 | 35 |
| Keys after each of three returns | 37, 39, 41 | 35 at the final return |
| Bindings to closed window IDs in `canvasWindowMap` after the third return | 11 | 0 |
| Canvas registrations still active in the primary window | 35 | 35 |

The original window had all five travelling Feed sparkline IDs back. Ten seconds later, after explicit GC in the Canvas SharedWorker, the native-close arm still had **six** old surfaces reachable through the latest `map[nodeId]` and **five** more as old window-specific bindings on IDs that now correctly point to live primary canvases. Those are 11 old `OffscreenCanvas` objects. Chrome listed only the original Workstation page. Both arms still reported the same number of port rows, so this comparison does not locate the cause in port retirement or establish how many native bytes were retained.

## Architecture and prior decisions

[Ideation Sandbox D#18730](https://github.com/neomjs/neo/discussions/18730) separates a main app and its participating popups from independent main roots. **Option C** shipped in [#19125](https://github.com/neomjs/neo/pull/19125): one Canvas SharedWorker per window group. A cooperating popup shares its opener’s Canvas worker; an independent fresh root gets its own. v14 admits a copied group ID with a live opener, or on reload, and otherwise mints a fresh one. [Carrier rule](https://github.com/neomjs/neo/blob/14.0.0/src/worker/CanvasGroups.mjs#L90-L110) · [Graduated scope](https://github.com/neomjs/neo/discussions/18730#discussioncomment-18564850).

The wider design is **optional isolation of the whole shared-worker set**. Option B covers the App, Data and VDom heaps as well as Canvas. OQ4 records the configuration question. v14 names only the Canvas worker per group; the wider boundary remains on the [roadmap](https://github.com/neomjs/neo/blob/14.0.0/ROADMAP.md#L59). The Workstation reproduction uses the intended shared-group arrangement and requires no change to how groups are formed.

## Acceptance criteria

- [ ] Repeat the product pop-out and native close with a canvas-bearing pane. Once it returns, every departed window’s surface is released from both canvas registries, including old owner entries for IDs still in use in the primary.
- [ ] Keep live registrations for those same node IDs intact. Verify the travelled sparklines still paint in the surviving pane, including after a subsequent pop-out/return. Preserve the existing Group Undo, component identity and history behavior.
- [ ] Add both native-close and Group Undo arms to the Workstation regression coverage. Verify per-window entries as well as total keys; the five old-owner bindings above are invisible to a count of the latest map alone.

Start with [canvas registration and cleanup](https://github.com/neomjs/neo/blob/14.0.0/src/worker/Canvas.mjs#L166-L233), [component unmount and destroy](https://github.com/neomjs/neo/blob/14.0.0/src/component/Canvas.mjs#L138-L184), and the native-return path. [#8118](https://github.com/neomjs/neo/issues/8118) records why a travelling canvas has window-specific ownership. Trace the first divergence from Undo before choosing a fix.

## Correction to the original Portal report

My earlier probe called `window.open(location.origin + '/', '_blank')` from Portal Home. That booted a **second complete Portal main viewport** while carrying the first root’s canvas group. The original header froze, and the worker retained registrations. That observation does not justify requiring two main Portal headers, heroes and footers to share their single-context renderers. I withdrew that acceptance criterion. The existing [group painting test](https://github.com/neomjs/neo/blob/14.0.0/test/playwright/e2e/core/CanvasGroupPainting.spec.mjs#L144-L195) uses independently keyed Sparkline witnesses. Separate no-opener roots and separate Chrome profiles kept painting in the controls. The original single-window Portal stall remains unexplained.

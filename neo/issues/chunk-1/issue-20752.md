# grid.View#syncBodies starts a flight when no row changed

## Context

Found while timing the VDOM pipeline for Discussion `#20751` (its table 3; the instrument is that Discussion's first comment and needs no source change). On `examples/grid/bigData`, a native scroll of `.neo-grid-view` by 50 px per frame for 120 frames (3,000 px/s) starts 121 flights. 86 of them return no delta. Each flight is the view at `updateDepth` 5 and ships 1,118 vdom nodes and 938 vnode nodes. Apple M5 Max, Chrome 157, real workers; a headed run gave the same 86 of 121.

- Live latest-open + closed sweep: checked latest 20 open (27 open, orange band; `#20750`..`#20676`; no open ticket or epic owns grid scroll cost) + closed searches (`grid scroll update every scroll event`, `syncBodies`, `grid scroll zero deltas flight`, `createViewData skip update unchanged rows`; `#17427`, `#17401` and `#20124` read with their Out of Scope and Avoided Traps) at 2026-11-11T03:15:30Z; no equivalent and no prior exclusion found.
- A2A in-flight claim sweep: the 37 newest messages across all read states (02:34Z to 03:15Z); no overlapping `[lane-claim]` or `[lane-intent]`.
- MC sweep: not run from this seat. A Fable seat reads no memory rows until the plane carries the fix of neomjs/neo-agent-brain#1580. The Knowledge Base ticket sweep (`grid scroll starts a vdom update on every scroll event although no row changed`, 12 hits, the three above among them) and the GitHub history stand in.
- Own-assignment sweep: 3 open in this repository (`#20498`, `#20682`, `#20726`), none on this surface.

## The Problem

A scroll that stays inside the row buffer changes nothing on screen, and every one of its scroll events still pays for a full flight:

| Per empty flight, median | ms |
| :--- | ---: |
| App worker (two tree copies, clone out, clone in, vnode adoption) | 2.8 to 3.3 |
| VDom worker (clone in, diff, clone out) | 2.5 to 2.7 |
| Main thread (unpacks and repacks the vnode tree, applies nothing) | 1.0 |

The 86 empty flights of that 2-second scroll cost the main thread 82.8 ms. At 24,000 px/s every flight carries rows (254 deltas at the median), so the waste is specific to slow and medium scrolling, which is how a grid is read.

Reproduce: run the instrument from D`#20751` with `-g "grid bigData"` and read `deltaHistogram` on the `PIPE grid-scroll` line.

## The Architectural Reality

Design authority: `"Row Skipping: If force is false and the record/rowIndex match, Row.updateContent skips VDOM generation."` (`Body#createViewData`, `src/grid/Body.mjs`) and `"The number of rows to paint before the first and after the last visible row, to enhance the scrolling performance"` (`bufferRowRange`). Skipping unchanged rows is the intended behavior; no record asks for a flight after a pass that skipped every row.

- `ScrollManager#onContainerScroll` calls `View#syncBodies(scrollTop)` on every scroll event (`src/grid/ScrollManager.mjs:194`, `src/grid/View.mjs:1534`).
- With fixed row heights `syncBodies` moves a body's `startIndex` only once the scroll crossed `bufferRowRange` rows; otherwise it rewrites `visibleRows`. Then each body runs `createViewData(true, force)`, where `Row#updateContent` returns early for a row whose record and index did not change (`src/grid/Row.mjs:817`).
- `syncBodies` then always sets `updateDepth = ROW_DISTANCE + maxCellDepth` and `denseUpdate = true` and calls `me.update()` (`src/grid/View.mjs:1598-1602`).
- That one flush is load-bearing: it is the only cycle that carries the silent row writes of the scroll path (`#17427`), the bodies' silent `isScrolling` class at scroll start and end (`#20124`), the scroll height, the aria row ownership, and the row-measure node of content-sized rows.
- A reply without deltas is forwarded to the App worker without a frame, and `DeltaUpdates#update` never runs for it (`worker.Manager#handleDomUpdate`). So no `update` listener on main, row pinning included, sees an empty flight today.

## The Fix

The outcome; the mechanism belongs to intake. `syncBodies` starts its flight only when the pass wrote something the flight would carry. Two candidate signals, neither tried: `createViewData` reports whether any row regenerated, was hidden, joined or left the pool; or the `needsVdomUpdate` flags that silent writes leave on rows and bodies.

## Decision Record impact

`none`. Discussion `#20751` weighs what a flight ships and who diffs it; this leaf holds under each of its options, because an empty flight costs the App worker its tree copies and its diff in all of them.

## Acceptance Criteria

- [ ] A scroll event that changes no row, cell, class, style or extent starts no VDOM flight. A unit spec moves `scrollTop` inside the buffer and counts `updateBatch` calls (`ScrollFlightMerge.spec.mjs` and the budget assertion in `Pooling.spec.mjs` are the precedents).
- [ ] A scroll that crosses the buffer still lands every changed row in one view flight, and the slot-remap reproduction of `#17427` stays green.
- [ ] The first event of a scroll still delivers `neo-is-scrolling` on every body, and the scroll end still removes it, each in one view flight.
- [ ] Content-sized rows, locked bodies (`bodyStart`, `bodyEnd`), the scroll edge and an open cell editor behave as before; their existing specs stay green.
- [ ] *(Browser)* The instrument on `examples/grid/bigData` at 50 px per frame reports no flight without deltas, or the PR names the remaining ones and why they must fly.

## Out of Scope

- What a scroll flight that does carry rows ships (D`#20751`, axis A).
- Throttling or debouncing the scroll handler.
- Horizontal scrolling, unless the same check covers it at no extra risk.

## Avoided Traps

- **Skipping on an unchanged `startIndex`:** content-sized rows re-render on every new start row, the scroll edge and the locked bodies have their own conditions, and the first event must still carry the `isScrolling` class.
- **Trusting "nothing is in flight" as "nothing changed":** `#17427` showed that a silent write the flush misses stays painted as a stale row, and that two runs at one sha can disagree. The signal has to come from the pass itself.
- **Comparing the trees in the App worker to find out:** that is the diff the flight would have run.

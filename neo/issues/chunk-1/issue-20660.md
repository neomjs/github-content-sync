# A `Date` record field turns `null` into 1970-01-01

## Context

`RecordFactory.parseRecordValue` converts every non-`Date` value of a `type: 'Date'` field with `new Date(value)` (`src/data/RecordFactory.mjs:469–470` at `a4e508d25e`, the 13.4.0 release commit). `new Date(null)` is the epoch, so a date that is absent comes back as a real-looking date. The sibling branches (`Float`, `Int`/`Integer`, `Html`, `String`) only run for truthy values, so they keep `null`.

I found this on 2026-11-08 while reading the field parser. I held it back until the 13.4 cut because the release gate said to file nothing new in Engine.

## The Problem

Measured at `a4e508d25e` with a plain node script on the engine's unit setup. The model is `{id: String, due: Date, age: Integer}`:

```
create due:null                      Date(1970-01-01T00:00:00.000Z)
control: create age:null (Integer)   null
create, due omitted                  undefined
control: create due:ISO string       Date(2026-11-09T10:00:00.000Z)
set({due:null}) after a date         Date(1970-01-01T00:00:00.000Z)
create due:undefined                 Date(1970-01-01T00:00:00.000Z)
create due:''                        Date(Invalid)
```

A record cannot hold "no date":
- Loading `{due: null}` stores 1970-01-01.
- Clearing a date with `record.set({due: null})` stores 1970-01-01.
- An explicit `undefined` does the same, because `parseRecordValue` defaults `value` to `null`.

The following is inferred from the code, not run:
- A `DateField` with the default `emptyValue: null` writes `null` when cleared (`src/form/field/Text.mjs:1184–1185`).
- So clearing a date cell in `examples/grid/cellEditing` stores 1970-01-01.
- Its renderer, `new Intl.DateTimeFormat('default').format(value)` (`examples/grid/cellEditing/MainContainer.mjs:142`, and the table twin at `examples/table/cellEditing/MainContainer.mjs:140`), shows `1/1/1970`.
- `Intl.DateTimeFormat#format(null)` also formats the epoch, so those two renderers need the empty case as well.

## The Architectural Reality

- `parseRecordValue` (`src/data/RecordFactory.mjs:420`) runs on every field write: `setRecordFields` (`:556`) for create and `set`, and the per-field setter (`:135`).
- `nullable` (`:462–467`) is the opt-out. `nullable: false` refuses `null` with a warning and keeps the old value. Without it, `null` is a legal value.
- `Store#getFilterValues` restates the conversion rule for raw items (`autoInitRecords: false`) at `src/data/Store.mjs:923`. A raw `Date`-field value that is not a `Date` refuses the count as `noncanonical-field`, because hydration would change it. That was right while hydration turned `null` into 1970. Once `null` stays `null`, a raw `null` is canonical and should count.
- Some consumers already read "no date" as `null`. The header value menus keep `null` as a distinct option (#19720). `examples/data/pipeline/MainContainer.mjs:47` renders `''` for a falsy value.

Design authority: `learn/guides/datahandling/Records.md:52`: "`nullable` (Boolean): If `false`, the field cannot be `null`." So a `Date` field without `nullable: false` may be `null`. Today it can't be.

## The Fix

1. `src/data/RecordFactory.mjs:469`: convert only a value that is not `null`: `if (type === 'date' && value != null && Neo.typeOf(value) !== 'Date')`. `null` stays `null`, and an explicit `undefined` becomes `null` through the existing parameter default.
2. `src/data/Store.mjs:923`: a raw `null` in a `Date` field is canonical: `type === 'date' && value !== null && !(value instanceof Date)`. A raw `undefined` still refuses, because hydration turns it into `null`.
3. The two cell-editing example renderers render `''` for an empty value, as the pipeline example already does: `({value}) => value ? new Intl.DateTimeFormat('default').format(value) : ''`.
4. `test/playwright/unit/data/RecordFactory.spec.mjs`: add rows for creating with `null`, `set({due: null})` after a date, and an explicit `undefined`. Add controls: an ISO string still becomes a `Date`, an omitted field stays `undefined`, and `nullable: false` still refuses `null`. `test/playwright/unit/data/StoreFilterValues.spec.mjs` gets the raw-`null` counting row.

## Acceptance Criteria

- [ ] A `Date` field created with `null`, or set to `null` after holding a date, reads `null`. An explicit `undefined` reads `null`.
- [ ] An ISO string still becomes a `Date`, an omitted field stays `undefined`, and a `nullable: false` `Date` field still refuses `null`.
- [ ] In a Store with `autoInitRecords: false`, a raw `null` in a `Date` field counts as its own value instead of refusing the count. A raw date string still refuses as `noncanonical-field`.
- [ ] Both cell-editing examples render an empty date cell as empty text.
- [ ] The `RecordFactory` and `StoreFilterValues` unit specs carry these rows, and the unit suite passes.

## Out of Scope

- `''` and unparsable strings, which become an `Invalid Date`. `Intl.DateTimeFormat#format` throws `RangeError` on that. Whether `''` means `null`, or whether a parse failure should be refused the way a `maxLength` violation is, is a design question. It gets a defect-note, not this fix.
- Date-only ISO strings parsing as UTC midnight. #19720 already formats that case.

## Avoided Traps

- A truthy guard (`&& value`) like the sibling branches. It would keep `0`, a valid epoch timestamp, as a number instead of a `Date`.

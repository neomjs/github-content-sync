# Calendar event drag uses setSilent and skips recordChange subscribers

## Context

Clio (`@neo-fable-clio`) found by reading `src/calendar/view/week/EventDragZone.mjs` (and its sibling `src/calendar/view/month/EventDragZone.mjs`) that event drops commit `endDate` and `startDate` via `record.setSilent(...)` plus a manual `doSort()` workaround citing closed issue `#2392`. Browser verification in Chromium `157.0.8103.39` against `dev` (`82458b0453b8a89f3a09974abf7f5c7ba9ae7f8a`) confirms that `recordChange` never fires on the events store (`recordChangeCount === 0`), leaving `recordChange` subscribers and `Neo.state.Provider` record bindings permanently stale after a drop while running `owner.updateEvents()` twice per drop.

## The Problem

When a user drags and drops an event in the week view (`src/calendar/view/week/EventDragZone.mjs:245-253,266`) or month view (`src/calendar/view/month/EventDragZone.mjs:157-164`), `dragEnd` mutates the record via `record.setSilent({endDate, startDate})`, calls `doSort()` directly on the events store, and then manually re-renders `owner`.

Empirical consequences verified in Chromium:
1. **`recordChange` subscribers receive `0` notifications (`recordChangeCount === 0`):** Any agenda/detail view, grid/list consumer, controller, or persistence hook listening to `eventsStore.on('recordChange', ...)` stays stuck on the pre-drag dates (`"2024-07-22 08:00 AM"` after the event moved to `"2024-07-23 09:45 AM"`).
2. **`StateProvider` record bindings stay permanently stale:** `Neo.state.Provider#onRecordDataChange` (`src/state/Provider.mjs:958-963`) ignores mutations with `silent === true`, so any component bound to a selected calendar `Record` in `StateProvider` never updates after a drag.
3. **Redundant double re-render on the dragged view + standalone crash risk:** Calling `doSort()` fires a coarse `load ({isSort: true})` (`src/data/Store.mjs:1441`), which already triggers `owner.onEventStoreLoad -> owner.updateEvents()`, and `EventDragZone#dragEnd` (`:266`) then calls `owner.updateEvents()` a second time (`primaryUpdateEventsCalls === 2`). In addition, `owner.getStateProvider().getStore('events')` at `week/EventDragZone.mjs:253` throws a `TypeError` if `Neo.calendar.view.week.Component` is configured with a direct `eventStore` and no `StateProvider`.

## The Architectural Reality

- `src/calendar/view/week/EventDragZone.mjs:245-253,266`: calls `record.setSilent({endDate, startDate})`, followed by `// todo: updating a record field which is included inside a sorter should trigger collection.doSort() / see: https://github.com/neomjs/neo/issues/2392`, `owner.getStateProvider().getStore('events').doSort()`, and `owner.updateEvents()`.
- `src/calendar/view/month/EventDragZone.mjs:157-164`: copies the same `record.setSilent({endDate, startDate})`, `eventStore?.doSort()`, and `owner.createContent()` sequence.
- `#2392` is long resolved: `Neo.data.Store#onRecordChange` (`src/data/Store.mjs:1644-1659`) automatically checks `this.shouldReapplySorters(data)`, runs `this.doSort()` when `startDate` is sorted, and then fires `recordChange` with the settled `index`.
- Both `Neo.calendar.view.week.Component` (`src/calendar/view/week/Component.mjs:430-431,743`) and `Neo.calendar.view.month.Component` (`src/calendar/view/month/Component.mjs:662`) already subscribe to `recordChange: me.onEventStoreRecordChange`, and `Neo.calendar.view.EditEventContainer` (`src/calendar/view/EditEventContainer.mjs:245,286,300`) already mutates `record` fields normally via `record.set`.

Design authority: `src/data/RecordFactory.mjs:323-328,341-346` (`set` vs `setSilent`: `"Bulk-update multiple record fields at once without triggering a change event"`), `src/state/Provider.mjs:958-963` (`#onRecordDataChange` ignoring `silent` writes), and `src/data/Store.mjs:1638-1659` (`onRecordChange` re-applying sorters before firing `recordChange`).

## The Fix

1. In `src/calendar/view/week/EventDragZone.mjs#dragEnd` (`:245-266`):
   - Replace `record.setSilent({endDate, startDate})`, the obsolete `#2392` `todo` comment, and `owner.getStateProvider().getStore('events').doSort()` with `record.set({endDate, startDate})`.
   - When `data?.cancelled` is truthy (or `record.set` caused no field change because the event was dropped back onto its exact starting slot, where proxy teardown still requires restoring the source DOM node), ensure `owner.updateEvents()` runs once; when `record.set` changed `startDate` or `endDate`, avoid calling `owner.updateEvents()` redundantly on top of `onEventStoreRecordChange` / `onEventStoreLoad`.
2. Apply the symmetric `record.set({endDate, startDate})` cleanup in `src/calendar/view/month/EventDragZone.mjs#dragEnd` (`:157-164`), ensuring a cancelled drag or zero-delta drop still restores `owner.createContent()` once without double-rendering on moved drops.

- [ ] AC-1: Completing an event drag in the week view and in the month view commits via `record.set({endDate, startDate})`, firing `recordChange` on `eventStore` with the changed fields and updating both `recordChange` listeners and `Neo.state.Provider` record bindings (`test/playwright/e2e/rendering/CalendarMonthEventDrag.spec.mjs` or a dedicated calendar drag spec via `npm run test-e2e -- <spec>`).

- [ ] AC-4: The obsolete `#2392` `todo` comment in `src/calendar/view/week/EventDragZone.mjs` is removed, and `npm run test-unit -- test/playwright/unit/calendar` stays green.

## Out of Scope

- Timezone date math in `week/EventDragZone.mjs:230` and `week/plugin/DragDrop.mjs:209` (tracked separately).
- Coalescing `Store#doSort` `load ({isSort: true})` with `Store#onRecordChange` `recordChange` inside `Neo.data.Store` itself (`src/data/Store.mjs:1648-1659`).

## Avoided Traps

- **Dropping `owner.updateEvents()` / `owner.createContent()` unconditionally when `startDate` and `endDate` did not change:** If a user drags an event slightly and drops it back into the same 15-minute slot (or presses `Escape`), `record.set({endDate, startDate})` is a no-op and fires neither `load` nor `recordChange`; that path still needs `owner.updateEvents()` / `owner.createContent()` to restore VDOM/DOM after proxy teardown.
- **Note on `Store#onRecordChange` (`src/data/Store.mjs:1650,1656`):** When `startDate` changes on a store sorted by `startDate`, `Store#onRecordChange` runs `this.doSort()` (firing `load` with `{isSort: true}`) and then fires `recordChange`. Check `WeekComponent#onEventStoreLoad` (`data?.isSort`) if avoiding a double `updateEvents()` on sorted `record.set` is desired.

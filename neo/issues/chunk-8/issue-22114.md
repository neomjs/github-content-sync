# Workstation tear-outs intermittently miss the boundary exit in hosted E2E

## Context

On 2026-11-23 the operator asked that the v14 release carry no flaky tests, and multi-window is its lead feature. In hosted Engine E2E, Workstation tear-outs driven by `apps/workstation/tour/NativeGestureDriver.mjs` intermittently fail before the vessel exists. ## The Problem

Observed: the driver arms the tear-out (`armed:true`) and moves the pointer past the window boundary. The dashboard sort zone never enters window dragging (`exitFired` reads `sortZone.isWindowDragging`), the pre-birth boundary probe records zero entries, and no vessel opens. This differs from the repeat-exit browser-permission refusal (#22112): there, `window.open` actually ran.

Inference, unverified: a race between arming and the first out-of-bounds move under hosted-runner load. Unknown: whether the product or the driver loses it, and whether it reproduces locally.

## The Architectural Reality

- `apps/workstation/tour/NativeGestureDriver.mjs` (L1011–1063) builds the diagnostic; `examples/dashboard/crossWindow/DemoBTearOutGesture.mjs:173` carries the same message for Demo B.
- `test/playwright/e2e/dashboard/TearOutMatrixRows4To7NL.spec.mjs:727` asserts that message on purpose as a red control, so the message is not the defect.

## The Fix

1. Discriminate first: run the row-1 and row-4 specs locally under CPU throttling (CDP `Emulation.setCPUThrottlingRate`, 4–6×) at `f8635546e0`. A red there localizes a race; then compare the driver's arming order with the zone's boundary listener.
2. Fix it in the layer that loses the race (driver or engine), which every spec shares. No spec-local sleeps, retries or quarantine.

## Acceptance Criteria

- [ ] A reproducing control: one of the specs red under throttling before the fix, green after.
- [ ] The fix sits in the shared driver or engine path; the specs gain no retries or waits.
- [ ] Post-merge: five consecutive full `dev` Engine runs without an `exitFired=false` failure, recorded here.

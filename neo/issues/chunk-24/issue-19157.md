# Release notes need an authored path outside resources/content before the tree is deleted

## Context

D#19051 graduated `RESOLVED` on 2026-09-24 and orders the retirement of the engine's `resources/content` as leaves under #17416. This is its item 4 (R1). The operator decided on 2026-09-23 to delete `resources/content` fully. The release notes (`resources/content/release-notes/v*.md`, 169 files) are the one authored family in that tree besides the concepts (#19093), and the published corpus (`github-content-sync`) does not carry them.

## The Problem

Every writer and reader of the notes hard-codes the path under `resources/content` (all verified on `dev`, 2026-09-24):

- `buildScripts/release/publish.mjs:124–126` refuses a release unless `resources/content/release-notes/v<version>.md` exists.
- neomjs/neo-agent-brain `ai/scripts/lifecycle/postReleasePreflight.mjs:160` admits only that path's deletion as the post-release starting state.
- neomjs/neo-agent-brain `ai/services/knowledge-base/QueryService.mjs:844` types `resources/content/release-notes/` (and `.github/RELEASE_NOTES/`) as `release`.
- neomjs/pages step 4.1 (pages#9, pages#10) reads the notes from `resources/content/release-notes` at the engine's release tag.
- `buildScripts/docs/index/release.mjs` builds the portal's `releases.json` from the same folder.

If the tree is deleted before these move, the next release stops at `publish.mjs`, and the pages deploy stops at its fail-loud step (D#19051, comment 18580522).

## The Fix

Give the notes one authored engine path outside `resources/content/` and move the files with their history. Choosing the path is this leaf's first decision; one option is `.github/RELEASE_NOTES/`, which the KB already types as `release`. Move every reader in one ordered window: the materializer (`publish.mjs`) comes before any KB upload, and the Brain's `postReleasePreflight` moves in the same leaf. Delivery is a `neo` PR (Resolves) with companion Brain and pages PRs (Refs), merged together.

## Acceptance Criteria

- [ ] **AC-1** The notes live at one authored path outside `resources/content/`, and `git log --follow` keeps their history.
- [ ] **AC-2** `publish.mjs`, the release index builder, the Brain's `postReleasePreflight`, the KB source typing and pages' step 4.1 all read the new path. None reads `resources/content/release-notes`.
- [ ] **AC-3** A `publish.mjs` dry run for the next version and a pages build at the release tag both pass against the new path.

## Out of Scope

- The conversation families, which are already in the corpus.
- The concepts (#19093).
- The deletion itself: its own leaf, blocked by this one.

## First decision: the path is `release-notes/` at the repository root, keeping the `chunk-N/` layout

**Why not `.github/RELEASE_NOTES/`,** although the KB already types it and `ReleaseNotesSource` already reads it:
- The notes lived there until #8451 (2026-01-09). They moved *because GitHub Pages filters `.github/` out*, and the portal fetches note bodies directly by the `path` in `releases.json` (`apps/portal/model/Release.mjs:25`).
- Going back would need a deploy-time copy into a served location for pages, and a second one for the engine's own dev portal.

**Why the root:**
- It sits outside the cache, so ADR 0004 §1.3 holds.
- GitHub Pages serves it as-is, and the portal reads the same path in dev and on the deployed site.
- `.npmignore` keeps it out of the tarball, as it does `resources/content` today; pages takes it from the engine tag, as pages#10 already does.

**A side effect in our favour:** the KB's `ReleaseNotesSource` points at `.github/RELEASE_NOTES`, which has been empty in both repos since #8451. Today the KB holds zero release notes, and repointing that source at `release-notes/` fixes it.

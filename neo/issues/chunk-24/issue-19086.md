# WorkstationNL dense control: the dark splitter fails the :active read on press

## Context

`test/playwright/e2e/workstation/WorkstationNL.spec.mjs` — "the real tour keeps density, data, Canvas output, themes, rails, and identities live" — reds deterministically at `:1294`: `expect(darkDockActive.horizontal.active, 'the real dark-mode splitter owns the active pointer target').toBe(true)` receives `false`. Three sightings, one run each, all 8/9 with this sole red: PR #19083's head `4cae0c08bc` (01:27Z), clean `dev@a186e92cfa` (01:29Z), and the review-response head of the same PR (02:51Z). Found while running the film tour's dense-tour control (#19070 AC-4); the film PR touches neither this spec, the dense screenplay, the splitter nor the theme.

## The Problem

The light-mode arm at `:1164` reads the same probe — `readDockChrome` (`:364`) returns `element.matches(':active')` for `.neo-dashboard-dock-split-horizontal > .neo-dashboard-dock-splitter-horizontal` — after the same `mouse.move` + `mouse.down`, and passes. The dark arm at `:1294`, later in the same test, fails. The engine's active paint contract (`resources/scss/src/dashboard/Container.scss:456`: `&:active` background, ring and handle tokens) is therefore not the difference; something about the second press is. Until it is classified, every Workstation whitebox run carries one red, and #19070's AC-4 can only be stated as baseline parity.

## The Architectural Reality

- The probe reads the UA pseudo-class, not an engine class: `:active` holds only while the pressed pointer's target chain includes the splitter. The press at `:1286–1290` aims at `dragSplitterBox`, measured at `:1260` after the dark toggle at `:1172`; the same test installs a `MutationObserver` on the root's class list just before the press (`:1273–1283`).
- `DockSplitter#onDragStart` (`src/dashboard/dock/interaction/DockSplitter.mjs:534`) projects the splitter's paint onto a drag proxy that mounts outside the splitter, and the main-thread `DragDrop` addon owns the mousedown → release bracket. If the proxy or a preview surface takes the pointer target on the second press, `:active` leaves the splitter while its background may still differ from hover — the assertion order would report exactly this red.
- #17889 (drag sensors → Pointer Events with pointer capture) changes that bracket; a fix here must not pre-empt it.

## The Fix

Classify first, with one instrumented run: at the press, read `document.elementFromPoint(x, y)`, the splitter's live `boundingBox()` against `dragSplitterBox`, and whether a `.neo-draggable` proxy exists — three facts that separate (a) a stale box, (b) a proxy or overlay taking the target, (c) an engine `:active` gap in dark mode. Then either fix the engine (c), or make the dark arm assert the engine's own active feedback — the `--dock-splitter-*-active` tokens on the element the engine actually paints — rather than the UA pseudo-class (a, b). The light arm keeps its read until the classification says otherwise.

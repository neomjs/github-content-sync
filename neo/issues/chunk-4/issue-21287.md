# A one-run duration table and thin headroom stop engine e2e shards

## Context

`#21259`'s post-merge AC missed ([comment](https://github.com/neomjs/neo/issues/21259#issuecomment-6961446846)): after `#21260` rebuilt `buildScripts/util/e2eEngineDurations.json`, run `44103700718`'s `e2e-engine (13/14)` still stopped at the 5-minute step ceiling with 69 of 70 tests passed. That comment left one question open: do the slow shards run long on the same files every time (a better table fixes it), or on runner noise (only headroom does)? This ticket measures it. The answer is both, and the table error sits in one spec.

**Measured**: pull-request runs of `test-e2e.yml` created after 2026-11-17T14:04Z, read at 21:55Z. Of 35 runs, 27 ran engine shards and 20 ran the full 14-shard matrix.

| Observation | Value |
|---|---|
| Mean shard step per run | 224 s (sd 6 across runs): the total load is stable |
| Slowest shard per run | mean 274 s, max 313 s |
| `e2e-engine (13/14)`, one fixed 17-file set, 8 runs | 191–312 s |
| … `portal/ExamplesCatalogNL.spec.mjs` inside it | 28.3–82.2 s (mean 57.5, sd 23.0); every other file sd ≤ 4.5 s; **table: 36.5 s** |
| `e2e-engine (7/14)`, one fixed 17-file set, 8 runs | 200–264 s, no file with sd above 5.4 s |
| All 17 steps at 265 s or more | 7 held ExamplesCatalogNL (71.5–82.2 s each), including all four at 282 s or more outside red-head run `44129891822`; the 8 without it on green heads reached 268–281 s |

**Instrument**:
- Step durations come from `GET /repos/neomjs/neo/actions/runs/<id>/jobs` (step `Run e2e (engine tier)`).
- A file's time is the sum of the list reporter's printed durations for that file in `GET /repos/neomjs/neo/actions/jobs/<id>/logs`. Printed durations exclude hooks, which the table's timestamp method includes, so these figures understate rather than overstate the table's measure.
- A shard's file set is its log's `selection:` line, compared by hash. Shards 3, 7 and 13 each saw five distinct sets in the window, so every cross-run comparison above holds one set fixed.

## The Problem

Two independent sources push a shard past the ceiling.

1. **A one-run table under-budgets a variable spec.** ExamplesCatalogNL runs 28–82 s on identical inputs, and the table recorded one fast run (36.5 s). The shard that receives it is planned about 40 s light on a slow runner, and it was in all four steps of 282 s or more outside the one red-head run.
2. **Runner speed varies per job.** Shard 7's fixed set, with no variable file, spans 64 s across runs. Green-head shards without the variable spec reached 281 s against a plan of about 210 s, a margin of 19 s.

A fresher table fixes neither. An average records ExamplesCatalogNL near 57.5 s, not the 72–82 s it cost in every slow step, and no table predicts a runner's speed.

## The Architectural Reality

Design authority: "A shard nearing it gets a sibling, never a higher ceiling: the ceiling is the wait every pull request pays." (`.github/workflows/test-e2e.yml` header, *Time*)

- `buildScripts/util/e2eCiSelection.mjs` sizes the full matrix with `FULL_SHARDS = {engine: 14}` (`:206`). A selection's count is `Math.ceil(FULL_SHARDS.engine * seconds(paths) / whole)` (`:562`), and `balancedShard` (`:420`) places files longest-first by `ENGINE_DURATIONS`.
- `engineDurations(text)` (`:445`) adds a file's cost over every line it receives, tracking each test's start by job name. Job names repeat in every run, so logs from several runs sum into one inflated figure. Today's table can come from one run only.
- `.github/workflows/test-e2e.yml:97–98` repeats `14` as the fallback matrix.

## The Fix

1. **Multi-run table:** `engineDurations` keeps each run's per-file totals apart and records each file's maximum across runs. `--engine-durations` accepts several runs' logs. Rebuild `e2eEngineDurations.json` from at least 5 full-matrix runs.
2. **One sibling:** raise `FULL_SHARDS.engine` from 14 to 15, and change the workflow's fallback lists at `:97–98` to match.

| Target surface | Source of authority | Proposed behavior | Fallback | Docs | Evidence |
|---|---|---|---|---|---|
| `e2eCiSelection.mjs --engine-durations` | `engineDurations` JSDoc (`:436`) | several runs' logs in, each file's maximum per-run cost out | one run's log yields today's table | `engineDurations` + `ENGINE_DURATIONS` JSDoc | unit spec below |

## Acceptance Criteria

- [ ] Given two runs' logs, `engineDurations` returns each file's larger per-run cost, not their sum (`test/playwright/unit/buildScripts/util/E2eCiSelection.spec.mjs`, red on `dev`).
- [ ] The committed table is built from at least 5 full-matrix runs, the PR names their run ids, and `portal/ExamplesCatalogNL.spec.mjs` reads at least 70 s in it.
- [ ] `FULL_SHARDS.engine` is 15, and the workflow's fallback matrix lists 15 shards.
- [ ] *Post-merge:* over the first 20 pull-request runs with engine shards after the merge, no engine shard step stops at the ceiling with its tests passing, and the slowest green-head step is at most 285 s.

## Out of Scope

- Why ExamplesCatalogNL varies threefold on identical inputs. A deterministic spec would lower its maximum but not the runner noise; it gets its own defect-note.
- A table that refreshes itself on a schedule.
- Raising the 5-minute ceiling, which the design authority rules out.

## Avoided Traps

- **A mean over runs:** it still budgets the variable spec about 20 s below its cost on the runs that overrun.
- **A fifteenth shard alone:** it keeps the 36.5 s under-budget, so the ExamplesCatalogNL shard still runs about 40 s over its plan on a slow runner.
- **Prior rulings, re-checked:** `#20521` rejected another shard while shards split by test count, and `#21259` rejected a fifteenth shard before a fresh table. Since then the split has become time-balanced, the fresh table has landed, and its AC missed. The sibling now answers runner noise, which no split can absorb.

# A web desktop shell joins the engine as src/desktop

Terminal predicate: a developer builds a web desktop (a launcher, a taskbar with a start menu and the open windows, app windows that open, minimize, restore and close) from `src/desktop/`, and `apps/webdesktop` is that family's first consumer, keeping only its demo's accounts, sign-in, permission panel and data.

## Context

#21061 built the web desktop demo from engine primitives and deferred this step in its Out of Scope: *"A window manager in `src/`: the demo composes existing primitives; promoting any part into the engine is a later decision."* On 2026-11-16 the operator asked for that decision: the desktop's parts should be reusable by others who build web desktops.

The engine gaps the demo hit already went into `src/`: menus that honor a tree-store filter (#21062, #21070), `TreeStore#isKept()` (#21068) and a `plugin.Resizable` boundary fix (#21073). The shell itself did not. On `dev` it is about 760 of the app's 1,700 lines: `Launcher` 190, `AppWindow` 128, `Desktop` 70, `TaskList` 58, `Taskbar` 56, the task model and store 61, and the window-manager half of the 384-line `ViewportController`.

## The Problem

Anyone who wants a web desktop on Neo today copies the demo's views and a controller that interleaves window management with the demo's sign-in and permission code. A copy receives no engine fix: the sign-out race that #21100 fixed lives only in the demo's controller. The work needs an Epic because the shell is several pieces with one shared API (the window manager, the launcher and its store, the shell container with its taskbar and window, its themes, and a guide), each one pull request, with the demo migrating piece by piece.

## Intended solution shape

A new family, `Neo.desktop.*`, composed from existing primitives: `dialog.Base` for windows, `list.Base` with `draggable.list.SortZone` for the launcher and the task list, `toolbar.Base` with a `menu.List` over a `TreeStore` for the taskbar and start menu, and `state.Provider` between a window and its desktop.

- **Window manager** (`core.Base`, owned by the desktop container): one window per app id, created on first open through a configurable window class and kept. It keeps open, restore, minimize and close in step with a tasks store, and closes the windows whose app the apps store's filter drops (`TreeStore#isKept()`). `reset()` cancels in-flight opens and hides every window (the demo's sign-out). It destroys what it created. Composition, not a base controller: consumers keep their own controllers.
- **Order belongs to the manager.** `dialog.Base` has one fixed `z-index` and no order among dialogs; the demo keeps its order as module state in `AppWindow.mjs`, which would be shared by every desktop on one App worker. Each manager keeps its own stack and sets the `z-index` of the windows it created, so any `dialog.Base` works as the window class.
- **Apps tree:** a `TreeModel` and `TreeStore` with generic fields, sorted by `order`, with the arrangement API the demo's store has (`arrange()`, `getArrangement()`). A consumer subclasses for its own fields; the demo adds `permission`.
- **Launcher:** icon grid; drag and keyboard reordering inside a group; opens on double-click and Enter, on a tap on touch devices; arrangement persistence behind one key, with `localStorage` as the default.
- **Taskbar, task list and task model:** the start button with its `menu.List` over the apps store, and the open windows.
- **App window:** a `dialog.Base` that grows out of its launcher icon, with minimize, maximize and close. Its public input is a `record` config; any state provider stays internal to it.
- **Desktop container:** workspace, launcher and taskbar; owns the window manager.
- **A second consumer:** `examples/desktop/basic` (three apps, no sign-in) ships with the container. It tests the seam, and the guide's blocks come from it.
- **Stays in the demo:** accounts, sign-in, the permission panel, the data, and the role-based filter. That filter is a recipe (one `included` filter with `includeEmptyValues: false`, written by the state provider), documented in the guide rather than built into the shell.
- **Naming:** inside `src/desktop`, a window is an app window addressed by `appId`. `windowId` keeps its engine meaning, a browser window. The `@summary` of the window manager and of the app window says so and points at `Neo.manager.Window`.
- **Theming:** `resources/scss/src/desktop/` with the neo-dark and neo-light variables the demo has, moved by each refactoring leaf. The cyberpunk, dark and light themes are new looks and get a leaf of their own.
- **Docs:** a guide, and a Structural Inventory row for `src/desktop/` in the Architecture Overview, in the first pull request that creates the folder.

Placement (structural pre-flight, full): considered `src/dashboard/`, `src/dialog/` and a new `src/desktop/`; read the Architecture Overview's Runtime Engine inventory. `dashboard` is DockLayouts under ADR 0029: docked panels, not free-floating app windows. `dialog` is the window primitive the shell composes. Chose `src/desktop/` because the shell's role matches no existing family. Map maintenance: needed (new inventory row). Scalability: the family has room for model, store and view classes. ADR conflict: none, since 0029 governs docking and this stays out of it. ADR genesis: not now; revisit with the tear-out of D#21204. Future-self risk: low, because the window-class seam keeps another embodiment possible.

**Timing:** the leaves land on `dev` after the Engine 14 cut. ROADMAP.md fixes that cut for Monday 2026-11-23, with its four new families on `dev` by Thursday 2026-11-19. A public namespace from a single consumer does not belong in its last week. The next cut is planned two weeks later. At that cut's re-read of the engine line, this epic becomes a row with its gate sentence, or stays beside the gate by a sentence there.

## Out of Scope

- Tearing an app window out into its own browser window: explored in D#21204, and follow-on leaves of this epic once it graduates. The window-class seam keeps it possible.
- Order among all floating dialogs of the engine: the manager orders only the windows it created.
- Authentication or authorization. Hiding UI is not authorization.
- Docking, which is `src/dashboard`.
- More than one window per app.

## Avoided Traps

- **Moving the demo wholesale:** accounts and permissions in `src/` would bake one authorization model into the engine.
- **A base controller that consumers extend:** it forces one controller hierarchy. The container owns a window manager instead.
- **A `permission` field or filter in the generic app model:** the filter belongs to the consumer.
- **Module state for an order an instance owns:** two desktops, or two browser windows of one app on a shared App worker, would share one stack.
- **"Window" without its meaning:** `windowId` names a browser window across `src/`; an app window without that rule makes a knowledge-base query for "window manager" return two unrelated classes.
- **A test fixture as the proof of reuse:** a shipped example is the second consumer.
- **A provider's data key as an unlisted public input:** the window takes a `record`.
- **Landing before the 14 cut:** it adds public API in the cut's last week.

### Stage 2 — Approach Elegance

✅ for the three things you asked about, ⚠️ for one the body does not name.

- **Composition over a base controller: yes.** A helper instance that a container creates from a config and destroys is the engine's own idiom (a grid's `selectionModel`, a timeline column's `timeAxis`). With `windowConfig(record)` the manager stays ignorant of the views, which is what keeps it replaceable.
- **The seam: yes.** `TreeStore#isKept()` lets the shell react to "the store no longer keeps this app" and never to "this account may not". The permission stays a recipe.
- **⚠️ Stacking is the one engine gap hidden in the demo, and the plan moves it as module state.** #21199 says a window is a `dialog.Base` with `toFront()`. `toFront` exists nowhere in `src/` (`git grep toFront origin/dev -- src`: no hit). `dialog.Base` has one fixed `z-index: 1000` (`resources/scss/src/dialog/Base.scss:8`) and no order among dialogs. The order lives in the demo's `AppWindow.mjs`, lines 9 to 30 and 116 to 128: a module-level `stack`, `baseZIndex = 10`, `restack()`, and `toFront()` bound to `mousedown`, with the comment "the demo opens one window per app, which keeps the stack far below 100". The plan as written:
  - leaf 1's manager calls `toFront()` on a "configurable window class" that `dialog.Base` cannot satisfy;
  - leaf 3 moves the module-level stack into `src/` "as the demo behaves today", where two desktop containers, or two browser windows of one app on a shared App worker, share one array.

  The choice I would make inside this epic: **the manager owns the order**. One stack per manager, it sets the z-index of the windows it created, and any `dialog.Base` then works as a window class. Order among all floating dialogs of the engine is a real question too, and larger; it belongs in Out of Scope by name.

### Stage 4 — Prescription Layer

⚠️ on two leaves.

- **#21199:** correct the `toFront()` line, and give the window class a ledger row: what the manager calls on a window (`show`, `hide`, `hidden`, and `toFront` or nothing, depending on the stacking choice).
- **#21201:** today the opener hands the window a state provider with `data.app`, parented to the desktop's provider (`ViewportController.mjs:80`; `AppWindow` binds `title: data => data.app.text`). In `src/` that data key is public API between the manager, the container and the window, and no ledger names it. A `record` config on the window as the public input, with any provider internal to it, would be the simpler contract. If the provider stays the input, its keys need ledger rows.

### Stage 5 — Avoided Traps Completeness

⚠️ Four to add:

- **"Window" already has a meaning here.** `windowId` occurs 1,566 times in 161 files of `src/` and names a browser window; `Neo.manager.Window` is the multi-window workspace's manager. The demo's `AppWindow` receives a `windowId` that is not its own. No rename is needed, but one rule and two sentences are: inside `src/desktop` a window is an app window addressed by `appId`, `windowId` keeps its engine meaning, and the `@summary` of `WindowManager` and `AppWindow` says so and points at `Neo.manager.Window`. Otherwise a knowledge-base query for "window manager" returns two unrelated classes with nothing to tell them apart.
- **Module state for an order that an instance owns** (Stage 2).
- **A fixture as the proof of reuse** (Stage 3).
- **A provider's data key as an unlisted public input** (Stage 4).

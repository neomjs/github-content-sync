# Grid anchor correction loses the anchor row for one frame, mid-list

## Context

`test/playwright/e2e/grid/AnchorCorrection.spec.mjs`, "rows that shrink above the view keep the row at its top edge still, mid-list", failed twice today on hosted CI, at unrelated heads, with the same sample:

```
Error: row 146 in every frame
expect(received).toEqual(expected)
  Array [
    0,
+   null,
  ]
```

- PR #20457 head `e2e5061f72`, run 42224252523, job e2e-engine (1/4). It passed on an unchanged-head re-run.
- PR #20440 head `c137fd8114`, run 42223069224, job e2e-engine (1/4), reported by Euclid.

Neither diff reaches the grid (a data-layer Store/Model change, a Clock size fix). The defect-note was captured first; this is its promotion on an independent second occurrence.

## The Problem

The arm guards the content-sized rows promise that a height correction above the view keeps the row at the view's top edge still in every animation frame. The received set `[0, null]` means the row never moved: every frame that saw it saw it at its starting position. In at least one frame, though, no rendered row carried record 146 at all.

So this is not an off-by-a-pixel jitter. For one frame the anchor row was absent from the rendered rows. Two readings stay open:
- **Product:** for one painted frame the body showed no row for the record at its top edge (a pooled row between two records, or a row range that left it out). That is a visible blink.
- **Instrument:** the tracker read the DOM between two delta applications that never reach the screen separately.

## The Architectural Reality

- The tracker (`defineGridState()` in the spec) reads `window.gridState()` in a `requestAnimationFrame` loop. It pushes `null` when no visible `.neo-grid-row` with a `data-record-id` has `[data-field="id"]` text equal to the anchor id. A pooled row whose id cell briefly shows another record is therefore indistinguishable from an unrendered one.
- #19692 (closed) is the closest precedent: "a recycled row can take its previous record's measured height". Its Avoided Traps record that the DOM can lag the vdom for a pooled row ("the vdom already names the new record, so it cannot see a lagging DOM").
- Shipped in #19664 / PR #19674 and #19697 / PR #19699 (both mine).

Design authority: the arm's own contract, "rows that shrink above the view keep the row at its top edge still", the outcome #19664 shipped.

## The Fix

1. **Discriminate first.** When the tracker records `null`, it also records which record ids the rendered rows showed in that frame and whether any pooled row was mid-reassignment. That separates a range gap, a pooled-row identity lag and an instrument tear.
2. **Then fix the side the receipt names.** For the product, keep the anchor's row rendered across the correction's flights. For the instrument, read only frames the grid has finished applying. No tolerance for `null`.

## Acceptance Criteria

- [ ] A receipt names which reading produced the `null` frame (rendered ids at that frame), from a local repeat or a CI capture.
- [ ] The root cause is fixed at the side the receipt names, without accepting `null` frames in the assertion.
- [ ] The arm passes `--repeat-each=30` locally on the fixed head, and the same command reproduces the `null` at least once on the unfixed head, or the PR says it could not reproduce locally and relies on the receipt.
- [ ] The other AnchorCorrection arms stay green.

## Out of Scope

- The keyboard-navigation edge (#19697) and the hidden pre-render (#19663).
- Retuning `settle()`. The `null` is recorded during the correction, not after it.

## Avoided Traps

- Do not filter `null` out of the tracked set. That hides exactly the frame this arm exists to catch.
- Do not retry the arm in CI. A blink that shows once in N runs is still a blink.

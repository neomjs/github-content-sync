# Engine CI runs each tier only when a change can reach it

Terminal predicate: an Engine PR push holds only the runner slots its diff needs, and no Engine CI job checks out the Brain. Each test tier runs only when the diff can reach it, and the fixed checks run as a handful of jobs, not dozens. Neural Link specs drive the page's own App Worker off-socket (#20370). The bridge and the tool definitions are the Brain's to test, and no CI runs the full Engine-plus-Brain cycle. The `dev` push runs in full every tier its diff reaches. Jobs and runner-minutes per push both sit measurably below this body's baseline.

## Problem scope

The neomjs organization runs on 20 concurrent job slots, and every repository's PRs share them. The operator, 2026-11-05:
- "otherwise we waste our 20 runners cap and delay team progress waiting on 'on hold' pipelines."
- "we are limited to 20 runner slots, which makes smarter ci scoping crucial … it is intense with 20+ open PRs."
- "ORG wide PRs as the limitation."

Engine CI spends that cap as if every change could break everything, and it starts a job for every check.

**Baseline.** I evaluated the committed `classify-test-scope.yml` script against the file lists of the 346 PRs merged into `dev` from 2026-10-13 to 2026-11-05, with the same harness `WorkflowScopeClassifier.spec.mjs` uses. It admits the full engine e2e tier (4 shards) and the full Brain-gated tier (10 shards) for 279 of them. At the shard times measured on #20321 (engine 3.7 min, Brain 3.9 min), that comes to about 16,200 runner-minutes: 66 % Brain-gated tier, 25 % engine tier, 7 % unit.

**The wait.** #20321 changed one blog post and its `blog.json` registration. Each of its ten Brain shards queued 7 to 20 minutes before starting, then ran about 4 minutes. Provisioning is only about 45 seconds of that, so the queue comes from the number of jobs, not from setup.

**The job count (2026-11-05, 15:19Z).**
- Open PRs: Engine 15, Brain 2, Institution 1, Skills 2.
- An Engine head starts 43–78 jobs. A Brain PR starts 34, and a Skills PR 6.
- Every Engine push also starts about 25 short jobs whatever it changed:
  - the shared PR baseline's ten jobs;
  - three `Classify test scope` jobs;
  - the lint and helper workflows.
- In the replay corpus, PRs average 15 test jobs that do work and 2.6 that start a runner only to report a skip.

Every job holds a slot from boot to finish, so short jobs cost slots out of proportion to their seconds.

**Three causes:**
1. **Misclassification.** Paths that no tier can reach still admit tiers: portal content data (6 PRs), `buildScripts/` directories outside the e2e launch chain (8), and `neo-agent-skills` version bumps (12). A change outside the E2E boundary still runs a one-shard Brain smoke (67 PRs), which tests the Brain's `dev` tip, not the change.
2. **Breadth.** A change inside the boundary runs every spec of both tiers. Of the 278 PRs inside it, 97 touch only leaf `src/` families (grid 57, dashboard 43, form 13), 19 touch only e2e specs or fixtures, and 29 touch only apps or examples.
3. **Job count.** Fixed checks run as separate jobs, and skipped tiers start runners just to say so. The shared baseline does this in every repository.

**Why an epic:** the three causes need different evidence and different authority:
- The first is a classifier correction that loses no coverage.
- The second changes which specs gate a PR before merge. #19655 (D#19599) set that to the full tier for any change inside the boundary, so it needs a dry run and its steward's signal first.
- The third changes required contexts, and those are the operator's rulesets, in every repository.

## Intended solution shape

- **One owner of scope.** `classify-test-scope.yml` keeps deciding every tier. No workflow grows its own `paths` filter, because a skipped required context strands a PR (`neomjs/neo-agent-brain#972`).
- **Fail toward running.** Every narrowing is a deny-list of paths or packages proven unreachable, so a new directory or dependency still runs every tier.
- **Report, never vanish, never spend a runner on it.** GitHub reports a job skipped by `if:` as Success, and that satisfies a required context. A workflow-level path skip leaves the context pending instead (GitHub's "Using conditions to control job execution"). So a skipped tier skips at job level, and its reason goes in the classifier's summary.
  - Required contexts become one per tier rather than one per shard, so none goes missing.
  - Contexts are the operator's rulesets, so each change ships with its ruleset edit.
- **One job per family of short checks.** A family of short checks becomes one job, with one step per check and every failure named, so it holds one slot.
- **The `dev` push is the safety net.** Every tier follows the push's own diff, which for a merge is the merged PR's, and runs its full population whenever that diff reaches it. So a PR-side selection miss (#20330) turns red on the next push, attributed to its merge commit. Until the Brain-gated tier retires (#20370), the classifier also forces it to `full` on a push. (Amended 2026-11-06 on operator direction: no CI runs the full Engine-plus-Brain cycle. Corrected 2026-11-05 after the #20332 review: an earlier version claimed "every tier in full".)

## Out of scope

- CodeQL and `build-all`: the `dev` ruleset requires both, and both are short.
- The Brain tier's reliability: 48 of 243 completed `dev`-push runs in the window were red (#17844, #19919).
- Other repositories' runners, and the PR Baseline queue stall of 2026-11-05.
- Required-context binding for the lint workflows (#17171).

## Avoided traps

- **Workflow-level `paths-ignore`:** strands required contexts.
- **Allow-lists of relevant paths:** they go stale silently. The comment on the classifier's E2E predicate records that history.
- **Fewer, longer Brain shards:** they save about 45 seconds of provisioning per shard but break the five-minute ceiling set for the e2e tier (#18408).

## Same-runner packing: measured follow-up to the operator's request

**Finding:** this is a distinct lever from choosing fewer tests. GitHub now documents native step groups that run concurrently within one job ([`steps.parallel`](https://docs.github.com/en/actions/reference/workflows-and-actions/workflow-syntax#jobsjob_idstepsparallel)). The standard public Linux runner has [4 CPUs and 16 GB RAM](https://docs.github.com/en/actions/reference/runners/github-hosted-runners#standard-github-hosted-runners-for-public-repositories). A matrix entry still creates another job/runner allocation. Documented syntax is not yet a hosted acceptance receipt for our workflows.

Source census: Engine dev `83006c9747c552ed0e4e0a496049f46211f9247a`. Timing sample: #20318, [unit/components run](https://github.com/neomjs/neo/actions/runs/42048502578), [Engine E2E run](https://github.com/neomjs/neo/actions/runs/42048502509), [Brain E2E run](https://github.com/neomjs/neo/actions/runs/42048502635). These are one-run observations, not a speedup benchmark.

| Population | Runner jobs today | Internal Playwright workers/job | Observed test-step duration |
|---|---:|---:|---:|
| Main units | 1 | 4 | 146s |
| Timezone probes | 2 | 4 | 3s and 4s |
| Components | 3 | 1 | 167–204s |
| Engine E2E | 4 | 1 | 122–260s |
| Brain E2E, full | 10 | 1 | 138–232s |

Each timezone job separately spent 9s installing dependencies and 11s bundling before its 3–4s test step. Browser shards also repeat setup: roughly 24–50s before Engine E2E tests and 32–89s before Brain E2E tests in this sample. Those costs matter, but most browser-shard time is still test execution.

### Recommended first change

Keep main units' existing four-worker execution, then run the two timezone probes as separately reported processes in that same prepared job. This makes the unit family **3 runner jobs → 1**, without adding browser contention or requiring native parallel syntax merely to overlap seven seconds of work. Preserve the `unit` required context and make it fail if any of the three processes fails; execute/report all three outcomes even when the first is red. Keep the existing dispatch selection, stale-head guard, both timezone signs, and full dev coverage.

The live dev ruleset requires `unit`, but not the two `unit-tz (...)` names individually. Thus this candidate can preserve the required name rather than introduce a ruleset migration. Separate logs, JSON reports and artifact destinations are still necessary: today the runs overwrite `/tmp/test-run.log` and share the unit JSON reporter path, while the two timezone runs share an output directory. The estimated extra test time is only the sampled 7s, but combined wall time must be measured rather than promised.

### Browser parallelism: bounded pilot before activation

Use two existing logical shards in one runner, with one shared dependency/browser preparation and independent ports, Bridge lifetimes, output roots, reports and per-shard results. Keep each shard's cold-start boundary and current selection unchanged. Verify that native parallel steps are accepted by our hosted runner, that one deliberate child failure fails the aggregate, that cancellation cleans up both processes, and that a complete receipt survives either child's failure.

Compare that two-way candidate with the same selections on separate runners. Measure push-to-required-green, runner occupancy, test-step duration, CPU/RAM and failure rate. A pair of one-worker invocations still shares four CPUs with Chromium workers, app workers, the dev server and the Bridge; it is not automatically equivalent to two runners. Current component/E2E comments record timing-sensitive drag/hover/geometry behavior, and existing paths/ports are not ready for concurrent invocations.

Do not evade #18408's five-minute test-time constraint by hiding sequential shards in repeated five-minute steps. A slower sequential packing fallback would require an explicit latency trade-off, not a reinterpretation of that direction. No production shard count, required context, quarantine or retry policy changes in this exploration.

This comment is the measured proposal before an implementation leaf/pilot contract, not a claim that same-runner browser packing is already validated. No workflow files changed.

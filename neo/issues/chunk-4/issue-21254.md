# check-spec-retirement flags spec deletions that never reach dev

## Context

Outside PR #21154 (the examples workbench, on the Engine 14 path; 18 covers of #21121 wait on it) is red on the required `baseline / guards` check at head `fbd481aaca`:

```
check-spec-retirement: 1 commit(s) delete unit spec files with no account.
  4df6805e49 chore(examples): replace ConfigurationViewport.spec.mjs, step 1 of 2 (#21143)
      deleted: test/playwright/unit/examples/ConfigurationViewport.spec.mjs
```

That spec is not on `dev`. An earlier commit of the same PR added it, and `b09f77caa0` renames its new version (`3-ConfigurationViewport.spec.mjs`) back onto the path. The PR's tip holds the suite, and its squash merge removes no coverage from `dev`. `baseline / guards` is a required check on `dev`, so the PR cannot merge, and the only repair open to the contributor is rewriting a commit message on their fork.

## The Problem

- The guard grades each commit of the range on its own: a `D` row of a unit spec without a `spec-retired:` line is a violation, whatever the range's tip holds (the `shas.forEach` loop in `collectViolations`, `buildScripts/util/check-spec-retirement.mjs`).
- Two shapes trip it without losing any coverage `dev` holds:
  - a spec the branch itself added and later deletes or replaces. This is the #21154 shape; replacing a file through the GitHub web UI produces a delete commit and an add or rename commit.
  - a `dev` spec deleted in one commit and restored at the same path by a later one.
- A squash merge lands the net diff, so neither shape reaches `dev` as a deletion.

## The Architectural Reality

- Design authority: "A deleted spec is the one regression the test suite cannot report." (header of `buildScripts/util/check-spec-retirement.mjs`, from #17151). A deletion that the tip undoes, or that removes a spec `dev` never held, is no such regression.
- CI runs the guard with empty stdin (`.github/workflows/pr-baseline.yml:78`), so `pendingRanges` scans `origin/dev..HEAD` on the PR merge ref. The pre-push hook scans `remoteSha..localSha`, or `origin/dev..localSha` for a new branch.
- `createGit(root)` is the guard's git port. `test/playwright/unit/buildScripts/checkSpecRetirement.spec.mjs` injects fake ports and has one real-git end-to-end arm ("the consumed path").

## The Fix

- In `collectViolations`, a deleted spec counts only when its range lands the deletion: the path is in the tree of the range's merge base (`merge-base <from> <to>`) and not in the tree of the range's tip. For CI's `origin/dev..HEAD` that merge base is the `dev` the pull request lands on. Each range reads the two trees once, and only after one of its commits deletes a spec.
- The git port gains `mergeBase(from, to)`. Both tree reads fail closed, as `treePaths` does today.
- Per-commit attribution, the account grammar and the surviving-subject check stay as they are.

*(Sharpened at implementation: the merge base comes from the range itself rather than from `origin/dev`. CI gets the same answer, and the guard's fixture repositories, which have no `origin/dev`, keep working.)*

## Acceptance Criteria

- [ ] A commit that deletes a spec the range's merge base does not hold yields no violation (unit, injected port).
- [ ] A commit that deletes a base spec which a later commit restores at the same path yields no violation (unit, injected port).
- [ ] A commit that deletes a base spec for good is still reported, and the existing arms stay green (unit).
- [ ] The #21154 shape in a real fixture repository (add a spec, delete it, rename a new file onto its path) yields no violation, and that arm fails on `dev` (unit, real git).
- [ ] An unresolvable merge base or an unreadable tree throws.

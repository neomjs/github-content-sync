# Grid columns can sit under a shared group header

## Context

Columns that belong together, like a quarter's three months or an address's street, city and zip, can't share a label in a Neo grid. Every column is one cell in one header row, so an app has to repeat the group in each header's text ("Q1 · Jan").

## The Problem

A grid can't render a header cell that spans a run of adjacent columns. The leaf header row carries sorting, resizing, header filters, column menus, drag-reorder and `aria-colindex`. A group label has to keep all of these working, and it has to stay aligned while columns resize, reorder and scroll.

## The Architectural Reality

- `grid.Container#createColumns` (`src/grid/Container.mjs` l.954) walks a flat `columns` array. It sends each column's header-button config to the start, center or end toolbar according to `locked`. It never reads a nested `columns` key.
- Each region's `grid.header.Toolbar` renders one row of `grid.header.Button` items (`aria-rowindex: 1`, `src/grid/header/Toolbar.mjs` l.85). `passSizeToBody` measures those buttons into the region body's `columnPositions` (l.386). The toolbar mirrors horizontal scroll in its `scrollLeft_` config (l.61). What moves it on screen is the main thread: `ScrollManager` registers the centre toolbar's root as the header node (`src/grid/ScrollManager.mjs` l.394), and `GridHorizontalScrollSync#onScroll` writes the scrollbar's `scrollLeft` onto that node in the same frame as the body (`src/main/addon/GridHorizontalScrollSync.mjs` l.67–80).
- The toolbar root has three jobs at once. It is the ARIA row, the scroll-sync node, and the flex items root: `getVdomItemsRoot()` defaults to the root, and the hbox layout puts its classes on `wrapperCls`, which is the root (`src/layout/Flexbox.mjs` l.168–181).
- `grid.header.Wrapper#syncAriaRows` (`src/grid/header/Wrapper.mjs` l.170–185) makes the regions' toolbars read as ONE ARIA row: the lead toolbar is `role="row"` and owns the others. `grid.Container` counts one header row in `aria-rowcount` (l.1881).
- Header drag-reorder runs through `draggable/grid/header/toolbar/SortZone.mjs` over the toolbar's buttons.

## The Fix

1. **Config.** A `columns` entry with its own `columns` array is a group, for example `{text: 'Q1', columns: [{dataField: 'jan'}, {dataField: 'feb'}, {dataField: 'mar'}]}`. `createColumns` flattens the leaves, in order, into today's pipeline and records each leaf's group. `locked` is set on the group and applies to every leaf.
2. **The leaf row doesn't change.** Sort, resize, filters, menus, drag, `aria-colindex` and `columnPositions` keep running on the same flat buttons.
3. **The group row is a projection.** Each region that has groups renders one more header row above its leaf row. A group cell's left edge and width come from its first and last leaf's `columnPositions` entries, so a leaf resize, a flex re-layout or a reorder re-projects the row without a second measurement. `grid.header.Wrapper` owns the group parts and places them beside its region toolbars, creating them on demand the way it creates `headerStart` and `headerEnd`. No part lives inside a toolbar, because the toolbar root has to stay the leaf row (see above). The centre part is a second node that `GridHorizontalScrollSync#onScroll` writes to, registered next to `headerId`, so it scrolls in the same frame as the leaf row.
4. **Reorder.** Header drag can't move a leaf out of its group, and it can't move an ungrouped column into a group.
5. **ARIA.** With groups, the group row is header row 1 and the leaf row is header row 2. Group cells are `columnheader`s with `aria-colspan` set to their leaf count. The group parts form their own cross-region row the way `syncAriaRows` stitches the leaf row: the lead part is `role="row"` and `aria-owns` the others. `aria-rowcount` counts both header rows. A grid without groups renders today's DOM unchanged.

## Acceptance Criteria

- [ ] A `{text, columns: [...]}` entry renders one group header cell above exactly its leaves. A grid without groups renders today's DOM, with no group row.
- [ ] After a leaf resize, a flex re-layout and a reorder inside the group, the group cell's left and right edges match its first and last leaf's edges (e2e, DOM rects).
- [ ] During horizontal scroll, the group row stays aligned with the leaf row (e2e).
- [ ] Replacing the whole `columns` array re-projects the group row. A consumer that regenerates its columns on every change, like a pivot view that derives its columns from pivot keys, gets correct groups each time.
- [ ] A group locked to `start` or `end` renders in its own region.
- [ ] Header drag can't drop a leaf outside its group.
- [ ] ARIA: there are two header rows, group cells carry `aria-colspan`, and `aria-rowcount` counts both header rows.
- [ ] One example grid uses grouped headers.

## Out of Scope

- More than one group level.
- Dragging a whole group, collapsing a group, and sorting or menus on a group cell.

## Avoided Traps

- **Nesting the leaf buttons inside group containers in the toolbar.** Layout would align the widths for free. But `getColumn`, the index-based `aria-colindex` in `createItems`, `passSizeToBody`, `Wrapper#getButton` and the SortZone all treat the toolbar's `items` as flat leaf buttons, so each of them would have to walk a tree. The projection leaves the leaf row untouched.
- **Measuring the group row separately.** `columnPositions` already holds the leaf geometry. A second measurement adds a layout read and a second source of truth that can drift.

### @neo-opus-grace - 2026-11-05T22:54:00Z

**Design for the group row (steps 2–5), decided before building.** Step 1 is on `grace/20379-grid-header-groups` (c81f12e6e3): groups are flattened into their columns, and each column carries `headerGroup`.

The constraint is the Wrapper's layout. `Wrapper#updateHeaders` sets `items` to exactly `getToolbars()` (start, centre, end) in an hbox. A row above them can't come from re-parenting the toolbars into per-region columns: `getToolbars()`, `applyColumnButtonOrder()` and the menu wiring address them directly. It can't come from width arithmetic either, which would drift from the toolbars' own layout by borders.

- **`Neo.grid.header.GroupRow`**, a component and the Wrapper's first item, present only while some column has a `headerGroup`. Its root is the group row's single ARIA row: `role="row"`, `aria-rowindex: 1`. It holds one `role="none"` part per region present, and each part holds that region's group cells. A cell is a `columnheader` with `aria-colspan` (its leaf count) and `aria-colindex` (its first leaf's grid-wide index). It is absolutely placed from that region body's `columnPositions`: left at the first leaf's `x`, width the sum of its leaves' widths. That is one source of truth and no second measurement.
- **Alignment comes from CSS grid.** While groups exist, the Wrapper adds one class and sets `grid-template-columns` from the regions present (`auto`, `minmax(0, 1fr)`, `auto` for start, centre, end). The toolbars auto-place into row 2. The GroupRow spans row 1 with `grid-template-columns: subgrid`, so each part sits exactly over its toolbar, sized by the toolbar's own layout. Without groups there is no class and no GroupRow: today's DOM, unchanged.
- **Re-projection:** the end of `Toolbar#passSizeToBody` (resize, reorder, flex re-layout) asks the Wrapper's GroupRow to re-project. `updateHeaders` creates, updates or destroys it, which covers a full `columns` replacement.
- **Scroll:** the centre part follows the scrollbar in `GridHorizontalScrollSync#onScroll`, the same frame as the centre toolbar. Its registration gains the part's id beside `headerId` (`ScrollManager` l.394).
- **ARIA:** with groups, the lead toolbar's leaf row becomes `aria-rowindex: 2`, and `grid.Container` counts one more header row in `aria-rowcount`.
- **Reorder (step 4):** the header SortZone refuses a drop that would move a leaf out of its group or an ungrouped column into one.

Evidence, per the ACs: unit specs for the vdom and ARIA attributes, and a real-pointer e2e for the edges after resize, reorder and scroll.

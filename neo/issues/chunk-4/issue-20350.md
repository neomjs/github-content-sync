# A checked list item needs two clicks to uncheck after disableSelection

## Context

This came up in the Round 2 review of #20336, on head `d9ca49bf55`.

#20336 adds a `checkedField` link to `useCheckBoxes` lists. Its fix for RA 1 keeps a record's checked state through a view reset. The selection model does not get the same treatment. `afterSetDisableSelection(true)` runs `selectionModel.deselectAll()`, and when `disableSelection` returns to `false` nothing re-seeds the model. The two holders of one fact then disagree until the next `createItems()`.

## The Problem

Reproducer: a unit test with a `selection-listmodel` (`toggleOnClick: true`) and records `a` and `b` checked.

```js
list.vnodeInitialized = true;
list.disableSelection = true;
list.disableSelection = false;

list.selectionModel.onListClick({currentTarget: list.getItemId(recA)});

expect(recA.checked).toBe(false); // receives true
```

- The item still renders checked, because `createItem()` ORs `record[checkedField]` into `isSelected`.
- `selectionModel.isSelected(aId)` is `false`, so `ListModel.onListClick` calls `select(record)` and the first click changes nothing. A second click unchecks the item.
- The control passes: without the toggle, one click unchecks.

## The Architectural Reality

- Design authority: the `checkedField` JSDoc on #20336, *"explicit item selection and deselection (`selectionModel.select()` / `selectionModel.deselect()`) write `true` / `false` back into `record[checkedField]`, while view-initiated resets (`disableSelection`, `selectedIndex = null`, `deselectAll()`) leave record data untouched"*. After a reset, the record holds the checked state, so the selection model has to follow it back.
- `createItems()` already seeds `selectionModel.items` from the checked records (#20336). In `singleSelect` it seeds only the first one.
- `afterSetDisableSelection` (`src/list/Base.mjs:274`) acts on `true` only.
- `ListModel.onListClick` (`src/selection/ListModel.mjs:69`) toggles based on `isSelected`.

## The Fix

When `disableSelection` turns `false` on a list whose `checkedField` link is active, re-seed the selection model from the checked records **and re-apply their item annotations** (`.neo-selected`, `aria-selected`). `deselectAll()` removed both, and `createItems()` normally rebuilds both, so seeding the IDs alone leaves the checkboxes unchecked on screen (Sophie's falsifier, comment 6669723495). Move the seeding into one method that both call, and repaint the marks through the existing annotation owner, `Neo.selection.Model#restoreSelection()` (`src/selection/Model.mjs:347`, as `list/Buffered.mjs` and `component/Gallery.mjs` use it), on the normal update path.

Keep the seeding event-free and keyed by `getItemId(getRecordId(record))`. Honour a custom checked field and the filtered store's order. Do not use `select()`, which can rewrite other records in single-select mode.

## Acceptance Criteria

- [ ] AC-1: A unit arm shows that right after `disableSelection` goes `true` → `false`, without the test calling `createItems()`: every checked record keeps its value, `selectionModel.isSelected()` is `true` for it, and its existing item carries `.neo-selected` and `aria-selected: true`. Then one `onListClick` on a checked item unchecks it, and only it. The control without the toggle stays green.
- [ ] AC-2: In `singleSelect`, after the same toggle, only the first checked record is model-selected, every record keeps its checked value, and the record-driven checkbox annotations match their creation state. The checked field ORs into the visual selection, so every checked record keeps its mark, not just the first.

## Out of Scope

- `ValuePicker` (no selection model) and buffered or tree lists, which have their own creation and identity paths; this leaf certifies ordinary lists only.

- `selectedIndex = null`: it clears the model on purpose, and the records keep their state (#20336).
- The per-change full pass in buffered list subclasses, which #20336's Round 1 noted.

### Prescription falsifier: re-seed annotations as well as IDs

I checked the proposed extraction against current source (unchanged in these files from dev `9b418b4764`) using the existing `UseCheckBoxes.spec.mjs` setup and real List/Store/selection-model objects in an isolated single-thread runtime. No implementation claim or tracked edit; this remains a contributor-ready leaf.

The original lost-click witness reproduces: without the toggle the first click changes `a.checked` to false; after `disableSelection: true → false` the first click leaves it true.

There is a second acceptance edge **before that click**. With two checked records and multi-selection:

| Phase | Record flags | Model selection | Existing VDOM marks |
| --- | --- | --- | --- |
| Initial | true, true | a, b | both `.neo-selected` / `aria-selected:true` |
| Disable then re-enable | true, true | empty | both marks removed |
| Copy only the `createItems()` seeding loop | true, true | a, b | still absent |
| Existing `restoreSelection(true)` control | true, true | a, b | both restored |

The restoration control adds **zero record changes and zero selection events** beyond the existing reset event. The following multi-select click unchecks only a. In `singleSelect`, seeding keeps only the first checked record in the model while preserving both record values; restoring its annotation also adds no record/selection event. **Both checked records are visually annotated at creation**, because `createItem()` ORs the record's checked flag into the visual state. The measured initial state is model selection `[true,false]` and annotations `[true,true]`; after re-enable plus restoration it is the same. AC-2 must distinguish model selection from those record-driven checkbox marks, rather than require the second checked record to become visually unchecked.

Why this matters: `selection.Model#deselectAll()` removes the annotations, while `createItems()` normally rebuilds them. Extracting only the IDs loses that second half. Checkbox glyph CSS is selected by `.neo-use-checkicons .neo-list-item.neo-selected` (`resources/scss/src/list/Base.scss`), so model state alone cannot certify the rendered checkbox.

**Suggested acceptance refinement:** assert record values, selected IDs and the existing item's selection/ARIA marks immediately after re-enable, without calling `createItems()` in the test, then exercise the first click. Use the existing annotation owner and the normal update path; the silent restoration above is a VDOM control, not a claim of native DOM delivery. Preserve event-free seeding, `getItemId(getRecordId(record))`, custom checked fields and filtered-store order. Do not replace it with `select()`, which can rewrite other records in single-select mode.

`ValuePicker` has no selection model, and buffered/tree subclasses have their own creation/identity paths; this bounded ordinary-list witness does not certify those subclasses. All probe-created instances were destroyed.

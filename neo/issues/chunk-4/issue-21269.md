# Make tooltips dismiss immediately when the pointer leaves the trigger and tooltip

## Requested behavior

Please make ordinary tooltips dismiss immediately when the pointer leaves their trigger and is no longer over the tooltip. The current lingering behavior feels sluggish, especially when moving between neighboring icon buttons.

A reusable component should get responsive tooltip behavior from the framework defaults without each developer repeating timing overrides.

## Current behavior

`Neo.tooltip.Base` currently defaults to:

```js
showDelay: 200,
hideDelay: 400,
stayOnHover: true
```

After the pointer leaves a trigger for empty space, the tooltip remains visible for the hide delay. Moving between buttons can leave the previous tooltip lingering while the next one waits to appear, particularly when the buttons use dedicated tooltip instances.

This request concerns the deliberate default delays, rather than a tooltip that remains stuck because of a lifecycle bug.

## Reproduction

1. Put several icon buttons near each other and give each a standard tooltip.
2. Hover a button until its tooltip appears.
3. Move directly to empty space: the tooltip lingers instead of disappearing immediately.
4. Move between neighboring buttons: the tooltip transition feels slow.
5. With a hoverable tooltip, move onto it and then leave it for empty space: dismissal should be immediate once neither the trigger nor the tooltip is hovered.

## Configuration that feels better

For simple, non-interactive button labels, the following configuration was verified to make switching prompt and dismissal immediate:

```js
tooltip: {
    text: 'Edit',
    showDelay: 0,
    hideDelay: 0,
    stayOnHover: false
}
```

This is a useful workaround, but developers should not need to discover and repeat these settings on ordinary components.

## Proposed framework improvement

- Use immediate dismissal as the default for ordinary tooltips once the pointer is outside the trigger and tooltip.
- Keep hoverable tooltips usable: when hover persistence is enabled, entering the tooltip should keep it available, and leaving both regions should dismiss it promptly. Any intentional grace period for crossing a gap should be treated separately from lingering after an actual departure.
- Make switching between adjacent tooltip targets prompt, without stale tooltip overlap. An intentional initial show delay can remain a separate policy from switching between already active targets.
- Preserve explicit timing overrides for applications that want delayed dismissal.

Please cover trigger-to-empty-space, tooltip-to-empty-space, rapid target switching, and entering/leaving before an asynchronous tooltip mount finishes.

## Related

- #19311 fixed timer cancellation and explicitly excluded changing the 400 ms hide delay.
- #20825 addressed asynchronous mount races and explicitly excluded changing delay duration or hover policy.
- #21268 concerns shared tooltips missing floating-dialog targets.

This request is about the framework's default interaction policy and responsiveness.

Thank you, @armando-ota. The reproduction and the boundaries you drew (#19311 and #20825 left the delays alone on purpose) made this quick to check. What `dev` does today (`a2d97b19b8`):

- The defaults are as you quote (`src/tooltip/Base.mjs:56-81`). Leaving a trigger arms the 400 ms `hideDelay` (`onDelegateMouseLeave` → `hideDelayed`, `:290-349`).
- Switching between neighbouring targets is already immediate for the shared tooltip, which serves every `tooltip` config without `ownInstance: true` (`src/component/Base.mjs:1399-1425`). While it is still shown, entering the next target re-aligns it and shows it at once (`src/tooltip/Base.mjs:322-325`). The overlap you saw comes from `ownInstance: true` tooltips, where every instance runs its own timers.
- Your workaround works per target because the shared tooltip applies each target's own config (`applySingletonTargetConfig`, `:218-241`).
- The 400 ms is how long the pointer has to cross the 10 px `targetMargin` gap (`:319-320`) into a hoverable tooltip. Elapsed time is the only signal the tooltip has today for telling a crossing from a departure.

**Decision: accepted as an enhancement, with one change of approach.** Hoverable stays the default: WCAG 2.1 SC 1.4.13 (Content on Hover or Focus) requires author tooltips that open on hover to stay up while the pointer moves onto them. Defaulting to `hideDelay: 0, stayOnHover: false` would swap the sluggishness for an accessibility failure. Instead:

1. Where the pointer goes decides a departure, not a timer. The tooltip's hit area bridges the gap to its target, and the leave handler reads where the pointer went (the main thread already sends a leave's `relatedTarget`, `src/main/DomEvents.mjs:344-360`). Into the tooltip, it stays. Anywhere else, it hides at once. `hideDelay` stays available as an explicit override.
2. One visible tooltip per browser window: showing one hides any other, `ownInstance` tooltips included.
3. Switching stays prompt: for a short window after a tooltip hides, the next target shows without `showDelay`.
4. Specs for your four cases: trigger to empty space, tooltip to empty space, rapid switching, and leaving before the mount lands.

I'm taking it. It builds on #21270 (one shared tooltip per browser window), so it lands after that merges.

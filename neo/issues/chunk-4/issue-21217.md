# Theme sources become plain CSS, and the theme build copies them

## Context

Graduated from Discussion #18182 on 2026-11-17 (`[GRADUATION_APPROVED by @neo-gpt-euclid @ body 2026-11-17T04:28:06Z]`, comment 19670420; quorum with the author's signal, comment 19670104). The operator's direction for 14.0, relayed in #21210: Sass goes, a clean cut with no migration path. This ticket is that Discussion's row 3c′ for the engine: the theme sources become plain CSS, and the theme build copies them instead of compiling them.

Measured on `dev` at `825047c9ea`: all 722 engine theme files that are not partials convert to plain CSS whose Sass output equals what the original compiles to, normalized and through autoprefixer (#18182, comments 19670297 and 19670385). The converter and its negative control are in the Discussion's evidence.

## The Problem

Sass is the last build tool a development workspace needs for the engine's own styles, and it does nothing in this tree that plain CSS cannot hold: every `color.adjust` call is a compile-time constant, the mixins take no arguments, and 665 of the files use nothing beyond nesting and `//` comments. Keeping it costs a compiler in every workspace's install and a second language for every theme edit.

## The Architectural Reality

- `resources/scss/{src,theme-*}/**` holds one file per class per theme (725 files, 11 of them partials). The stylesheet loader asks for `dist/<env>/css/<folder>/<class>.css`; `theme-map.json` lists which classes have sheets in which folders.
- `buildScripts/build/themes.mjs` compiles each non-partial file with `sass.compile`, then runs postcss (autoprefixer; cssnano for production) and writes `dist/<env>/css/**`. It collects roots from the engine, from every dependency whose `package.json` names a `neo.scss` folder, and from the workspace's `resources/scss`.
- `buildScripts/helpers/watchThemes.mjs` rebuilds changed files; `buildScripts/util/developmentThemeAssets.mjs` derives the map's class census from the non-partial source tree.
- Other readers of `resources/scss` or of SCSS syntax: `buildScripts/create/{class,scss,theme}.mjs` (scaffolders), `buildScripts/helpers/convertDesignTokens.mjs`, `buildScripts/util/{movePlan,moveStyleTransforms,check-theme-coverage,check-theme-surfaces,check-theme-value-files,check-relative-links}.mjs`, and 29 test files.
- `package.json` devDependencies: `sass`, `postcss-scss` (beside `postcss`, `autoprefixer`, `cssnano`, which stay).

## The Fix

1. **Sources.** `resources/scss` becomes `resources/css`: every file converted by the #18182 converter. That means `//` comments become block comments, mixins and CSS-emitting modules are inlined, Sass-script values are replaced by what Sass computes, and a top-level rule that holds a nested rule under a mixed-specificity list or a declaration after a nested node takes Sass's flattened output in place (D2, D3). The two control-flow files take Sass's compiled output (D4). Nesting is kept everywhere else.
2. **Build.** The theme build copies `.css` sources and post-processes them as today; the map comes from the `.css` tree; the watcher copies instead of compiling. `sass` leaves `package.json`; `postcss-scss` leaves it too unless a lint still needs a parser postcss lacks.
3. **Package contract.** The `neo.scss` field of a package's `package.json` becomes `neo.css`, pointing at its plain-CSS root. A workspace's own `resources/css` replaces `resources/scss`.
4. **Every other reader** in the list above reads `.css` and `resources/css`; scaffolders write `.css`; tests follow.
5. **The converter is part of the pull request, not of the package.** One commit adds it and runs it; a later commit removes it together with Sass. The pull request body carries its proof output. The consumers' conversions run it from the pull request's head.

## Avoided Traps

- **Moving a declaration across a nested rule by property name:** a shorthand also sets its longhands (#18182, comment 19670346). Flatten the containing rule instead.
- **Lifting single nested rules out:** it reorders them against their siblings (#18182, comment 19670216).
- **Keeping SCSS support for packages:** the clean cut has no migration path; the two known packages convert in the paired leaves.
- **Shipping the converter in the package:** it needs Sass, which this change removes.

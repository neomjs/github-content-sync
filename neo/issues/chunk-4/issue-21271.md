# Preserve user-sized windows and only constrain them when desktop bounds change

## Requested behavior

Please provide framework-owned desktop/window boundary handling that preserves a user's chosen window size and position.

A desktop changing size should not reapply the window's initial percentage dimensions. The window should only be adjusted if the new usable desktop bounds would leave it out of bounds.

## Scope and attribution

This is a request for a documented framework policy for desktop app windows or boundary-constrained dialogs. Reapplying initial dimensions from a consumer's resize handler is application behavior; this report does not claim that Neo's dialog class itself resets windows to a fixed percentage.

The goal is to avoid requiring each consumer to implement geometry ownership, boundary observation, and clamping independently.

## Desired interaction

1. Open a resizable window inside a desktop workspace and manually resize or move it.
2. Enlarge the desktop: preserve the window's size and position.
3. Shrink the desktop while the window still fits: preserve the window's size and position.
4. Shrink the desktop so the window extends outside it: move the window back inside using the smallest necessary adjustment.
5. Only reduce the window's dimensions if it is too large to fit within the available workspace at any position. Adjust only the dimensions that need it.

Observe the actual configured desktop/workspace size rather than resetting window geometry for every browser resize or repeated ResizeObserver notification.

## Proposed acceptance criteria

- User-selected geometry remains authoritative after a resize gesture finishes.
- Unchanged desktop dimensions and repeated identical resize notifications produce no geometry writes.
- A desktop size change produces no geometry writes for windows that remain fully in bounds.
- Moving a window back into bounds is preferred to shrinking it.
- If the window is larger than the available workspace, shrink it only as necessary and keep its controls reachable; document behavior when configured minimum dimensions exceed the available area.
- Expanding the desktop does not automatically expand or recenter normal windows.
- Observe the configured boundary container, including a desktop workspace that excludes a toolbar/taskbar, rather than always using document.body.
- Delayed measurements must not overwrite a newer user drag/resize or apply to a closed/destroyed window.
- Maximized windows may follow the available desktop area as a separate, explicit state; restoring should use the normal window geometry according to a documented policy.

## Framework resize integration

The same geometry contract should keep dimension configs and the rendered dialog/drag-preview dimensions synchronized. In the public resize implementation, Resizable writes wrapperStyle while DragZone initializes proxy dimensions in style; component.Base.updateStyle gives style precedence for a single-root component. Consumers should not need a custom adapter to make ordinary resizable dialogs retain their new size.

### @neo-opus-grace - 2026-11-17T18:50:19Z

Thank you, @armando-ota. Your scope paragraph was right that the engine never re-applies percentage sizes, and your resize paragraph pointed at a real engine bug. What `dev` does today (`a2d97b19b8`):

- A move already turns a dialog's geometry into px: `dialog.Base#onDragEnd` writes `height`, `left`, `top` and `width` into `style` (`src/dialog/Base.mjs:672-714`). Nothing in `dialog.Base` or `plugin.Resizable` watches the boundary container's size. So nothing re-applies a configured `width: '40%'`, and nothing keeps a window inside a container that shrinks either.
- **Your "Framework resize integration" paragraph is a bug, and a worse one than a missing adapter.** In `examples/dialog`, a dialog that was moved once cannot be resized at all. A +150 px drag on the right handle leaves it at 410 px, while an unmoved dialog goes from 410 to 557 px. The resize preview never follows the pointer in either case. On a single-root component, the move's `style` masks the resize's `wrapperStyle`. I filed it as #21280 with the trace and credited your report. It ships on its own, ahead of the desktop work.

**Decision: accepted as an enhancement for the rest: windows stay inside a boundary container whose size changes.** Your interaction list and ACs are the contract. Placement:

1. It goes in `dialog.Base` as an opt-in config keyed on the existing `boundaryContainerId`, so any bounded dialog can use it, not only desktop windows. The desktop's app window turns it on. One observer per boundary container supplies the size, and an unchanged size writes nothing (your second AC).
2. A maximized window following the workspace is a state of its own, owned by the window manager (#21199).

It lands with the desktop shell (#21198), after the Engine 14 cut. I've linked it there as a sub-issue and taken it.

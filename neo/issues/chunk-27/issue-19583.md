# A popup re-opened by Undo or a perspective has no road home but close

## Context

#19569 measured a window that was re-opened for a restored vessel workspace (`openTopologyWorkspace` → `NativeVesselTransaction.embodyWorkspace`), in the full film tour, headed. The re-opened window has no clean way home:
- the title-bar return is refused;
- a stack drag brings the stack home but leaves the emptied window open;
- a scripted close is refused.

A user's own close does return its panes. The measurements are in #19569's status table.

Users reach the same window kind without a perspective. After a popup is closed, the toolbar's **Undo** re-opens it through `replayWorkspaceReturn` → `embodyWorkspace`. Measured headless at `a852b8ca6e`, the re-opened window loads `?workspace=workstation-vessel:feed`, the re-birth config, not the tear-out's `?popout=feed`. Two observations on that path have no explanation yet; they are recorded on #19569:
- Both first-batch runs logged `Neo.tab.plugin.Overflow: project() threw against a live owner`; neither tear-out control did.
- In 2 of 4 re-opens, the window showed its tab strip without the pane for 30 s.

## The Problem

The documented ways home do not hold for a re-opened popup. A user who closes a popup, presses Undo and then drags the stack home is left with an empty window.

## The Architectural Reality

- Design authority:
  - `learn/guides/uibuildingblocks/DockLayoutsWindows.md`, lifecycle: "four roads home — Undo, Reset, stack return, physical close";
  - `apps/workstation/README.md`: "**Undo** reopens the popup with its panes; **Redo** returns them and closes it again."
- `VesselWorkspace#retireReturnedVessel` closes an emptied vessel only through its tear-out record (`resolveTearOutVessel(itemId)` → `nativeWindows.retire`).
- The return that a popup's close performs clears that record; #19569 measured this. The engine's `Workspace#onDockWorkspaceReturn` releases the tear-out records of the returned items. Nothing re-records them when `embodyWorkspace` re-opens the window.
- The re-opened window's identity and capabilities differ from a tear-out's:
  - `VesselWorkspace#getNativeWindowOpenConfig` opens it as `workstation-restored-<uuid>` with no `nativeCapabilities`;
  - a tear-out opens as `tearout-<itemId>` with `{close, position, resize}`;
  - `NativeVesselTransaction.closeVessel` checks both the window name and the route's `close` capability.
- One close path already reaches a re-opened window. Redo in `replayWorkspaceReturn` runs `clearTopologyIdentity` + `closeTopologyWindow`, fenced against the binding, its generation and the snapshot.

## The Fix

Two candidates; a witness decides between them:
1. **Close on empty without a tear-out record.** When `retireReturnedVessel` finds no vessel record for an emptied workspace that still has a bound window, close it through the same fenced topology close that Redo uses. The close path is shared, not copied.
2. **First-class re-embodiment.** Open re-born vessel windows under the tear-out name, with the tear-out capabilities, and record native ownership on bind. Then the title-bar return and the scripted close work as well.

The close-on-empty witness can run headless as a direct transfer commit. A title-bar-return witness needs real window geometry, so it runs only where it can stay off the visible screen.

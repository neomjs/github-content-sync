# The release-note archive leaves the engine for the content corpus

## Context

`.github/RELEASE_NOTES` holds 169 files: the archive v8.1.0–v13.1.0 plus the pending `v13.2.0.md`. `neomjs/github-content-sync` publishes the same 168 archived notes under `neo/release-notes`, chunked at 100 (`chunk-1` 100, `chunk-2` 68, `_index.json`). `v13.1.0.md` is byte-identical in both, and nothing keeps the two copies equal. The flat folder grows by one per release toward GitHub's 1,000-entry directory listing cap. Neo has 1,196 releases, so a backfill would cross that cap at once.

How the copy got here: #19157 chose `.github/RELEASE_NOTES/` as the authored path. #19159 is the operator's call to delete `resources/content`, executed by #19322 on 2026-09-29. It `git mv`'d the chunked archive there flat and made the authored file the archive, while the corpus kept publishing the same notes.

## The Problem

There are two archives and one of them is unguarded. A correction to an old note lands in one copy only. The engine also carries content that the 13.2 split moved out of it.

## The Architectural Reality

Design authority: the operator, 2026-10-10: *"gut feeling: except for the pending v13.2 release notes, we should remove items from the neo repo"*, followed by the request for this ticket. This supersedes #19159's *"The authored file is the archive; `publish.mjs` reads it there and no longer deletes it after the release."* The authored path stays (#19157). This is aligned with ADR 0004's single corpus with ordinal-100 chunking (`learn/agentos/decisions/0004-github-content-architecture.md`).

The readers of the flat archive at `dev` 5698517f19:

|---|---|---|
| Portal | `apps/portal/neo-config.json:7` `releaseNotesBasePath` | fetches the notes at runtime |
| Release index | `buildScripts/docs/index/release.mjs`, root from `buildScripts/util/contentRoot.mjs:50` `getEngineReleaseNotesRoot` | writes `releases.json` with paths relative to the declared root |

| Pages | `neomjs/pages` `buildScripts/updateNeoVersion.mjs:130-183` (step 4.1) | copies `release-notes` from the engine tag and every other family from the corpus pin |
| Brain KB | neomjs/neo-agent-brain: `ReleaseNotesCorpusSource` reads the corpus; `ai/services/knowledge-base/helpers/coreCorpusProfilePlan.mjs:35` omits the engine-path `ReleaseNotesSource` | expected unchanged; verify |

## The Fix

1. `git rm` v8.1.0–v13.1.0 from `.github/RELEASE_NOTES`. The folder keeps only the pending `v<next>.md`.
2. The archive readers take the corpus root (`neo/release-notes`, chunked, `_index.json`). The pending note still comes from the engine wherever a build needs it before the corpus has it, because the corpus gains a release's note only after the post-release sync.
3. In `publish.mjs` the note stays authored at `.github/RELEASE_NOTES/v<version>.md`, and "stays there as the archive" leaves the JSDoc. The previous note leaves the engine once the corpus carries it; the PR picks and states the trigger.
4. Pages step 4.1 (a companion PR in `neomjs/pages`) takes `release-notes` from the corpus pin plus the tag's own note.
5. ADR 0004, `CodebaseOverview.md` and the specs follow the new shape.

## Acceptance Criteria

- [ ] AC-1 `.github/RELEASE_NOTES` holds only the pending note.
- [ ] AC-2 A local Portal build lists v8.1.0–v13.1.0 plus the pending note, and renders one archived note. Evidence: the `releases.json` count and the rendered note.
- [ ] AC-3 The release-note steps of `publish.mjs` pass for 13.2.0. Their specs move red→green with the new shape.
- [ ] AC-4 Pages step 4.1 builds from the corpus archive plus the tag's note. The companion PR merges before or with this one.
- [ ] AC-5 `git grep RELEASE_NOTES` is audited, and every remaining hit reads only the pending note.

## Out of Scope

Backfilling the notes before v8.1.0, changing the corpus layout, and the Knowledge Base ingestion path.

# A board example scrolls 10,000 cards in windowed columns

## Context

A leaf of #21346, the planning examples under #21140. The visitor's question: does the board stay fast when one column holds thousands of cards?

No contributor labels: the capability is read from the source ([the check on `#21346`](https://github.com/neomjs/neo/issues/21346#issuecomment-6982869553)) and has not been driven or profiled. A maintainer builds it, and the profile is the first step.

## The Problem

The scheduler and the Gantt chart each have their scale example (`scheduler/bigData`, `gantt/bigData`). The Task Board has none, and a backlog column is where a board grows long.

## The Architectural Reality

- `maxRenderedCards_` (`src/board/Column.mjs:85`, default 100; `null` renders every card) and `overscan_` (`:87`): a column renders a window of its cards.
- Template: `examples/board/basic` (not edited); `examples/board/swimlanes` shows a store and a card model in files of their own. Specs for the family: `test/playwright/e2e/board/`.
- Shared files stay out of this pull request (`#21539`: every examples pull request that edits them makes the others stale): the catalog's data, its two specs and `test/playwright/externalBrainSelection.mjs` belong to #21613, which takes the record below as written.
- Design authority: n/a — a new example; it calls no existing behaviour wrong.

## The Fix

1. **Profile it first** on a scratch copy of the base example with 10,000 seeded cards: the time to the first frame, the cards in the DOM, and a scroll of the longest column from top to end. A defect becomes an engine ticket, linked here as a blocker.
2. **A new folder `examples/board/bigData`:** a support desk's backlog. Ten thousand tickets generated in the example from a seed, with varied titles, tags and assignees; five columns, about 6,200 tickets in "New". One line reads "10,000 cards · n in the DOM", where n is counted live. The data lives in a store of models.
3. **The record, for #21613:** id `board-big-data`, name "A board of 10,000 cards", `feature` "10,000 seeded tickets in five columns, about 100 rendered per column", `lookFor` "Scroll the first column to its end, then drag its last card into another column: the counts change and the DOM stays small." Cover: the five columns with the counter line.

## Acceptance Criteria

- [ ] The example names its card count and the live count of cards in the DOM.
- [ ] The longest column scrolls to its end without a blank stretch, shown in a frame taken mid-scroll.
- [ ] A card from the end of the longest column can be dragged into another column, and both headers' counts change.
- [ ] The pull request gives the profile's three numbers and the machine they were measured on.
- [ ] A spec under `test/playwright/e2e/board/` asserts that the DOM holds at most five windows of cards after a scroll and after a drop.
- [ ] No console error. 1440 × 900 and 390 × 844. Every theme the base example's `neo-config.json` lists.
- [ ] **Look:** the first frame at both sizes, in the dark theme, is on the pull request beside `board/basic`'s, read cold by one reader of the builder's seat. No control in the example's toolbar keeps its default style.
- [ ] The pull request edits no shared file.

## Out of Scope

Engine changes. Swimlanes at this size. Loading cards from a server.

## Avoided Traps

- **Ten thousand identical cards.** The seed varies what a card shows.
- **A count written as a literal.** Both numbers are computed.
- **A scale example that fetches.** Its data is generated in the example.

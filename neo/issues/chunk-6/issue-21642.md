# `npm run build-all` under 30 s on the M5 Max

Not a good first issue: it is an owned, release-week ask from the operator, and the fix depends on measurements a contributor's machine cannot reproduce.

## Context

The operator (@tobiu), 2026-11-20: "build-all went from 27s to 87s on my macbook m5 max. opposite direction. we removed SCSS to gain speed." He timed `npm run build-all` on the M5 Max (18 cores) that the maintainer seats share.

- **Measured:** on `dev` today the command takes 50 to 58 s on that machine (per-step table below).
- **Inferred, not measured:** his 87 s fits a checkout from before b53c6906a6 (#21281). That commit replaced the clone build of highlight.js (20 to 33 s) with an esbuild bundle of the installed package. AC-1 measures this.
- **Unknown:** the commit and flags behind his 27 s. So the gap from 27 s to about 50 s is open.

## The Problem

`npm run build-all` (`node ./buildScripts/build/all.mjs -f -n`) is the engine's full build: maintainers run it after a pull, and `publish.mjs prepare` runs it for every release commit. Moving the themes to plain CSS (1cc757647f, #21217) was expected to make it faster. On the operator's machine it is twice as slow as he remembers.

## The Architectural Reality

`buildScripts/build/all.mjs` runs every step as a blocking `spawnSync`, one after the other, in this order:
- `npm i` by default (:142);
- five bundles (:146 to :163);
- themes (:167);
- `buildThreads.mjs -e all`, dev and prod in one process (:173);
- `check-dist-paths` (:177);
- `esmodules.mjs` (:183);
- `generate-docs-json` (:190);
- four docs copies, the SEO copy, then the build-id stamps.

None of the heavy steps is new: `buildThreads`, `esmodules` and `generate-docs-json` have been in it since 7e91f744ee (2026-01-17). The webpack and ESM builds changed often in November (#20602, #20702, #20738, #20880, #20956, #20979, #21192, #21295).

Per-step medians on `dev` 4444747966, on the M5 Max. Three runs replay `all.mjs`'s sequence with its flags, at a 1-minute load of 9.6 to 10.9:

| Step | Median |
|---|---|
| `npm i` | 1.14 s |
| five bundles (parse5, marked, mermaid, Monaco, highlight.js) | 0.90 s (highlight.js 0.07 s) |
| themes | 1.59 s |
| `buildThreads.mjs -e all` (dev + prod) | 31.31 s |
| `check-dist-paths` | 0.38 s |
| `esmodules.mjs` | 5.48 s |
| `generate-docs-json` | 8.61 s |
| docs copies (4) + SEO copy | 0.75 s |
| sum | 50.16 s |

One full `npm run build-all` measured 58.3 s earlier the same evening.

Design authority: n/a — the ticket calls no behaviour wrong by a record. The target is the operator's measured ask, and The Fix measures before it changes anything.

## The Fix

1. **Measure first (AC-1).** Build the same per-step table at four commits:
   - 1cc757647f^, before plain CSS;
   - b53c6906a6^, before #21281;
   - `dev`;
   - the commit of his 27 s (13.0.0 if he names none).
   Take a median of three per step and record the load. The table names which steps grew, and by how much.
2. **Then the levers the table ranks.** Two are visible in the code today but not yet measured:
   - The heavy steps run in sequence on 18 cores, though dev threads, prod threads, ESM and the docs parse share no output. `check-dist-paths` waits for prod, the docs copies wait for the docs JSON, and the stamps wait for everything.
   - `npm i` runs on every build: 1.1 s here, more after a lockfile change.
3. **Before Monday's cut,** ship only a change inside `all.mjs` that the table supports. Anything wider waits until after the cut.

## Acceptance Criteria

- [ ] AC-1: The per-step table at the four commits, median of three with the load recorded, is posted here and names the steps that grew.
- [ ] AC-2: `npm run build-all` on `dev` finishes in under 30 s on the M5 Max (median of three, load recorded). It produces the same outputs: `dist/development`, `dist/production`, `dist/esm`, the docs output, and their build-id stamps.
- [ ] AC-3: CI's `build-all` job passes, and `publish.mjs prepare --rehearse` reports every gate ✅.
- [ ] AC-4: `all.mjs`'s JSDoc states which steps may run together, which wait, and why.

## Out of Scope

- The first run of a new app (`npx neo-app`): #21213 and neomjs/create-app#80.
- CI runner queueing: #21541.
- Replacing webpack.

## Avoided Traps

- **Reading a duration from a log line.** "Bundling highlight.js…" is the visible line, but the step takes 0.07 s on `dev`.
- **Closing a measured claim by number-matching.** His two numbers resemble two rows of a hosted runner's first-run table (neomjs/create-app#71), but he timed this command on this machine.
- **Unbounded parallelism.** Two webpack builds plus ESM and the docs parse at once can exhaust a small laptop's memory. Bound the concurrency, for example by `os.cpus()` and free memory, or keep an opt-out.

One real `npm run build-all` per commit, warm: 51.8 s, 64.8 s (load 15), and 58.3 s on `dev` earlier the same evening.

- **No step grew.** The warm totals of the three November commits sit within the load's noise (48 to 54 s), and every step is in the same range.
- **The 87 s fits a cold build before #21281.** On a fresh `dist`, the old script cloned highlight.js. That took 27.2 s on the first cold run and 5.6 s on the second, so it depends on the network. The whole cold run took 91.8 s. Since b53c6906a6 that step bundles the installed package and is gone from the cold path.
- **The 27 s is not reproduced at any measured commit.** Load is the confounder: about ten seats share this box, and warm runs at a load of 10 to 15 take 48 to 54 s. 13.0.0 could not be measured.
- **The lever the table ranks is the sequence.** `buildThreads -e all` builds dev and then prod in one process (28 to 32 s warm). ESM (5 to 6 s) and docs JSON (8 to 10 s) follow it. These four share no output, and they run one after another on 18 cores.

Next: a prototype inside `all.mjs` that runs dev threads, prod threads, ESM and the docs JSON together, with concurrency bounded by cores and free memory and identical outputs. It gets the same median-of-three measurement on this machine. It becomes a pull request before the cut only if it measures under 30 s and `prepare --rehearse` passes on it.

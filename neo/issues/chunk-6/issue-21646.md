# build-all runs its independent build steps together

Not a good first issue: a measured, owned step toward #21642, the operator's release-week ask.

## Context

#21642 asks for `npm run build-all` under 30 s on the M5 Max. Its AC-1 table (#21642 comment 7048805060) found that no step grew between 17 and 20 Nov. Most of the time is in four steps that share no output but run one after another: `buildThreads -e all`, which builds dev and then prod (28 to 32 s), `esmodules.mjs` (5 to 6 s) and `generate-docs-json` (8 to 10 s). This leaf is the first lever the table ranks. #21642 stays open for the 30 s outcome.

## The Problem

`buildScripts/build/all.mjs` starts every step with a blocking `spawnSync`, so 18 cores wait on four builds in sequence.

## The Architectural Reality

The four write disjoint trees and read only the sources:
- dev threads write `dist/development`;
- prod threads write `dist/production`;
- `esmodules.mjs` writes `dist/esm` (`esmDistTransforms.mjs` refuses an input tree that overlaps it);
- `generateDocsJson.mjs` writes `docs/output`;
- no webpack config enables a filesystem cache.

Three steps read their output and must wait for them: `check-dist-paths` (`dist/production`), the docs copies (`docs/output` into both dists) and the build-id stamps. Within one environment, the main and app-worker webpack configs copy into the same folder, so the seven worker builds inside `buildThreads.mjs` are not independent of each other. They stay sequential.

Design authority: n/a — no behaviour is called wrong; the change keeps every output byte-identical (AC-1).

## The Fix

In `all.mjs`, run threads dev, threads prod, `esmodules.mjs` and `generate-docs-json` through a bounded pool:
- the pool runs a quarter of the cores at once (four on 18 cores, one on a 4-core CI runner, where the sequence stays as it is);
- after a failed step it starts no new one, and it exits with that step's status;
- the dependent steps run after the pool.

The `child_process` stub of the build specs gains the asynchronous `spawn` twin, and `buildId.spec.mjs` pins the two threads invocations.

## Acceptance Criteria

- [ ] AC-1: The four output trees are byte-identical between the sequential and the parallel build (same build id), every file hashed.
- [ ] AC-2: On the M5 Max, the median of three real builds drops against `dev`'s sequential build, measured alternately at the same load.
- [ ] AC-3: A failed step exits with its status and publishes no build id; the build specs pass.
- [ ] AC-4: CI's `build-all` job passes.

## Out of Scope

- The seven worker builds inside `buildThreads.mjs` (a lever for #21642 after the cut).
- `npm i` on every build.
- The 30 s target itself (#21642).

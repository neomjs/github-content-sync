Resolves #757

The `turnPresenceHook` progress beacon (`PostToolUse … progress`) now runs `"async": true` with no `timeout`, so no tool call waits on presence. The start (`UserPromptSubmit … start`) stays synchronous at 2 s, once per prompt. Start opens the turn's interval, and an async start can land after the turn completed and open one for a finished turn.

The harness enforces no timeout on an async hook. The writer's one MCP deadline (`hookWriteTimeoutMs`, 1.5 s across every stage) is therefore the only bound on a background run, and the manifest's `$comment` says so. Seats pick up the flag on their next projection: `reconcileClaudeEvents` retires owned entries and re-appends the manifest's.

Evidence: L2 (unit: the manifest's registrations, the reconciliation that carries them into a seat's settings, and the service's terminal-before-start hazard) → L3 required for #757's Post-Merge Validation (a re-projected seat's live transcript). Residual: the post-merge transcript check, Residual-Owner: #67.

### 🔬 Depth Floor

**Challenge:** A background start can arrive after the turn has completed.

The [changed prompt registration](https://github.com/neomjs/neo-agent-brain/blob/f0adccde40a6d6d9a2b983b67875238ccab5d4bd/ai/scripts/lifecycle/hooks/claude/events.manifest.json#L35-L42) permits the model to proceed while its start request is pending. The [Claude contract](https://code.claude.com/docs/en/hooks#run-hooks-in-the-background) confirms this behavior. The hook sends no stable `turnId`; `TurnPresenceService.recordTurnPresence` creates a new id for every start. Meanwhile, [successful add_memory](https://github.com/neomjs/neo-agent-brain/blob/f0adccde40a6d6d9a2b983b67875238ccab5d4bd/ai/services/memory-core/MemoryService.mjs#L688-L709) terminalizes only the currently active interval.

Executed the exact `TurnPresenceService` class at this head with SQLite `:memory:`, an injected identity and the source defaults:

| Order | Result |
|---|---|
| Start, then completion | `getFreshTurnPresence` returns null. |
| Completion at +500 ms, delayed start at +1000 ms | Completion returns `noop/no-active-turn`; the later start creates an active interval. A read at +1100 ms reports `fresh: true`, with the default freshness horizon 30 minutes later. |

The delayed start is still within the existing 1.5-second exchange budget. The budget limits delay; it does not make arrival order safe. The current tests verify manifest flags and replacement, but neither test crosses the terminalization boundary.

A narrow repair is to retain the bounded synchronous prompt-start registration while making `PostToolUse` asynchronous; an equivalent causality-preserving solution is also valid. The required outcome is below, not a demand for a new subsystem.

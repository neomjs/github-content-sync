Submit immediately after pasting, and stop retrying. Small diff, and the reasoning is @tobiu's: a successful keystroke into the target's text field *is* the confirmation, so a focus race inside the sub-second gap to submit is not worth the damage the machinery caused on every ordinary message.

**The retry loop was a cause of the symptom, not a mitigation.** The script pastes and only afterwards reaches steps that can abort, so a retried attempt can leave attempt N's text in the field while attempt N+1 aborts at an earlier guard. Text present, no submit, no error — and retrying makes that *more* likely. `deliverOsascriptWithRetry` → `spawnOsascriptOnce`: one attempt, no loop, no 800ms backoff.

**What I deliberately did not touch, and why:** the ten `assertTargetFrontmost` sites. They gate **typing** and are what stops a wake being pasted into another seat's window — a real harm this path's own history records. Guards stay; only the retry goes.

**One classification I kept against my own first instinct:** a failure at a *post-submit* guard (user-input restore) still reports `delivered`, because `key code 36` has already fired and the wake was submitted. My first pass removed that too, on the theory that `delivered` should mean "the script ran clean." That was me over-applying the directive into a correctness regression — it would turn real deliveries into `failed`, and an existing spec pins it. Caught before pushing.

## A confirmed inert guard, found while chasing the submit boundary

The retry removal is one half of this PR. The other is a defect I found by reading the path the submit actually takes, and it is a **guard that could never fire**.

`buildDialogGateArgs` read the focused element with:

```applescript
set focusedRole to role of focused element of window 1
```

**That is not valid AppleScript** — `focused element` is not a term. Verified two ways: the minimal expression, and the exact emitted gate script, both fail to **compile** with `-2741` (*Expected end of line but found identifier*).

A compile error is not a runtime error, so the surrounding `try` cannot catch it — the script never runs at all. The `interactive dialog pending` branch below it is therefore unreachable, the caller's message match (`/interactive dialog pending/`) does not match a compile error, and delivery **fails open**. Every delivery since this gate was written bypassed the check it documents as armed.

**Why it matters for submit, in the operator's own frame:** a wake that lands in the prompt field and submits *is* an operator prompt. The gate exists precisely to notice when that is not true — when focus is some non-text element, an operator dialog owns the input path, and typing a wake plus Return goes to the dialog instead of submitting. That is the one place the code could have noticed "this Return will not submit", and it was structurally incapable of noticing.

Fixed by reading the focused element as the AX attribute it actually is:

```applescript
set focusedElement to value of attribute "AXFocusedUIElement" of window 1
set focusedRole to role of focusedElement
```

**Not claimed:** that this fixes the submit gap. It is a confirmed defect with a confirmed inert mechanism, and it is a plausible contributor — but "plausible contributor" is exactly the overclaim this PR has already been corrected for once. The falsifier for RA-1 is still the native turn-start witness, and it is still owed. Note also a real behaviour change: a gate that now fires will start **deferring** deliveries when a dialog is genuinely up, where before it never could.

**The test is a compile, not a mock.** `osacompile` is pure syntax and needs no Accessibility permission, so it runs where the probe itself cannot. It compiles the argv the code actually emits, and asserts the invalid construct is gone. Red on the old construct, green on the fix.

Resolves #712

A seat's PAT is presented only to the forge host it was stored for. This is leaf 2 of #684 (GitLab parity).

- **`FleetRegistryService.defineAgent`** takes `forge` and `forgeHost`:
  - GitHub, the default, records neither, so existing rows are unchanged.
  - A GitLab seat records `forge: 'gitlab'` and its instance's bare `https` origin, beside the PAT.
  - Only `defineAgent` writes these fields. `updateAgent` (the path `setRepo` and `setAvatar` use) patches `metadata` only, and `configureAgent` allowlists its fields, so no scoped verb can re-point where the PAT goes.
  - The host is validated as an origin whose hostname is `[a-z0-9._-]`, so it can key git's `-c` config verbatim. A parser admits `=` in a host, which git would split on. A refusal never echoes the host, which could carry a token in its userinfo.
- **`gitCloneCommand`** takes the credential's origin (default `https://github.com`). It presents the PAT only to an `https` URL with no userinfo on exactly that origin. The child's token variable becomes `NEO_SEAT_FORGE_TOKEN`. GitLab accepts any non-empty username beside a PAT, so `x-access-token` stays.
- **`startAgentProvisioned`** threads the row's `forgeHost` through `ensureAgentRepo` and `provisionAgentRepo` for the working repository and every extra.

Why the binding is load-bearing: `setRepo` is a wire verb. If the clone followed the working repository's host instead, one re-point would send a seat's PAT to a host of the caller's choosing on the next start.

Evidence: L2 (unit, red-first). Residual: AC-4 (installed, owned by #684).

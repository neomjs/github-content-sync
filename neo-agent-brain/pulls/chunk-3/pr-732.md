The first-run recipe, its host-owned record and the host effects — the Brain half of Epic neomjs/neo-agent-institution#351's points 1 and 2 under ADR 0041. Three modules beside the plane readers and probe in `ai/services/fleet/` (the sibling pattern the ticket names; no new folder) and one CLI beside `initServerConfigs.mjs`:

- `setupRunRecord.mjs` — the record: schema 1, `{runId, recipeVersion, target: {planeId, dataRoot, endpoint}, consents, receipts, history}`; bound by the plane id with the data root as corroborating evidence (`describeBinding`: the same id over another root is `target-mismatch`; a run holding no root expectation binds on the id); `retireCurrentProof` moves consents and receipts into readable history on a target or version change; `readSetupRecord` names an unreadable or malformed file so a run starts fresh and says so. Pure, no writer.
- `hostEffects.mjs` — the ONE writer (`persistSetupRecord`, owner-only, atomic) and the three v1 effects: `write-env` (the plane carrier, 0600), `write-secrets` (0600), `compose-up` (`docker compose -p <project> --env-file <carrier> -f … up -d --wait` in the checkout's `deploy/cloud`). `applyEffect` writes a `pending` receipt before a handler and `accepted` after, so a crash in between is a `pending` receipt on disk: a resume marks it `reconcile-required`, never calls the handler, and only `settleReceipt` with an `ok` observation that matches the target settles it. An accepted receipt for the same input never re-runs; a handler without an executable local handler is an `operator-action` receipt. `recordConsent` stores a choice or a reference (short scalar) — the record has no slot for a secret.
- `firstRunRecipe.mjs` — `RECIPE_VERSION` 1, ten steps (placement · preset · plane-credential · advanced[folded] · write-env · write-secrets · compose-up · served-plane · validation · done), `evaluateRecipe({target, record, observers, presets})` pure over injected observers: a question reads the record's consent, an effect reads the fresh observation of its result BESIDE its receipt (a receipt alone is never green; a changed or vanished result fails; a pending receipt is reconcile-required even when the result is observable), an observation reads its owner. `recommendPlacement` is the headroom rule: recommended only above `HEADROOM_BYTES` (4 GiB) host margin with a non-negative guest margin, a bare fit is possible-not-recommended with its margin shown, a `candidate` preset (no recorded floor) is never recommended by default, the probe's refusals ride through unchanged. `exitCodeFor`: 1 on any failed or reconcile-required step, else 0 on a green terminal step, else 2.
- `ai/scripts/setup/firstRun.mjs` — the CLI renderer: reads or creates the record (retiring a mismatched binding into history, out loud), evaluates, answers the pending questions (TTY only), settles reconcile-required effects when the served plane matches, performs the effects through the module, re-evaluates, prints text or `--json`, exits with the disposition. No AiConfig bootstrap (it runs before any container exists, like the prescriptions entrypoint); the setup root is `--setup-root` with `~/.neo-ai/setup` as default, `NEO_HOST_SETUP_RECORD_ROOT` overriding it the way the prescriptions root is — read once inside `parseArgs`. Production observers: the placement probe, the carrier and secret files by digest and mode, the compose project, the served plane through `runHealthcheck`. `--fake-host <file>` is the declared test seam.

Evidence: L2 (pure modules over injected observers and hosts; the CLI runs as a child process on a fake host) → L2 required (AC-1…AC-5). Residual: AC-6, Residual-Owner: neomjs/neo-agent-institution#351.

Change class: capability — four new files, three new specs, no existing file touched.

## Deltas from ticket

- Placement is an observation with a recommendation, not a question: v1 has one placement (this host) until the cloud bundle leaf (#697) adds a second answer; the CLI asks two questions (preset, credential) and folds `advanced`. The ticket's "three questions" count includes placement.
- `hosted` has no recorded quality floor yet (#714), so the headroom rule shows it as *possible* on every host and recommends nothing on the 32 GiB tier — honest until the floor instrument records a hosted run; the spec pins it.
- Validation without a consented preset reads `ok` with the observed dimension reported (an attached plane's dimension is what it is); with a consented preset a dimension mismatch fails.
- The production `validation` and `done` observers are not wired yet (the recipe reports `unknown`, never green); the provider round trip and the first persistence are #86's bar and ride the next leaf with the guides. The served-plane observer uses `runHealthcheck` with `healthy,degraded` (a matching target is not readiness).
- The CLI prompts read the credential as a FILE PATH (an existing file holding the PAT), so no secret value ever crosses the terminal or the record; the PAT reaches the carrier (`GH_TOKEN`) and the secret file through the effects.
- No `ai:*` npm entry yet — the operator runs `node ai/scripts/setup/firstRun.mjs`; the entry rides the guide leaf (#86) with its script-plane declaration.
- Source comments name the decision ("bootstrap-record decision §2.x") rather than the ADR number: the archaeology checker treats `ADR NNNN` as provenance; the ADR mapping is here.

**Author self-finding (2026-10-02, drawing #384's card from this PR's real output): the placement step misstates its cause on the likeliest outside host.**

On the placement probe's own 32 GiB fixture (14 GiB other use, 16 GiB Docker VM → 15.5 GiB host budget), `recommendPlacement` is correct row by row:

```
possible  hosted       host margin 13.0 GiB · no recorded quality floor: a candidate, never recommended by default
refused   local-small  host margin −2.2 GiB · the host budget falls 2.2 GiB short
refused   local-full   host margin −5.9 GiB · the host budget falls 5.9 GiB short
```

The step's reason is `no preset clears the headroom; possible: hosted`. That claims a headroom shortfall which no row has: hosted clears the 4 GiB headroom by 13 GiB and is only possible because it has no recorded floor, while the local presets are refused outright. The step's summary (`the host bears a supported preset with headroom`) is also false here, although the status reads `ok`.

Fix, folded into my response to the review rather than moving the head mid-review: the reason names each possible preset's actual cause and the refusals, and the summary stops claiming "supported". The status stays `ok`, because the operator may still choose a possible preset explicitly. An arm on this exact fixture goes red first.

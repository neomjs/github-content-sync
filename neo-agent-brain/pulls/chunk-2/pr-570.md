Resolves #568

🌿 The runtime now asks the Memory Core one question every half minute instead of the whole diagnostic every ten seconds, and "is it serving" stopped being the service's biggest customer.

The two MCP-probed services' compose blocks move from `10s / 10s / 12` to `interval: 30s`, `timeout: 15s`, `retries: 4`: a third of the probe calls. Docker starts the next interval after a check completes and reports `unhealthy` after `retries` consecutive failures, so a dead service is reported within 120–180 s (checks failing at once … every check running to its timeout) instead of 120–240 s; the timeout covers a contention-inflated interpreter start (the probe's own timing split). The local overlay overrides only `test`, so it inherits the cadence. `mcpHealthcheck.mjs` calls the `healthcheck` tool with `freshObservability: false`: on mc-server, `HealthService` answers from its cached healthy payload inside its five-minute window instead of re-running its Chroma probe and inspection on every tick (a degraded or unhealthy result is never cached, so recovery still reads fresh); the MC tool wrapper's own state reads — drain, corpus projection, deployment inspection, vector-generation health — still run on every call and are the tool's own cost, out of scope here; kb-server's `healthcheck` declares no such option and ignores the field (a live call with it succeeded on the plane), so there the cadence is the whole saving. The compose-shape spec pins the exact cadence and the worst-case bound; a KB arm pins the absent option.

Evidence: L2 (unit: the probe's call shape, the exact-cadence arm with its worst-case bound, the KB schema arm) → L4 required for AC-3 (one hour on the recreated plane). Residual: AC-3, Residual-Owner: #64 (AC-9; ledger row in comment 5854871745).

Micro-review eligible: contained — three numbers in two compose blocks, one boolean on the probe's tool call, and the arms that pin them; no consumed shape changes.

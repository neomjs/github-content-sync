Resolves #485

The corpus now carries each origin's release notes, and `syncNotes` writes again:
- `--corpus-only` runs the `releaseNotes` facet into `<root>/<repo>/release-notes/`. The destination guard holds that folder inside the origin, as it does for the other facets. `includeReleaseNotes` is gone, since no caller passed `false` any more.
- When notes are wanted, `fetchAndCacheReleases` takes its fast path only if every in-window note is on disk with a cached hash; otherwise it fetches the bodies. The published corpus caches its 1196 releases as `{publishedAt}` only, so flipping the flag alone would have published an index of ~168 notes, no note files, and exit 0.
- `syncNotes` reads the cached hash before anything assigns it, and records a hash only after the write. Through `SyncService` it had skipped every release since neomjs/neo `322064b1eb` (#16011, 2026-07-26), because `metadata.releases` holds the same objects.
- A note that can't be written, or that has neither a body nor a file on disk, fails the facet. The run exits nonzero and nothing is published.
- The three changed specs join `brain-unit.yml`'s run list, so CI executes them.

Prescription checked: `ai/services/github-workflow/sync/ReleaseNotesSyncer.mjs` owns the concern. The ticket's first prescription, flipping the corpus flag, was necessary but not sufficient; see Test Evidence.

Evidence: L2 (unit arms plus the real CLI child against scratch corpus roots) → L3 required for AC-4 (a published corpus revision). Residual: AC-4, Residual-Owner: neomjs/neo#19157 (the release-notes window; this is its first step).

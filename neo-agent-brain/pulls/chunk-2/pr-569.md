Resolves #567

🌿 The channel built to see a plane die had been blind since it shipped, and from now on a read that could not look says so instead of saying "nothing died".

Two fixes on one channel. `DeploymentRuntimeAccessService` now spells the `since` / `until` bounds of `/events` and `/containers/{id}/logs` the way the Engine API takes them — Unix seconds with the RFC3339 fraction carried verbatim (`toDockerQueryTime`; Docker's inspect stamps hold nanoseconds and `Date.parse` keeps milliseconds, so the fraction never passes through it) — instead of the RFC3339 the `docker` CLI converts and the daemon refuses (`strconv.ParseInt … invalid syntax`, Docker 29 / API 1.53, reproduced on the plane's socket); the receipts still echo the RFC3339 bound the caller supplied, so the wire interval and `appliedSince` / `appliedUntil` name the same instants and their consumers are unchanged. `selectLastServiceDeath` now reads the service entry's own `deathRead` beside its `deaths`: a failed read is `unavailable` with the bridge's reason and a bridge-disabled channel is `disabled`, so the healthcheck's `lastDeath` can no longer say "observed, no death" for a service whose event read failed every cycle — which is what it said 48 minutes after this morning's mc-server OOM abort.

Evidence: L2 (unit: query-shape arms on both endpoints including two nanosecond bounds inside one millisecond, the projection's failed-read arm, the bridge and both healthcheck suites) → L4 required for AC-3 (a real death recorded on the plane). Residual: AC-3, Residual-Owner: #64 (ledger row in #64 comment 5854871745).

Micro-review eligible: contained — one time-spelling helper on two query strings and one guard in a projection, no consumed shape changes; the vocabulary (`unavailable` / `disabled` + reason) already exists.

## Deltas from ticket
- The receipt fields keep the RFC3339 spelling (the ticket left it open): `appliedSince` / `appliedUntil` are read as timestamps by the bridge's log-slice and event-cursor consumers, so only the wire spelling changes.
- A snapshot written before `deathRead` existed keeps today's observed reading (no `deathRead` field → `available`), so an older plane's healthcheck does not turn `unavailable` on upgrade.
- The ticket's conversion (`Date.parse(stamp) / 1000`) was wrong above millisecond precision; the ticket's Fix and AC-1 now say what ships (found in R1).

## Test Evidence
The daemon's refusal and the accepted spelling were reproduced against the plane's Docker socket (Docker 29.2.1, API 1.53): `GET /events?since=2026-09-27T07:20:00Z…` → `{"message":"strconv.ParseInt: parsing \"2026-09-27T07:20:00Z\": invalid syntax"}`, the same for `/containers/{id}/logs?since=…`; `since=<unix>.5` → 200 on both. The plane's live snapshot carried the same message under mc-server's `errors[]` with `deathRead.status: 'unavailable'` while the healthcheck read `lastDeath: {status: 'available', record: null}` (receipt on #64, comment 5854182787).

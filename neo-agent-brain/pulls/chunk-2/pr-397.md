Resolves #398
Refs #306

JSONL backup metadata currently presents a client-process Chroma path as the server's physical storage. The descriptor now records `kbChromaCoords.path` and `mcChromaCoords.dataDir` as `null`, each with `storageReason: physical-storage-not-observed`. Resolved endpoint coordinates and shared topology remain available to consumers; logical restore continues to import the bundle's JSONL data.

This delivers the metadata child of the wider storage-authority repair. Daily compaction, physical execution and recovery remain tracked by the open parent, `#306`.

Evidence: L2 (actual bundle metadata serialization and isolated SDK restore controls) → L2 required for #398. Residual: none for this delivery child.

### 🔬 Depth Floor

**Challenge** — three, all non-blocking, all V-B-A'd:

1. **AC-2's new arm cannot fail today, and nothing in it says so.** `restore.mjs` reads exactly two topology keys — `meta?.topology?.chromaUnified` and `meta?.topology?.shared_topology` (`:1211`–`:1212`). I ran the census: `git grep -E 'kbChromaCoords|mcChromaCoords|storageReason'` over the whole tree at `d9a2a03` returns **five hits in `backup.mjs` and zero consumers anywhere else** — the two spec files are the only other holders. So `null physical storage coordinates preserve JSONL restore topology` passes identically for the patched value, the *pre-patch* value, or no key at all. That is genuinely the right proof of AC-2 as worded ("restore accepts that descriptor"), and it has real teeth *forward* — the day someone makes restore read `.path` it goes red. But a later reader will mistake it for a coupling test. One comment line citing `restore.mjs:1211-1212` converts it from a control that looks like it passed into a stated non-coupling pin.
2. **`storageReason` is an invariant.** Both objects hardcode `'physical-storage-not-observed'` unconditionally, so the field can never distinguish *not observed* from *observed and genuinely absent*. That is correct for everything this producer can write today. It becomes a trap the moment #306's physical-compaction work gives some caller real storage authority and the branch here is forgotten — a consumer keying on the reason's presence would read the first observed bundle as unobserved. Worth carrying on #306 rather than here.
3. **The fix deletes information instead of relabeling it.** The configured `dataDir` is no longer recorded anywhere in the bundle. Honest, and no code misses it — but `configuredDataDir` next to a null `dataDir` would have kept the forensic pointer ("which deployment produced this bundle?") while making the same claim. Your call; I am not asking for it.

**Actively looked for and cleared:**

- **`undefined` silently dropping a key.** Removing `?? null` looked like it could turn a missing leaf into a *missing JSON key* (`JSON.stringify` drops `undefined`), which is the silent direction of the error. Falsified: `engines.chroma.host`/`.port` are **formulas** (`ai/configBase.mjs:2690-2691`) over `hostProd`/`hostTest`/`portProd`/`portTest` leaves with non-null defaults (`'localhost'`, `8000`, `18180`). `undefined` is unreachable, and the retained `'host' in ...` assertions pin it.
- **JSDoc deletion.** The old block carried the `chromaUnified === false` legacy-bundle detection and the "refuse to clobber" consequence; the new summary drops both. Cleared — that policy lives at its owner, `restore.mjs:57-58` and `:1198`. One fact, one artifact.
- **Placement.** `npm run ai:structure-map -- --files --loc` — no new module, no new config surface; the change stays in `ai/scripts/maintenance/backup.mjs`, which already owned serialization.

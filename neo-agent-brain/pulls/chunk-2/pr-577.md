Resolves #576

Every agent holds its GitHub PAT, per the operator's ruling that Fleet Manager needs at least one per agent:
- `defineAgent` requires the credential.
- The provisioned start resolves the PAT once, before any checkout, and hands that value to the spawn.
- `start()` refuses a missing or blank PAT on every path, restarts included, so a blank value stored before the requirement cannot start a seat either.
- `onboardPeer` reads the PAT from the variable `--credential-env` names.

An untokened seat's `gh` would otherwise fall back to the machine's keyring account.

Evidence: L2 (unit arms against real registry writes and recording start seams; each new refusal arm red on dev first) → L2 required (AC-1 to AC-4). No AC residuals.

### 🔬 Depth Floor

**Challenge — the one real defect: the documented recovery for an existing row is not executable.**

The Post-Merge Validation says: *"No verb attaches a PAT to an existing row, so each one is re-defined with its PAT."* The first clause is correct, and the second clause cannot be carried out:

- `defineAgent`'s own JSDoc, as rewritten by this PR, states **"Existing ids reject"** and that every edit of an established resident must use a scoped authority — `configureAgent`, `setRepo`, `setAvatar`, or the Brain-only launch override — and must *"never replay this credential-bearing creation surface."*
- `configureAgent` cannot be that authority for a credential. Its `allowed` set is exactly `['id', 'harnessType', 'mcpServers', 'mcpTarget']`; anything else hits `reject('unsupported field …')`, and its JSDoc says credentials are *"mechanically rejected."* That refusal is the right design — I am not asking you to widen it.
- This diff adds no new verb that writes a credential.

So a row that exists without a PAT has **no** path to acquiring one, and therefore can never start again. Three ways to close it, any one sufficient: add a narrow `setCredential(id, credential)` as a first-class scoped authority (it fits the existing `PUBLIC_SENSITIVE_KEY_RE` discipline and the two-store transaction already in place); or let `defineAgent` accept an explicit re-credential for an existing id under a scoped authority, which is a one-key widening of the "existing ids reject" rule; or — minimum — correct the Post-Merge text to the recovery that actually works today (remove the row, then define it) and say plainly that a populated registry has no in-place upgrade. **Today this is latent, not live**: #573 measured that no seat exists under the old layout and @neo-opus-vega reports the plane's fleet registry is *empty*, so there is nothing to migrate. It becomes live the moment the operator adds the first agent without a PAT — which is the next thing that happens on the FM-connected goal.

**Second watch, cheap to state:** `onboardPeer` puts the variable *name* in argv (`--credential-env <NAME>`) and the value in the environment. That is the correct split — the name is visible in `ps` and carries no secret — and the help text says so. Worth keeping that sentence if the flag is ever renamed, because the safety property lives in the prose as much as in the code.

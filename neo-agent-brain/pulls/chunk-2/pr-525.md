Resolves #508 (phase 1 of 2 — the false assurance)

## The defect

`check-aiconfig-test-mutation` carried the rule id **`B4`**, and ADR 0019's forbidden-pattern table marked B4 — *"SAFETY-CRITICAL — runtime writes to `AiConfig`"* — as `` `[guarded: check-aiconfig-test-mutation]` ``.

The implementation matched only `storagePaths`, `database`, `collections`, `logPath`. It had **two** incidental references to `openAiCompatible`, neither of them detection logic, and the result field was named `dbPathHits`.

So asking "is B4 enforced?" against the ADR's own table returned a **false assurance**. That is worse than an absent guard: an absent guard is a known gap, while a guard that reads as coverage converts an audit question into a wrong answer. I asserted the weaker version of this on #501 — "it never flagged the writes it exists to catch" — which was wrong in mechanism, and this is the correction.

## What this PR does, in the order that stops the false claim first

1. **The gating rule's id is now `B4-DB-PATH`.** It says what it gates. A rule that no longer overclaims is the whole minimum fix.
2. **The full B4 scope ships as a second, tested, REPORT-ONLY rule** that prints its measured count on every run. The surface stops being invisible *today*.
3. **ADR 0019's B4 row is marked `PARTIAL`** with both halves named, recorded in that record's own amendment convention.

**Report-only is a sequencing decision, not timidity.** Turning the full rule on today would red seven specs whose correct fix is an injected config snapshot, and a gate muted within a day teaches the next reader that the gate is optional. Per-leaf escape markers are explicitly *not* that story — they are how 146 leaves becomes 146 unexamined exemptions. Promotion to gating is phase 2, and it is a wiring change in one place.

## Measurement

Via this file's own `codeMask` and root grammar — an identifier ending in `Config`, any leaf, an assignment:

| | |
|---|---|
| shared-config writes in `test/**` | **598** |
| distinct leaves | **146** |
| spec files involved | 53 (30 hits already allowlisted) |
| top 7 files | ~336 of 598 |

The CLI and an independent probe agree exactly, which is the only reason I trust either. **Concentration is the load-bearing fact**, and so is the leaf mix: the dominant class is config-**varying** tuning knobs (`openAiCompatible.*` retry/timeout leaves, `vectorDimension`, `remSleepBatchLimit`) — precisely the class this file's own header already names as having no by-construction story yet.

## Corrections to my own published numbers

I reported **"356 writes across 81 leaves"** in #508's body and in the #510 PR body. That came from a `grep` matching `aiConfig.` literally, which misses every other `*Config`-shaped root and all bracket access. **The accurate figure is 598 / 146.** My per-file figure for the retry spec (80 writes / 12 leaves) was measured directly and is exactly right — the aggregate was the crude one, not the specific claim.

The first probe also reported a confident **0 / 0**, because I filtered matches with `mask.includes(' ')` when `codeMask` returns a **boolean array**, discarding every hit. The probe now asserts a positive control: a known code-write is found and a known comment-write ignored, so a future zero cannot be a broken probe wearing a measurement's clothes.

## Review focus

- **The id change** is the fix; everything else is sequencing. If you think `B4-DB-PATH` is the wrong name, that is the thing to argue.
- **The allowlist asymmetry is deliberate**: an allowlist entry justifies a DB-path mutation specifically, so it suppresses the gating rule and does *not* suppress the report-only one. Pinned by an arm.
- **I did not touch the retry spec.** 80 writes / 12 leaves wants an injected config snapshot, not twelve seams; that is phase 2 and a different change.

Residual: promoting `B4-SHARED-CONFIG` to gating once the top seven specs have a real injection story. Tracked on #508.

Resolves #504

🌿 Stepping aside for a starving lane now means the lane runs, and a courtesy that ran nothing has become unsayable.

The picker swaps the eligible representative for the registered waiter it would yield to at admission. `MaintenanceBackpressureService.findStarvingWaiterToPromote` is the selection-time twin of the admission gate: the same ledger read, the same `findWaiterToYieldTo` rank gate and starvation bound, evaluated for the would-be winner and restricted to waiters that are candidates this poll; `selectByPriority` reads it through `policyContext.findStarvingWaiter` beside the bootstrap oracle, fail-open, and the `{winner}` shape is unchanged. The admission-side yield stays as the backstop for out-of-process acquirers. The coverage warm-up from #498 is keyed on the lane being owned (in the registry) and enabled instead of running, so the polls after a yield no longer let the snapshot expire and re-grant rank 1b.

Measured on the local plane with #498 deployed: at every tenant slice end the lane yielded (`… yielding to starving dream (deferred since 16:20:10Z)`), re-acquired 54 s later, and the dream never ran; with the tenant lane paused, `memory miniSummary backfill` yielded the same way and nothing ran. From ~16:50Z no heavy lane ran at all until the fairness threshold was raised by hand at 17:57Z, after which the dream ran 17:58:26–18:00:44Z.

ADR 0022: this acts at release-time selection, the ADR's own lever (§2.1), keeps `{winner: Object|null}` (§2.4 AC-2), preempts no running holder, and opens no §2.5 escalation path.

Evidence: L2 (red-first pipeline arms through the real service and the real waiter ledger; the plane symptom reproduced, and the plane's run once the threshold was raised) → L2 required (AC-1, AC-2, AC-3). Residual: AC-4's live run between two tenant slices, under Post-Merge Validation.

agent-preflight: hosted, ran clean.

### 🔬 Depth Floor

**Challenge 1 — the promotion's reach depends on a registry-order property no arm pins.** After `topEligible = promote(topEligible)`, the fallback loop returns the first candidate that either lacks `taskMeta` or *is* the representative. So a non-heavy candidate sitting earlier in registry order than the promoted waiter wins, and the promotion becomes a no-op for that poll.

I could not turn this into a defect: a winner that lacks `taskMeta` never reaches the lease gate, so it never yields and never starves anyone — which makes the no-op benign in the case I can construct. But "benign in the case I can construct" is not "pinned", and the fix's reach now rests on that ordering. **Falsifier for a future session:** put a candidate without `taskMeta` ahead of the waiter in the registry and assert the promotion still fires. If it does not, the arm is wrong about the fix's coverage; if it does, the property is worth pinning.

**Challenge 2 — `promote(bootstrapWinner)` reads as single-layer but is double-gated.** The call site sits after the priority-0 early return, so a priority-0 winner is never displaced. And the seam's own rank gate refuses to let a lower-ranked waiter displace a bootstrap-critical winner — which is exactly what AC-2's arm pins and proves. So the behavior is right and the layering is right. The cost is purely readability: a reader can reasonably think an ordinary waiter can displace a bootstrap winner at that call site. A half-line in the picker's docblock saying the seam re-checks the rank would cost nothing and would save the next reader the derivation I just did.

**Documented search — things I looked for and did NOT find.** A second fairness policy or a second starvation constant anywhere in the diff (the reuse is literal; one definition each). A widened warm-up boundary — checked `enables.tenantRepoSync` is populated from the real `orchestrator.tenantRepoSyncEnabled` at `pipeline.mjs:155-163`, so the gate reads a live production value and not a field only the tests set.

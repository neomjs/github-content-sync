Resolves #583

`fleetGraphScene` now serves the whole graph the viewer may see, with the Golden Path route as its overlay, instead of the route's 150-node neighbourhood. One Memory Core read, `get_graph_scene` (`GraphService.readSceneGraph`), answers it under the graph's row-level security. The Fleet expands it into the scene shape the FM already lands, so the Institution needs only the Brain pin bump.

On the live plane (the method's logic run read-only in the MC container), a viewer with no identity gets 145,743 nodes and 213,516 edges. 68,277 of those nodes have no visible relation, and `counts.unlinked` says so. The read takes about 5 s. The answer is 17.4 MiB, 42.4 MiB on the MCP hop (text plus structured content), and the scene to the FM is 43.4 MiB. Read as me, the graph is 164,465 nodes.

Evidence: L2 (unit arms over a real SQLite GraphService and over the source; the live figures replicate the method read-only) → L2 required for AC-1 to AC-4. Residual: the deployed call and the installed render, Residual-Owner: #533.

## Deltas from ticket
- **A columnar answer.** A tool result crosses as pretty-printed text and as structured content, so the object shape would have cost well over 100 MiB on that hop. The columnar form costs 42.4 MiB there, and the Fleet expands it.
- **A paged read.** About 5 s of synchronous SQLite would stall the Memory Core's one thread for every agent. The read pages by keyset (5,000 rows) and yields between pages. It is therefore not one atomic snapshot, and the method says so.
- **`counts.unlinked`.** Nearly half the visible nodes (mostly FILE and DIRECTORY rows) have no visible relation. They stay in the scene, the count names them for a layout that places them apart, and a budget cut drops them first. At both layers the counts describe the lists delivered, recounted after every budget or byte cut (Emmy's Round 1: a byte cut had left `unlinked` above the node count).
- The byte trim was quadratic, with a full stringify per dropped edge. It is linear now, and drops nodes once no edge is left to cut.

### Three things this settles, two of which I had wrong

1. **Edges are node-id pairs, and the consumer does the indexing.** I asked Grace whether the "edges-as-index-pairs" contract was load-bearing, which framed it backwards. The merged consumer builds `at` from *sorted ids* and gates every edge on `at.has(from)`, so an **index pair would fail that check and the edge would be silently dropped** — not rendered wrongly, silently gone. If your read emits indices anywhere, that is the bug that would hide.
2. **A budget cut that keeps a route id but drops its node is a supported state.** `GraphSceneEnvelope.resolveRouteId` filters `route.filter(id => held.has(id))` precisely because *"a budget cut can keep a seed in the route and drop its node."* So a paginated read does not need to guarantee route/node correspondence — it needs to guarantee the **order** of the ids it does return. Node-size scaling reads seed rank directly, so **rank order must be stable across pages**; a page that returns seeds in a different relative order will make node sizes jump between reads.
3. **Route ids may be origin-qualified.** The route can carry `neomjs/neo#issue-9853`; a bare `issue-9853` resolves only when exactly one origin holds it. Worth knowing if the producer qualifies ids, because a bare id that is ambiguous deliberately resolves to nothing rather than guessing.

Resolves #466

An OOM-killed container read as a clean exit to every observer the swarm consults. `docker inspect` describes the *restarted* run, so `ExitCode 0` / `OOMKilled false` survive a kill; the new cgroup's `memory.events` resets `oom_kill`; the process runs no handler. Only the Colima kernel log and Docker's bounded event buffer knew — and a 1 Hz sampler rotated the `die` events out within minutes, so the swarm's own readers could not recover them.

## Deltas

- **Bounded event read** on the socket the bridge already holds. Pages a finite `since`..`until` window, filters on the orchestrator's own project label, never opens the streaming socket. `includeEvents` + `eventLookbackMs` are additive config leaves; zero event cost when disabled, and the holder's single-live-watchdog topology is untouched.
- **Per-service cursors and capped death history** in the snapshot, so a container never seen alive is still attributable and a long-lived service cannot grow unbounded state.
- **OOM→die folding** into a `lastDeath` diagnosis that both MCP healthchecks surface verbatim, with the raw event retained as the evidence channel behind the summary.
- **`selectLastDeath()`** extracted so the Memory Core and Knowledge Base projections cannot drift.

Deliberately out of scope: no unload/load actuation, no `replacement-required` terminal, no rehydration of the process map on orchestrator restart. The recovery actuator's authority boundary is unsettled, and this PR is detect-side only.

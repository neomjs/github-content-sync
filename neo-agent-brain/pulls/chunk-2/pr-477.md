Resolves #476
🌿 *A graph WAL can no longer keep a burst's size after the burst is gone.*

SQLite reuses a WAL file after a checkpoint instead of shrinking it, and nothing set `journal_size_limit`. The plane's graph WAL stood at 9.7 GB around 3.3 MB of live frames. `SQLite.mjs` now sets the limit to 64 MiB on every graph connection, so a checkpoint that resets the log also truncates the file. This is disk hygiene, not a performance fix.

Evidence: L1 (a spec on the real `initAsync` path, with a control run with the pragma removed). Residual: none.

## AC Evidence
| AC | Coverage |
|---|---|
| AC-1 | CI: `SQLiteWalSizeLimit.spec.mjs`, "every graph connection limits the WAL to 64 MiB", reads the pragma back as 67108864 |
| AC-2 | CI: `SQLiteWalSizeLimit.spec.mjs`, "a checkpoint that resets the WAL truncates the file to the limit". Outside CI: with the pragma removed, both tests fail. The pragma reads `-1`, and the WAL stays at 80,096,952 bytes |

## Deltas from ticket
None substantive. The spec is added to the Brain Unit run list, because the `--list` step only collects it.

## Test Evidence
- **The control run** in the AC-2 row.
- **All graph unit specs:** 175 passed locally.
- **The better-sqlite3 probe** (#476) shows the mechanism outside the store. Without a limit, a 50.9 MiB WAL is still 50.85 MiB after a checkpoint and reset. With an 8 MiB limit it is truncated to 8.00 MiB.

## Post-Merge Validation
One receipt, after the next plane recreate: the graph WAL truncates to at most 64 MiB at its first checkpoint reset, and the recreate receipt records its size.

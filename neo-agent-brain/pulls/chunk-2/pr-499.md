Resolves #496

The Fleet cockpit can now read the computed Golden Path through one wire method. `fleetGoldenPath` is a read-observe verb on `FleetControlBridge` backed by a `goldenPathSource` slot (the `tasksSource` shape, the same honest not-wired default), wired at the fleet-server boot from three existing truths: the synthesizer's `computed-route.json` sidecar beside the handoff (validated with `validateComputedRouteResult`, passed through under the producer's own `status` / `freshness` / `capturedAt` / `expiresAt` / provenance, items in producer order — never re-ranked), the corpus-projection admission for the `computed-golden-path` consumer (current / last-known-good / withheld, the contract `get_context_frontier` already applies), and the REM pipeline counts through the same operation boundary as the tasks source. Each axis answers as itself: a missing, unreadable or contract-invalid sidecar is a typed degraded reason, a failed REM read is its own unavailable axis with a redacted detail, and the admission keeps the contract's own reason code. The wire vocabulary, the S1 slice ledger (`awaiting-s3`, like `fleetTasks`) and the scope-class ledger (`read-observe`) carry the verb; both parity specs list it.

Evidence: L1 (unit: the source's axes and envelope, the wiring, the bridge default, the ledgers) → L2 required (AC-1, the wire answer from a running fleet server) — a post-merge row until a plane pin carries this, since the composed server's S1 policy degrades every `awaiting-s3` verb by design and the dev bridge server is what the cockpit reads today. Residual: AC-1's live read.

## Deltas from ticket

The current setup already uses a free port and unique paths, so this repairs resource leakage without claiming to fix the historical suite failures.

A durable generated-directory receipt is necessary because the setup worker can exit while the Playwright runner remains alive. The receipt therefore records the setup worker's parent runner, with POSIX process birth tokens to reject PID reuse. Its log path is tied to the same data-directory stem; a per-candidate lock prevents concurrent reaping. Failed receipt writes stop the newly spawned owned process before cleanup.

Windows and unavailable identity probes conservatively skip inherited cleanup. Old leftovers without a receipt remain unknown. Explicit caller data remains caller-owned. No production daemon, ingestion configuration, or cross-checkout cleanup is changed.

### 🔬 Depth Floor

**Challenge**: One, and it is a proportionality question rather than a defect.

**+498 / −10 of fixture code to reap leaked test processes.** Birth tokens to defeat PID reuse, an exclusive lock per candidate, a group-emptiness requirement, and a re-read at the stop edge — that is a lot of machinery for a suite that leaks servers.

**I think it is justified, and I want the reasoning on record rather than assumed:** the cost is not proportional to the *problem* (leaked processes), it is proportional to the *blast radius of being wrong* (killing a live process someone else owns). Every one of those four mechanisms exists to prevent a false positive, and a cheaper reaper — pattern kill, age heuristic, path heuristic — buys its simplicity by accepting exactly that risk. AC-5 refusing pattern kill outright is the same judgement stated as a constraint.

Resolves #552

🌿 The roster stops paying for the whole mailbox on every glance, so a cockpit left open can no longer make the swarm's memory unreachable.

`who_is_online` derived its review-load trail by selecting every `MESSAGE` node and parsing each row's full blob in JS on every call (29,814 rows on the local plane; the projection then dropped everything older than its 30-day horizon). With the cockpit ticking it every 15 s, mc-server's single thread sat at 83–99 % all day and every peer's call queued 5–10 s. Two changes: `_readReviewLifecycleLoad` now bounds the read to the projection's own horizon in SQL and projects the four fields it reads with one `json_extract` per row, so no blob reaches JS and no row outside the window is touched; `SQLite.mjs` declares two idempotent expression indexes over the JSON column — a partial `sentAt` index over `MESSAGE:` rows that turns the trail read into a range search, and a `label` index that every `json_extract(data, '$.label') = ?` read (AgentIdentity, WAKE_SUBSCRIPTION, MESSAGE, …) now rides. Nothing the derivation returns changes: `deriveReviewLoad` already skipped rows below the floor before building any loop state, so the SQL bound is the same set.

Evidence: L2 (two arms on the in-memory storage; one red at dev) + L2 (the query timed on a throwaway copy of the live 3.2 GB graph, below) → L4 required (the deployed plane's tool metrics, AC-1 / AC-3). Residual: AC-1, AC-3, Residual-Owner: #64.

### 🔬 Depth Floor

**Challenge** — three, all measured, none blocking:

1. **The read's type assumption is stricter than the projection's, and the failure renders as zero.** `deriveReviewLoad` accepts any `sentAt` that `new Date()` parses, including epoch numbers. The SQL bound compares `json_extract(...) >= ?` against an **ISO string**. I measured SQLite 3.54.0 directly: an ISO-text value passes the bound (`1`), an **integer** value fails it (`0`) — SQLite orders every number before every text, so `number >= text` is never true. A numerically-stored `sentAt` would therefore vanish from the trail regardless of recency, and `deriveReviewLoad` treats a missing entry as *zero* — the live obligation disappears rather than erroring. **It cannot happen today**: `MailboxService.addMessage()` is the single writer and stamps `Date#toISOString()`, and `wakeCoalescePolicy.mjs:91` already rejects any `sentAt` that is not canonical ISO. So this is latent, not active, and I am not going to inflate it. But this query is the first place that depends on the *storage type* instead of parsing permissively, and the invariant currently lives in a sibling file. Ask: pin it where it is now load-bearing — one arm seeding a non-ISO `sentAt` and asserting it is either handled or refused. Then the safety is a test rather than a convention.
2. **The `EXPLAIN QUERY PLAN` arm tests a near-miss query.** The arm omits `AND json_extract(data, '$.label') = 'MESSAGE'` and projects one path where the shipped query projects four. Your body separately quotes `SEARCH Nodes USING INDEX idx_nodes_message_sent_at` from a 3.2 GB live copy, which *is* the shipped shape — so the claim is verified, just not guarded. One predicate in the arm and the regression becomes CI-visible instead of a one-time receipt.
3. **No write-side number, on the hottest write table.** You give read latency, index size (5 MB) and build time (1.8 s) but not the cost the indexes impose on ingest. `Nodes` takes a row per message, and `SQLite.mjs:143-145` already fans every node write into a `GraphLog` trigger, so each message now maintains two more expression indexes on a process your own numbers show at 83-99 % of a core. The net is very likely strongly positive — the read is 240/hour, the writes are the mailbox — so this is an ask, not a gate. A before/after insert-throughput number on the copy you already have would close it.

Resolves #490

The corpus tenant now reads each origin's release notes:
- **A second corpus route.** `ReleaseNotesCorpusSource` emits one `release` chunk per note, named `<origin>/<file>` (`neo/v13.1.0`).
  - A note's identity is the tag of the item in `<origin>/release-notes/_index.json` whose `path` names it, never a file name. An index that can't say which note is which refuses, as the root index does.
  - `deploy/cloud/kb-config.yaml` declares the route beside the conversation route, and the two split the territory.
- **Ranking.** `QueryService`'s exact-version boost also matches an origin-qualified name. A query for `v13.2.0` therefore still ranks its note first once neomjs/neo#19159 removes the engine's notes.

Evidence: L2 (the real profile runner over a real revision reader bound to a fixture corpus; the vector query over a stubbed collection) → L3 required for AC-3 (the deployed tenant). Residual: AC-3, Residual-Owner: neomjs/neo#19157 (the release-notes window, open past #485, which closes with #491).

## Deltas from ticket
- A separate extractor instead of extending `ConversationCorpusSource`, following the KB's model of one extractor per content family. The ticket's amended note says why, and that failure isolation is *not* the reason: the runner awaits each route with no catch.
- `inferSourceType`'s path prefixes were the first idea for typing. They serve only the lexical rescue of local files. Tenant chunks carry their own `type`, so no path rule changes.
- `QueryService.queryDocuments.spec.mjs` and `KbTenantBootstrapContract.spec.mjs` join `brain-unit.yml`'s run list with the new spec, because they pin this change.
- Merge order with #491 doesn't matter. Without notes in the corpus, the route yields nothing and refuses nothing.

Resolves #532

A provisioned seat published its wake envelope once per hand-copied file and never again. Nothing in
provisioning placed the OpenCode plugin that publishes the envelope on each new session, so the "two
producers, one contract" statement at `ai/daemons/wake/daemon.mjs` had a runbook step behind it rather
than an installer. This makes the generated `write-wake-envelope` hook install the plant itself, which
is the same tmp+rename discipline it already uses for the envelope.

**The plant is inlined as base64, read once at module load.** Base64 rather than a template literal
because the plant is ~19 KB of JavaScript and embedding source in a generated string literal invites
escaping that would break the byte-equality contract *silently*. Inlined rather than copied at launch
because a hook that read the plant from the Brain checkout would make a seat's wake lane depend on a
repository the seat may not have.

## The live red was worse than the ticket assumed

The ticket frames the problem as "provisioning installs nothing". Measuring it found a second, sharper
state on a **live seat**: two plants installed side by side —

```
neo-wake-envelope.js    16129B  Aug  1 19:00
neo-wake-envelope.mjs   19028B  Sep 26 09:20
```

— neither carrying a `GENERATED` marker, and ~3 KB apart. OpenCode loads every plugin it finds and
nothing in the system records which one won. So the real exposure is not only the missing installer;
it is that hand-installing has **already produced an ambiguous install** and no check surfaces it. The
hook now names sibling plants rather than resolving them, because which file is authoritative is not
its call — but a reporter who wants that resolved needs a ticket, and I have not filed one since the
choice of authority is a maintainer decision.

## Deltas from ticket

- **Report-and-skip, never clobber.** A generator that silently overwrote or deleted a file it did not
  place would be a worse failure than the drift it exists to surface, so a differing install is reported
  with both byte counts and left untouched.
- **An unset `XDG_CONFIG_HOME` warns loudly** rather than skipping quietly. The shared-root fallback
  would resolve outside the seat, and a silent skip is indistinguishable from a healthy install — the
  exact failure this change removes.
- **Sibling plants are reported, not removed**, for the reason above.

## Test Evidence

Outside-CI, because the `ai/**` tier cannot run under local playwright at this seat (the Brain-tier
packages are absent, so `unit-brain` skips). The receipt is a **node-module instrument**: the generator
is imported directly and the generated hook is executed as a real child process against a temp seat
home. That measured, by running it:

- fresh install → `plant installed at …`, installed bytes **sha256-equal** to the source plant;
- second run → `already current`;
- appended `HAND EDIT` → `DIFFERS from the generator and was left untouched … (19038B installed,
  19028B generated)`, and the edited bytes were **unchanged** afterwards;
- a `neo-wake-envelope.js` sibling → `OTHER wake-envelope plants present … neo-wake-envelope.js — the
  loaded one is not determined by this hook`, and both files remained;
- `XDG_CONFIG_HOME=''` → `XDG_CONFIG_HOME is unset — the wake-envelope plant was NOT installed`.

The generated hook was also run through `node --check`: the emitted script parses. That check earned its
keep immediately — my first attempt at the generated string was a **syntax error**, caught by parsing
the output rather than by reading what I had written.

**Noted, not changed:** `ai/scripts/lifecycle/hooks/kimi-code/wakeEnvelopeHook.mjs` is the Kimi-harness
sibling, and the plant is an OpenCode plugin so it does not apply there. Two asymmetries are real — the
Kimi hook is a module while this one is a string literal inside the generator, and `normalizeAgentIdentity`
is duplicated inline across both — but both belong to a cross-harness question this ticket does not own.

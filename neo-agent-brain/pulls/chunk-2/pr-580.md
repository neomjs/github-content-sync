Resolves #578

🌿 A receipt says what its write did now, and "the record is no longer present in storage" is no longer something a fresh server can say about a row it just updated.

`narrowWriteResult` returned `Number(result.lastInsertRowid)` as "the GraphLog id the update's trigger wrote", and `writeReceiptField` read that value as the landed flag. SQLite restores `last_insert_rowid()` when a trigger program ends, so after the UPDATE the value is the connection's last PLAIN insert: `0` on a freshly started mc-server — every `mark_read` and `archive_message` answered `status: 'not_applied' … the record is no longer present in storage` from 13:07Z on today's `230593f` cut until the drain projected the first new message — and a stale rowid afterwards, wrong but truthy. The narrow writes now return the Boolean their JSDoc always promised (`changes > 0`), `writeReceiptField` keys `written` / `already-set` / `missing-row` on it, and the receipt vocabulary is unchanged. The own-row acknowledgement the id was meant to enable stays #20's (writer identity on the row); the global-max ack is untouched, its KNOWN-GAP comment now says why the log-id route cannot be built.

Evidence: L2 (unit: a file-backed storage arm that reopens a fresh connection — red on dev, `0` where `true` is expected; the mailbox arm that asserted `> 0` now asserts the Boolean; the receipt, mailbox and graph suites green) → L4 for AC-3 (the first `mark_read` on a recreated mc-server answers `read`). Residual: AC-3, Residual-Owner: #64 (the next cut's receipt; ledger comment 5854871745).

Micro-review eligible: contained — one return expression, one consumer variable, two arms, one CI list line; no wire shape changes.

Resolves #578

🌿 A receipt says what its write did now, and "the record is no longer present in storage" is no longer something a fresh server can say about a row it just updated.

`narrowWriteResult` returned `Number(result.lastInsertRowid)` as "the GraphLog id the update's trigger wrote", and `writeReceiptField` read that value as the landed flag. SQLite restores `last_insert_rowid()` when a trigger program ends, so after the UPDATE the value is the connection's last PLAIN insert: `0` on a freshly started mc-server — every `mark_read` and `archive_message` answered `status: 'not_applied' … the record is no longer present in storage` from 13:07Z on today's `230593f` cut until the drain projected the first new message — and a stale rowid afterwards, wrong but truthy. The narrow writes now return the Boolean their JSDoc always promised (`changes > 0`), `writeReceiptField` keys `written` / `already-set` / `missing-row` on it, and the receipt vocabulary is unchanged. The own-row acknowledgement the id was meant to enable stays #20's (writer identity on the row); the global-max ack is untouched, its KNOWN-GAP comment now says why the log-id route cannot be built.

Evidence: L2 (unit: a file-backed storage arm that reopens a fresh connection — red on dev, `0` where `true` is expected; the mailbox arm that asserted `> 0` now asserts the Boolean; the receipt, mailbox and graph suites green) → L4 for AC-3 (the first `mark_read` on a recreated mc-server answers `read`). Residual: AC-3, Residual-Owner: #64 (the next cut's receipt; ledger comment 5854871745).

Micro-review eligible: contained — one return expression, one consumer variable, two arms, one CI list line; no wire shape changes.

### 🪜 Strategic-Fit Decision

- **Decision**: Approve
- **Rationale**: The premise was not merely "a receipt read as missing" but a **mechanism**, correctly identified: SQLite *restores* `last_insert_rowid()` when a trigger program ends, so a trigger's INSERT never updates the connection's value. The old JSDoc asserted the exact opposite — that the `node_update`/`edge_update` trigger's `GraphLog` insert meant `lastInsertRowid` named "this write's log position". The fix is the minimal correct one — return what the statement can actually prove (`changes > 0`) and delete the false claim rather than hedging it. ### 🔬 Depth Floor

**Challenge — the new JSDoc is strong enough to be over-read, and over-reading it breaks wake delivery.**

`SQLite.mjs:12–13` now says, correctly and emphatically, that `lastInsertRowid` cannot name a trigger-written row. A future maintainer who takes the general lesson rather than the specific one — "this API is untrustworthy in this store" — would delete `:766`'s `{eventId, logId: Number(info.lastInsertRowid)}`, which is a **top-level** INSERT where the rowid is exactly right. That is the over-correction, and it is not cosmetic: `:766` feeds the append-only log's position, and `wokenWatermark.mjs:66–70` treats any non-finite `logId` as *conservatively new* (`!Number.isFinite(logId) || logId > mark`). So a broken `logId` there does not withhold wakes — it makes every coalesced event look new forever, which is a **wake storm** rather than a missed wake, and it would be blamed on the wake daemon rather than on this store. Worth one clause in the JSDoc distinguishing the two (`lastInsertRowid` is unreliable **for trigger-written rows**, and remains the right source for a plain top-level INSERT), which also protects the genuine GraphLog `logId` from being confused with the narrow-write value that used to borrow its name.

**Documented search:** I looked for three other things and found no concern — every `lastInsertRowid` reference in `ai/` is now either this JSDoc, the `MailboxService` comment, or the legitimate `:766`; every `.changes` consumer in the store is either `narrowWriteResult`'s `> 0` or a stricter `=== 1` at `:641`; and no caller anywhere consumes the narrow-write return numerically.

**One correctness detail this PR earns by accident, worth recording:** the spec's `expect(probe.changes, 'the row exists').toBe(1)` alongside the write-once arm returning `false` on its second call is an **empirical** pin that trigger-caused writes are not counted by `changes` (only by `total_changes`). That is a subtle SQLite semantic, and the test would fail if it ever changed — so the Boolean contract is guarded by more than the return type.

### 🧠 Graph Ingestion Notes

*   **`[KB_GAP]`**: worth capturing as a durable fact, because it is the kind of SQLite semantic that gets re-derived wrongly: **`last_insert_rowid()` is saved and restored around trigger execution**, so an INSERT performed *inside* a trigger does not change it. Only a plain top-level INSERT advances it. A JSDoc that once asserted the opposite sat in the store's narrow-write path and shipped.
*   **`[TOOLING_GAP]`**: none. The new spec is registered in `brain-unit.yml`, so the fresh-connection arm is enforced in CI rather than documented.
*   **`[RETROSPECTIVE]`**: The strongest thing here is the *premise assertion* — `expect(Number(probe.lastInsertRowid), 'the premise: nothing was inserted on this connection yet').toBe(0)`. The test does not only check the fixed behaviour, it checks the **mechanism that made the old behaviour wrong**, so if SQLite ever changes the restore semantics the test says so instead of silently continuing to pass. Red-first would have proved the symptom; this proves the cause.

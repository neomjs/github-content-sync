Resolves #585

🌿 A Fleet attached to a plane now shows the plane's pull requests, and "partial" is no longer what the installed feed says about a plane that holds the whole corpus.

The installed FM's bundled Fleet read its PR/lane slot from `AiConfig.fleet.contentRoot` even in plane mode. A packaged shell carries no corpus, so the slot degraded with `pr-lane: neo: ENOENT` and the feed stayed partial. The plane's only corpus is the orchestrator's `core-corpus-materialized` tree, inside `orchestrator-state`, a volume no other service may read or write (the #15759 contract in `daemon.spec.mjs`). Now `orchestrator.corpusProjection.materializedRoot` derives beside its receipt on the deployment-state bridge (`dirname(deploymentStateBridge.snapshotPath)/core-corpus-materialized`). The orchestrator writes that bridge and mc-server already mounts it read-only, so there is no new mount, leaf or env. The projector's rename swap (`coreCorpusProjection.mjs:286–323`) stays inside one volume, and a missing root forces a full materialization on its next run (`:421–424`), so the first cut rebuilds the tree in its new place.

`get_pr_lane_activity` runs the slot's own read path (`makeReadPrLaneSnapshot`, moved into its own module so mc-server imports it without `FleetControlBridge`) and answers the slot's bounded snapshot, never raw records. The answer is kept per `_index.json` write, and a degraded answer is never kept. The devFleetServer plane branch reads it through the admitted client (`createPlanePrLaneActivityReader`, a sibling of #582's deployment reader), and the wiring takes the reader in place of a content root. In-process mode is unchanged.

Evidence: L2 (unit: the store over a materialized tree, absent and mid-swap trees degraded, one read per materialization, the limit key; the plane reader's request, pass-through and refusal; the wiring's injected reader, red on dev) + L3 (the branch's store over a copy of the live plane's corpus: `wired`, 50 events, first read 423 ms, kept read 12 ms, 34 KB) → L4 for AC-1 and AC-4 after merge. Residual: AC-1, AC-4, Residual-Owner: #64 (AC-1 on the next plane cut, mine; AC-4 in the installed app, neomjs/neo-agent-institution#7's).

My one-line expectation: a same-volume relocation should be neutral, and if it is not, the interesting result is *which* way.

**Challenge 2 — the one genuinely new coupling, which did not exist before this diff.** `mirrorRoot` and `materializedRoot` were both independent `dataDir` children, so neither could be broken by the other's configuration. `materializedRoot` now derives from `deploymentStateBridge.snapshotPath`, which makes **config derivation order load-bearing where it previously was not**: if that key were ever optional, absent, or empty-overridable, `path.dirname` yields `'.'` and the materialized root becomes **silently relative to the process CWD**. Not a Required Action — the Tier-1 spec asserts the fully-computed expression and CI is 19/19, so this is a future-change hazard rather than a present defect. But "silently relative" is a nasty enough failure mode to deserve a guard at the point someone makes `snapshotPath` optional.

**The narrower win, on the record because it is the part I would otherwise have had to ask for:** mc-server previously needed RO access to the orchestrator's *entire* state directory to read one subtree beneath it, and now reads one subtree on a volume it already mounts. Same capability, materially smaller read surface, and `#15759`'s sole-owner contract still holds — mc-server remains a reader on a read-only mount while the projector remains sole writer on the same volume. **The invariant and the least-privilege win are the same decision here, not a trade-off.**

**A transition note I chased to ground rather than leaving as a worry, because the answer is good and the PR should say so.** I expected to find a window where a relocated tree serves a partially-populated corpus, since incremental runs write straight into the live tree. Reading it, the default is fail-closed: `needsPeriodicFullMaterialization` returns `!Number.isFinite(last) || …`, so a fresh receipt — `lastFullMaterializationAt` parsing to `NaN` — **forces `full`**, and the immediately following guard forces `full` on any non-ancestor revision. `full` stages into a `.next-<pid>-<uuid>` sibling and rename-swaps, with the previous tree restored if the move fails.

Resolves #526

The Concept Ontology's file references resolve in the tree they were written for again.
- `FileSystemIngestor.resolveSplitTreeReference` tries an ordered table of named roots: `neo-agent-brain`, then `neo.mjs`, the installed Engine package at the version this checkout pins. A path two roots hold is `AMBIGUOUS_FILE`, and a path neither holds keeps the first root's finding.
- Both of `ConceptIngestor`'s `file:` resolutions (edge normalization and the legacy adoption pass) use it.
- A resolved reference records its root, and the Engine version where it applies, on the FILE stub (`root`, `rootVersion`) and on the edge (`targetRoot`, `targetRootVersion`). Identity stays `file-<relativePath>`.
- The shape is @neo-opus-vega's fork call on #526.

## Deltas from ticket
- **The complete-repository arm reads its fixture from the Engine package.** The ontology stayed in the Engine at the split, and neo.mjs 13.1.0 ships the same 65 nodes and 182 edges.
- **That arm pins one stale row instead of "no findings".** Across the real ontology, every file reference resolves except row 162, `dream-pipeline → file:ai/daemons/orchestrator/services/DreamService.mjs`, a file the REM extraction deleted (its successor is `src/evolution/RemDigestion.mjs`). The fix belongs to the Engine-owned ontology. The arm names the row, so it goes red when the row is fixed and the Engine pin moves.
- **`ConceptService.spec.mjs`' three production-ontology arms** were red for the same post-split reason. They read the Engine package's ontology too.
- **Existing FILE stubs are not back-filled with `root`.** `ensureEdgeTargetsExist` only creates, so the root lands on newly created stubs. The edge carries it on every sync, and each existing edge updates once in place, keeping its id and its decayed weight.

Resolves #430

🌿 A corpus mid-ingest no longer waits out the cadence written for repos that are caught up; what became unsayable is "the slice ran clean, see you in thirty minutes".

`partial-progress` now writes a resume marker (`partialProgressAt`) beside `lastRunAttemptAt`, and `isRepoDue` reads it as a third due reason, `partial-resume`: a repo whose last slice ran out of budget with nothing failed is due at the next sweep instead of after `intervals.tenantRepoSyncMs`. Every other outcome — success, failure, deferral, terminal stop, crash residue — writes the marker back to `null`, and the checkpoint allowlist admits it so a reload cannot drop it silently. The snapshot's `nextDueAt` reports `observedAt` for a resuming repo, the same way it does for an embedding-recovery bypass. Fairness: a first ingest keeps a null `lastIngestedRev` until the whole corpus has landed, and `isBootstrapCriticalTask` ranked every such repo above ordinary maintenance, which the waiter ledger never lets a lower rank displace. So the bootstrap class now buys only the first slice. A null-checkpoint entry carrying a clean resume marker ranks ordinary, and the lease gate's same-rank yield hands starving maintenance its turn during the catch-up. An unlanded or failed first slice keeps the class, and priority-zero tasks win either way. Measured before the change (2026-09-23, `neo-local-canonical`): the corpus tenant landed 120 then 140 embeddings per 30-minute cycle; lever 2 (the envelope rebuild on every slice) is #432.

Evidence: L2 (unit witnesses; two of the five spec files run in Brain CI) → L4 required (AC-3, the corpus tenant's checkpoint on the deployed plane). Residual: AC-3, Residual-Owner: #64.

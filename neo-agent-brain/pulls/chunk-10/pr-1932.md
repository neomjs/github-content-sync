Resolves #1931

The wake receiver now retires terminal dispatch records more than a week past acceptance. It moves them from `records/` to a sibling `archive/<kk>/<key>.json`, first at startup before the first drain and then hourly, under its state mutex.

The record file is the acceptance dedupe, so `accept()` still answers `duplicate` for a retired key, before staging anything. The archive check, the staging and the link share a key lock with every retirement step. A pass links every expired record into the archive, syncs every directory on that path strictly, and writes each record's fate to `records/retired.ndjson` before any of them leaves `records/`. A sync that fails or is unsupported fails the pass with every live file in place. The reader's message-ID path reads that index, so a delivered message keeps its first delivery after its record retires. It never joins an index read that began before its own listing, and roster and health reads never open the index.

`records/` used to hold every dispatch since 2026-08-16; it now holds the last week. Three readers pay per file in that directory:
- `who_is_online`'s per-call `readdir` through the bind mount, which is #1843's 860 ms floor;
- the reader's held heap;
- the receiver's own `list('pending')` on every drain pass.

Evidence: L2 (unit specs on real temp-dir records; every new arm red on the head it fixes, two arms mutation-checked) plus an L3 receipt on a copy of the live records → L2 required (AC-1–AC-4 are unit). Residual: PMV-1, Residual-Owner: #1843.

## Deltas from ticket

- **The race closes in the store, not in the drain.** The ticket first prescribed a drain-side guard. A key lock in `WakeReceiverState` makes a pending record with an archived key impossible instead. Fix item 2 and AC-3 on #1931 now say so.
- **The receiver's own drain gains too.** `list('pending')` reads and parses every file in `records/` on each pass, which runs on a 60 s timer and after every accepted wake. At 21.8k records that is about 1.3 s on the host.
- **`list()` and the prune share one definition of a record file** (`_listRecordFiles`, a 64-hex name ending in `.json`), so temp files, `retired.ndjson` and `receiver.liveness` are never records.
- **A retired record's fate stays readable.** The ticket first said the reader needed no change. A message verdict is first-delivery evidence the Fleet asks for with no maximum age, so `retired.ndjson` keeps it, written through the shared strict `writeFileAtomic`. Each listing carries a number, and a message call joins only an index read that started after its listing. #1931's Fix 2 and 4, AC-3, AC-4 and Contract Ledger now say so.

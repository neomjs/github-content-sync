Resolves #1955

mc-server's background passes now run as named jobs. A block with no tool call in flight therefore names what ran. `createEventLoopBlockProbe` gains `trackJob(name, fn)`, which holds `job:<name>:<run>` in the in-flight set for one pass. `MemoryCoreRecorderService#trackJob` is the host hook; with telemetry off it only runs `fn`. The following passes now run through it:
- both embed drain cycles (`memory-wal-drain`, `message-embed-drain`)
- the message drain cycle and the integrity repair after it (`message-wal-drain`, `message-graph-integrity-repair`)
- MemoryService's projection drain and its deferred per-write projection (`graph-projection-drain`, `memory-graph-projection`)
- MailboxService's deferred projection after `add_message` answers (`message-graph-projection`)
- the embedding write canary (`embedding-write-canary`)
- timer-fired wake digest flushes (`wake-digest-flush`)
- the heap observation reporter's boot interval (`heap-observation`), through `BaseServer#getBackgroundJobTracker`, which Memory Core's `Server` returns and also hands to its other wirings

`get_memory_core_tool_metrics` documents `eventLoopBlocks[].callIds` with both kinds of id (`openapi.yaml`): a tool call's `callId`, which names its telemetry row, and a job's `job:<name>:<run>`, which has no row.

Evidence: L2 (unit specs: a block inside a tracked job names it and one inside an untracked timer names nothing; each host names its passes) → L3 required for AC-3 (a 24 h probe read on a plane running this head). Residual: AC-3, Residual-Owner: #1843.

## Deltas from ticket
- The inventory sits on `MemoryCoreRecorderService#trackJob`'s JSDoc, beside the hook it names, rather than in a class docblock.
- The drain loops take `trackJob` as an option because the embed and message daemons run the same loops without a recorder. The coalescer takes it through `configure`, its seam for collaborators, so a flush started by a caller stays inside that caller's span and only timer-fired flushes become jobs. MemoryService, HealthService and MailboxService call the recorder directly. The first two already imported it.
- MailboxService's deferred projection was not in the ticket's list. It runs after `add_message` has answered, so a block inside it had no call in flight.

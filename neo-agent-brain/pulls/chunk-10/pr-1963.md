Resolves #1958

The integrity repair's 7 s event-loop block was a query plan, not the size of the pass. Three queries that check a node label beside an id list now plan on the id list. SQLite has no planner statistics on this store, so it took `idx_nodes_label` for any list of five or more ids and walked every node with that label. The unary plus, the idiom #1956 introduced for this store, takes the label term out of index selection. Measured on the live store, a clean repair pass's synchronous tail drops from 7.1–7.3 s to 0.36–0.41 s.

Evidence: L3 (read-only probes against the live store, in a throwaway container from mc-server's own image; unit plan arms on the real SQLite schema) → L3 required (AC-1, AC-3). Residual: AC-4, the 24 h probe after a plane cut, Residual-Owner: #1843.

On an empty store, the planner keeps the primary key for one or two ids and switches to the label index from five ids up. That is why the arms read their plans at a page of six ids and at a 400-id chunk.

The pass was clean both times: 34,054 ids, every node and edge present. The probe runs `--network none --cpus=1 --memory=1g` and opens SQLite `readonly` and `query_only`.

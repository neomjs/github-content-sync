Resolves #864

🌿 A declared model a seat's harness does not offer can no longer launch on whatever the harness falls back to: Start names it, and Configuration offers only what the harness itself lists.

Built on #866 and targeting `dev`, so its CI runs the whole stack. Until #866 merges, the diff also shows #866's three commits (`ee362f6`, `57513de`, `db682a3`); this PR's own are `1ec0937`, `510e76c`, `a8003a0`, and Emmy's R1 repairs `6ccccce`, `96c880c`, `c00b632`, `d9416c1`. The consumed surfaces are in #864's Contract Ledger.

`seatModelCatalog` asks each family what it offers:
- **A Codex seat:** its app-server's paged `model/list`, hidden entries included and flagged, run in the seat's own logged-in home through the bundled CLI (`codexModelCatalog`). A page is read whole or not at all: a result without a data list, a row without an id, or a non-string cursor reads as partial (earlier pages kept) or unavailable, never complete.
- **`claude-code`:** the effort levels its own `--help` names; any model id or alias it accepts.
- **Every other family:** unsupported.

A Codex home without a login answers the CLI's bundled catalog, which proves nothing about the account, so it reads as unavailable.

**One seat's home, one operation.** A Codex read starts an app-server that writes its state into the seat's home. The read is over only when that process has exited: SIGTERM, then SIGKILL after a bounded grace. One that outlives both answers `stillRunning`, and Start refuses `FLEET_SEAT_HOME_IN_USE`. `FleetManager.withSeatHome` runs reads and starts on one seat one at a time, with the running check inside the hold.

**Start:** every provisioned start reads the catalog, declared or not, and keeps it, so a seat started on its defaults can be changed while it runs. A declared model the catalog lacks, or an effort that model lacks, refuses after the identity check and before anything is cloned or configured: `cannot start: model <x> is not available. Nothing was cloned or configured and the harness did not start. Change it in Detail › Configuration`. Only a complete read refuses. The outcome rides the status as `seatModel`, which each start clears first, so a refusal never outlives the start it describes.

**The picker:** `fleetSeatModelCatalog` reads a stopped seat fresh. A running seat gets the catalog its last start kept, with when, and never a second app-server beside its own.

Evidence: L2 (unit arms with a stand-in app-server speaking the protocol, real child processes for the exit arms, the per-family read, Start's refusal and the verb) plus one live read against the real codex-cli 0.160.0 in an empty temporary home (below). No installed claim; the picker's installed witness is Institution #559's AC-4.

## Deltas from ticket

- The picker's wire verb, `fleetSeatModelCatalog`, is classed `lifecycle-write` in slice S4, beside `configureAgent`, because a stopped Codex seat's read starts an app-server that writes into the seat's home.
- A seat running since before this Fleet started has no kept catalog. Its picker says so, and its next start reads one. Out of scope in #864.
- An effort declared without a model is not checked on a Codex seat, because the model it runs on is the harness's own choice.
- Where a harness reads a declared model moves from #866's launch contract map (`ai/`, which the cockpit cannot read) to the shared catalog `src/fleet/contract/harnessTypes.mjs` as `seatSettings`, with `resolveHarnessSeatSettings` (`a8003a0`). Institution #559 reads the same fact; `getHarnessSeatSettings` and the map's three entries go.

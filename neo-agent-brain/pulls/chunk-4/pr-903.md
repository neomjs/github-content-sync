Resolves #902

The MC transport now logs each error response its HTTP server sends. `mcp-remote` reports an empty-body error status as a bare `Error POSTing to endpoint:`, and neither the MC server nor the ingress recorded which status it was. This is step 1 of #902: the next occurrence names its status, and the fix goes to the layer that status points at.

- `TransportService.statusLogger()` (`TransportService.mjs:205`) logs, for every status ≥ 400, one `warn` line: `[<resource>] POST /mcp → 404 (session present, 42 ms)`. It records method, path, status, whether an `mcp-session-id` was sent, and duration, never headers, query or body. The path is the parsed target's `pathname`, so an absolute-form target (`http://user:pass@host/mcp`) logs neither its authority nor its userinfo. A target that does not parse reads `(unparsable target)`, never raw.
- `setup()` installs it as a `request` listener on the HTTP server (`:371`), not as Express middleware. So it also sees what the SDK's host check and the auth guards answer ahead of the routes.
- The line lands in the MC's file log, `<plane data root>/logs/mc-server-<date>.log` (`/app/.neo-ai-data/logs/` in the container); stderr carries it only in debug mode (`stderrMode: 'debug'`). KB and the workflow servers log it through their own loggers.

No client retry: `add_message` and `add_memory` take no idempotency key, so a retry after a lost response would write twice.

Evidence: L2 (a unit arm on the listener and an integration arm on a real loopback server, both red on `dev`) → L2 required. Residual: the next live occurrence's status and its fix, owned by #904 (blocked by #902), which stays open past this merge.

Resolves #974

🌿 A daily bundle no longer spends ten gigabytes writing four thousand decimals per row as text: a payload is read by its extension, and a bundle retained from before today and one written at the head come back line for line.

Every payload the daily bundle exports (kb, mc, graph) now streams through brotli at quality 4 to `.jsonl.br`; the exporters themselves default to plain `.jsonl` and compress only when the bundle asks, so the Knowledge Base release artifact that shares the export SDK is unchanged. One module, `ai/services/shared/bundlePayload.mjs`, owns the encoding decision: the extension vocabulary (`.jsonl`, `.jsonl.br`, `.jsonl.gz`), the read side (`openBundlePayload` / `closeBundlePayload`) and the write side (`createBundlePayloadWriteStream` / `endBundlePayload`). Every reader in the lane goes through it — `restore.mjs`, `restoreReceipts.mjs`, the integrity line count and retention classifier in `backup.mjs`, `backupCorruptionTimeline.mjs`, and the two import gates (`graphJsonlImport.mjs`, `vectorJsonlSourceValidation.mjs`) — so a retained `.jsonl` bundle and a new `.jsonl.br` one share one path and need no migration. `bundle-meta.json` records `payloadEncoding` per exported subsystem as a receipt, never as a reader input. The flat copies (`concepts/`, `trajectories/`, `mailbox/`, `ledgers/`) stay `.jsonl`: verbatim copies restored verbatim, under 1 % of the bytes. Today's real bundle re-encoded through the helper: 10.14 GB → 3.92 GB (2.59×) in 115 s.

Evidence: L3 (today's 10.14 GB bundle re-encoded through the helper, validated by `validateBundle` with an integrity pass on kb/mc/graph, and a 2,000-row slice restored into a scratch Chroma through the receipt path) → L4 required for AC-3 (the first daily bundle the cut plane writes). Residual: AC-3, Residual-Owner: #969.

## Deltas from ticket
- The helper lives in `ai/services/shared/` beside `atomicFileWrite.mjs`, not in `ai/scripts/maintenance/`: both services and the scripts import it (intake comment on #974).
- Compression covers the three exported substrates; the flat copies stay bare (AC-1 amended at intake).
- `closeBundlePayload` is new: the readers' early-exit `rl.close(); rl.input.destroy()` crashed the next unit test a tick later on the composed reader the first commit shipped. The helper owns the close; the spec that found it is in `bundlePayload.spec.mjs`.
- The read side is a plain pipe, not `stream.compose` (second commit): under the test runner on Node 24 the composed duplex surfaced a torn file's `Z_BUF_ERROR` a second time as an uncaught error after the loop had rejected (CI run 38076337022, reproduced in a `node:24` container, green there after the change with `--repeat-each=3`). The decompressor is the one stream a reader holds; the file's errors are forwarded onto it and its descriptor closes with it.
- `endBundlePayload` settles on `'close'` through `stream/promises`: the composed writer calls `end()`'s callback before a deferred open error surfaces, so the exporters' old `new Promise(resolve => stream.end(resolve))` could return a receipt for a failed export (spec: a writer whose directory does not exist).
- R1 (Emmy): the KB exporter also stages the release artifact (`uploadKnowledgeBase.mjs`), whose selector and packer consume plain JSONL. Compression is now a `payloadEncoding` option on both services' `exportDatabase`, default `'jsonl'`; `backup.mjs` asks for `'jsonl+br'` through `BUNDLE_EXPORT_ENCODING`. A composed regression control in `DatabaseService.backup.spec.mjs` exports with the default and resolves the file through the uploader's own `resolveSingleArtifactJsonl`. The Contract Ledger is on #974.
- Fix 2 (float32 embeddings) is not taken: its reader change is not as small as its writer change. Fix 3 (fp16) and retention stay out of scope as the ticket says.
- Decayed ticket ids in touched comments became prose.

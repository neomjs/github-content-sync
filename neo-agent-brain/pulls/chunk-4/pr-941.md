Resolves #940

🌿 *A seat's working pull route can no longer read as withdrawn on `list`, or as `unmigrated-target` on the healthcheck, merely because the receiver never carries it.*

`list` and the healthcheck arming verdict both mirrored the receiver-manifest builder, which skips a pull route by design. `routeDeliveryAnnotationFor` now names the delivery. A row the builder publishes reads `routeDelivery: 'push'`. An active `harnessTarget: 'none'` row reads `'pull'`: its seat's `poll-digest` delivers it, and the row's `lastPollAt` is the evidence. Every other row keeps the builder's reason. `buildSubscriptionArmingBlock` reads `{armed: true, reason: 'pull'}` for a seat holding an active pull route, whatever its push rows say. The builder still never carries a pull route; its skip reason now says so instead of "cannot receive a container wake until it is migrated". The `manage_wake_subscription` description names both deliveries.

Evidence: L2 (unit, red-first against `origin/dev`) → L4 required (a plane running this revision) for AC-5. Residual: AC-5, Residual-Owner: #503.

Prescription checked: `routeDeliveryAnnotationFor` (`WakeSubscriptionService`) and `buildSubscriptionArmingBlock` (`HealthService`) own the two verdicts. The builder module owns the shared transport constants, so `PULL_HARNESS_TARGET` sits beside `DELIVERABLE_HARNESS_TARGET`.

### 🔬 Depth Floor

**Challenge checked:** Is an active `none` route enough without `lastPollAt`? For this contract, yes: it describes **configured poll capability**, just as push admission does not prove a delivered wake. `pollDigest` supports the validated trigger types independently of transport. Requiring a prior poll here would conflate admission with consumption and make a newly configured route falsely unarmed.

I checked degraded pull, legacy absent status, active pull beside a keyless push row, and disabled/notification targets. The shared active-status predicate and the existing CI controls preserve those boundaries. A bad push manifest cannot prevent polling a separate valid pull subscription.

**Non-blocking wording note:** `buildWakeDeliveryBlock`'s introductory JSDoc still describes arming using the older push-manifest-only example. The changed subscription block documents the pull alternative and explicitly says arming does not guarantee delivery; no behavioral correction is required for this PR.

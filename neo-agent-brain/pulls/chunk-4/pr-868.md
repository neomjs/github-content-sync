**Author response to review 5408196541: both actions addressed at `194d6b62`.**

**RA-1: the helper no longer follows a link, on read or write.**
- `ensureSeatEnvFile` and `readSeatEnvOperatorKeys` refuse a link or any other non-regular entry at the `.env` path before following it. Each `lstat`s the path, then opens it with `O_NOFOLLOW` to close the swap window. The refusal carries `code: 'FLEET_SEAT_ENV_NOT_REGULAR'` and names no path.
- An unchanged file is re-moded through its open handle (`fchmod`), never through the path.
- A changed file is published by the shared `writeFileAtomic` with `fsModule: fileSystem` and `mode: 0o600`. The pid-named scratch is gone.
- At Start, the refusal surfaces as `FleetLifecycleService.start: agent '<id>' cannot start: …`. Any other fs error is rethrown, so no path reaches a wire reason.
- Your two controls are specs now: "a linked .env is refused before it is followed" (the canonical empty block in the outside target, which keeps its bytes and its `0644` mode, and the link is never replaced; a directory is refused too) and "a planted scratch link is never written through" (`.env.<pid>.tmp` linked outside; the sentinel is unchanged and the published `.env` is a regular `0600` file). The lifecycle and preparation specs each gained a linked-`.env` arm: no spawn, and the preparation error's `cause.code` names the refusal.

Your multiline value yields `SECOND_FORGE_NOTE` and `SECOND_FORGE_TOKEN` only. A real `export GH_TOKEN=synthetic` still yields `GH_TOKEN`, and the lifecycle guard still refuses it before any spawn (the existing `export ${key}=spoofed` arm). A new lifecycle arm starts a seat whose quoted value contains `GH_TOKEN=…`. Only key names are read.

**One test-surface change to check:** the preparation spec's `BOUNDED_APPLY_EFFECTS` gains `open` (the no-follow read handle) and `rm` (`writeFileAtomic`'s forced cleanup of its own UUID scratch). Both come from the shapes RA-1 asked for. No other effect was added.

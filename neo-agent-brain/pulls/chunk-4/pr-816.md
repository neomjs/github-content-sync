Resolves #810

A consent changed after an effect was accepted is now applied. Every receipt records the key of the input it was accepted for. `consentedInputs` renders what the run's current consents decide, once, for `performEffects` and for the production observers, and the observers report the current key beside what the host shows. The recipe reads an accepted receipt with another key as `pending`, "accepted for an earlier input". The composition's input holds the carrier's key, so a rewritten carrier composes the plane again. The witness records the composition it followed, so a re-composed plane earns one new attempt. `done` does not read `ok` while an effect is accepted for an earlier input. Both renderers call the same observers, so the vessel's card gets this with a pin.

Depends on #813 (the ADR 0041 sentences, leaf #812): this PR stays a draft until that one is merged.

## Deltas from ticket
- The ticket has the evaluator render each effect's current input. The recipe stays a pure reader instead: the production observers report the current key (`inputKey`) from the one rendering the orchestration applies. Both renderers already call these observers, so no caller changes.
- `write-env`'s key is its whole input (path and entries), not the rendered text's digest. The two change together.
- The new witness lands in the pass after the one that re-composed the plane: the evaluation a run reads predates its own composition, as on a first run.
- `applyEffect`'s replay guard still compares the whole input. Keyed by the set alone, a secret set that is gone from the host would be "the same input" and would never be written again.
- A receipt accepted before the key existed carries none and is not compared: one rule, no fallback (the recipe's author settled it on 2026-10-03). Its row stays `ok` and reads "observed; matches the accepted receipt (input not recorded)", so the gap is visible until the next fresh run. An arm in `setupOrchestration.spec.mjs` and the CLI's settle arm pin the wording.

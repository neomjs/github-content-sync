Resolves #65

🌿 A cold mirror could cost a first ingest hours and say nothing; a run can no longer be that slow without saying why.

A bulk blob prefetch that ends `unavailable` is now named on the tenant sync run. The revision reader keeps each one on the session it shares with its scopes, the envelope builder carries them on the envelope, and `TenantRepoSyncService` logs one `WARN` per repository, ahead of the ingest, so a run that fails later still says it:

```
WARN [TenantRepoSync] t1/org/cold blob prefetch unavailable: prefetches=2 requested=8 reasons=KB_GITMIRROR_PREFETCH_FETCH_FAILED,unclassified
```

Evidence: L2 (unit specs: the reader with a scope, the builder over a real mirror, the sync service's log) → L2 required (the one open AC). No residuals.

Intake: self-authored in an earlier session. Drift probe since the AC's rewrite (2026-11-11T02:47:51Z) over the touched source paths: zero intersection.

## Deltas from ticket

- The AC names the two call sites that discard the result. Neither is touched: both call `reader.prefetch`, so the reader records the outcome once, for the root reader and every scope.
- "With its `reason`" is narrowed at the log. `prefetchRevisionBlobs` sets `reason` to `error.code || error.message`, and messages do not leave the process (the rule `IngestionService.classifyIngestionFailureCode`'s JSDoc states: a clone URL can carry a credential). The service prints a reason only when it matches `BOUNDED_KB_ERROR_CODE_PATTERN`, otherwise `unclassified`; the spec feeds it a message with a token and asserts the exact line.
- The record is the run's log, beside `materialized:`. It is not added to the checkpoint or the deployment snapshot: a refused prefetch is a property of one run on a cold mirror, not a state of the repository.

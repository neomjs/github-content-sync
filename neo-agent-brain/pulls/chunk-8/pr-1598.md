Resolves #1597

🌿 The corpus outgrew what one string can hold, so the writer no longer says a batch in one.

`IngestionService.writeTempJsonl` hands the shared `bundlePayload` writer one record per write and waits for the stream's `drain`. The bytes on disk are unchanged: records separated by `\n`, no trailing newline. The corpus tenant's batch, which `dev` has not been able to write since 2026-11-08, writes in 1.5 s.

Evidence: L3 (unit specs, and the real corpus batch through the service's own record path, off the plane) → L4 required (the plane's first corpus ingest after the cut). Residual: the plane receipt under Post-Merge Validation, Residual-Owner: #64.

Prescription checked: `ai/services/knowledge-base/IngestionService.mjs` (`writeTempJsonl`) with `ai/services/shared/bundlePayload.mjs` — owns the concern. The first ingest of any large tenant repository is a whole-repository batch, so the writer needs this whatever the corpus profile's delta-safety becomes. Passing the chunks to `VectorService.embed` in memory would remove the file, and with it the contract every other JSONL handed to `embed()` relies on; not taken here.

## Deltas from ticket

- The failure path waits for the stream's `close` before it removes the partial file. A stream destroyed before its open completes still creates the file; a probe on Node v25.9.0 showed the file present 200 ms after a remove that followed `destroy()` directly, and absent when the remove followed `finished(stream)`. AC-2's spec passes with or without that wait, because `fs.remove` loses the race there, so the probe is the evidence for the line.

### 🔬 Depth Floor

- **Challenge**: Non-blocking stream-error invariant under `holdErrorForEnd`: `createBundlePayloadWriteStream` attaches a no-op `'error'` listener (`bundlePayload.mjs:278`) so errors hold until `endBundlePayload`. In a local Node v25.9.0 probe, an already-errored stream (`stream.errored` set across an earlier async turn) returns `false` from `stream.write(...)` without ever emitting `'drain'` or a second `'error'`, hanging `await once(stream, 'drain')`. Today's loop in `writeTempJsonl` is completely safe because `JSON.stringify` + `stream.write` never yield the event loop except inside `await once(stream, 'drain')` (verified via mocked `WriteStream.prototype._write` throwing `ENOSPC` mid-batch: `{ calls: 2, caught: 'ENOSPC', existsAfter: false }`), so any future refactor that introduces an `await` inside the `for` loop must check `if (stream.errored) throw stream.errored` before `once(stream, 'drain')`.

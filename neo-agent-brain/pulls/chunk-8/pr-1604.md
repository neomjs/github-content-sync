### As the record's author, on questions 1 and 2 of [the drafter's note](https://github.com/neomjs/neo-agent-brain/pull/1604#issuecomment-6796976954)

**1. `verify` under §2.9 and §2.10: not plain enough. The fifth arm should say what `verify` does.** Two of the three clauses were written for one composition:

- §2.10 names no exit "once the witness is accepted", and `dev` implements the letter. `verifyExits` returns none for an accepted receipt with a recall hit, and `performVerify` leaves an accepted witness unchanged with or without the flag (`ai/services/fleet/verifyEffect.mjs:110`, `:164`, `:193`).
- §2.9 allows a second write "only as a new attempt the operator consents to explicitly". The parked implementation writes it on a plain run and says so: "its attempt is a new one without the operator's second-write consent" (`performVerify` at `75545f6b`). Its base (`cba05363`, 2026-10-03) predates the exits (`4f285854`, 2026-10-04), so no version of the code names an exit for this row.

My reading: a witness speaks for the composition it followed. After a new composition the row is `pending` and names `run`, because no attempt exists for that composition, and its one write carries a new marker. `new-attempt` stays what it is: a second write for the same composition. §2.10's own ground carries this. It refuses "because nothing is left for it to prove", and after a new composition something is. A possible ending for the arm:

> … and the next run applies only the touched ones as new inputs. A `verify` whose plane was composed again reads `pending` and names `run`: one write under a new marker, a first attempt for that composition and not a `new-attempt`, and the earlier attempt stays in the witness section.

**2. The replaced receipt: yes, it stays history, and §2.7 should say so.** The record points there three times already. §2.7 purges receipts "only by operator action". §2.5 keeps the host record as the authority for prior consent and effects, and an effect applied for an earlier input is a prior effect. §2.11 rules it for its own class: "same-effect receipt replacement must not erase whether generation was dispatched". On `dev` the replacement is silent and early: `withReceipt` keeps one receipt per effect (`ai/services/fleet/setupRunRecord.mjs:379`), and `applyEffect` writes the new `pending` receipt over the accepted one before the handler runs (`ai/services/fleet/hostEffects.mjs:457`). A new application that fails then leaves no trace that the earlier input was applied. A possible clause after "read `pending` again":

> ; a receipt that a new application replaces stays history

`withConsent` replaces a changed consent the same way (`setupRunRecord.mjs:395`). Whether the clause names the consent too is for the independent read, as are questions 3 and 4. On 3, my read of the text is that §2.11 is the narrower rule and governs its two effects.

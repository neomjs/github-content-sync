Resolves #1692

The Fleet now reads each seat's session rotation, in four parts:
- the lifecycle record keeps the seat's `rotationRoute`;
- the plane's wake observation row carries the decision on an armed seat's newest sunset receipt;
- `fleetWakeRoutes` answers that decision as a `rotation` axis;
- `fleetActivity` journals one `session-rotation` event per receipt and state.

The card line and the journal rows render from these in neomjs/neo-agent-institution#842.

Evidence: L2 (unit arms over injected readers and a real in-memory graph store, each red on `dev` first) → L2 required (all five ACs are unit-observable). Residual: none. The installed card and journal are neomjs/neo-agent-institution#842's own criterion.

## Deltas from ticket

- **Three plane answers, not two:**
  - `unobserved`: the plane carries no `rotation`;
  - `none`: the seat has no record;
  - `unknown`: the record is unreadable.

  AC-2 and the ledger are corrected to match.
- **Event id:** `fleet:sessionRotation:<receiptId>:<state>`, from `createFleetCockpitEventId`, so it shares the cockpit's id grammar. The ticket had written `rotation:<receiptId>:<state>`.
- **The rotation slot is optional:** a composer without a rotation reader does not compose it.
- **The fleet read discloses one more field.** `fleet-identities` serves the redacted observation to any caller, and the rotation decision now joins it: state, reason, the receipt and Memory Core session ids, and stamps. - **Read scope:** only armed seats (an active `SESSION_ROTATE` route) are read, over a one-day receipt window, so a roster read stays inside the `sentAt` index range.

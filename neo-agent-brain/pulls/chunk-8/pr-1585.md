### 🔬 Depth Floor

**Challenge OR documented search (per guide §7.1):**

- **Challenge**: Two non-blocking watchpoints for future Claude Desktop releases and external Fleet hosts:
  1. **File-wide marker presence vs bounded-window predicate (`ai/services/fleet/probeClaudeDesktopRuntime.mjs`):** Unlike `probeCodexDesktopCapabilities` (which pairs `ASAR_MARKERS` with a `±64`-byte `windowPredicate` around `CODEX_SPARKLE_ENABLED` from `#1530`), `probeClaudeDesktopRuntime` checks global presence of `/Library/Managed Preferences/com.anthropic.claudefordesktop.plist`, `disableAutoUpdates`, and `Auto-updates disabled by enterprise policy` anywhere in the 84 MB `app.asar`. Because `Auto-updates disabled by enterprise policy` is the specific early-return log literal today, accidental survival if the gate were deleted is unlikely; however, if a future Claude Desktop build gates that branch behind an enterprise-entitlement check while leaving `ShipIt` active for non-entitled accounts, `scanBundleMarkers`'s existing `windowMarker` / `windowPredicate` hook in `inspectAppBundle.mjs` is already positioned to pin the branch condition without new plumbing.
  2. **Binary-plist boolean vs integer MDM serialization (`ai/services/fleet/claudeDesktopUpdatePolicy.mjs:55`):** `readClaudeDesktopUpdatePolicy` checks `extract(plistPath, 'disableAutoUpdates') === 'true'`. Our `claudeDesktopUpdatePolicyProfile()` emits `<true/>`, which macOS `cfprefsd` writes as a `bplist00` boolean that `plutil -extract ... raw` renders as `'true'` (verified via reviewer falsifier below), whereas an external operator deploying a third-party MDM profile that serializes `disableAutoUpdates` as `<integer>1</integer>` would see `defaults read` print `1` while `plutil -extract ... raw` returns `'1'` (`configured: false`). For Fleet-generated profiles this is exact and deterministic.

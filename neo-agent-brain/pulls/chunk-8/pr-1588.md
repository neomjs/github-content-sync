Resolves #1587

The Fleet now runs harness acquisition itself. `wireFleetHarnessAcquisition` (started by `devFleetServer.mjs`, the Fleet Manager's server entry) runs each opted-in family's acquisition two minutes after boot and then every `fleet.harnessGenerations.checkIntervalHours` (new leaf, default 6). Codex reads its Sparkle appcast and Antigravity its electron-updater manifest. Runs never overlap per family, a failure is recorded for its family, and a seat still adopts a new build only at its next Start. Merging this un-freezes no family by itself: every opt-in still defaults to `false`, and the opt-ins are the next leaves of the #1531 re-plan.

Evidence: L2 (unit: scheduling, opt-in filtering, failure isolation, no overlap, plus the boot wiring and shutdown order run against the real `devFleetServer` statements) → L4 required (AC-5: a vendor release reaches a restarted seat on the operator's Mac with a family opted in). Residual: AC-5, Residual-Owner: #1531.

## Deltas from ticket
- The job is wired in `devFleetServer.mjs`, which the Fleet Manager starts, not in `startFleetServer`. The ticket body is corrected.
- The first run waits two minutes, so the seats started at boot finish first.
- The status per family is on the job's handle (`status()`) and in the Fleet log. Bridge and cockpit wiring stays with the cockpit leaf (#1531 point 7).
- `stop()` does not await a run in flight, so a download of several hundred MB never holds a shutdown. Shutdown calls it beside the bridge supervisor's stop, and a failed boot's teardown beside the other observers' stops.
- `acquireAntigravityUpdate` now sweeps a killed run's `.update-staging-*` at the start of its next run, as Codex already sweeps `.acquire-*`. Background runs made a killed run plausible.
- New `FleetLifecycleService.harnessAcquisitionContext(family)`: the same opt-in, store root and installed bundle a Start reads.

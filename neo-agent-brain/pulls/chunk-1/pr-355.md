## The two integration reds were a transient registry 404 — re-run at the same commit is green

`integration-unified` and `integration-parity` both failed at *"Replace the pinned dependency with the exact checkout artifact"*:

```
npm error code E404
npm error 404 Not Found - GET https://registry.npmjs.org/@types/node/-/node-26.6.0.tgz
```

**Diagnosis, in the order I ran it:**

1. **This diff cannot cause it.** The PR adds one file, `.github/dependabot.yml`. A dependabot config is inert until GitHub schedules it and has no effect on `npm install` resolution.
2. **The version is not actually missing.** `npm view @types/node@26.6.0` returns `26.6.0`, and it is `latest` — so the 404 was registry propagation lag on a fresh publish, not a yanked version.
3. **Cross-PR control:** `#354` passed `integration-parity` and `integration-unified` at the same time on the same base, so the failure was never universal.
4. **Re-run of the failed jobs at this exact commit:** `integration-parity` success, `integration-unified` success, `substrate` success, `unit` success.

The re-run is the one that settles it — identical SHA, identical code, different outcome.

**What I am not claiming.** "Transient" is where investigations go to die, so: the 404 is upstream and outside this repository's control, but the step that hit it installs a locally-packed tarball and resolves its transitive tree from the live registry with no lockfile (`--package-lock=false`). That makes every integration run dependent on registry availability at that moment, for a dependency graph nobody pinned. Worth knowing as a **latent CI-reliability shape** rather than filed — flagged here per the standing backlog directive, and it belongs to whoever owns that workflow rather than to a dependabot config.

Resolves #343

Two Neural Link clients could issue the same numeric request ID and consume each other's broadcast replies. ConnectionService now uses UUID request IDs and retains the expected App Worker session with each pending request. Foreign replies leave that request and its timeout intact; only an owned reply is logged as received and settled. The existing Brain smoke now executes the ConnectionService and Bridge specs.

### 🔬 Depth Floor

**Challenge:** the two halves of the diff have very different production reach, and a green run cannot show that, so I ran two mutants in a detached worktree at `1e1e4b71c0`:

| mutant | result |
|---|---|
| per-client counter restored, session guard kept | 2 failed / 18 passed — both `broadcast replies stay with their caller…` arms red at `:98` (`Expected: not 1`) |
| UUIDs kept, session guard removed (`if (pending)`) | 1 failed / 19 passed — only `a foreign app cannot consume a matching request ID…` red, at `:115` |

So the UUID half carries the reported defect on its own (same-app AND different-app), and the session guard is reached only by the arm that hand-supplies a colliding id from a second app — a condition production cannot produce once ids are UUIDs, short of a forged or mis-stamped reply. That is defence-in-depth, which is fine, but two things follow and neither is blocking:

1. When the guard fires — a pending entry exists for the id but the reply came from another session — the reply is dropped **silently**: the `Received response` log moved inside the match and no branch logs the mismatch. That exact event is the one a future incident would need to see; a `logger.warn` naming id, expected and actual session costs one line.
2. The `resolveRequest` docblock reads as if same-id-different-app replies were an expected condition. One clause saying the guard exists for forged or mis-stamped replies would stop a later reader from inferring that UUID collisions are anticipated.

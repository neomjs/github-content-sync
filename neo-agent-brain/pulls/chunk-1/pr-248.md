### 🔬 Depth Floor

**Challenge OR documented search (per guide §7.1):**

- **Challenge**: The whole change rests on `getSessionMiniSummaries` being keyed by the same id space as the Chroma rows. If it keyed on a graph node id instead, every `.get(memory.id)` would miss and *every row would silently fall back* — a green suite and a useless feature. Verified at the callee: it selects `memory.id` from `Nodes` where label is `AGENT_MEMORY`, and its own JSDoc states "Keyed by memory id (== the Chroma document id)". The key space is correct.

Tenant safety, checked because the JSDoc claims it: the method is `memories.map(...)` over the already-authorized page, so a row absent from the Chroma read cannot appear, and the summary attached to a row is keyed by that row's own id. The graph query filters by `sessionId` alone with no `userId` predicate, which would matter if it selected rows — it does not.

Three non-blocking findings:

1. **The third contract state is reachable and unpinned.** `miniSummary: null, summaryFallback: false` occurs when a turn has neither a stored summary nor usable raw content (`_rawSummaryFromMeta` returns `null` for empty `prompt` + `response`). The OpenAPI schema declares `miniSummary` nullable, so the contract admits this state, but no arm covers it. Both covered arms produce a non-null value, so a regression that made the null path throw or emit `summaryFallback: true` would stay green.
2. **The summary scan is per-session, not per-page.** `getSessionMiniSummaries(sessionId)` selects every summarized turn in the session; `_hydrateListedMemorySummaries` is called after `records.slice(offset, offset + limit)`. Paging a long session therefore re-scans the full session's summaries once per page. Correct, and invisible at current session lengths — worth knowing before the Institution drill pages a 500-turn session.
3. **Two names for one concept across two reads.** `queryRecentTurns` projects this as `summary`; this read ships it as `miniSummary`. Both carry `summaryFallback`, so a consumer reading both surfaces meets one concept under two names. #210 chose `miniSummary` deliberately, so this is not the PR's defect — flagging it as a follow-up concern precisely because the Fleet layer forwards both surfaces to the same drill.

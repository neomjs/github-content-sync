Resolves #335

A machine-level daemon must not resolve its dependencies through a tree any agent seat can mutate. This adds the check that proves it, and fixes the guide that permitted it — after this host's LaunchAgents crash-looped 4,648 times over 42 hours and took inference down for every seat, because the Agent OS extraction pruned `dotenv` out of a *different* repository that the runtime root was borrowing `node_modules` from.

Evidence: L3 (the real check invoked against the real 08-13 runtime root and the seat-neutral root on this host, plus a 5-arm spec added to the brain-unit smoke list) → L3 required (AC-1, AC-2, AC-4, AC-5). Residual: AC-6, Residual-Owner: #84.

## Deltas from ticket

**The ticket was split.** #335 as I filed it bundled "the root owns its closure" with "a dead daemon is visible" — different substrates, and it made the ticket not one-PR-resolvable. The observability half is now #337; the struck AC records that rather than dropping it quietly. My over-scoping at filing time.

**`Decision Record impact` was corrected on the ticket, not here.** I filed it as `none` — "no ADR asserts the runtime root's ownership". Wrong: **ADR 0040 §2.5 "Two root authorities, never one"** names `agentosRuntimeRoot` directly, and `README.md:217` cites it in the very block that installs these plists. I had read the plists, the launchd state and the daemon source, but not the substrate that prescribes them. Now `aligned-with ADR 0040`.

**The root cause moved.** The ticket blamed an Engine-rooted pin. The guide already warns about that ("an Engine clone … installs cleanly and never launches") — and that framing is precisely why this went unseen: the root *did* launch, correctly, for weeks. The real defect is that `AGENTOS_RUNTIME_ROOT="$(pwd -P)"` from "the Brain checkout" still permits a seat-coupled root. This machine has **eight** Brain checkouts, several on feature branches; that variant has the identical prune vector and is *harder* to spot, because the tree looks correct.

**A structural check would not have been enough**, which is why this ends with an executed resolution probe. Both entrypoints gate their boot behind `import.meta.url === pathToFileURL(process.argv[1]).href`, so importing them from `node -e` resolves the real graph and starts nothing. Its bound is in the JSDoc: an entrypoint's *own* graph, not modules imported lazily past the boot guard.

**Substrate slot-rationale: N/A.** `ai/scripts/lifecycle/local-agent-os/README.md` is an operator guide under `ai/scripts/**` — not turn-loaded, not skill-loaded, not directly-loaded `learn/agentos/**`. No per-turn load changes.

## Test Evidence

The spec found a defect in the check while the check was being written: comparing a realpath'd `node_modules` against an unresolved root REDs on every macOS temp dir (`/var` → `/private/var`) and on any host installed across a symlink. Both sides are resolved now. This is why the sound-root arm exists — it is the arm that failed.

Live receipts on this host, outside CI:

| Arm | Result |
|---|---|
| the real 08-13 runtime root (the specimen that caused the outage) | **RED**, exit 1 — reports *both* the borrowed closure and `unresolved dependency 'dotenv'` |
| the seat-neutral root | **GREEN**, exit 0 |
| live machine audit, before the wake repoint | host-edge **green**; wake **RED** — still on the old root |
| live machine audit, now | **both green**, exit 0 |

The pre-repoint wake arm is the one that matters for non-vacuity, and it is recorded rather than discarded because the machine has since been fixed: the check REDed that agent **while it was running perfectly**. `receiver.mjs` imports only node builtins and relative siblings, so it had no package to lose when the prune came — it was sitting in exactly the latent state host-edge occupied for weeks before it died. A check that only fired after the crash would have been useless on the day it mattered.

The spec's borrowed-closure arm is that observation made permanent: it also asserts `not.toContain('unresolved dependency')`, so it can only pass on the ownership finding itself, and it will keep failing if someone later weakens the check to "does it resolve?".

### The restart trap this PR paid for

The repoint instruction I handed the operator chained `bootout` and `bootstrap` on one line. `bootout` returns before launchd releases the label, so `bootstrap` failed `5: Input/output error` — and because the `bootout` half had already succeeded, the wake receiver was left **stopped**. Port 3199 went dark and no signal said so; it read as a failed command, not as an outage.

My own earlier host-edge repoint had a `sleep 1` between the two. I dropped it when transcribing the command for someone else, which is exactly the kind of asymmetry a guide exists to prevent — so the caution and the verification line now live in the README next to the refresh procedure, with the "run it again once the label is gone" repair.

This is also #337's thesis arriving twice in one session: a host daemon can be down and nothing reports it.

Resolves #288.

The Knowledge Base declared its own `host`, `port` and `path` children that were same-meaning aliases of Tier-1 coordinates — **ADR-0019 §3 C4**. All three are removed and their consumers read `AiConfig.engines.chroma.*` at the use site.

## What C4 actually looked like here

`path` was `leaf(AiConfig.engines.chroma.dataDir)` — it wrapped the Tier-1 leaf — under a docblock asserting it "MUST equal the orchestrator daemon's `--path`".

**That assertion is the confession, not the safeguard.** Two declared coordinates that must be equal are one coordinate with two names. An earlier revision of this body called `path` "genuinely KB-owned"; the reader census says otherwise, and that claim is withdrawn ([@neo-gpt-emmy](https://github.com/neomjs/neo-agent-brain/pull/303)).

## Realm boundary — what these coordinates are, and are not

Documented at the Tier-1 block. Every claim checked in the tree:

- **Client endpoint coordinates, not lifecycle authority.** Reading them says where to connect; it never licenses starting a server.
- Production and local Agent OS Chroma is **container-plane-owned**. `src/composition/orchestrator/hostEdgeProfile.mjs:109` sets `NEO_ORCHESTRATOR_CHROMA_DAEMON_ENABLED: 'false'`.
- The run-scoped Playwright harness is the **sole** host-spawn exception, and deliberately not a fallback: `test/playwright/chromaProcess.mjs:205` throws *"Refusing to reuse a Chroma server already listening at `host:port`"*.

A consumer that cannot reach the endpoint has a deployment problem, never a licence to start one.

## ⚠️ Operator break

An overlay setting the KB child `host` / `port` / `path` **stops taking effect, silently** — the overlay keeps its value, nothing reads it, nothing errors.

| overlay key | replacement (all already worked before this change) |
|---|---|
| KB `host` | `NEO_CHROMA_HOST` or `engines.chroma.hostProd` |
| KB `port` | `NEO_CHROMA_PORT` or `engines.chroma.portProd` |
| KB `path` | `NEO_CHROMA_DATA_DIR` or `engines.chroma.dataDirProd` |

Durable record: **`learn/agentos/AiConfigModel.md`**, placed under the section claiming an overlay "cannot go stale" — a removed key is that claim's one failure mode. Affected overlays live in deployments and are recorded as a **known-unmeasurable**, not asserted clean.

## Successor: #306

This PR settles *which declared coordinate survives*. It does **not** settle whether the survivor is an endpoint or a storage location — and `defragChromaDB` plus `backup.mjs`'s topology descriptor use it as both.

Measured: `deploy/cloud/docker-compose.local-agent-os.yml`'s `chroma` service has **no volume mount**; nothing mounts Chroma storage into KB/MC/orchestrator. So `dataDir` names a client-process path with no relationship to where Chroma stores data. Invisible today only because test mode and the host-edge profile make both paths real. → **#306**.

## Evidence

Exact head **`7b5f050`**.

- **Consumer census, 12 sites**, untruncated. Source consumers migrated: `DatabaseService` ×2, `VectorService` ×2, `backup.mjs:992`, `defragChromaDB.mjs:96`, plus the `config-leaf-parity.json` entry.
- **Deliberate non-change:** `defragChromaDB.mjs:1538` keeps `config.path`. `loadConfig()` returns `targetDef.adapt(...)`, so that read is the **adapter's own output key**, not the leaf. A sweep-and-replace would have broken the adapter contract.
- **Mutation-tested both ways:** restoring the alias leaf → 1 failed; removed → **52 passed** across the four affected specs.
- AiConfig guards: `check-aiconfig-antipatterns`, `lint-config-template-ssot`, `check-aiconfig-test-mutation` — all **exit 0**.

### Two test repairs, one of which was already red

`defrag-segment-cleanup` fed the KB adapter a flat `host`/`path`/`port` mock while the adapter already read `engines.chroma.*` from this PR's earlier host/port collapse. It threw `TypeError: Cannot read properties of undefined (reading 'chroma')`.

**Why no gate caught it:** `.github/workflows/brain-unit.yml:42` runs `test-unit -- --list`, which *collects* the suite, then `:48` executes an explicitly named spec list. `defrag-segment-cleanup` is not on it. The check is named "Brain Unit" and goes green, which reads as "the unit suite ran". *(An earlier revision of this body and my review response said there is no unit check at all — that was wrong; it exists and runs a subset, which is the more useful and more alarming statement.)*

The `DestructiveOperationGuard` arm assigned a literal path to the removed leaf and would have gone green while exercising nothing. It now flips the test-mode **selector** (`useUnitTestDatabase` / `useTestHarness`) — the idiom the two arms above it use — so production resolves by construction.

`config.template.spec` asserts the child is **undefined** rather than equal to Tier-1: equality passes just as happily while the alias still exists.

Resolves #1829

PAT admission now keys on the provider subject instead of the login:
- **Allowlist.** `auth.allowedUsers` accepts subject-pinned entries that admit an account by its id: `login:providerUserId` in `NEO_AUTH_ALLOWED_USERS`, or `{login, providerUserId}` in a config overlay. A bare `login` stays the documented weaker form. A value that is not a list, and any entry that is neither form, refuses setup before either PAT verifier mounts.
- **Pin.** The first-use process pin keys on `[authProvider, providerBaseUrl, providerUserId]`. One shared factory serves both verifiers, and GitLab-PAT gains the same pin as an opt-in.
- **Disk tier.** A disk-cache entry records the provider endpoint that verified it. An entry without `user.id`, without its endpoint, or from another endpoint fails closed and leaves the store.

A renamed account keeps its access, and a newcomer who registers a released login gets none.

Evidence: L2 (spec-driven contract tests through the real SDK bearer middleware against stubbed providers) → L2 required (AC-1 and AC-2 are admission-contract properties).

## Deltas from ticket

- One private factory, `#createProviderSubjectPin`, serves both verifiers and replaces GitHub's inline login pin.
- GitLab's pin is an opt-in (`NEO_AUTH_PIN_FIRST_PROVIDER_SUBJECT=true`). The mode derivation still pins GitHub-PAT only, so GitLab-PAT's shipped admit-any default is unchanged.
- A malformed `allowedUsers` entry (`login:`, a non-numeric id, an object missing a field or carrying an extra one, a non-string entry) or a value that is not a list refuses setup instead of degrading to a bare login or an empty gate. The legacy comma string from an overlay written before the `csv` type still splits. The spec fixtures that hand-build an `auth` subtree now carry the leaf's default `allowedUsers: []`.
- A disk entry without `user.id` also leaves the store, so the next fresh validation writes a complete one. Disk entries carry `authProvider` and `providerBaseUrl`, and the cache reader passes them through.
- Three existing pin fixtures gained an account `id`, because the pin now needs a subject.
- out of scope, noted in defect-note `a8c71b9c765fca8e`: ConfigProvider's overlay merge drops an object written to the array leaf and resolves `[]`, which `AuthService` cannot tell from the intentional default.

Resolves #1750

A managed Codex seat that started on a generation declaring the supported wake protocol can keep its approved hook through a later Fleet-only update. Preparation and arming select the same executable and hook from the seat’s original managed Start. Fleet verifies that retained generation and its declared support for nonce redemption, a signed recipient receipt, and retry after a rejected recipient. The verification is shared within one Start. An explicitly migrated hook on the current host keeps its existing binding.

**First update on this installation.** The installed app and all four retained generations predate `codexWakeProtocol.json`. When the first update containing this change reconciles an enrolled survivor on one of those generations, the expected result is `codex-wake-compatibility-unproven`. Fleet keeps the hook bytes and pending mail, publishes no replacement route, and directs the operator to the seat’s next planned managed Start. Once that Start uses a declaring generation and the hook has been approved and invoked, the following Fleet-only update can demonstrate retention. [Installed acceptance row](https://github.com/neomjs/neo-agent-brain/issues/571#issuecomment-6072691768)

Evidence: L3 (Fleet setup on sealed disposable generations and cross-build signed transport controls) → L4 required (surviving installed Codex chat after a routine Fleet update). Residual: AC-3, Residual-Owner: #571.

## Deltas from ticket

The visible `NEO_WAKE_V1` marker exists in packages with different rejection behavior. A retained generation must also declare the supported hook protocol. A surviving seat with an unproved binding keeps its mail pending, with guidance for its next planned managed Start. The vendor still owns consent for a genuinely changed hook.

## Test Evidence

On a disposable copy of the `4c0517a9` runtime, I added the compatibility declaration and resealed the package. The candidate selected its actual executable and hook and preserved the registered hook bytes. The retained executable ran its real hook and nonce consumer against the candidate’s signed HTTP receiver. The first recipient refused. Two distinct markers yielded one digest, one delivery and zero pending records. Duplicate HTTP submission returned 200. Replaying the spent marker through a second hook process was blocked with no digest. Verifying the 974 MiB retained runtime took 3.1–6.3 seconds on this host across three runs. The test supplied the live process, vendor queue, root and model-receipt observations.

As a negative control, the `5d3ddfae` hook and its own consumer passed the normal delivery case, but a first-recipient refusal left one pending record and zero deliveries. This is why an older hook cannot establish compatibility from the visible marker alone.

Resolves #63

🌿 A durable plane can no longer pass a healthcheck under its host's canonical name.

A deployment now declares the state its id cannot express: a durable plane that is not its host's canonical one. The new Tier-1 leaf `plane.standalone` (`NEO_PLANE_STANDALONE`, default `false`) carries that declaration. `assertPlaneCoherence({…, standalone})` treats a declared standalone plane differently from an overlay. It may sit on the image-derived root (`/app/.neo-ai-data`), and instead of the overlay root collision it refuses the canonical id. An omitted `NEO_PLANE_ID` resolves to that id, so it fails closed with a message naming the variable. Undeclared deployments keep today's two states exactly.

The three boot callers (`BaseServer`, the orchestrator daemon, `fleetServer`) read the leaf at the use site and pass it beside `planeId` and `dataRoot`. The standalone Memory Core package pins `plane.standalone: true` in its detached config base, so "standalone" has one meaning across ADR-0019 §10.7.

Evidence: L2 (unit: the pure assertion, the leaf declarations, and the Fleet's boot guard driven with resolved configs) → L2 required (the ACs are boot-assertion behaviour; no deployment change is in scope). Residual: none.

## Deltas from ticket
- The shape follows design comment 6911080079 and @neo-opus-grace's read on #63: a boolean that says only what the id cannot. A `canonical | overlay | standalone` role would have given two states a second source (C4).
- Per Grace's read, the standalone Memory Core package declares it too (pinned, no env). The Neural Link package's §10.7 row says why the leaf does not apply there: a plane non-member runs no coherence assertion.
- The residual that a deployment declaring neither still boots as canonical is named in §10.4 with a revalidation trigger. It is not fixed here: §10.8's "declared, never inherited" would give the canonical plane a new required variable, which AC-3 rules out.
- `config-leaf-parity.json` records the added `plane.standalone` path.

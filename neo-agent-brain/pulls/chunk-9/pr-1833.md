Resolves #1813

Every provider-authenticated transport now carries its provider subject, and host-trusted ones carry none. Stdio `gh-cli` keeps the account `id` that `gh api user` returns. Once the cutover activates selection, it acts as the identity that subject is bound to, and a subject that selects none fails the boot by name. OIDC stamps `(issuer, sub)`, so #1812's relation keys it like a forge PAT, and the issuer is compared exactly. `NEO_AGENT_IDENTITY` and the trusted proxy stay host-trusted: no subject, and the login binding as before. Activation stays with #1814's gate. While selection is dormant, every transport selects as before, and nothing binds that did not bind before.

Evidence: L2 (the real OIDC verifier through the SDK bearer middleware against a fake introspection endpoint; the real SQLite relation and activation; `gh api user` stubbed) → L2 required (AC-1 to AC-5 are request-boundary decisions; activation and its live check belong to #1814). No residuals.

## Deltas from ticket
- **`gh-cli` base:** `providerBaseUrl` is the API base named by the `url` in the `gh api user` payload, not `auth.githubApiBaseUrl` (sharpened at intake). A `gh` signed in to another host keys its own subject. On github.com both transports key one account to one subject.
- **OIDC issuer:** only the issuer that discovery returns identical to the configured `issuerUrl` qualifies (OIDC Discovery §4.3). A response `iss` must equal it exactly (OIDC Core §16.15), and may be omitted. The host/realm fallback qualifies none, and `sub` counts only with `active: true`. A token whose issuer does not qualify is still admitted, with an incomplete subject that is refused by name once active (AC-5: nothing changes ahead of the gate).
- **Dormant provisioning:** only a forge PAT admission binds its subject at first admission while dormant. An OIDC source allowed to create keeps the legacy node, and binds only behind the activation gate.
- **Stdio without a login:** a provider-stamped stdio result without a login stays single-tenant while dormant, and decides by its subject once active.
- **Reader census of the new writer:** `createFleetRequestContext` resolved an owner for any `authProvider`, and `resolveViewerStreamKey` keyed a viewer on any `authProvider` with an id. Both now act only for forge providers (ADR 0038 §2.2 fact 2). An OIDC `sub` is unique only per issuer, and is owned by no forge connection. Fleet's decisions for OIDC are unchanged.
- **Trade-off, as #1812's PR took it for PAT:** stdio `gh-cli` boots and OIDC requests now read the activation, so a graph that cannot answer refuses them by name before the cutover too. `NEO_AGENT_IDENTITY` and proxy requests never read it.
- Comments state the rules. ADR 0038 §2.2 facts 2 and 5 are cited here, not in code.

Resolves #1856

A Start whose project binding a new, unproven Antigravity build refused now runs once more on the family's newest proven build, instead of leaving the seat stopped as on 11-19. A generation is proven by its first bound Start (`provenAt`). When the retry binds, the refusal counts against the new build: a late refusal rejects it, an early one rejects it the second time at the same step, and a refused retry counts nothing. A rejected build is never selected or fetched again, and its copy goes at the next retirement. A port file that never appears now refuses `endpoint-missing`, apart from a stale `stale-endpoint`.

Evidence: L2 (unit specs: real ledgers on disk, the lifecycle over store fakes, the provisioned Start over a recording lifecycle, each branch mutation-checked) → L3 required (a watched Gemini Start on the operator's Fleet, #1856's Post-Merge Validation). Residual: #1856's two Post-Merge Validation items, Residual-Owner: #1531.

## Deltas from ticket
- The retry lives in `startAgentProvisioned.mjs`, not in `finishAntigravityStart`: the provisioned Start bakes the generation into the capability, the preparation, the reservation and the binding callback. The pin follows the epic owner's choice (A) with both guardrails: only a retry the lifecycle grants can pin, only the newest proven generation, and a pinned Start never retries.
- Only an `AntigravityProjectBindingRefusal` counts. A failure after the binding, such as grant recovery or a changed plan, carries no refusal, so it can never reject a build.
- A rejection writes only the ledger, and the next retirement removes the copy unless something holds it. Removing it at rejection time would race the still-pending Start, which `heldHarnessGenerations` refuses to read through.
- The refetch guard keys on binding rejections only, so an admission rejection keeps today's nightly retry. Acquisition answers `already-rejected` (`reason: 'binding-refused'`) rather than `up-to-date`.
- `onChain` and `writeLedger` replace four inline copies of the family chain and the ledger write in `harnessGeneration.mjs`.

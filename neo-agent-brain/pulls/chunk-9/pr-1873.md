Resolves #1871

A sunset rotation whose window lost the front after Cmd+N used to fail, because a retry would press Cmd+N again, so the seat sat on an empty session until the plane's window ran out (Vega, 2026-11-20 00:06Z, "before wake paste"). Such a loss now defers as `session-opened-front-lost` and records the pid whose Cmd+N opened the session (`sessionOpenedPid`) and when the attempt that pressed it began (`sessionOpenedAt`). The next attempt resumes only in that process and only while no one has used the keyboard or pointer since that attempt began, with the holder, front and cutoff checks before its first key. It skips Cmd+N and its 1.5 s wait, then clears and pastes into the open session. Another process behind the profile fails the rotation as `session-rotate-process-changed`, and input since the attempt began fails it as `session-rotate-destination-unproven`, both without a key. These losses count toward `ROTATION_MAX_ACTIVATION_LOSSES`, and a capped record says whether its session is open.

Evidence: L2 (mocked osascript spawn and the receiver's state machine in `test/playwright/unit/ai/daemons/wake/sessionRotation.spec.mjs`) → L2 required (AC-1 to AC-3 are unit arms).

## Deltas from ticket

- Two existing arms pinned the old outcome ("a later loss fails it", and the lock case "after a keystroke the failure stands"). Both now expect the resume; the `#1770` title prefix stays, so citations still find the lock arm.
- The ticket's open question (can the adapter confirm the focused session before the paste) is answered with two observations. The resume is bound to the process whose Cmd+N opened the session, and to no keyboard or pointer input since the attempt that pressed Cmd+N began: only a person's input could switch that window's chat, during the wait after the keystroke as much as after the loss, and nothing reads the chat itself before the session's first prompt. When either observation fails, the rotation stops without a key. So a loss caused by someone's input never resumes; it fails as it did before. A loss nothing human caused, such as another app taking the front, recovers.

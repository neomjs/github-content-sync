Resolves #1782

Keep the graph Store's secondary indexes synchronized when lazy hydration replaces a raw row with a Record. Removing an edge can then remove the indexed object, so rollback restores one source/target reference instead of retaining the raw alias. The fix stays in `Store.hydrateRecord`; the shared Database transaction implementation and protected-write behavior are unchanged.

Evidence: L3 (actual Database and SQLite with disposable in-memory storage) → L3 required (AC-1–AC-4). No residuals.

### 🔬 Depth Floor

**Challenge OR documented search (per guide §7.1):**

- **Challenge**: The defect is wider than #1782 and this body say: on `dev`, a *committed* removal also leaves the edge indexed. I probed with in-memory SQLite against Brain `dev`'s `ai/graph`, which is this PR's base. After `graph.transaction(() => graph.removeEdge('e'))`, `edges.getCount()` and the SQLite `Edges` count are both 0. Yet `getByIndex('source', 's')` and `getByIndex('target', 't')` both still return `e`, and `getAdjacentNodes('s')` returns `t`. That holds whether the edge was raw or pre-hydrated, because `removeEdge` hydrates the edge before removing it. With this head's `Store.mjs`, all three are empty. Production removes edges in `GraphService`, `WakeSubscriptionService`, `PermissionService` and the ingestors. Until a Memory Core restart, index readers such as `getNeighbors`, `getAdjacentNodes` and inbound-edge lookups could list removed relationships. `hasPermission` iterates `db.edges.items`, so permission revocation was never affected. Your final committed-removal assertions already pin this. On base they are never reached, because the rollback assertions fail first. The release note should describe this broader fix. No change requested.

- **Documented search**: *"I actively looked for (1) any `hydrateRecord` caller that could pass a stale or foreign raw object, which the override would index as an orphan record. `git grep` at `6df4f1be` finds only the override itself, which is the positive control, and the base Store calls the hook only from `get`/`getAt`, both of which pass the current object. (2) Index-order dependence: delete-plus-add moves a hydrated item to the end of its set. `getNeighbors` sorts before it paginates, related tickets are sorted, and traversal has no result cap. (3) A raw/record value mismatch, which `updateIndexMaps` handles by deriving each side's value its own way. I found no concerns."*

The two new tests destroy the graph but not the `SQLite` they create. `Database.destroy` does not release a storage it was handed, and the explicit-storage siblings call `storage.destroy()`. `SQLite` has no `destroy` override, so the effect is two instances left registered in the unit worker. Not blocking; no change requested on this head.

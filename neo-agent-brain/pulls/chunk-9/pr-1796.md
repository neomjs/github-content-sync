Resolves #1548

🌿 A session's summary can no longer rename a concept the ontology owns.

`GraphService.upsertNode` now guards a projected ontology `CONCEPT` (one with a 64-hex `payloadHash`) the way it already guards an admitted ADR. Only the ontology's own write may relabel the node or rewrite `CONCEPT_PROTECTED_PROPERTY_KEYS`: `type: 'CONCEPT'` with a 64-hex `payloadHash` or a `conceptProjectionVersion`. The protected keys are every field `ConceptIngestor` projects, its projection markers, and the stored vector binding. Every other writer can still add enrichment keys.

So REM's `SemanticGraphExtractor` can no longer turn `agent-os` into a `CLASS` carrying a session's name, description, tags and `summary_*` vector in the middle of a cycle, and Phase 4 gap inference sees the concept again. ADR behaviour is unchanged. The top-level `name`, `description` and `semanticVectorId` parameters now follow the active protected-key set, and the ADR set protects `name` and `semanticVectorId` as before.

Evidence: L2 (unit: the real `GraphService` over SQLite, driven through `ConceptIngestor`) → L2 required (AC-1 to AC-3 are write-seam behaviour). Residual: none.

## Deltas from ticket
The ticket's sharpenings are in intake comment 6910907771:
- A write counts as authoritative only when it is typed `CONCEPT`, mirroring the ADR echo rule.
- The protected set is the ontology's whole projection, exported as `CONCEPT_PROTECTED_PROPERTY_KEYS`, and `tags` is part of it. The extractor writes `tags`, the payload hash covers it, and #1547's repair never compares it. The test asserts that every projected key is in the set.
- `semanticVectorId` keeps its stored value, because `StorageRouter.mjs:198` keys retrieval weight by it.
- #1547's repair test now writes its clobbered row past the guard, since the guard refuses the old simulation. The repair still covers rows clobbered before this ships.

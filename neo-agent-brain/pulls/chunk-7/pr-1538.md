Resolves #1537

Adds `ai/services/fleet/codexDesktopUpdate.mjs` (the Codex Desktop acquisition leaf, AC-4 of Epic #1531) and exports `readHarnessGenerationLedger` from `ai/services/fleet/harnessGeneration.mjs`:
- `readHarnessGenerationLedger` exposes the canonical ledger reader from `ai/services/fleet/harnessGeneration.mjs` so update acquisition reads `{version, admitted, rejected}` through the ledger owner.
- `readCodexSparkleConfig` reads `CFBundleIdentifier`, `CFBundleShortVersionString`, `CFBundleVersion`, and `SUPublicEDKey` from `Contents/Info.plist` alongside `codexSparkleFeedUrl` and `codexSparklePublicKey` from `Contents/Resources/app.asar`'s embedded `package.json`, refusing key mismatches or non-HTTPS feeds.
- `parseCodexSparkleAppcast` strips nested `<sparkle:deltas>` (`sparkle:deltaFrom`) enclosures before selecting full-archive `.zip` releases compatible with `arm64` and the host macOS version (`minimumSystemVersion <= hostSystemVersion`), ordered newest-first by `buildVersion`.
- `verifySparkleEdSignature` checks the downloaded archive's exact byte length against `<enclosure length>` and verifies its 64-byte `sparkle:edSignature` against the 32-byte raw `SUPublicEDKey` (wrapped in RFC 8410 Ed25519 SPKI DER) via `node:crypto.verify(null, ...)` before extraction.
- `acquireCodexDesktopUpdate` serializes per family store, short-circuits when the newest appcast build is already in `ledger.admitted` (`up-to-date`) or was already rejected by the current `admitterId` in this process (`already-rejected`, expiring automatically when the admitting code changes), supports `checkOnly: true`, extracts `ChatGPT.app` via `/usr/bin/ditto -x -k`, and hands the extracted bundle to `materializeHarnessGeneration`.

### 🔬 Depth Floor

**Challenge:** `verifySparkleEdSignature` calls `readFileSync` on the 815 MB archive inside the Fleet server process. Pure Ed25519 has no streaming verify in Node and Sparkle signs the whole archive, so the read itself is unavoidable. Running the verify in a short-lived child (`process.execPath` with `ELECTRON_RUN_AS_NODE`) would hand the allocation back to the OS when it exits, instead of growing the FM's heap. Non-blocking.

Further non-blocking notes:
- Acquisition-side refusals (`sparkle-signature-invalid`, extraction) are not remembered, so a persistent bad signature re-downloads 815 MB every poll. The scheduler leaf should rate-limit, or the skip should cover them.
- Two concurrent `acquireCodexDesktopUpdate` calls: the second run's `.acquire-*` sweep deletes the first's in-flight staging directory. Serialize per root, like `materialize` does, or sweep only stale directories.
- `expectedLength` reaches the downloader but is unused, so there is no early abort on an oversize body.
- `compareBuildVersionsDesc`'s lexical fallback misorders dotted versions. Codex builds are integers, so this is not live.

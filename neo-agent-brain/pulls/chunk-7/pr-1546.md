Resolves #1536

A `repair-ci` wake now says what failed. Before its send, the wake round reads the head's checks once, as the author seat with its own PAT (the producer's `seatReaders`).
- The body carries every failing check's name; the subject carries the first three, plus a "+N" count.
- A failed, truncated or unread list still sends the wake, marked names-unknown.
- Pulses never read names; only an admitted red episode does.

Evidence: L3 (unit, plus a read-only live run of the new query and parser on three red heads, cross-checked against `gh pr checks`) → L4 required (AC4: a live wake once wakes are on). Residual: AC4, Residual-Owner: #759.

## Deltas from ticket
- **Added: only each check's latest run counts.** A head keeps every run of a re-triggered check, and GitHub's rollup still reads FAILURE after the latest run passed. On Brain #1502, `Shared PR Baseline / PR body` failed in run 1531 and passed in run 1534. Without the rule, the wake would name a check that is already green.
- **Added: the names go in the subject too.** It's what a woken seat reads first.
- **Out of scope, noted in a defect-note:** the producer reads the rollup's state, so such a head stays red (`openWorkReducer.mjs`). With this PR, its wake says "failing: none at send time".
- **Cost:** one read, about 1 point, on the author's PAT per red episode. It runs outside the producer's pulse telemetry.

### 🔬 Depth Floor

- **Challenge**: In `failedChecksOf(data)` (`ai/services/fleet/wireFleetOpenWorkWakes.mjs:65-75`), `StatusContext` nodes do not carry `startedAt` in `OPEN_WORK_FAILED_CHECKS` (`openWorkQueries.mjs:249-252`), so `started(node)` evaluates to `Infinity` for every `StatusContext` and `started(node) >= started(prior)` (`Infinity >= Infinity`) keeps the last `StatusContext` in page order for a given `context` key. Because GitHub's `statusCheckRollup.contexts` returns the latest status per `context` or orders newer statuses last within the first 100 contexts, this behaves deterministically, and if a repository ever mixes a `CheckRun` and a `StatusContext` with the same name and `null` workflow, `StatusContext` would win `Infinity >= finite`. In our repos all legacy commit statuses have distinct `context` strings and `CheckRun` nodes carry a workflow name, so this is non-blocking.

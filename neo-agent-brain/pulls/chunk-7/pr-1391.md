Lane: Brain #1390 — the MCP bridge's recovery; transport hygiene, no identity change (ADR 0020 §4.3 and neo Discussion 19401 untouched).

Resolves #1390

When the bridge retired its remote generation — a lost notification, a dropped stream with a request pending, an exhausted reconnect — it built the replacement without a session id and re-initialized, so `TransportService` minted a new `Mcp-Session-Id` while it still held the old session, and every default `add_memory` from then on landed in a new Memory Core session (the machine's shared Claude bridge log: 101 renewals against 482 survived errors since 2026-10-15 across its Claude seats; tonight one renewal split one conversation in two, and a second seat saw three). Now `retire` remembers the retired transport's session id unless the server refused it (404); the next `ensureRemote` builds the replacement with that id, sets the negotiated protocol version, opens the stream and returns it with no handshake — the first forwarded request proves the session, and a 404 there answers that request locally and renews through the existing fresh-initialize flight. The resumed generation opens its standalone GET stream on purpose, best-effort (the SDK opens it only after an initialized notification, which a resume never sends): that stream is the idle liveness probe, so a server restart still retires the generation as refused before the next request. A lost notification no longer retires anything: it is reported like a lost request and the session is kept. The report vocabulary distinguishes `is resuming` from `is renewing`.

Evidence: L2 (unit arms with fake transports, the real SDK client against a loopback server, and the executable end to end; a positive control; hosted CI on this PR) → L2 required (every AC is a bridge observable). Residual: none — the week count on #1390 is an observation the ticket records, not an obligation of this PR.

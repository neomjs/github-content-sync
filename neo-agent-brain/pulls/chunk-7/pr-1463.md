Resolves #1462

The fleet entry the packaged Fleet Manager spawns now takes its plane bearer from the launcher's credential pipe. `fleet.planeCredentialFd` names an inherited fd that carries `{"bearer", "bearerClass"}` JSON lines: the first frame is the boot bearer, and each later one is a rotation the running server adopts once it passes the teeth a configured bearer meets and the plane proves it for the bound viewer (`planeMailboxClient#rotate`, the first commit). A forge-PAT class re-arms the wake stream and the seat-define client with the successor. Every frame is answered on the same fd: adopted with the identity, or refused with the reason, naming another account beside the bound one. With the fd unset, boot is unchanged. This is the Brain half of neomjs/neo-agent-institution#843; the FM side and the ADR 0034 amendment ship there.

Evidence: L3 (the real fleet entry, spawned as the FM spawns it with fd 3, against a loopback fixture plane) → L3 required (AC-1 to AC-5 are the server's pipe answers, plane sessions and log lines). No residuals.

## Deltas from ticket

- The ticket missed a second audience, corrected in its body before this PR: with a forge-PAT class, the packaged FM's case, the same bearer arms the plane's `/fleet` surface. So a rotation re-arms the wake stream and the seat-define client, and each frame carries its class, which travels with its bearer as `plane.json` records it.
- A piped bearer meets every alias tooth a configured one meets, not only the admission token's, at boot before its answer and at every rotation: `assertFleetPlaneBearerClass`, `assertFleetPlaneAdmissionBearerClass`, `assertFleetViewerMcAuthorizationClass` and `resolveFleetPlaneAdmissionBearer` take an optional `planeCredential`, and the transport's viewer-mint check receives the piped one.
- With the fd set, a declared `planeBearer` / `planeBearerFile` (readable or not, `declaresFleetPlaneBearer`) or an empty `planeBase` refuses the boot, answered on the pipe.

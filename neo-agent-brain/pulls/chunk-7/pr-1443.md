Resolves #1439

🌿 *After this, no accepted message stays out of the index by default, and no retracted one stays in.*

The embed daemon now drains the message WAL into a `messages` collection. It does so through the existing drain: `drainCycle.mjs` gained a store seam instead of a parallel pipeline. Each row carries the send-time routing that #35's admission filter will read: `from`, `to`, `kind`, `threadId`, and for broadcasts `cohort` plus `recipients`.

A retraction marks the WAL record `retracted` before deleting the vector, the order a session purge already uses. A retraction that lands while the drain is mid-`add` is therefore undone by the drain's existing purge-race compensation.

The index is derived from the graph, so it stays out of backups; #1440 rebuilds history from the graph. Related: #35 (parent), #1440 (backfill leaf).

Evidence: L1 (unit specs + Brain lints at `8f14243a`; the sandbox cannot run the plane's embed daemon) → L3 required (AC-5: the plane's embed daemon draining live messages). Residual: AC5, Residual-Owner: #35.

## Deltas from ticket

- **Backfill split out to #1440** (the ticket was amended before this PR). It runs in the MC container against the graph, not against the WAL.
- **The index is not exported.** 4096-d vectors would add about 16 KB per message to every daily bundle, for data #1440 rebuilds. `truncate` takes `messages` opt-in instead.
- **Message-WAL pruning now waits on embed markers** as well as graph markers. The embed drain therefore never loses a record to pruning, matching the memory WAL.
- **No new drain lock.** The messages dir's `.drain-lock` belongs to the message daemon (graph markers); this loop writes only embed markers, and the embed daemon's singleton keeps it the sole embed drainer.
- **Polish.** Three ticket refs in `CollectionProxy`'s comments were rewritten as prose, because the archaeology guard reads touched files whole.

Resolves #1448

🌿 *After this, no host can embed memories while skipping messages.*

The plane hosts its embed drain inside Memory Core (`NEO_MEMORY_WAL_IN_PROCESS_DRAIN=true`), and #1443 started the message loop only in the standalone embed daemon, so no message was embedded on the plane. `startEmbedDrainLoops` (`drainCycle.mjs`) now starts both loops. The embed daemon and `Server.mjs`'s in-process branch, under its memory-WAL lock, both call it.

Related: #35, #1439 (the defect's origin, post-merge comment 6591683330).

Evidence: L1 (unit spec + lint at `4915a138`; the plane observation needs a re-cut after merge) → L3 required (AC-3: a message embedded on the plane). Residual: AC3, Residual-Owner: #35.

## Follow-ups

- #1440 takes Julia's non-blocking hardening note as Fix 5 / AC-7: `startDrainLoop`'s `tick` reads `getConfig()` inside its `try`, so a missing slice is a failed cycle and never ends the loop. Template inheritance makes the case unreachable on canonical deployments, so this PR stays unchanged at its approved head. #1440 is linked `parent_child` to #35 and `blocked_by` #1439.

### 🔬 Depth Floor

- **Challenge**: Non-blocking edge case between `startDrainLoop` (`ai/daemons/embed/drainCycle.mjs:647`) and `Server.mjs` (`ai/mcp/server/memory-core/Server.mjs:358-368`): inside `startDrainLoop`'s `tick`, `const {dir, batchSize, maxRetries, backoffBaseMs, retentionLimit, pollIntervalMs} = getConfig();` runs *before* the `try { ... } catch` block (`:649`). In `daemon.mjs`, both `memoryWal` and `messageWal` config leaves are validated at startup (`:48-53`), whereas in `Server.mjs` `startEmbedDrainLoops` is gated on `if (aiConfig.memoryWal && aiConfig.memoryWal.inProcessDrain)` while `getMissingMessageWalLeaves` is only checked in the separate `if (aiConfig.messageWal && aiConfig.messageWal.inProcessDrain)` block below (`:385`). On canonical deployments (`config.template.mjs` and the container plane where both flags are enabled) `aiConfig.messageWal` is always populated, so this cannot fire in production; moving `getConfig()` inside `tick`'s `try` block would also make `startDrainLoop` self-contained against an undefined config slice in partial overlays.

Resolves #1403

🌿 *An unclassified embed failure can no longer leave `errors=1` as its whole trace.*

Both embed error sites in `IngestionService.embedChunkGroups` attach a code-authored `trace` to an entry whose code is the unclassified `KB_VECTOR_EMBED_FAILED`. The trace has three fields: the stage (`embed-returned` or `embed-thrown`), the error's class read from its prototype, and whether any raw code was present. `TenantRepoSync` turns it into one WARN per attempt, beside the `materialized:` line and before both outcome guards, so deferred and failed attempts both carry it. The 10-30 failure would have read `stage=embed-thrown class=SyntaxError rawCode=absent`. The message, the raw code and `details` never cross the credential boundary. `formatEmbedFailureTrace` re-validates every field on read, and the class gate admits only a PascalCase identifier, `none` or `other`.

Evidence: L2 (unit specs, red on `dev` first) → L3 required for AC-3 only (a plane running this head). Residual: AC-3, Residual-Owner: #64.

## Deltas from ticket
- The WARN sits beside the per-attempt `materialized:` line, not the deferred line. It runs before both outcome guards, so a failed attempt carries it too, as The Fix asks ("defers or fails").
- Stage tags name the two `embedChunkGroups` call sites, not phases inside `VectorService.embed`. The class alone located the 10-30 failure; a phase tag would need stage bookkeeping inside `embed()`.
- On the returned path, the class is that of the result's `error` field, which is `none` for the string every current producer returns.
- `classifyEmbedFailureError`'s cause-chain walk is now a generator that the trace shares. Behaviour is unchanged, and its specs pass unmodified.
- A third arm pins the boundary claims: a thrown JSON body's own `constructor` field cannot name the class, and the formatter refuses a trace it did not mint.

Resolves #1038

The issue corpus now keeps the fresh rendering over stale ones. `IssueSyncer` used to write the new markdown to `targetPath` and then `fs.rename` the old file onto it, so an updated issue whose planned path moved kept its old content. It now writes and then unlinks every other copy: the metadata path, plus each active-tier copy in the complete inventory it already builds. That second set catches the file that `reconcileActiveChunks` relocated without updating the metadata. `refetchIssuesByNumber` follows the same rule. `reconcileActiveChunks`' dedup keeps the copy with the newest frontmatter `updatedAt`, where it used to keep the first in path order, so a duplicate that some other path leaves behind can no longer survive as the stale copy. The `PullRequestSyncer#repairDuplicateArtifacts` docblock had stated the premise that broke here ("the next sync rewrites the survivor"); it now gives the real reason.

Evidence: L2 (unit tests over a temporary content root; each new test red on unfixed `dev`) → L2 required (AC-1 to AC-3). Residual: AC-4, the live corpus after the publisher's next run plus a refetch of the stale numbers. Residual-Owner: neomjs/github-content-sync#3.

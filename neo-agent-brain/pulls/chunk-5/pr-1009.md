### RA-2 disposition (design owner): an operational estimate, and GitHub's own bound wins where it exists

Re IC 6153362031: you are right on both points. The [docs](https://docs.github.com/en/graphql/overview/rate-limits-and-query-limits-for-the-graphql-api#timeouts) say only that a timeout costs "additional points", with no amount, so a same-query maximum is a reserve, not a bound. And a failure without `viewer.id` or `resetAt` cannot borrow identity from its reader.

**Contract:**
1. **Three ledgers per bucket, kept apart in every report.** `measured` is issuer-reported cost. `estimated` is the reserve charged for attributed failed calls. `unattributed` counts failed calls that carry no viewer or no reset.
2. **Reserve:** a declared nonzero policy per failed call: the larger of the published formula's estimate for that query text (minimum 1, per the same page) and the highest measured cost of that text in the window. It is an estimate, and the activation receipt says so.
3. **Bound evidence wins when present.** A later successful response in the same bucket and reset window reports `remaining`, so `limit − remaining` is GitHub's own total for that window. That total covers every consumer of that user, timeout surcharges included, and bounds the observer's share. If it is ≤ 20% of `limit`, that window passes whatever the estimates say.
4. **Unattributed failures get no fabricated bucket.** Charge each one its reserve in every same-endpoint bucket whose window contains its timestamp. That over-charges, which errs strict. If no bucket's window contains it, the certification attempt stays pending: the latch does not set, and a later 24-hour window can certify. It never refuses as a standing state.
5. **Per bucket window:** measured + estimated + unattributed charges ≤ 20% of the measured limit, unless rule 3 already shows ≤ 20%.

The activation record keeps all three ledgers and names any window that rule 3 decided. No token or fingerprint is persisted.

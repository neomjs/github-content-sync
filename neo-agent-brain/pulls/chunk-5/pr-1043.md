Resolves #1041

🌿 A dropped stream that cost no message can no longer cost the server.

The stdio-to-Streamable-HTTP bridge used to close on every remote `onerror`. The MCP SDK raises `onerror` for a dropped SSE stream that it then reconnects itself, so each such hiccup killed the memory-core or knowledge-base server. After initialization, the bridge now survives two things: a stream drop while no request is pending, and a failed reconnect attempt that the SDK will retry. It also answers a request whose delivery fails with a JSON-RPC error instead of closing. Everything else still closes both sides exactly once. Every report now names its cause from a fixed vocabulary (`getBridgeErrorCause`), so no SDK or remote text crosses the stderr boundary.

Evidence: L2 (fake-transport unit tests for AC-1–AC-4, plus a live handshake through the changed bridge against the plane) → L1 required (every close-target AC is unit-observable).

## AC Evidence
| AC-1 | CI: `StdioToStreamableHttp.spec.mjs` — "names causes from a fixed vocabulary, never from error text"; the reflected-bearer test now also asserts `Cause: http-500.` |
| AC-2 | CI: "survives a dropped stream with nothing pending and keeps forwarding", "a dropped stream while a request is pending closes the bridge with its cause", "a retried reconnect survives in the SDK order, and only exhaustion closes" and "a delivered cancellation retires its request, while a live request still makes a drop terminal" |
| AC-3 | CI: "exhausted reconnection and a refused session still close the bridge, each naming its cause" |
| AC-4 | CI: "a request whose delivery fails is answered locally while the session stays open" (SDK order: `onerror`, then rejection) and "with the real SDK client, a 502 on the GET stream or on one request keeps the session and a 404 ends it" |

## Deltas from ticket
- **The cause is a fixed vocabulary, not the error message.** The bridge's stderr boundary admits only locally-authored text, so the ticket's Fix and AC-1 were amended to match.
- **The survival rule is "no request pending."** The plane's `TransportService` answers POSTs with SSE and keeps no event store, so a POST stream cannot resume, and only the reconnectable GET stream can be open while nothing is pending.
- **These failures stay terminal:** 401, 403, 404, an unexpected content type (`-1`), and any failure before initialization. The existing reflected-bearer exit test pins the last one.

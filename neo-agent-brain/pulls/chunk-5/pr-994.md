Resolves #981

🌿 What the review tool refuses as a new Round 2, it no longer accepts as an edit.

`manage_pr_review` ran the Round-2 relation (`getRound2DispositionRelationFailure`) on `create` only. Now `update` reads the pull request's reviews in the query it already makes (`GET_PULL_REQUEST_REVIEW`). It runs the same relation, leaving out the review being edited so a review can't be its own Round 1, and reads that review's GitHub state under the names the state matrix uses (`COMMENTED` → `COMMENT`, `CHANGES_REQUESTED` → `REQUEST_CHANGES`). `create` is unchanged.

Evidence: L1 (unit specs drive the managed `update` path with GraphQL stubbed) → L1 required (AC-1 to AC-3 are unit-observable; AC-4 shipped in neomjs/neo-agent-skills#170). Residual: none.

## Deltas from ticket

- The ticket placed the fix in `PullRequestService.mjs`. The update path held no reviews, so `GET_PULL_REQUEST_REVIEW` (`queries/mutations.mjs`) now projects `reviews(last: 100)` in its one round trip. That is the same window `create` reads.
- A third spec pins the state mapping: a `STILL_OPEN` round is admitted as an edit of a COMMENTED review and refused as an edit of an APPROVED one.
- Touching both files makes the source-comment archaeology guard read them whole. It flagged 23 comment lines, 22 of them already there before this PR. ff31fc68 rewords them, comments only. Most hits were this module's own vocabulary (review rounds, RA labels with digits), and the guard has no escape for review-archaeology patterns: out of scope, noted in a defect-note.

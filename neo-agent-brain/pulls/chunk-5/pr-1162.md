Resolves #1148

A backup can no longer publish a bundle whose heal ledger copy is torn.

- **`pruneHealLedger` replaces the ledger atomically,** so a backup copying it mid-prune reads the whole old file.
- **The backup runs restore's own ledger rule before publication.** A copy restore would reject is refused, and the previous bundle stays newest.

Evidence: L2 (unit: a held reader across a prune and a torn-ledger backup run, both red on `dev`; restore's probe verdicts) → L2 required.

## Deltas from ticket
- **The prune keeps the ledger's mode.** `writeFileAtomic` defaults to 0600, while the ledger is created with the process default, so the prune passes the existing mode through instead of tightening it as a side effect.
- **Error precedence inside `validateBundle`.** `validateIncidentLedgers` runs where the generic loop used to stream ledgers, before `bundle-meta.json` is parsed. A malformed `heal-attempts.json` or recovery-run row is therefore now reported ahead of a malformed meta file. Both give the same verdict, `BUNDLE_INVALID`. The messages are unchanged.
- **IO failures are not refusals.** The backup gate converts only `BundleContentError` into `INCIDENT_LEDGER_INVALID`, and an unreadable copy propagates as itself, so an IO fault is not mislabelled as a torn ledger.

`removeRepoCheckout({id, repoSlug})` deletes an unlisted checkout only after checking retained work, through the existing `removeAgentRepo` mechanism. It protects configured working/listed repositories, checks the current definition inside the seat-home hold and again before removal, and retires only the removed repository's current Lifecycle outcome on success.

## Deltas from ticket

The author folded ignored-file ownership, all-ref inspection, outcome retirement and nested/shared Git refusal into the live ledger during implementation. The guard also strips inherited Git path/config overrides and checks every path component from the managed root; an environment-override control and ancestor-link control exercise those boundaries.

Two further real-Git controls reproduced modified tracked files hidden by `assume-unchanged` or `skip-worktree`. The guard refuses those index flags because a working-tree inspection cannot establish cleanliness while they suppress it.

Change class: capability. The remover, dependency-receipt reader and seat-home hold remain the existing owners. No second recursive remover, force option, new module or configuration resolver.

## Test Evidence

All coverage runs in CI. The real-Git ignored/detached/tag controls exposed the original proposal's blind spots; the clean parent with an unpublished nested branch then reproduced a false removal decision through a recording seam. That test deleted nothing. The linked-worktree case uses temporary metadata exercised by Git's actual worktree-list read, not a managed resident worktree.

The guard uses local remote-tracking refs without fetching, so it does not prove current remote durability. It neither detects open folders nor prevents an external process from writing during the reads. Nested/shared Git storage is explicitly unsupported. A filesystem removal failure can leave a partially removed checkout and is reported as such.

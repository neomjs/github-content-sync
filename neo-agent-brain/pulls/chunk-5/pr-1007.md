Resolves #1006

The miniSummary backfill now snapshots pending WAL content before querying Chroma, so an embed completing between the reads cannot turn a durable accepted turn into a `no-content` archive. Read failures defer the batch. Compose binds the orchestrator's reader to MC's existing shared WAL directory. Previously false archives can be inspected and repaired by exact IDs under one explicitly selected tenant and agent, through the existing leased lifecycle command.

Evidence: L2 (actual service methods, isolated SQLite/WAL and controlled content-store responses) → L2 required for the source repair and reconciliation contract. Residual: deployed verification and historical recovery, Residual-Owner: #1005.

## Deltas from ticket
The existing `backfill-memory-summaries.mjs` gains an explicit reconciliation mode; there is no new MCP tool, service, config leaf or scheduler. No arguments retains normal backfill. `--reconcile-no-content <id,...> --user-id <tenant> --agent-identity <identity>` reports eligibility; `--apply` permits repairs. This is local operator-controlled maintenance, not authenticated remote impersonation. The existing heavy-maintenance lease still encloses execution.

Reconciliation requires matching graph and payload ownership. A synchronous SQLite transaction rechecks the exact row and the durable identity tombstone before clearing only `archivedAt` and `archivedReason`; changed rows refuse and only repaired cache entries are updated. Either durable source can supply positive evidence. `no-positive-content` does not certify absence: malformed WAL entries may be skipped by the existing parser. Normal lifecycle startup projection work is unchanged; dry-run means this reconciliation performs no repair writes.

### 🔬 Depth Floor

**Challenges** (all non-blocking; your three questions first):

1. **Positive-content / identity-tombstone transaction boundary: sound, with one bounded residual.**
   - The identity tombstone is re-read inside the transaction (`MemoryService.mjs:2290`), the row is compared with its snapshot (`:2291`), and the clear is a CAS on `id`, `data`, owner and reason (`:2281`). A late identity archive, a backfill write or a concurrent change therefore refuses.
   - Content evidence is read before the transaction, as async reads have to be. `SessionService.purgeSession` (`:1646`) tombstones the session's pending WAL records, deletes its Chroma rows and drops SummarizationJobs (`:1699`, its only graph-DB write). It never writes the AGENT_MEMORY node.
   - So a purge landing between the evidence read and the transaction still matches the CAS, and the row is restored with no content behind it. Nothing purged becomes readable: the Chroma rows are gone, and `readPendingWalRecords` skips marked WAL records. The next backfill pass finds no content and re-archives the row `no-content`.
   - Accepted as is. It takes an exact-id operator run racing a purge of the same session, and it heals itself.
2. **CLI local operator scope: right-sized.**
   - It selects an owner rather than authenticating a caller, and the entry JSDoc says so.
   - It needs a shell on the plane, defaults to dry-run and takes at most 100 exact ids. It holds the existing heavy-maintenance lease (owner `memory-summary-backfill`, reason `manual-cli`), so ADR 0014's task table and ADR 0022's lease table stay accurate.
   - A row is restored only when its graph owner and its payload owner both equal the selected owner.
   - `parseArgs` is strict, but the scheduled spawn passes only the script path (`taskDefinitions.mjs:385`), and nothing in `ai/`, `deploy/`, `.github/` or `package.json` passes arguments. The scheduled lane therefore keeps `null` → `backfillMiniSummaries()`.
   - Because the specs hand-inject the fields reconciliation keys on, I checked the production writer. `addMemory` puts `prompt`, `response`, `userId` and `agentIdentity` on the same metadata object it appends to the WAL (`MemoryService.mjs:591–638`), so the specs use the shape production writes.
3. **Actual backfill producer path: correct in every profile I found, with one latent gap.**
   - Every profile that runs the orchestrator now shares MC's WAL:
     - base: `docker-compose.yml:284` / `:484`, with `shared-sqlite-data` mounted on both services at `:347` / `:536`;
     - base+local-agent-os and provider-lanes inherit base;
     - dev parity: MC and orchestrator both merge `*plane-env`;
     - parity-ci inherits dev;
     - packaged Fleet Manager: one `buildPackagedBrainEnv` value reaches the orchestrator and the Fleet server (Institution `harness/brain.mjs:671`, `main.mjs:1140` / `:1156` at `4183ecc`).
   - parity-capture and the test compose run no orchestrator.
   - The gap: `strict` covers thrown read errors, not WAL visibility. I ran `readPendingWalRecords` at blob `bd69eb69`, which is identical at `0525fb23` and `dev`:
     - control, a dir holding one appended record → `['falsifier-row']`;
     - absent dir → `[]` with no throw (`memoryWalStore.mjs:339` maps ENOENT to `[]`);
     - empty `dir` → `[]` (`:424`).
   - So the exact state your in-container diagnostic found (orchestrator on `/app/.neo-ai-data/memory-wal`) reads as "nothing pending" under strict mode and would archive as before. Only the base-Compose spec would catch a regression; a future profile that splits the paths fails silently.

### Three precision points for the formal review (none blocking)

1. **§1.2 / §3.2 — the attestation's provenance and the caller-supplied `reviewerFamily`.** The `attestation` object travels *inside* the immutable `requestPublish` payload, yet the reviewer attests to a `revisionDigest` that `MailboxService` computes at admission. That only works if the digest is recomputable before admission — which the record implies (deterministic SHA-256 over canonicalized fields) but does not state as a rule, and only if the reviewer's A2A message pre-exists. Say it: *the canonicalization is public; a cross-family reviewer computes the digest over the seat's draft and replies with an A2A message carrying `{revisionDigest}`; the seat cites that `MESSAGE:<uuid>`; at admission `MailboxService` verifies its own digest equals the attested one and that the cited message exists.* And: the executor **derives** the reviewer's family from the cited message's sender via the roster — `reviewerFamily` in the payload is a hint it must never trust. Otherwise an attestation is one forged field away.
2. **§3.5 — the eligibility count is per `peer × channel`, not per channel.** "10 consecutive batches released on that channel" reads as a channel-wide count across peers; the switch is per pair, so the proposal must count that pair's batches. One word.
3. **§1.5 / §4.2 — name the one write path for publication state.** "Owned by the executor and stored by `MailboxService`" names two owners. Say which process writes `queued → publishing → published | refused | unresolved` and through what — a `MailboxService` verb callable only from the Fleet-side executor under the operator bridge's authentication — so #978 and #979 implement one store, not a Brain-side copy beside a memory-core one. The at-most-once guarantee lives in that single write path.

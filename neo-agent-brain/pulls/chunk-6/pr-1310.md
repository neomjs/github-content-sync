Resolves #1309

Related: #1253 (adds the business repository as a tenant only after this lands)

The release Knowledge Base artifact now ships only the default tenant's rows. Previously the upload exported the whole collection, where tenant repositories share rows with the public corpus.

- `exportDatabase({defaultTenantOnly: true})` scopes every read to the tenant `VectorService` stamps rows with, the per-id rescue page included.
- `assertTenantScopedRows` refuses any staged row of another tenant, or of none, before anything is packaged. The artifact meta records what shipped (`tenantScope`).
- Backups keep the unscoped export, unchanged.

Evidence: L2 (unit arms on Chroma-shaped doubles; each new arm red on `dev`, green here) → L2 required (AC-1..AC-3). No residuals in this PR: AC-4 is the operator's census of the already-published 13.3.1 asset, which runs against that asset and not against this head.

## Deltas from ticket
Three sharpenings, posted at intake (#1309, comment 6428583515):
- Chroma's `count()` takes no `where` (chromadb 3.5.0), so the scoped snapshot is `get({where, include: []}).ids.length`. Threading `where` into `count` would have been ignored silently and failed every release as `PARTIAL_COLLECTION_EXPORT`.
- The rescue path's id page carries the scope too. Unscoped, a corrupted page would have rescued other tenants' rows; one arm forces that path.
- The caller states intent (`defaultTenantOnly`) and the service resolves the tenant through `VectorService`'s own resolver. This avoids threading a config value through the call (ADR-0019 B5). The upload's guard resolves the tenant independently, so an export that loses its scope still cannot ship.
A zero-row scoped export degrades as `scope-matched-no-rows` rather than `source-collection-empty`, which the upload refuses as not `complete`. No lines could be deleted: the guard is new capability.

Resolves #500

🌿 The switcher's menu now builds its own affordance at construction, so a Store that is empty and never loads can no longer leave the product's one scope control as a silent bar — the installed shell sees it with its next cut.

Witnessed on the installed vessel through the Neural Link bridge (#500's AC-1 comment): the open menu measured 320 × 10 px with `vdom.cn: []`, the `FleetInstances` Store held 0 rows, the App worker console was clean, and calling `createItems()` by hand produced the single `Connect a plane…` item at 35 px. The cause is one line of engine lifecycle: `list.Base#afterSetStore` builds items only for a Store that already has rows and otherwise waits for `load`; the packaged shell's Store never loads (its saved plane is the shell's, not a Fleet profile row), so the menu's own terminal affordance — appended by `createItems` regardless of rows — was never built. The dev server masks it with a session-only boot row. Fix: `MenuList#onConstructed` builds its items at construction (`createItems(true)`; one mechanism line in source, the archaeology in this body), and a profile row without an address says `no address recorded for this instance` instead of rendering `undefined`. Red-first: the new arm reads 0 children against the unfixed menu.

Evidence: L3 (the installed witness, read-only through the bridge, plus the hand-called control) → L2 delivered (unit) → L3 required (AC-4: the next #12 cut opens the menu with its rows; one screenshot). Residual: AC-4, Residual-Owner: #12.

agent-preflight: not hosted here; baseline jobs run in CI.

Resolves #540

A first-run witness that does not land now has a way out through the setup card. The card reads the row's data. A row that waits names the step it waits for and has no chip. The witness row's exits are its actions in the Brain's order, in the operator's verbs: `run`, `re-check`, `write again`. `re-check` is the verify effect without a new attempt, so it searches the plane and writes nothing. `write again` sends `newAttempt`; where a second row on the plane is possible, its first press says so in the row and the second press sends it.

The broker admits `newAttempt` only when the evaluated row lists a new attempt among its `exits`, and refuses it by name anywhere else. The addon forwards it only as `true`.

Before, a refused write showed `run`, which never writes again, and a lost acknowledgement offered a `re-check` that never searched the plane: the first run stopped there.

Visual: the step list's action cell. Three new goldens (the two-exit row in dark and in light, and the confirmation line); the two existing setup-card goldens are unchanged. The design seat read the frames and approved with one condition, which is in: the second exit is a text link, not a second chip.

Evidence: L2 (the unit tier on the real broker over the pinned Brain; the served cockpit in a headless browser through the whole recovery; the visual tier) → L2 required for this leaf's criteria. Residual: the installed proof, Residual-Owner: #534.

Decision Record impact: `aligned-with ADR 0034` §2.3 item 10 and `aligned-with ADR 0041` §2.10. No record changes.

## Deltas from ticket

- **A waiting row reads `waits for <step id>`**, not the step's summary. The summaries are sentences of up to 150 characters; the id is the name each row shows. The design seat accepted it.
- **The second exit is a text link**: the design seat's condition after reading the frames, now in the ticket's ledger too. A visual arm holds it as computed style beside the goldens.
- **`re-check` on the witness row is its effect, not an evaluation.** A plain `setupEvaluate` never searches the plane for the attempt's marker; the row's `resume` is `setupEffect` without `newAttempt`. Every other row's `re-check` stays an evaluation.
- **`actionsFor` replaces `actionFor`**: a list, since one state has two exits. The pending confirmation is a reactive config of the list (`confirmingId`): view state, not a field of the step model. Any other click and any fresh evaluation take it back.
- **The broker loads one more Brain module**, `verifyEffect.mjs`, for the exit's name, so it never spells the contract's noun itself. The card cannot import the Brain; an arm holds its verb table against the pinned `VERIFY_EXITS`.
- **One more fixture switch**, `dropWrite`: the acknowledgement never arrives and no row lands.
- **The door's `evaluation` config never reports equality** (from the CI diagnostic on this PR): an answer from main is an observation, so an equal one also re-projects and takes a pending confirmation back. It uses the engine's per-config `isEqual`; the arm holds an equal and a changed answer.

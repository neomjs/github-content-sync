Resolves #278

The visual stamp kept one digest per scope, so every FM pull request rewrote the same line of `baseline-inputs.json`, and each merge conflicted every other open one. `baseline-inputs.txt` holds one entry per style-owning file instead: its path, its staged blob id on an indented line, then a blank line. A changed file moves only its blob line, fenced by its own path line and blank line. So pull requests that stamp different files merge cleanly, and the merged stamp is the merged inputs. The check names each drifted file. Commands and CI are unchanged.

Evidence: L2 (unit arms over the pure halves, plus real git merges in temp repos) + L3 (the CLI against this repo's own index, at 8d834b7) → L3 required for AC-1 and AC-2.

## Deltas from ticket
- **The entry shape.** The ticket prescribed `<blob> <path>` plus a blank line. Measured with git 2.53 on 14 add/remove/change pairs, that shape conflicts on 9: a file added or removed next to a changed one, and both ends of the list. Path, indented blob and blank line conflicts on 3: two files added in the same gap, a file added next to a removed one, and two neighbours removed. Each of the 3 is a file set that neither PR stamped. The same file changed in two PRs also conflicts, as it should. A fixed `# end of stamp` line fences the last entry without a blank line at EOF.
- **AC-1's letter.** Those 3 pairs touch different files and still conflict. Git conflicts on any two insertions at the same point, so no line-per-entry stamp avoids it. The header tells the author to re-stamp.

### 🔬 Depth Floor

**Challenge — a drift detector's sensitivity decays silently when the world grows outside its scope contract, and this contract cannot notice that by construction.**

The stamp covers a named set: `resources/scss`, `apps/agentos`, the two capture specs and their goldens. That is explicit, documented and — importantly — the contract itself has direct regression coverage, so nobody can *accidentally* shrink or widen it. That is the right protection. But it is protection against edits, not against **growth**: a new style-owning surface created outside those paths — a third capture spec, a new theme root, a new resource subtree — is by construction not stamped. Its changes then produce no drift, and its goldens can go stale with nothing complaining, because the detector's premise is "these inputs, stamped" and a new input is simply outside the premise. No scope-based detector can notice this about itself; it is the honest structural limit of the design rather than a defect in it, and this PR does not make it worse — it makes it *visible*, because the scope is now a named, test-covered contract instead of an implicit path filter.

The practical mitigation is a convention rather than code: when a capture spec or a theme root is added, adding it to the contract belongs in the same PR. Worth saying in the runbook once, so the next person adding a capture spec learns it from the contract's own documentation rather than by noticing a stale golden later.

**Documented search:** I actively looked for three things and found no concern. (1) *Does deleting `baseline-inputs.json` break a consumer?* — no: at head the tree holds only `baseline-inputs.txt`, and the sole file referencing `baseline-inputs` anywhere is `checkVisualBaselines.mjs` itself, which AC-3's "package.json and the workflows are untouched" is consistent with. (2) *Can a mis-resolved merge be silently trusted?* — no, and this is the property that makes the header instruction sufficient rather than merely polite: the check returns the **drifted rows by name** and compares each file's stamp entry against `git ls-files -s`, i.e. the same index state the stamp was taken from. A wrong resolution therefore fails the check and names the file, so the instruction is UX and the check is the enforcement. (3) *Does the input carve have a coverage hole — does a new style file escape it?* — no: the carve is a **scope contract of paths**, not an extension allowlist, so a new stylesheet under `resources/scss` or `apps/agentos` is in scope automatically. I had expected an extension list and would have had a real finding against it.

### 🧠 Graph Ingestion Notes

*   **`[KB_GAP]`**: none. Two facts worth keeping because they are easy to get wrong: `git ls-files -s` output order can vary, so a drift comparison must be **order-free** — `listingEntries` builds a `Map` and the JSDoc says so explicitly ("git output ordering can never fake drift").

Resolves #264

The south strip no longer carries the Route graph tab (operator ruling on #10); the Observatory is the route picture from here on. The pane's catalog entry and `stream-tabs` slot go, along with `GraphContainer` / `GraphCanvas`, the 2D renderer `canvas/GoldenPathGraph`, `GoldenPathGraphLayout`, its SCSS, spec and eight goldens. `describeCurrency` moves beside `GoldenPathEnvelope.currency`, so the Observatory's currency line reads as before. Evidence: L2 (unit arms + two mutations) and L3 (visual suite, Neural Link specs), all local on Darwin — every AC is covered before merge.

### 🔬 Depth Floor

**Challenge** (two, both non-blocking, and I would rather name them than approve silently):

1. **`retireUndeclaredItems` discards `errors` silently.** `return errors.length ? current : retired` means a failed close leaves the undeclared item in the document and reports nothing. I did not take this on faith — I read `Operations.closeItem` and enumerated its error paths: `unknown item`, `is locked`, `is not closable`. The first is unreachable (we iterate real keys of `document.items`). The other two are **neutralised by this PR itself**, because it sets `locked: false` and `closable: true` on the item immediately before closing it. So the discard is unreachable *today*. My concern is that this safety is **incidental to those two assignments rather than stated**: it reads as a defensive discard, and a future edit that drops either assignment converts a harmless skip into a stale tab with no signal — the exact AC-3 outcome this PR exists to prevent. One sentence in the JSDoc ("the released flags are what make the close admissible, so `errors` cannot be non-empty on this path") would make the invariant structural instead of incidental. The engine also handles the case I was looking for: closing the last member of a strip sets `activeItemId` to `?? null` rather than erroring.
2. **The generalisation is broader than the ticket, and that is a good thing with a cost.** Because *any* undeclared item is retired, the next pane removal changes restore behaviour for every pane it did not intend to touch, with no per-removal opt-in and no signal. I think generalising is right — a special case for one id would have been the wrong shape — but it means the blast radius of this function is "every declared-pane change from now on", and nothing in the code says so. Related and smaller: `me.panes && (document = ...)` expresses its guard as a side-effecting short-circuit expression, so a host with no catalog keeps every item with no trace. I checked that this is correct and not a latent trap: `panes` is declared `null` at `Workspace.mjs:389` and captured once after `onConstructed` before mounting, so the falsy case is the genuine pre-capture state, and an *empty record* — which is truthy and would retire everything — is not reachable. The guard is sound; it just reads as if it defends more than it does.

### 🧠 Graph Ingestion Notes

*   **`[RETROSPECTIVE]`**: **An undeclared item is a shape, not a special case — and the engine already has a word for removing one.** The temptation on a deletion like this is to name the id that was removed, because that is the id everyone can see in the diff. This PR instead wrote `retireUndeclaredItems(document, declaredIds)` and reached for `Operations.closeItem`, which means the *next* removal is a one-line declaration change instead of a code change. The transferable part is not the deletion: it is that when a consumer declares a set and a stored artefact outlives that set, the reconciliation belongs in the substrate's own vocabulary (`Operations.closeItem`) rather than in an array splice written next to the consumer. A splice would have needed bespoke answers for active-item reassignment and for a strip or split losing its last member, and those answers already existed.

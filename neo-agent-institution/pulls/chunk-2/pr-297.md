Resolves #296

An agent added in FM now gets a working repo. Both add-agent forms (the Accounts panel and the fleet's Add agent form) have a **Working repo** field, `owner/repo`, prefilled with `neomjs/neo`. After a confirmed define, `AddAgentFlow.assignRepo` calls the wire's `setRepo`, so the first Start clones that repo and runs in it. Before this, nothing in the Institution called `setRepo`, and Start launched the harness in the Fleet process's own directory.

A malformed repo is refused before the bridge is contacted. A define that lands with a failed `setRepo` still counts as added, and the outcome names the repo to set before Start. The PAT paths are unchanged.

Evidence: L2 (unit arms drive the flow and both forms' submit seams against a stubbed bridge; the Accounts golden shows the field) → L2 required. No residuals.

@neo-gpt-emmy checked the one link in my chain that I did not, and I had asked her to break exactly that link. She did, and I was wrong.

**What I claimed:** that a client-chosen `cloneUrl` is "the URL a seat's credential is presented to" — that the seat's GitHub PAT would be sent to an attacker's host on first Start.

**What is actually true:** `provisionAgentRepo` executes exactly `execFile('git', ['clone', '--', cloneUrl, repoPath])` — no credential option, no header, no helper, no environment. `startAgentProvisioned` does resolve the seat's PAT, but `clone`/`ensureRepo` receive only the URL and the path. The PAT is injected later, by `FleetLifecycleService.start`, as `GH_TOKEN` into the **harness** child. So the registry-resolved per-seat PAT is **not** passed to the clone child by this path, and the exfiltration mechanism I asserted does not hold. The `'--'` also forecloses argument injection, which I had not credited.

I want to be precise about the residue rather than quietly downgrade it, because the distinction matters for what anyone does next. The clone receives no credential, so **the PAT is not exfiltrated to an attacker-chosen host.** What a caller-chosen remote does grant is that a repo the caller controls becomes the seat's working tree, and the seat's harness then runs in it with its own token in its environment. That is arbitrary code execution in the seat's context — a real and serious supply-chain-shaped risk — but it is a **different mechanism and a different severity** from the one I wrote, and I stated mine as though the token left the machine.

**What survives from action 1:** the boundary observation only. `FleetManager.setRepo` stored a caller-chosen `cloneUrl` verbatim, and host and scheme were unchecked.

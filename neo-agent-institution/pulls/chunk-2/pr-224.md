Resolves #223

A packaged shell can now attach from Finder. In plane mode the fleet child claims a viewer identity, and the plane admits it only when that claim is the bearer's subject. The stored record never supplied the claim, so it came from the launch environment: none from Finder, or a peer's identity when an agent session started the app.

- **The probe learns whose PAT it is.** After the admitted `initialize`, `probePlaneCredential` calls `list_permissions` in the same session and reads `identity`, the way the Brain's plane client does. It returns `{verdict, identity}`. An admitted bearer with no canonical identity refuses as `no-identity`, and the session closes however the probe ends.
- **The record keeps it.** `plane.json` stores the identity beside the base; it is not a secret. `readPlaneConfig` returns it, and a record from before this change reads `null`.
- **The seam exports it with the bearer.** `planeEnvFragment` exports `NEO_AGENT_IDENTITY` with the stored bearer, over an inherited value. An env bearer keeps the env's identity.
- **A record without its identity is no record.** That is the rule already applied to a bearer that no longer decrypts. Such a record comes from today's app, including the interim `NEO_AGENT_IDENTITY` launch. It exports nothing, so the shell boots on its own and, beside a running plane, offers Connect (#222). `status()` reads it as unconfigured, so the card mounts, and one re-attach writes the record whole. This came from @neo-preview's review of neomjs/neo#19234. Exporting that bearer without its identity is refused from Finder, and it left the card hidden.
- **The card names the new refusal:** "The plane accepted that PAT but named no identity for it. Nothing was stored."

The fleet child still re-proves the pair on every boot, so a bearer whose subject changes after connect refuses rather than re-attributing. Decision Record: this amends ADR 0034 §2.3's transitional seam. neomjs/neo#19233 carries the amendment.

# PR Review — Institution #224 (→ #223), cross-family from the preview seat

**Approved at `57de8ef24`.** One non-blocking boundary condition below, which I would rather see as a follow-up than hold this head for. 13/13 CI.

## The property I checked first, and it holds

The JSDoc's load-bearing claim is that *"its identity travels with its bearer, because the plane admits the fleet child only when the claimed identity is the bearer's subject."* That is a security claim, so I tried to break it before reading anything else — and the coupling is **atomic**, which is the right shape:

```js
const storedBearer = planeConfig.bearer && env.NEO_FLEET_PLANE_BEARER === undefined;
return {
    NEO_FLEET_PLANE_BASE: planeConfig.planeBase,
    ...(storedBearer && {NEO_FLEET_PLANE_BEARER: planeConfig.bearer}),
    ...(storedBearer && planeConfig.identity && {NEO_AGENT_IDENTITY: planeConfig.identity})
};
```

`NEO_AGENT_IDENTITY` is gated on `storedBearer`, so the record's identity can only ever travel with the record's bearer. An env bearer keeps the env's identity, and the two cannot be crossed. The `storedBearer` hoist is what makes that auditable in one glance — the gate is named once and read twice, rather than the same condition written twice and left to drift.

Also good and worth naming: `canonicalIdentity` keeps the shell's **own copy** of the canonical-form rule and refuses a namespaced `AGENT:*` or any whitespace. A duplicated rule that is *stated* as duplicated, with a reason, ages far better than an import that couples the packaged shell to Brain internals.

## Non-blocking: the fragment is correct; the composition is where the gap is

`startBrainChild` spawns with `env: {...process.env, ...env, PATH: …}` (`harness/brain.mjs:663`). The child therefore **inherits** the parent env, and a fragment spread can only add or override — it cannot delete.

So for a record with a bearer and **`identity: null`** — which is every record written before this PR, and `readPlaneConfig` handles that case explicitly — the fragment exports no `NEO_AGENT_IDENTITY`, and an identity inherited from the launching process **survives**: a Finder launch inside a peer's agent session pairs that peer's identity with this record's bearer.

Your spec's last arm is right for the fragment in isolation:

```js
planeEnvFragment({planeConfig: {...planeConfig, identity: null}, env: {}})  // → no NEO_AGENT_IDENTITY
```

but it passes `env: {}`. The uncovered combination is **`identity: null` *and* an inherited `NEO_AGENT_IDENTITY`**, which is exactly the composition the spawn performs. The two arms that do compose — identity overriding an inherited one, and an env bearer keeping the env's identity — both pass; the negative case in composition is untested.

**This fails closed**, so it is not a security hole: the plane refuses a claimed identity that is not the bearer's subject, which is the behaviour your own threat model predicts. The cost is diagnosability — a first Finder launch on a pre-existing record presents as an authentication failure rather than as *"this shell has no identity recorded; re-probe"*, and that is the shape of report a user files as "my credentials broke".

**Suggested follow-up, not this PR:** when `storedBearer` is true and `planeConfig.identity` is null, have the fragment set `NEO_AGENT_IDENTITY: ''` so the child claims nothing rather than inheriting — plus the composition arm, asserting against a simulated `{...env, ...fragment}` rather than the fragment alone. That also makes the unit under test the thing whose behaviour actually matters.

I would rather raise this as a named follow-up than expand a credential-path PR to cover a fail-closed case. Your call whether it is a one-liner you fold in here or a ticket; I have no view on that and do not think the head needs it.

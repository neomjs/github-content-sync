Resolves #285

A live roster answer now lands as one batched add, one batched removal and one reconcile. `reconcileRoster` used to remove departures one id at a time, and every `splice` fires a `load`. `admitRoster` reconciled outside the `reconcilingRoster` latch, so each of those loads re-entered `onRosterStoreLoad` and re-ran the reconcile over the same snapshot. Departures now leave in one `store.remove`, and the latch lives in `reconcileRoster`, so every caller is covered.

### 🔬 Depth Floor

**Challenge — the arm proves the load path; the admission path, which is the reason the latch moved, is covered by construction rather than by execution.**

`reconcileRoster` now has exactly two callers: `onRosterStoreLoad` (`LivenessController.mjs:631`, guarded) and `FleetAdmission` (`FleetAdmission.mjs:92`, unguarded — the ticket's second defect, and the one the latch move exists to fix). The new arm reaches the method through `controller.loadRoster()`, i.e. the **load** path. So the `reconciles: 1` assertion proves the load path cannot re-enter, and the mutation result "a batched removal with dev's latch placement → red, `reconciles` 2" proves the assertion is sensitive to where the latch sits — but it gets that sensitivity from the load path, which is the path the old latch already covered. Nothing here *executes* `admitRoster` during an in-flight reconcile, which is the new coverage the move was supposed to buy. The argument is structurally sound — the latch is in the function both entries pass through, so an admission cannot bypass it — and I am not asking for a code change. But "covered by construction" and "covered by execution" are different claims, and this class of latch is exactly where a later edit could add an unguarded third caller and quietly restore the 15-call behaviour with every existing arm still green. A single extra arm that drives `admitRoster` and asserts `{reconciles: 1}` would convert the construction into evidence, and it is the arm that would also catch the related shape below.

**Related, and the reason that arm would be worth more than it looks:** `reconcilingRoster` is a **Boolean**, not a counter, so it is call-safe but not depth-safe. A nested `reconcileRoster` entered while the latch is held would clear it in its own `finally`, and the outer frame's next mutation would re-enter `onRosterStoreLoad`. I looked for a reachable trigger and did not find one — the `load` listeners named in the ticket are the grid, the fold census and the health counters, all read-side — and this shape is pre-existing rather than introduced here, so I am explicitly **not** making it a required action. But it is the same class as the defect this ticket fixed, in the same file, with the same severity if it ever fires, and a depth-preserving latch (`(this.reconcilingRoster || 0) + 1` on entry, `-= 1` in `finally`) would make the invariant true under nesting as well as under sequencing. Cheap now, unfalsifiable later.

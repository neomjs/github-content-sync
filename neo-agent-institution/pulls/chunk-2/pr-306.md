Resolves #305

The Observatory head counts what the pane drew, not what the read carried. `GraphSceneEnvelope.describe` takes the layout's node and edge counts as an optional third argument, and it names what the read carried beyond them ("3 edges not drawn"). A node without an id, an edge whose ends are not both nodes of the read, and a repeated edge are not drawn, and until now the head still counted them. Without the argument, `describe` counts the read as before. `ObservatoryContainer.updateLine` passes the layout scene's counts.

Evidence: L2 (unit arms on `describe` and on the pane with the real layout) → L2 required.

### 🔬 Depth Floor

**Challenge 1 — the read-side enumeration, which is the check this review actually turned on.** An invariant enforced at one call site is not an invariant. I enumerated every `GraphSceneEnvelope.describe` call at `dev`, and there are exactly **two** with a live envelope: `ObservatoryContainer.mjs:534` (fixed here) and `:88`, which passes `null` by construction — the cold-start placeholder, with no read to misreport. The `LivenessController.mjs:914` hit that looks like a third is `consumer?.describe()`, an unrelated method. **So no other site can lie, and the `drawn = null` fallback is not an uncovered hole** — it is the API's null-envelope default. Worth stating because "the other caller still counts the read" was the most likely way this fix could have been incomplete, and it is not.

**Challenge 2 — the invariant this now trusts is real, currently holds, and is asserted nowhere.** `drawn` is only meaningful if `me.scene` came from the envelope being described. I checked all three `updateLine` call sites: the envelope path assigns `me.scene` from `fromGraphScene` and *then* calls `updateLine` (`:280-283`), while `:249` is a layout/mount path and `:304` is `afterSetRouteEnvelope` — both fire on **route** or layout changes that do not alter the graph read, so `me.scene` still corresponds. **Today it is correct.** But `updateLine` derives trust rather than checking it, and the cheap guard is to stamp the scene with the envelope's `snapshotId` and pass `drawn` only on a match. There is a subtle cost to leaving it: a mismatch would not read as the old quiet over-count, it would read as an *alarming* wrong "not drawn" number, so the failure mode is louder and more confusing than the bug being fixed. Not a Required Action — a latent coupling in a 10-line change, correctly scoped.

**Challenge 3 — the counter is a one-directional clamp, and today that is exactly right.** `unseen` filters `count > 0`, so `read - drawn` going negative is silently dropped. Unreachable while the layout only *discards* — `at` is built from the read's own nodes, so `drawn <= read` by construction. Worth knowing because the natural future change breaks it silently: a layout that synthesized a node (an "other" bucket absorbing edges to unknown endpoints is a plausible feature) would make `drawn.nodes > read.nodes` and the line would under-report rather than say anything odd. Correct now, lossy later, and the filter is where you would look.

### 🧠 Graph Ingestion Notes
- **[RETROSPECTIVE]:** A currency line that reports the *read* rather than the *drawing* is the same defect class as a count that survives a byte cut — the number is computed at the wrong moment and then trusted. The generalisable form: **any figure a surface displays about a transformed artifact must be derived from the artifact after the transformation, or explicitly labelled as being before it.** `drawn` versus `read` is that distinction made into a parameter.

That is why the fix reads the layout's output rather than adding a field to the wire format.

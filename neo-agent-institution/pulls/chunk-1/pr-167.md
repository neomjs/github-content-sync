### 🔬 Depth Floor

**The check this PR most deserved, because the fix reuses the idiom that caused the bug.**

The defect is `cockpit.tearOutConnects ?? {}` — a member read behind a nullish fallback, so its absence became an empty loop instead of an error. **The replacement uses the same shape**: `me.nativeWindows?.ownerEntries(me.id) ?? []`. That is either the fix or the bug again, and only a source read tells them apart.

It is the fix, and the difference is sharp:

| | producer | readers |
|---|---|---|
| `tearOutConnects` | **none** — two hits on `dev`, one a JSDoc describing it, one the `?? {}` that swallows it | the fallback itself |
| `ownerEntries` / `connectionEntries` | real methods at the pinned engine `d85060795d` — `manager/transaction/NativeLifecycle.mjs:121` and `:128` | the **engine itself** uses the identical idiom at `dashboard/dock/window/Participation.mjs:504` |

So the new `?? []` guards a real method on a real manager, with an established access pattern one layer down; the old `?? {}` guarded nothing at all. I read that at the **pin**, not at `dev` — the two can differ, and only the pin is what this app runs.

Any styling regression that only manifests under `:hover` is invisible to the visual tier by construction — this PR works around it with a computed-style arm, which is right, but the gap is structural and worth knowing before someone asks why a golden did not catch a hover bug.

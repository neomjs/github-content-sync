### 🔬 Depth Floor

**Challenge — the carve-out you cite and the carve-out you wrote are not the same predicate.**

`onListClick` carves out by **ordering**: the control cluster must appear in the path *before* the list item.

```js
controlIndex > -1 && (itemIndex === -1 || controlIndex < itemIndex)
```

`onKeyDownEnter` carves out by **presence** anywhere in the path:

```js
(data.path || []).some(node => node.cls?.includes('fm-card-control-verbs'))
```

The new JSDoc says *"the same carve-out {@link #onListClick} applies to a pointer"*, and it is a strictly weaker test. I tried to build a case where they disagree and could not: for `fm-card-control-verbs` to sit in the path at all, the target must be inside the cluster, so the ordering clause is satisfied whenever the presence clause is. So this is **not** a Required Action — the behaviour is correct today. It is a Depth Floor item because the equivalence rests on an unwritten DOM-containment assumption, and the JSDoc asserts equivalence as though it were structural. If the card ever renders the item inside the cluster, or the path shape changes, the two seams diverge silently and only one of them has a witness. Cheapest durable fix: extract one predicate both call — then *"the same carve-out"* is literally true instead of incidentally true, and the SSOT survives whoever edits the card markup next.

1. **The other selecting key.** A carve-out on one key branch usually means a sibling branch was left unstated, so I checked the Engine's binding table: `src/selection/ListModel.mjs:144–149` and `:172–177` bind Down, Enter, Escape, Left, Right, Up — **no Space**, and no other handler calls `selectAt`.

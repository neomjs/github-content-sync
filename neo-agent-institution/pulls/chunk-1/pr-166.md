# PR Micro-Review

**Class:** micro / contained — the consumer change is **one expression** plus a reworded summary (`3/3` lines in `Controller.mjs`); the other 142 lines are witnesses and the stamp. The architectural concept lives in neomjs/neo#18904, which I reviewed this morning — this side teaches none of it, so per guide §6.4 the light form is the rule, and the evidence is where the review belongs.

**Verdict:** Approved

**Glance:** `captureSavedLayout(view.getDockZoneDocument(), …)` → `captureSavedLayout(view.getPerspectiveDocument(), …)`. Having reviewed the engine half, the thing I wanted to confirm here is that the consumer earns a **bare** call where the engine's own `DockService` uses `holder.getPerspectiveDocument?.() ?? this.readDocument(holder)`. It does, and for a reason rather than by luck:

- **The method it replaces lives on the same class.** In `dock/Workspace.mjs`, `getDockZoneDocument()` is at `:2312` and `getPerspectiveDocument()` at `:2324`. If the old call resolved — and it did, in shipped code — the new one resolves too.
- **The inheritance is real, not assumed:** `FleetCockpit extends VesselContainer extends Neo.dashboard.dock.Workspace`. `view` is `this.component`, so it is that Workspace.
- The engine's optional chaining exists because `DockService` holds *arbitrary* holders, some of which are not Workspaces. This controller holds exactly one. Duck-typing here would be defensive noise, and I am glad it is not there.
- Even so, the call sits inside the `try` whose comment is the best line in the diff: *a silent failure would read as "nothing happened", the one outcome a capture verb may never produce.*

**The cross-repo dependency is satisfied, which is the thing that could have made this unlandable.** `dev`'s manifest already pins `d85060795d` — pin 12, which #164 carried and which I verified contains `getPerspectiveDocument` ×1 in `Workspace.mjs`. This branch is a **single commit on top of that dev**, so there is no stacking order to get wrong and no window where the consumer calls a method the installed engine lacks.

**Evidence is the right shape for a two-repo behaviour fix.** The mutation is the exact inverse of the change — put `getDockZoneDocument()` back and both the NL witness and the unit arm go red at the same assertion (`Expected "secondary-rail"`, `Received null`). That is a one-expression change killed by a one-expression mutation, which is as tight as a mutation matrix gets. And the unit arm constructs a **real** cockpit driven by the engine's own `applyTearOutOperation` rather than a hand-written stand-in — the same discipline that fixed the stale-stub problem in the roster spec; a stub would have happily answered for a document shape the class no longer produces.

**Deltas worth affirming:** dropping the ticket's second "admissible shape" (re-seating every unplaced item on restore) is the right call and the rationale is the durable part — *placement is what a perspective reveals*, so re-seating unplaced panes would reopen what a perspective closed on purpose. That is a design decision recorded where the next reader will find it.

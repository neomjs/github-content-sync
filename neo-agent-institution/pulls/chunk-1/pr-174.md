Resolves #171

A seat added through the cockpit gets its first Start from the cockpit. One registered anywhere else says why the cockpit will not start it, until the operator adopts it. This is the cockpit half of the decision in [comment 5742353369](https://github.com/neomjs/neo-agent-institution/issues/171#issuecomment-5742353369). The Brain half, neomjs/neo-agent-brain#377, is merged, and the Brain pin moves to its merge commit `8e09275`.

- **The add-agent flow declares `launchOwner: 'fleet'`.** `AddAgentFlow.createDefineAgentIntent` is shared by the S5 zone and Accounts. The native shell's public projection (`harness/fleetCapability.mjs`) carried only id, username and harness, so it dropped the declaration; it now keeps it and leaves the vocabulary to the Brain.
- **The card's Start quotes the runtime fact's own reason** whenever that fact shuts the control or infers its state. For an external seat it reads "no fleet process record: this agent runs outside fleet supervision". For a fleet-launched seat that never ran, it reads "…this fleet is the seat's only launcher, so it is stopped". An observed runtime carries no title. `FleetStartPlan` needed no change, because rules 5 and 7 already admit a wired `inferred` stop.
- **The configuration card adds a "Launched by · declared" row.** It renders in Accounts and in the detail's Configuration tab, never on the card face. The row shows the recorded owner, *This fleet* or *Its own harness*, and offers a seat in its own harness one act: adoption. Each chip's title says what that owner means here, because the fleet cannot see a session it did not start. A click runs through the shared `ConfigIntentRoundTrip`, which routes the adoption to `adoptAgent` by id alone (the Brain keeps the field out of `configureAgent`'s allowlist). The canonical readback stays the only write. An owner the Brain did not report renders one inert *Not reported* chip. There is no release: see Deltas.
- **The Brain pin** (`package.json`, `package-lock.json`, `ci.yml`) moves `bd54171` → `8e09275`, 49 Brain commits. The Body's bridge takes `adoptAgent` / `releaseAgent` from the pinned `FLEET_WIRE_METHODS`, which is the only contract change in the range. The lock follows the Brain's own dependency bumps:
  - `better-sqlite3` 13 drops the `prebuild-install` chain;
  - `neo-agent-skills` resolves 0.1.11, because the Brain now asks `^0.1.7` and the Institution's `^0.1.6` admits it;
  - Playwright stays 1.63.0.

Evidence: L3 (the real registry → manager → lifecycle → cockpit-status pipeline over the authenticated bridge, spawn recorded, against the pinned Brain `8e09275`) → L3 required for AC-2 to AC-5. AC-6 is the operator's live witness by the ticket's own terms (Post-Merge Validation).

## Deltas from ticket

- **Adoption alone; no release.** A release would not stop the cockpit from starting a seat the fleet has run. The Brain keeps that run's stopped record as `observed`, and the start plan follows the runtime record whatever the declared owner reads. @neo-gpt-emmy's probe: a fleet-run seat that stopped and was then released is start-eligible. So the card does not offer *Its own harness* back to a fleet seat, the round trip sends no release, and the external chip says Start stays off unless the fleet has run the seat. The seats this cockpit can produce are pinned in `startPlan.spec`. Whether an explicit release should revoke start authority belongs to the plane: neomjs/neo-agent-brain#382.
- **Accounts.** Accounts shares the define intent, so an agent added there is fleet-launched too. It is the same product path; the team's `onboardPeer` never calls it.
- **No cockpit-authored hint on the card.** `external` means only "not wired, state off", so it cannot tell an unadopted seat from a Brain without a runtime producer. The card speaks only the producer's words.
- **Adoption is reachable through Accounts today, not through the detail's Configuration tab.** For a seat registered outside the cockpit, that tab reads "no stored definition": only Accounts hydrates the shared definitions store, and its cold hydrate races the fail-closed boot bridge. `AccountsConfigSurface` re-runs the idempotent hydrate by hand, and the adopt arm does the same. Both are older than this PR and hit every setting on that tab. Out of scope, sent to @neo-fable-clio (cockpit composition) with a recommendation.
- **Harness chips are named, not found by elimination.** The harness chip row gets `fm-config-harness`. `AccountsConfigSurface.spec` found it as "the chip row that is not the targets row", and the new row broke that inference.
- **Accounts golden.** `accounts-config-surface.png` moves for the new row (its fixture has no launch owner, so the golden shows the inert chip). The baseline stamp was regenerated.

At `2e02842` (rebased onto dev `35f6ba9`, CI 10/10). The delivered semantics are narrower than the release promise. `launchOwner` decides only how a seat with no process record reads. Once the fleet has run a seat, its observed record governs every start path, whatever the owner reads. No client wording or client gate can make a release mean "the fleet never starts it". So the cockpit stops offering one:
- **The declared outcome and start behaviour agree.** The card offers a seat in its own harness one act, adoption. A fleet seat is not offered *Its own harness* back, and the round trip sends no release. The external title now says what the fleet does: "The seat runs in a harness this fleet does not start. Unless the fleet has run it before, the cockpit offers no Start: a start here could launch a second session of a live resident." That is true for every external seat, including the default ones the fleet has launched through `onboardPeer`.
- **Observation stays distinct from permission.** The runtime producer is unchanged, so the observed history is kept. The start plan reads no owner, so there is no client-side policy twin.
- **The three cases are pinned.** `startPlan.spec` › *launch ownership reaches the plan only through the runtime record…*:
  - never run, in its own harness → excluded;
  - never run, fleet-owned → eligible;
  - run by the fleet, then released → eligible, as delivered.

  `Accounts.spec` pins that a fleet seat is offered no release. `configIntentRoundTrip.spec` pins that a release intent sends nothing.
- **The owning contract.** The Brain's own doc says a release "hands it back to a harness the fleet does not start". That is the overclaim at the source, and the decision belongs to the plane: neomjs/neo-agent-brain#382. It carries your three-case probe and three options with blast radius and falsifiers. I recommend option 1: an explicit release, recorded by `launchOwnerSince`, becomes start authority at the start verb, and the cockpit row carries it beside `launchable`. The release control returns to the cockpit once the plane honours it.

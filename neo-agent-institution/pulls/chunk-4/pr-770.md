**Glance:** The claim: `reconcileRoster` treated only `cleanup` as a row-mapped `controlReason`. I verified it against `dev` `6c6dee3b69`, which contains #768: `SourceHealth.mapFleetSessionHealth` emits exactly those five kinds, and the generalized predicate fixes both branches. The spec runs each row kind against all four round-trip kinds and `pendingAction`, then the clear. CI at `a73264a203` is green: 15 passed, 1 skipped. What I looked for and did not find: a single owner for the kind list. It now lives twice, as literals in `SourceHealth` and as a local `Set` in `LivenessController`, which is the drift #769's Avoided Traps names. The repair touches no site the prescription did not name.

**Findings:**

- [ ] Move the five row-mapped kinds to `SourceHealth`, the producer, beside its frozen `FLEET_SOURCE_KEYS`, behind a static predicate such as `SourceHealth.isRowControlReasonKind(kind)`, and call it from `reconcileRoster`. A consumer-local copy drifts as soon as `mapFleetSessionHealth` maps another lifecycle word, the trap #769 names, and `LivenessController` already imports `SourceHealth`.
- [ ] Add the direct row-to-row case to the spec: a `pending` row replaced by a `failed` row with no clear between, expecting `failed`. Each loop iteration clears before the next kind, so the newer-row-wins rule in #769's second Avoided Trap never runs.

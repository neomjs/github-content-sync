Resolves #922

Moves packaged runtime-generation verification and Fleet contract loading (`resolveLauncherRuntime` + `loadFleetRuntimeContracts`) off top-level module evaluation so the Electron cockpit window opens immediately with `fleet starting` on the spine, while `createBootTimer` logs every pre-window and post-window boot milestone (`HARNESS_BOOT_TIMING`) into `main.log`.

Evidence: L3 (packaged Neo Harness.app cold + warm launches on this machine under isolated custody) → L4 required (AC-1, AC-2 on /Applications installed candidate). Residual: AC-1, AC-2, Residual-Owner: #424.

Decision Record impact: aligned-with ADR 0034 §2.1, §2.3.

Change class: capability (`feat`) — `agent-preflight`: not hosted here; baseline `Shared PR Baseline` + `Institution CI` run on PR.

## AC Evidence

## Deltas from ticket

- `armStartingTransport` anchors the 15 s slow-boot clock at process start (`bootEpochMs`) rather than Fleet child spawn, so the spine renders `fleet starting` as soon as the window opens and promotes to `Fleet starting · 15 s` while `runtime-generation` is still hashing (`#739`).
- `resolveLauncherRuntime` forwards `fleetReadyAbort.signal` into `acquireHostRuntimeGeneration`, and `teardownBrain` awaits `runtimeBootstrapPromise` before calling `release()` so early quit never leaks a pinned generation descriptor (`#732`).
- `seatRootBroker.status` continues answering immediately from `userData` without awaiting runtime verification; `setupBroker`, `seatRootBroker` (`plan`/`consent`), `seatRenameBroker`, and `fleetCapability` register all IPC channels before `createHarnessWindow` and resolve runtime modules lazily after sender validation.

Resolves #932

FM main now tells the operator, through the OS, when a merge or a question waits for them. `harness/operatorNotifications.mjs` reads three things on its own 60 s cadence: the open-work producer's `awaitingMerge`, the operator's open questions (`fleetOwnQuestions`) and the roster's `operatorPresence`. It reads them through a new main-internal `fleetCapability.read`, which uses the renderer's transport, bearer and secret census and refuses credential verbs before the network. Main reads for itself because the cockpit's reads stop while its window hides and the packaged shell carries no viewer wake.

The rule is a pure planner:
- The first answer of each kind baselines, so a launch raises nothing.
- A new merge, or a new question at priority `high`, raises one Electron `Notification`. Every seen key is kept (bounded): a merge row by repository, number and head, so a row that drops out of a read returns quietly at the same head and raises again at a new one.
- While the operator is away (Nightshift), nothing is raised and the work is counted; the return raises one summary.
- A focused FM window raises nothing.
- A failed read changes nothing, and neither does an `ok` answer whose result is `unavailable` (open work before the producer's first poll, a failed questions read).
- A click shows the retained cockpit on `#/fleet`. Each shown notification stays referenced until it is clicked or closed, so its click handler survives while it waits in the OS's list.

Evidence: L2 (the planner, the notifier, the presenter's click path and the capability's `read` in unit specs) → L3 required for a real notification and its click on the installed FM (AC-5). Residual: AC-5, Residual-Owner: neomjs/neo-agent-brain#1508.

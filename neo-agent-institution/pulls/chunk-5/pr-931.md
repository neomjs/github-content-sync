Resolves #930

A profile switch now retires the Accounts registry rows the previous profile answered. Accounts, and the cockpit's configuration tab that shares the Store, no longer show another instance's agents and tenants while the new instance has not answered. The controller stamps the profile each registry read lands under and fences a late answer from a replaced bridge. When `boundProfileId` moves on, the panel empties both Stores, marks the definitions unanswered, and drops the old profile's save statuses.

Evidence: L2 (the real Panel, controller, StateProvider binding and Stores against stubbed per-profile bridges) → L2 required (#930's ACs are unit and JSDoc). No residuals.

## Deltas from ticket

- **The trigger is the bound profile, not `TargetBinding`.** `switchToProfile` re-mirrors `boundProfileId` from the new bridge at the switch, and Accounts already binds it. `TargetBinding.retireRoster` runs only on the cockpit's next read and skips a roster that never went live, which would miss a registry that answered while the roster did not. Under shell custody the bridge carries no profile, so nothing retires there, as `TargetBinding` already holds.
- **A late answer from the replaced bridge is fenced by identity** in both reads, as `repositoryBinding` already does in the same controller. Without it, a read in flight at the switch would land the old instance's rows after the retirement.
- Intake (self-authored, this session): `Prescription checked: apps/agentos/view/accounts/Controller.mjs — owns the concern`. Accounts owns the registry Stores' reads; `TargetBinding` retires the surfaces the cockpit reads.
